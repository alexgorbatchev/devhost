# devhost app contributor notes

Local rules for the `devhost` Rust CLI app in `apps/devhost/`.

## Documentation policy

- The public docs under `packages/docs/src/content/docs/` must always be kept up to date. They are where every feature is documented, however small, each in the page that owns it (see `packages/docs/AGENTS.md` for the layout). Update them in the same change whenever you change:
  - CLI usage
  - manifest behavior
  - injected environment variables
  - routing behavior
  - logging behavior
  - devtools behavior
  - limitations, caveats, or failure modes
- After every behavior change, review the docs and `README.md` for statements the change made inaccurate, and correct each one. This applies to the README as well: what it already says must stay true.
- `README.md` is the project's sales flyer and the docs landing page, not documentation. Keep it short and persuasive: a hook, the handful of main features as one-line benefits, a quick look at a manifest and its output, one install command, and links into the docs. Options, flags, configuration, setup details, troubleshooting, and contributor material belong in the docs site. This README intentionally leaves out the generic README sections (How it works, Options & flags, Setup). Ask the user before adding a feature or section to it; correcting, tightening, or removing README text needs no approval. Keep its install command free of version numbers, so a release needs no README edit.
- `AGENTS.md` files must be kept up to date after workflow, policy, or contributor-expectation changes.
- `RELEASE.md` must be kept up to date after tag, packaging, or GitHub release workflow changes.
- If the manifest contract changes, also update `devhost.example.toml` and the devhost skill at `skills/devhost/SKILL.md` (and its reference files).
- Update `skills/devhost/SKILL.md` in the same change as any change to a command, argument, option, short alias, type, default, environment variable, output, exit code, or side effect, and set its `last_modified`. `TestSkillCoversTheWholeInterface` fails while it omits a command, flag, argument, or environment variable, or leaves a flag's type or non-zero default off the line that names the flag; check what the file says about them against the implementation yourself, because the test compares names and values only.
- Write the skill for someone operating `devhost`: affirmative usage instructions and facts. Keep its frontmatter `description` to when the skill applies. Contributor rules belong in the `AGENTS.md` files. `SKILL.md` and its reference files carry no negative instructions: `TestSkillGivesNoNegativeInstructions` fails on `do not`, `don't`, `never`, `must not`, `should not`, `avoid`, and `refrain`. Say what to do, or state what devhost does or rejects.
- If devtools-specific contributor rules change, also update `packages/devhost-ui/AGENTS.md` and the nested files under `packages/devhost-ui/src/devtools/`.
- If the tag-driven binary release flow changes, also update `RELEASE.md` and the relevant shared guidance in the repo-root `AGENTS.md`.
- **CRITICAL:** `packages/docs/sync.ts` regenerates the public docs landing page from `README.md` and the manifest reference from `devhost.example.toml`. After editing either source, you **must** validate `packages/docs` so the GitHub Pages content stays in sync.
- Do not leave docs, README, or AGENTS examples/rules stale after changing implementation details.
- Repo-root `README.md` is a symlink to this workspace README; update `README.md` here, not the root symlink.

## Rust CLI

The Cargo package lives directly in `apps/devhost/` (`Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `src/`, `tests/`, `vendor/`, `licenses/`). Use `just devhost build`, `just devhost run <args>`, or `just devhost run-ai <args>` (also forwarded from root `just cli` and `just run-ai`).

`just devhost run` and `just devhost run-ai` stamp the checkout with compile-time `DEVHOST_BUILD_SOURCE_DIRECTORY`. For a standalone development executable, set that variable while invoking `just devhost build`. The runtime `DEVHOST_DEV_SOURCE_DIR` takes precedence; a missing stamped checkout warns and serves embedded assets. `build-release` clears the source stamp so optimized release executables remain independent of the build checkout.

Use `just devhost build-release` for an optimized native release binary at `apps/devhost/target/release/devhost`, or `just devhost compile` to also copy it to `apps/devhost/bin/devhost`. It stamps `metadata.json`, rejects mismatched GitHub release tags, and remaps source paths. The release profile uses optimization level 3, thin LTO, one codegen unit, stripped debug information, and unwinding for cleanup; normal debug and incremental builds retain their defaults. `--target <triple>` selects an installed target; `--cross` uses an installed `cargo-zigbuild` and Zig.

Run `just setup` for a fresh checkout. Run, build, test, lint, and coverage recipes refresh the generated browser assets under `apps/devhost/dist/devtools/` and `apps/devhost/dist/statuspage/` before Cargo embeds them; direct Cargo commands require those assets to exist already.

`just devhost build-release-artifacts` builds the five distribution targets (`darwin-arm64`, `linux-x64`, `linux-arm64`, `linux-x64-musl`, `linux-arm64-musl`) with the established executable/archive layout plus compiled-dependency licenses, SHA-256 checksums, and source/toolchain provenance. Use `--targets=<comma-separated archive suffixes>` for a subset and `--output=<new directory>` for an explicit output. Linux GNU uses `cargo-zigbuild`'s glibc 2.28 baseline; musl must be static. Build the macOS archive on macOS and verify its system-library dependencies, minimum OS, and ad-hoc signature. Existing output directories are never overwritten. See `RELEASE.md` for prerequisites and native acceptance.

Use `just devhost test-affected <base>` to select the package from changed source, fixtures, embedded UI/design assets, or shared test inputs. Use `just devhost test <args>` for focused feedback, `just devhost check` for formatting, strict Clippy, script tests, and Rust tests, and `just devhost coverage` for 90% first-party line and function coverage (integration tests are excluded from the denominator):

```bash
just devhost check
just devhost coverage
```

Root `just fix` formats first-party Rust with `cargo fmt --package devhost`, preserving vendored dependency formatting. Coverage builds use line-table debug information in their separate instrumented target; normal development builds retain their configured debug information and incremental state. Cargo uses the pinned `rust-toolchain.toml` toolchain. CI requires hosted native Rust checks on Linux x64 (with MSRV Rust 1.98.1 and 90% coverage), Linux ARM64, macOS ARM64, and macOS Intel alongside root `just check`.

On macOS, the shared HTTPS health fixture requires `DEVHOST_HEALTH_TRUST_DIR` with a trusted `root.pem` and its `server.pem`/`server.key` for `127.0.0.1`. Hosted CI creates its own temporary CA on disposable GitHub-hosted macOS VMs through `test-support/macosHealthTrust.sh prepare` and relies on disposable VM teardown for final removal of the temporary trust record; that script refuses contributor machines. Follow the [native HTTPS fixture procedure](../../docs/internal/references/macos-https-health-fixture.md) before running this test locally; never install its CA implicitly.

## Development workflow

From the repository root, build and register a protected development override for the dotfiles-managed `devhost` shim:

```bash
just dev-bootstrap
just dev-bootstrap /path/to/dotfiles
```

The default target is `~/.dotfiles`. The command rebuilds the embedded devtools bundle and compiles `apps/devhost/target/release/devhost` with a `999.0.0-dev--<release>+<short git SHA>` (`<release>` is the nearest reachable `vX.Y.Z` tag without its `v`, or `0.0.0`) `DEVHOST_BUILD_VERSION` override and a `DEVHOST_BUILD_SOURCE_DIRECTORY` override naming this checkout, then registers the executable through `dotfiles tool dev use devhost`. Dotfiles copies it into its configured development store and routes the shim there; release payloads remain unchanged. The selected project must declare `devhost`, and the dotfiles CLI on PATH must support `tool dev use`. An old CLI produces an update instruction. Run `dotfiles tool dev off devhost` in the target project to resume managed releases. Plain `just devhost build-release` retains the metadata version and clears the source stamp.

Run the app from source in the current directory with agent-facing output (`AGENT=1`); `just devhost run` is the human-mode equivalent:

```bash
just devhost run-ai --help
```

Preview startup timeout and recovery pages from the repository root with `just devhost demo-recovery`. The separate `demos/recovery/devhost.toml` deliberately leaves its automatic port closed and times out after ten seconds. Open the URL printed by devhost (`https://recovery.localhost/` with the default local config). Machine config selects the suffix and configured relay automatically. Restart repeats the deliberate failure; Ctrl-C stops the demo stack.

With a source checkout (recorded by development builds, including `just run`, or set through `DEVHOST_DEV_SOURCE_DIR`), the control server exposes `/__devhost__/pages/` on root-routed domains. This standalone page gallery shares the real 404, recovery, backend-unavailable, and file renderers. Preview snapshots stay non-ready, use sample logs and worktrees, and reject restart/worktree mutations without calling live stack callbacks. File examples are read from `demos/pages/files/` in the selected checkout. The gallery is absent outside development mode; restart the source stack after editing embedded templates or styles.

Rust and Bun script test recipes use the root `test-support/runTests.sh` for command-owned temporary storage and cancellation cleanup. The runner exports the physical temporary path so Git, shells, and tests agree on macOS.

`scripts/buildDevtoolsBundle.ts` refreshes the generated injected devtools assets under `dist/devtools/` and status-page assets under `dist/statuspage/` embedded at compile time via `include_dir!` / `include_str!`: the static `devtools.js` entry, lazy JavaScript chunks and WOFF2 subsets under `assets/`, and precompressed `.gz` representations. Both output directories are intentionally ignored. Production builds must define `process.env.NODE_ENV` as `"production"`; the source loop sets the internal `DEVHOST_DEVTOOLS_DEVELOPMENT=1` build switch for development diagnostics and retains old hashed chunks for active tabs. Production builds remove obsolete artifacts before embedding.

`assets/statuspage/theme.js` is the tracked shared theme script embedded by `src/statuspage.rs`. Render every built-in page through the shared React views in `packages/devhost-ui/src/statusPages/`, composed from `@alexgorbatchev/shadcn`; do not add hand-written HTML page templates or inline page behavior. This includes 404, recovery, unavailable-backend, running-stack directory, file listing, Markdown, and preview-gallery views. Their JavaScript is embedded in the document so pages need no app, control-asset route, or CDN. Service data must never become trusted script or HTML. The managed proxy serves its 404 stylesheet beside the page; other pages inline the same stylesheet. Markdown uses the UI package's `react-markdown`, `remark-frontmatter`, and `remark-gfm` dependencies with raw HTML disabled and the default safe URL handling; leading YAML front matter, parsed with `yaml`, renders through `renderFrontMatter` as a GitHub-style key/value table, or as a YAML code block when it is not a valid mapping. All pages share the system-theme script. Keep token values in the design package.

The builder resolves the browser main and Redux registration through the UI package's public exports, using that package's own resolution context. Keep the served entrypoint list explicit: additional component-library exports are available for composition, and enter the browser asset graph when imported by a served entrypoint. The Redux monitor remains a separate internal browser entry beside its public registration module.

Devtools control requests are token-free for trusted local development; native chat mutations and WebSocket attachments require an Origin matching the request authority. `/__devhost__/config.json` serves instance configuration with `no-store`; the static entry fetches it before mounting. Unversioned `inject.js` URLs redirect without caching to content-versioned URLs. Production entry URLs, hashed chunks, and fonts use one-year immutable caching; source-mode `inject.js` stays uncached. Gzip negotiation belongs only to asset responses, preserving native WebSocket handling. Keep generated chunk/font URLs and the Rust asset route aligned.

The same existing browser build embeds `redux.js` (public host registration), `redux-monitor.js` (genuine upstream inspector), and its emitted `redux-monitor.css`. The separate `/__devhost__/redux` document loads the upstream inspector stylesheet; it never reaches the host document. Preserve the complete build output graph, including emitted chunks/fonts and gzip representations, rather than a fixed entry-file count. Redux modules and styles use the same content-versioned immutable production responses and uncached source rebuilds as other browser assets. Failed source builds return HTTP 503 instead of stale registration, monitor code, or styles; injection retains its compilation-banner behavior. No Node/desktop runtime is shipped.

A development build records its checkout root through compile-time `DEVHOST_BUILD_SOURCE_DIRECTORY`: `just dev-bootstrap`, `just devhost run`, and `just devhost run-ai` set it; plain `just devhost build-release`, `just devhost compile`, the demo recordings that use it, and release artifacts leave it empty. `load_dev_source_checkout` in `src/devtools/dev_source.rs` uses `DEVHOST_DEV_SOURCE_DIR` first and the recorded checkout otherwise, and points the running stack at that devhost checkout. A recorded checkout that is not a devhost checkout only warns and keeps the embedded assets, because the bootstrapped binary runs every project's stack. Each request for `/__devhost__/inject.js` compares `packages/devhost-ui/src/devtools/` against `apps/devhost/dist/devtools/devtools.js` in that checkout and, when sources are newer, runs `just --justfile <checkout>/apps/devhost/justfile build-devtools-bundle` before serving the bundle, so a browser reload shows UI changes. All three paths derive from the checkout root in `src/devtools/dev_source.rs`; keep them in sync with `scripts/buildDevtoolsBundle.ts` and the `build-devtools-bundle` recipe. `devhost start` rejects a path that is not a devhost checkout, naming the variable. A build that fails or writes no `devtools.js` renders a `DEVHOST COMPILATION ERROR` banner and is retried on the next reload; builds are serialized, so retries never overlap.

## Release workflow

- Follow `RELEASE.md`; it is the authoritative runbook for the tag-driven GitHub Release binary flow.
- Release trigger: push a `v*` tag whose version matches `metadata.json`.
- The publish workflow attaches versioned `.tar.gz` binaries for `darwin-arm64`, `linux-x64`, `linux-arm64`, `linux-x64-musl`, and `linux-arm64-musl` to the matching GitHub Release.

## Done policy

- Done means the required docs are updated (the public docs, relevant `AGENTS.md`, `RELEASE.md`, and `devhost.example.toml` when applicable) and `README.md` has been reviewed for inaccuracies, required validation for the affected scope has passed, and any temporary local processes started for validation are stopped.
- When changes affect the shipped `devhost` executable or its user-visible behavior, run `just devhost compile` successfully before yielding to the user.
- If `just devhost check`, packaging checks, or required documentation updates were skipped, failed, or are blocked, report the app work as incomplete and call out the exact blocker.
- Release work is not done until the tag exists remotely, the publish workflow has reached its expected result, and the matching GitHub Release state is confirmed.

## Manifest configuration and casing rules

- Normalize `host` strings and arrays into one ordered hostname list. Keep one process, port, and document injection server per service. Claim and clean up each hostname independently; publish all service routes with one Caddy reload and restore the entire group on failure. Use the first hostname for single-value service references and metadata.

- Resolve every service port before evaluating health URL templates. Timing-only health tables inherit TCP readiness on fixed or automatic ports; explicit probes retain their kind and timing across port retries and reloads. Build direct HTTP URLs from connectable bind addresses, validate resolved health targets as loopback HTTP/HTTPS, and keep explicit numeric TCP targets fixed.

- **MANDATORY camelCase rule:** All keys across the entire TOML manifest must use standard `camelCase` naming conventions. Never introduce kebab-case (hyphenated), snake_case, or mixed casing for properties in the manifest.
- This rule applies to both top-level tables and nested keys, including (but not limited to) `idleTimeout`, `externalToolbars`, `bindHost`, `httpPort`, `httpsPort`, `adminAddress`, `defaultAction`, `injectPort`, `dependsOn`, `primary`, `managed`, `restartServices`, etc.
- When defining or updating schema validation logic or structs in Rust (`src/manifest/`), always ensure allowed-keys lists, parsed fields, struct members, and `serde` rename attributes explicitly enforce and respect `camelCase`.
- Never submit or merge schema additions that break this naming contract.

## Service supervision boundary

- Command-mode `devhost serve` uses the stack supervisor without a manifest. Keep discovery scoped to the contained command process tree, verify HTTP before routing, and reconcile late or closed listeners through the normal route transaction. Session names combine an inferred app name and a random ID; reserve DNS label space for port and machine suffixes. Preserve issued short aliases on their original port and retain port-qualified hostnames as other ports close. Detached startup waits for the first HTTP route; command exit ends the session. Keep session list/info/stop controls and restart identity synchronized with the public docs and operator skill.

- Stack registration atomically checks root and included manifest ownership under the shared stack-record filesystem lock. Preserve the loaded input files through validation and reserve new inputs before reload mutations; retain the previous inputs on failure and release removed inputs only after success. Registered live owners take precedence over `killZombies` recovery.

- Every stack registers itself with `caddy.RegisterStack` before it claims anything and unregisters last in its cleanup, so `devhost stop` and `devhost stack list` know a stack that holds no hostname or port. A stack record, hostname claim, fixed port claim, or route registration names its owner by PID and start identity (`ownerStartIdentity`, from `internal/procid`). Decide whether an owner is still running with `routeMutationIsOwnerAlive`, never by PID alone: a PID is reused, and the answer decides which process `killZombies` and `devhost stop` signal. A record without an identity comes from an older devhost and is checked by PID. `internal/caddy` owns the record formats; other packages read owners through `caddy.ReadLiveStackOwners` and do not parse the files. A stack records its manifest path as it was named, so every command that looks a stack up by manifest (`start --detach`, `stop`, `stack restart`, `stack find`) compares `caddy.ManifestIdentity` of both paths exactly, which resolves symbolic links; never compare the recorded path directly. `devhost stop --worktrees` still finds each manifest's Git repository from its path as named, the selected one included, so a manifest linked from another repository keeps the scope in its own. Tests that need a running stack's records start a process that makes real claims, as `startStackOwner` in `internal/services` does.

- Startup and reload share one fresh `caddy.ZombieCleanup` per claim pass across fixed ports, hosts, and route registrations. It caches success or failure per PID and start identity, and confirms exit before reclaiming a claim or logging `Stopped zombie PID ...`. Exit confirmation recognizes an unreaped OS zombie as exited; the old process's parent may not reap it. Keep the real-process and failure regressions in `internal/caddy/zombie_cleanup_test.go`.

- Single-service restarts retain assigned automatic ports and report collisions with the **Restart Stack** recovery action. Full-stack restart uses the last accepted manifest, refreshes managed auto ports, stops all managed services before relaunching them with rebuilt port templates/environments, retains selected worktrees and control/document listeners, and remains retryable after launch/routing failure. Fixed ports and external processes stay unchanged. Signal only owned listener processes during cleanup; an unrelated listener taking over a stopped service's port must neither be killed nor prevent stack recovery.

- Manifest hot reload owns service changes and include-glob membership. Validate the whole candidate before mutations; every setting reloads, so there is no reload boundary. The control server runs for the whole stack and takes devtools settings through `UpdateSettings` after routing accepts a reload; document servers check `ShouldInject` per request; `idleWatch` restarts on an `idleTimeout` change. Serialize reloads, restarts, and worktree refresh/switch operations. Preserve compatible automatic ports and saved checkout selections; compare effective injected environments, restart dependents and affected repository groups, and restore prior services/routes on failure. Track live routes and claims for shutdown instead of capturing startup lists. Keep replacement health pending until routing accepts it.
- Keep signal handling live while reload work runs. Cancel lifecycle health polling and start/status commands on shutdown, join reload work before final cleanup, and skip restoration launches during shutdown. Filter manifest events by tracked files and include membership before debouncing. Preserve recovery blocks for every unaffected service, including services outside Git. Reuse known repository identity when an inactive configured checkout has disappeared, then validate the selected checkout's configuration and service directories.
- Request the reload that follows startup with `manifestWatcher.check`, which waits out the same debounce as a save. Do not read the manifest beside the watcher: that read applies a save made while the stack starts, the save's own event applies it again, and a configuration whose launch fails then stops and restores the services twice.
- `devhost start <service...>` accepts service names and group names from `[groups]`. A selection runs the named services, group members, `alwaysStart` services, and their `dependsOn` chains (`startedServiceNames` in `internal/services/selection.go`). Groups merge from includes; validate their service references after the complete merge, reject duplicate group names and service-name collisions, and retain requested group names for membership changes on reload. `ResolvedManifest.Services` holds only the started services, so claims, routes, watches, worktree groups, and health cover nothing else; `ResolvedManifest.Stopped` holds the rest with resolved addresses. Read `Stopped` wherever a started service can name another one, as templates and `CreateInjectedServiceEnvironment` do, and keep a stopped automatic port across reloads: an address that changes when a service starts restarts every service that references it. Starting a stopped service goes through `applyConfiguration` with a longer list of requested names, so it gets the claim, launch, routing, and rollback steps of a reload. The dependency order always lists every service; skip the names that are not in `Services`. Reloads and stack restarts pass the current requested names on.
- A service that joins a repository group must not restart its siblings: `expandReloadGroups` spreads a change through a repository only from services the previous manifest already ran.
- Worktree discovery uses the existing picker Refresh button and refresh on picker open. Discover additions and inactive deletions without manifest edits. A missing running selection stops that repository's services and watchers, retains its selected path with a recovery error, and blocks new tool launches until explicit checkout recovery; other repositories remain independent. Missing means deleted, no longer registered with Git, or part of another repository, and nothing else: the running checkout's manifest belongs to hot reload, so a refresh judges that checkout without reading it and never stops services over an invalid edit, a missing service directory, or another stack's claim there (`worktree_list_leaves_a_rejected_running_manifest_to_hot_reload`).

- Removing the last route must retain that Caddy instance's admin address, bind host, and HTTP/HTTPS ports. Shutdown must not reset to default listeners or reload another instance. Keep the regression in `internal/caddy/route_shutdown_test.go` and exercise the real recording workflow when changing this lifecycle.
- Service test fixtures must support `TMPDIR` inside this checkout: `t.TempDir()` can inherit its Git repository. Verify repository identity or use an isolated Git fixture; `runGit` drops every `GIT_*` variable, so `GIT_CEILING_DIRECTORIES` has no effect, and a test that needs a path outside any repository names one under the filesystem root. Startup-crash tests observe service or repository recovery state and explicitly signal shutdown; a failed worktree switch does not emit the ordinary service-exit log message.
- Worktrees are enabled by default; `[worktrees].enabled = false` disables discovery and saved-selection restore. When enabled, keep all services sharing a Git common directory in one selected checkout. Persist one active stack selection per original manifest path before restarting. Load the target checkout's manifest at the repository-relative path and resolve its includes, service set, directories, and routes. Validate before stopping the entire managed stack in reverse dependency order; start in dependency order and use each daemon's launch cwd for its stop command. Keep the ownership path, the original root manifest path, stable; the stack takes the target manifest's settings, including its name. Turning worktrees on during a reload forgets the saved selection (`forgetWorktreeSelection`) so the running checkout stays; a disk reload that turns them off while `selectionAwayFromRoot` reports another checkout switches back to the configured checkout through `switchWorktreeLocked` instead of applying the edit. Watch the selected manifest after success. Restore the previous stack and selection after switch failure. Missing saved selections remain stopped for explicit recovery; never silently fall back or leave a partially switched group running. An ordinary startup is not a switch: a service that fails there is recovered alone and never stops the healthy services of its repository, because one crash must not take down pages that work. Services outside Git participate in full-stack switching.
- For manifest stacks, during foreground startup and after detached readiness, keep the supervisor, sibling services, routes, and devtools alive after foreground service exits, including startup crashes and successful exits. Retain the exit code and logs for web UI recovery, reporting a signaled process as `128` plus its signal number (`readProcessExitCode`); shutdown remains explicit or driven by the configured idle timeout. Failed restart attempts must reset pending state and remain retryable.
- All manifest stacks and standalone `devhost serve` sessions in one state directory share a single on-demand supervisor daemon (`devhost _daemon --state-dir <dir>`, owned by `src/daemon/{mod.rs,protocol.rs,server.rs,client.rs}`), serialized by `<state>/daemon.lock`, advertised via atomic `0600` `<state>/daemon.json`, and listening on a `0600` Unix socket inside a `0700` owner-verified directory (`<state>/run/daemon-<pid>.sock`, falling back to `<tmp>/dh-<euid>-<hash12>/d-<pid>.sock` when the path exceeds 90 bytes). The daemon `chdir("/")`s with deterministic `umask(0o022)`, verifies peer UID (`SO_PEERCRED` / `getpeereid`) on accept, checks `PROTOCOL_VERSION` and execution-context fingerprint (UID + Linux namespaces/seccomp/NoNewPrivs) on `Hello`, strips private devhost env vars while forwarding per-stack UTF-8 and non-UTF-8 environments, isolates stack threads with RAII `StackCleanup` unwind guards and `catch_unwind`, joins retired stack/connection threads in the accept loop, reaps both tracked and untracked Linux `PR_SET_CHILD_SUBREAPER` orphan zombies without touching registered `DirectChildGuard` PIDs, and exits automatically once the last stack stops. Each stack/session gets a unique `stack_id` decoupled from the shared daemon PID across stack records (`stacks/<stack_id>.json`), host/port claims, routes, devtools origin verification, worktree owner lookups, in-process `killZombies` cancellation, and `StackDirectoryPage` React keys; `devhost stop` never signals a live daemon PID directly.
- `devhost start --detach` (`src/daemon/client.rs` `run_detached` + shared helpers in `src/services/detach.rs`) launches the stack inside the shared supervisor daemon on Linux and macOS only (`check_detach_platform`). Every path to one manifest shares one launch lock, one append-only `0600` log, and one failure record under `<state>/logs/`, named `stack-<SHA-256 of manifest_identity>`. Under the lock, a live stack with the same manifest identity, detached or foreground, is reported as `Already running` and the command exits `0`. Keep that check under the lock: without it a losing caller reports a stack that then fails, and none is left. The caller releases the lock when it returns, which can be before its stack settles: it stops waiting for a failed stack's cleanup, or it dies. So a stack that records this manifest's detached log and is not `Ready` is not reported: `await_earlier_start` waits, within the same budget and signals as the lock, until it is ready (then `Already running`) or gone (then launch). Restart replacements record a log in a `<state>/restart-*` directory and foreground stacks none, so neither is waited for. The existing stack record and daemon `Ready` event form the readiness handshake: the strict detached stack publishes `Ready` only after routes and both watchers are live and a final recheck of every started service, external ones included, passes its exit status and a health re-probe. Before readiness, a launch, health, or routing failure stops the attempt; foreground startup retains browser recovery. A strict startup failure that a service caused writes that service to `<log stem>.failure.json` before cleanup, because neither its exit code nor its removed stack record can name it. The lock wait and readiness share the `detached_startup_timeout` budget. The caller ends every failure with a `Failure` naming the cause and log, following up to 30 lines of the attempt's log tail once launched. `stack restart` resolves one project manifest even with `--all` (restarting in-place via `RestartStack` RPC unless upgrading a single-stack daemon). `restart` exports specs, drains old daemons while preserving un-reopenable file serve sessions, retires removed launch directories, converts legacy pre-daemon stack processes into `StoredLaunchSpec`s, and starts replacements inside a fresh daemon. The success, already-running, `Log:`, log-tail, and failure lines are public output: `reference/output.md` ("Detached start"), `reference/cli.md`, the stack lifecycle guide, `start --help`, and `skills/devhost/SKILL.md` describe them, and `tests/detach_lifecycle.rs` and `tests/single_daemon.rs` pin their exact contracts. Change them together.
- Register selected routes before launching children. Serve standalone startup/recovery documents for root routes, aliases, and path routes independently of toolbar enablement; retain service launch/health failures and logs for explicit recovery. Keep documents pending until health and routing succeed, preserve the original browser URL, and never launch a browser. Recovery control requests keep the public Origin and pass the same `crossOriginProtection` as control requests; their Host is the service's, so the route-host rule does not apply. Apply `proxyLocalOrigin` translation only to app traffic. Assets and WebSockets keep their direct routes. Shutdown signals must cancel startup health waits; retain the in-flight child in runtime ownership for centralized shutdown progress and verified cleanup.
- Publish foreground restart recovery only after replacement health and route refresh succeed. Share route configuration between startup and restart; update document backends without replacing their listeners. Failed route updates must restore prior registrations and configuration, stop the unrouted replacement, preserve retryable recovery, and report rollback failures. Protect runtime manifest snapshots from concurrent health reads during auto-port retries.
- The shared Caddy listeners (`adminAddress`, `bindHost`, `http`, `httpPort`, `httpsPort`) come only from the devhost config file that `internal/config` reads (`config.toml` in `DEVHOST_CONFIG_DIR`, `XDG_CONFIG_HOME/devhost`, or `~/.config/devhost`); manifests reject a `[caddy]` table and route registrations carry no listener settings. `<state>/caddy/applied.json` records the settings Caddy runs: route changes render for them and reload through their admin address, and only `caddy.ApplyManagedCaddySettings` (stack startup and a saved config file) or a managed Caddy start changes them; stop removes the record. Without a record no managed Caddy of that state directory runs, so route changes (`readRouteSettings`) record and render but never reload, and the stack directory sync does nothing: a reload would reach whatever Caddy answers on the default admin address, and the next start renders every route for its own settings (`TestRouteChangesWithoutAppliedSettingsReloadNothing`). Every route mutation and settings change holds the `routes.lock` file lock in the Caddy directory, so concurrent stacks never render with different settings; never take it twice in one call chain. Startup stale cleanup performs no reload. Tests point `StartStackOptions.ConfigPath` or `DEVHOST_CONFIG_DIR` at a config file of their own, and services tests start stacks through `startTestStack`, which writes one from the manifest's Caddy settings. `testenv.IsolateHome`, called from `TestMain` in every package that starts stacks or runs the CLI, keeps each test process away from the machine's config file and state directory: it points `HOME`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `DEVHOST_CONFIG_DIR`, and `DEVHOST_STATE_DIR` into a new directory, so an explicit `StartStackOptions.Environment` that names none of them falls back there too. Its config file names the unreachable admin `127.0.0.1:1`, so a test without its own Caddy fails instead of reloading the machine's shared Caddy (`TestStackWithoutAConfigCannotReachTheMachinesCaddy`). A helper process started from the test binary keeps the directories its parent test gave it.
- Keep `proxyLocalOrigin` translation and Origin rejection scoped to the selected service's Caddy handlers. The document hop retains public Host for forwarding metadata while translating Origin to the app address; asset and WebSocket hops translate both. Preserve the option and assigned address across aliases, restarts, and route rollback. Validate the incoming public Origin before translation, including duplicate header values.
- Treat service cleanup as a generic containment contract with platform-specific backends; do not hardcode Linux-only assumptions into shared orchestration code.
- Linux may use stronger containment primitives (currently child-subreaper setup). Descendant tracking and the post-signal managed-port watch (`lateListenerMonitorDuration`, 2 seconds after each stop) run on every platform; listeners are read from `/proc` on Linux and through `lsof` elsewhere, where a missing `lsof` detects none. macOS and other platforms are best-effort and may have weaker guarantees.
- Read the process table in-process: `/proc` on Linux, the `kern.proc.all` sysctl on macOS.
- The containment tracker never trusts a bare PID: the system gives a PID to another process once its holder exits, and signalling tracked PIDs by number can kill unrelated programs. `src/services/containment.rs` records each descendant with its `src/procid.rs` start identity, walks the tree from the root only while the root keeps its own identity, drops entries whose PID is gone, a zombie, or held by a later process, keeps an adopted daemon whose identity is unchanged, and verifies start identity (using Linux `pidfd` where supported) immediately before signalling. Platforms without a start identity fall back to PID alone.
- Keep user-facing docs honest about those guarantee differences. Do not describe foreground-service shutdown as perfect or identical across platforms.
- Services that intentionally daemonize, detach, or escape the tracked foreground process tree are unsupported in foreground `command` mode unless there is an explicit cooperative lifecycle contract. Use daemon lifecycle mode for those services instead.
- Treat undocumented `DEVHOST_*` environment variables as internal implementation details. Do not document or rely on them as part of the public service contract unless they are intentionally promoted in `README.md` and covered by tests.
- **Auto-Shutdown Idle Timeout:** The stack-level auto-shutdown monitors Caddy proxy access log modification times (stack-isolated at `caddy.AccessLogPath`, `<caddy-paths>/logs/stack-<manifest path hash>_access.log`, named by `stackAccessLogName` from the root manifest path so a rename keeps it; a manifest-free session uses its name) and active control server WebSocket connections. Upon timeout, the supervisor triggers a clean, graceful cascading teardown (sending `SIGTERM` and cleaning up routing configurations). To support both automated tests with very short timeouts (down to 10ms) and larger production settings without CPU overhead, the log poller and check tickers use adaptive polling intervals (scaled to `idleTimeout / 2` with a minimum of 10ms).

## Logging rules

- All devhost-owned logs must go through the injected logger utility.
- Devhost-owned foreground lines must use the injected logger prefix.
- Manifest logs must use the manifest `name` as the prefix label.
- Pre-manifest logs must fall back to the `devhost` label.
- Retained child diagnostics and browser log records keep `[service-name]` prefixes. Format foreground stack and service output at the CLI writer boundary: human mode uses padded `name | ` prefixes with distinct terminal colors and aligned continuation lines when the width is known; agent mode uses compact `name: ` prefixes without padding, added colors, or wrapping. Include the manifest's logger label in the shared layout before startup, share it between stdout and stderr, and respect `NO_COLOR` and `TERM=dumb`.
- Stack shutdown names the received signal before stopping services, logs each managed service's stopping and successful cleanup once with the manifest prefix, then `Stack stopped.` only after service and routing cleanup succeeds. Keep child diagnostics visible and preserve signal exit codes.
- Startup health errors retain the checked target and actionable configuration hints in logs and recovery state. Explain health-check termination before signaling a foreground service. Report a detected TCP loopback mismatch once per startup attempt while continuing to check the configured target.
- Generated managed Caddyfiles retain runtime logs in `caddy.runtime.log` using Caddy's native rotating file writer. Capture `caddy start` stdout/stderr in per-instance `caddy.stdout.log` and `caddy.stderr.log`, replaced on each start, so inherited background output handles never leak into the terminal or keep command-output pipes open. Surface only the current startup's runtime diagnostics.
- Route displayed Caddy lifecycle, setup, and reload output through the injected logger and shared CLI layout. Lines Caddy writes use the `caddy` label (`caddy | ` / `caddy: `) and go through `writeCaddyOutput` in `internal/caddy/output.go`; devhost's own messages about Caddy use the `devhost` label. Register `caddy` in each layout that can show Caddy output. Known failures provide a summary and recovery command; human admin-availability errors omit raw transport details, which remain available in agent mode.
- Screen Caddy output before showing it. After a successful command show only Caddy's warnings, errors, and unrecognized lines; after a failure show the rest too. Lines devhost reports itself or that no user setting changes belong in `screenedCaddyMessages`, each with the reason it is left out. Replace a known case with a devhost message that says what it means; do not show raw Caddy lines a reader has no context for.
- Devhost owns local CA trust. The managed Caddyfile sets `skip_install_trust`: Caddy otherwise installs an untrusted root on every configuration load, so each route reload would run `sudo` again from the background process, where nobody can answer it. After devhost starts Caddy, it checks the root with `ReadRootCertificateTrust` and runs `caddy trust` once in the foreground, with `SUDO_PROMPT` carrying the `caddy` prefix. It warns with `UntrustedRootCertificateWarning` instead when it cannot ask (agent mode or no terminal) and when installation fails; a stack that joins a running Caddy warns once. Keep the native adapt regression in `internal/caddy/trust_test.go`.
- Do not print successful Caddy reload chatter during default `devhost start` runs; only print it for `devhost start --debug` or explicit `devhost caddy ...` commands.
- Surface Caddy output on failure, and surface successful reload output only for `devhost start --debug` or explicit `devhost caddy ...` commands.
- Report the failure that ends a command with `cliout.WriteFailure`, and format a warning written outside the logs with `cliout.Warning`; do not hand-write a `failed:` or `WARNING:` prefix for either. A person gets `[ERROR]`, an optional `[INFO]` hint, and `[WARN]`; under `AGENT=1` an agent gets `ERR:` with the whole error and `WARN:`. Wrap an error in `cliout.Failure` where the command line is known (`internal/cli`, `internal/app`) to give a person a hint, or a summary when the error repeats itself or names internals. Devhost-owned foreground logs use `name: ` prefixes in agent mode; foreground stack logs share the human terminal layout with child logs, including warnings within them.
- A test that asserts on a failure or warning line sets `AGENT` itself with `t.Setenv`, because the line depends on it and the test may run under an agent.

## Native chat boundary

- `internal/devtools/chat_journal.go` retains full native replay in private temporary files unlinked on open; stream snapshots under the session and socket write locks before live registration. Keep final shutdown frames, retain closed-session replay until resume or stack shutdown, and stop the native process on journal failure. `chat_log*.go` summarizes activity through the injected logger and the browser's `chat` log stream; keep message text, screenshots, tool arguments/output, and response contents out of activity summaries, and bound diagnostic lines.

- Every chat endpoint takes a required chat target (`chatTarget` query, `target` in the session request) that `chatRoot` in `internal/devtools/chat_project.go` maps to a directory: `project` is the page's routed checkout, and `devhost` is the dev-source checkout root, rejected when the stack has none. Never accept a directory from the browser.
- Use installed Codex app-server and Claude Code stream-json protocols with the configured CLI authentication, settings, environment, and selected checkout. Do not inject approval, sandbox, or system-prompt overrides. Omitted models preserve native configured defaults; discover selectable models from each native catalog.
- A Codex `turn/completed` with native status `failed` sets session status `error` and retains `turn.error.message`, with a generic fallback when absent. Keep retryable native errors active until completion, clear active turn state on completion, and clear the previous failure when starting the next turn.
- Native chat sessions belong to the stack across page reloads and closed tabs. Keep in-flight turns alive, retain exact native events for replay, and expose native session IDs for resume. Closing a session (`POST /chat/sessions/{id}/close`) and stack shutdown cancel and join owned process groups; a closed session stays listed with status `closed` and its replay events, so a page can resume it through its native session ID. Starting a session with that `resumeId` gives it the native ID at once and drops the closed records of that conversation (`dropClosedLocked`), so each conversation is listed once; never drop a running session.
- Relay native approval and user-input requests without approving them automatically. Accept a response only for a currently pending native request ID; publish pendingRequestIds with snapshots and state so replay cannot resurrect resolved requests.
- `src/devtools/agent_activity.rs` serves live transcript events, which can hold anything an agent read. Admit only direct local requests to the control server's own `127.0.0.1:<port>` address, because routed hostnames share the application's origin and page scripts could read them. Do not relax that guard or add transcript content to another route. Each open stream runs `agent_watcher::run` with `start_at_end`, a checkout filter, and a private temporary state directory. The stream stops its watcher and removes the directory on close. Keep the activity test that appends a turn immediately after the first lifecycle frame to check that existing history is skipped and new events arrive.
- `chat_panel.go` saves the dragged chat panel position in `<state>/chat-panels/<manifest key>.json`, replacing the file whole. It lives on the server because `localStorage` is per origin and one manifest serves several hostnames. A damaged file costs only the saved position.
- `src/devtools/agents.rs` serves the running agents list through `agent-watcher`'s `Snapshotter`. Keep its discovery caches between scans, scan only on request, share each snapshot for five seconds, and return successful results alongside a partial-failure notice. Exercise the handlers with a fixture process snapshot provider.
- Settle a Claude send on its `command_lifecycle` frame, on the echo, or on an error result. `system/init` arrives after the first message's frames, so a frame is its own evidence: do not gate on `msg_lifecycle_v1`. A wait that expires after a successful write is `unconfirmed`, never a failure; the pending entry stays for a late frame, and the socket's send worker moves on. Send `clientUserMessageId` to Codex, where the RPC response means queued and a timeout means unconfirmed. The browser's command ID is the native ID when it is a UUID, so replay can find the message. Never resend: Claude Code silently drops a repeated UUID and Codex dedupes nothing.
- Claude Code reports `session_state_changed` only with `CLAUDE_CODE_EMIT_SESSION_STATE_EVENTS=1`, which `startChatProcess` sets. Once those frames arrive they own the status, because a queued message can start right after a `result`; the only exception is `idle` after an error result, which keeps the failure.
- Interrupt with `cancel_queued` when `interrupt_cancel_queued_v1` is advertised, so Stop means the same on both harnesses. Codex discards pending input on interrupt; Claude Code otherwise runs it. The receipt's `still_queued` messages will still run, so never resend them.
- Forward active Codex sends through `turn/steer` with the expected turn ID and active Claude sends through streaming input. Keep approvals and interrupts readable while awaiting a send acknowledgement. Retry a steer as a new turn only after explicit native rejection and observed completion.
- Append the current `[devtools.chat].prompt` as user-message workflow instructions on each send; keep native system prompts and permission settings intact. An empty prompt disables this addition; manifest reload affects existing sessions on their next send.
- Validate PNG/JPEG data URL attachments and bound encoded payloads to 8 MiB before forwarding native image inputs. Never accept browser filesystem paths or remote attachment URLs.
- Run `DEVHOST_TEST_INSTALLED_HARNESSES=1 go test -race ./internal/devtools -run TestChat -count=1` from `apps/devhost/` when changing native client protocols. Installed-client startup and discovery tests do not send inference requests.
- `[devtools.chat].enabled` and `[devtools.annotations].enabled` independently configure native chat and the context selector. The former annotation actions/adapters and terminal/Vim launch configuration are rejected. External non-Vim IDE links and React source/highlight metadata remain available.
- The chat routes are registered for the whole stack and answer 404 while `ChatEnabled` is off (`whileChatEnabled`), so a reload turns chat on or off without a restart; sessions already running keep running and keep their sockets. Chat requests that change a session, and the session socket, also need an `Origin` (`requireChatPage`): the control guard has refused a foreign one, and a client with none is not a page.

## Control server and test networking rules

- Every control request passes `guardControlRequests` (`internal/devtools/request_guard.go`). Unsafe methods go through the standard `http.CrossOriginProtection`; websocket upgrades use the gorilla upgrader's default origin check, so never give an upgrader a `CheckOrigin` that accepts every origin. Both kinds, and every `/__devhost__/config/` request, must also name a Host that is a loopback name or a route this stack owns (`OwnsDocumentURL`), which refuses a page whose own name was rebound to the control port. Requests with a body must be `application/json`. A local tool that sends no browser headers passes, except on the chat routes above.
- The config editor writes only the paths `ListConfigFiles` returns, only for a client whose address and every `X-Forwarded-For` entry are loopback, and only content that passes `CheckConfigFile`: the reader overlay plus `resolveReloadCandidate` and `validateServiceWorkingDirectories`, which a reload also runs. The write starts no reload of its own; the file watcher applies it, and `HealthResponse.Configuration` counts finished reloads per source so the page can tell when the reload after its save is done.
- Never close a websocket client while holding the control server lock: a close waits for that client's in-flight write, which can stall on a dead connection. Drop the client from server state under the lock, release it, then close.
- End a browser connection the server closes on purpose with `closeWith` and a close code, never with bare `close`: the page reopens every connection that ends without `1000` (normal closure). Use `1001` (going away) when the stack stops, so pages reconnect to the next run, and `1000` when what the connection served is over, such as a closed chat session. Bare `close` is for a connection that is already broken or that the browser is closing.
- A client attaching to a chat session or the log stream must receive its snapshot before any broadcast. Take the client write lock before registering it for live publication; chat attachment and publication share the session lock.
- Health has no snapshot message: `publishHealth` records the health sent last and sends it as one step under `healthMu`, and an attach goes through it, so the health read for a new client also reaches the earlier clients it is news to. Do not set `lastPublishedHealth` anywhere else.
- Resource usage follows the health pattern: `publishResourceUsage` reads the sampler, records the message sent last, and sends it as one step under `resourcesMu`; an attach goes through it. `[devtools.resources]` resolves to `hostusage.Intervals`, where a zero interval is a readout that is off; with all three off no sampler runs and `/__devhost__/ws/resources` answers 404. `UpdateSettings` restarts the sampler when the intervals change and, when they all turn off, closes the open resource streams with `1000`, since what they served is over. The readouts do not count toward `hasEnabledDevtools`: they show in the toolbar other devtools features bring, and never inject the overlay by themselves. `Stop` joins the sampler after closing its clients.
- Write to a browser connection only through `websocketClient.write`, `writeJSONMessagesLocked`, or `writeTextReaderLocked`. Each sets a write deadline (`WebsocketWriteTimeout`, ten seconds by default), so a page that stops reading cannot block whoever publishes to it. A write that misses the deadline leaves the connection unusable: drop the client, as every caller does on a write error.
- A test that hands a port number to devhost or to a child process, or needs an address that refuses connections, takes the port from `nettest.ReservePort(t)` or `nettest.ReservePorts(t, n)` (`internal/nettest`). Do not close a listener and expect its port to stay unused: another test or process can claim it first.
- `internal/nettest` reserves through `github.com/hashicorp/consul/sdk/freeport`: the ports lie outside the range the kernel assigns to `:0` listeners, and each one returns to the pool when the test ends. It calls `freeport.Take`, not `freeport.GetOne` or `freeport.GetN`, which write two lines to stderr for every reservation. Call freeport only through `internal/nettest`.
- A test that needs a Caddy admin endpoint uses `caddytest.StartAdminServer(t)` (`internal/caddy/caddytest`), or `caddytest.UnusedAdminAddress(t)` for a Caddy that is not running. Both clean up when the test ends.
- A test that starts a stack, or otherwise lets devhost run Caddy, writes the managed executable with `caddytest.WriteExecutable(t, paths.ExecutablePath)` first. Without it the Caddy command fails: in a test binary (`testing.Testing()`), `ResolveManagedCaddyExecutablePath` never falls back to the `caddy` on `PATH`, because on a developer machine that is the Caddy every devhost stack shares, and a test once loaded its own routes into it (`TestTestBinariesNeverRunTheCaddyOnPath`). Native Caddy tests run the machine's executable explicitly, through `exec.LookPath` and their own reserved admin and listener ports.
- A test that starts a stack in the background registers the cleanup that stops it and waits for it to return before it waits for any readiness, and gives startup no deadline of its own: wait for the stack's own events (signal registration, the control server, its return). A test that gives up on a deadline leaves the stack running while cleanup deletes its directories; the stack then reads a missing config file, which leaves every setting at its default, and recreates its state from those defaults. Likewise, a startup-crash test gives the crashing service an unreachable health timeout, so startup fails by the exit it tests and never by a timeout a loaded machine can reach first.
- Tests never run the machine's `ssh`, `sudo`, `codex`, or `claude`. The chat test servers (`startChatControlServer`, `startChatTargetServer`) take the command that starts native harnesses when they start: `refuseChatHarness(t)` fails the test that starts one, and `chatHelperCommand(t)` runs the helper process for a test that needs a session. A test of a command that reaches another machine or needs privileges, such as `caddy trust-remote`, sets `PATH` to a directory holding only the fakes it needs.
- A test that runs a Bash script drops `BASH_ENV` from the child's environment, as `shimEnvironment` in `cmd/devhost/shim_test.go` does: a non-interactive Bash sources that file, and a developer's startup file can reorder `PATH`. A `go` other than the one `go test` chose then compiles against the `GOROOT` `go test` exported. A non-interactive `sh` reads no startup file, so `#!/bin/sh` fixtures need nothing. CI sets no `BASH_ENV`, so reproduce such a failure with a `BASH_ENV` file that prepends a directory to `PATH`.
- A Go browser test takes the Chromium the repository installs from `browsertest.Locate(t)`, starts it with `AllocatorOptions`, and keeps its profile and generated fixtures in `browsertest.RunDirectory(t, prefix)`, under `<os.TempDir()>/devhost-e2e`. Measure text contrast with the `Contrast` function it returns, the one the UI stories use.
- Do not make a test beat a timer. Use an unreachable timeout while a test attaches or inspects, a short one only where the test waits for the timer to fire, and read scheduled state directly instead of sleeping to prove that nothing happened.
- Git and the shell report physical paths, and tests compare them with paths built from `t.TempDir()`. The shared runner resolves `/tmp` before exporting it; packages also call `testenv.UsePhysicalTempDir()` from `TestMain` when direct `go test` invocations need the same guarantee, as `internal/app`, `internal/services`, and `internal/devtools` do. Reproduce a failure of this kind on Linux by running the tests with `TMPDIR` set to a symbolic link.
- Managed Caddy defaults to `bindHost = "0.0.0.0"` (all IPv4/IPv6 interfaces), with `http = false`; admin and service bind defaults remain on loopback. Route changes render the Caddyfile for `runtime.GOOS`, and macOS retains its omitted `default_bind` behavior for explicit `127.0.0.1`. A Caddy test fixture that route code later rewrites, or an expectation compared with what it wrote, renders for `runtime.GOOS` too; a literal operating system belongs only in tests of the rendering itself.
- Bump the restart generation in `src/caddy/generation.rs` when a changed runtime policy requires a fresh Caddy process; ordinary reloadable changes keep the generation. Keep restart proof bound to PID and process start identity, write it only after a healthy start, and preserve downgrade checks under the shared route lock. Cover new restart requirements with native Caddy regression tests.
