# Chat with a coding agent: research

Proposal: [Chat with a coding agent](agent-chat.md). Shared patterns: [UX pattern reference](../patterns.md).

Scope: the journey from the first intent (a person on a routed page opens **Chat** to have a coding agent change the checkout that page runs) to a finished outcome the person can read, review and take back, through the operations involved: discovering harnesses (`GET /__devhost__/chat/harnesses`), starting or resuming a session (`POST /__devhost__/chat/sessions`), the session socket (`/__devhost__/ws/chat`: `send`, `respond`, `interrupt`), closing (`POST /__devhost__/chat/sessions/<id>/close`), stack stop, and the agent CLI's own edits, commands and Git operations in the checkout. Page context capture (page-context), the **Disable Reloads** request (reload-control) and the running-agents list (running-agents) appear only where they enter this path.

Evidence: the devhost repository at `edb5c0fc01cabae490e92ac23d4c785ec896c4ed` (code, tests, `AGENTS.md` files and public docs), the only repository read; its product code is identical to the reviewed build. "Verified" means read in code, tests or docs at that revision, or observed in a recorded review run named by its finding ID; "Hypothesis" means inferred and not tested, and each one names the condition under which it holds.

## Owner-confirmed product rule

> **Chat edit mode (owner decision q4, 2026-11-16 16:19):** the chat composer offers an explicit, visible choice of how the agent handles a message: **This checkout (live)** edits the checkout the page runs, so hot reload shows the change (the default when the message carries page context); **New worktree (review before merge)** is today's workflow, shown explicitly; **Make tickets** has the agent file tickets for the problem instead of editing, by injecting an instruction such as "make tickets" and assuming the agent has the skills to do it (for example an issue-tracker skill). Every sent message shows which mode applied; nothing commits or merges unless the worktree mode is chosen and shown. This changes the documented default workflow prompt (guides/annotations.md, "The workflow prompt"), a contract change the redesign states. The default for messages without page context is a design call to settle in Phase 7 (for example the conversation's last choice).

The pattern reference records it as `O1` (decided). Three further owner rules govern this flow and are intended, not defects: devhost never answers or pre-approves an agent's approvals or questions; **Delivery unconfirmed** and the refusal to resend a message protect against double sends; chat never asks for API keys in the browser. The contributor contract in `apps/devhost/AGENTS.md` ("Native chat boundary") adds that devhost passes the installed CLIs "the configured CLI authentication, settings, environment, and selected checkout" and must "not inject approval, sandbox, or system-prompt overrides" (Verified: `apps/devhost/AGENTS.md`, "Native chat boundary").

The reframed gap: working in a new worktree, committing and merging are intended when the person picks **New worktree (review before merge)** and the message shows it, and editing the running checkout is intended in **This checkout (live)**. The gap is that today nobody picks: one built-in prompt, appended out of sight to every message, always chooses the worktree-and-merge workflow; before Send the page names neither the checkout, nor the workflow, nor whether the agent will ask before acting; and afterwards devhost keeps no record of what the agent changed and offers no way back (Verified: steps 5, 15, 22 and 31 below). Relaying approvals without answering them is likewise intended; the gap is that a CLI configured never to ask produces no approval at all, and the page does not say so (Verified: step 13 and the negative searches below; the never-asking turn itself is a Hypothesis, consequence 3).

Claude Code starts as `claude -p` with stream-json input and output and `--permission-prompt-tool=stdio`, plus `--resume` when resuming; Codex starts as `codex app-server` (Verified: `apps/devhost/internal/devtools/chat_sessions.go:134-142`). The process runs with the checkout as its working directory, inherits devhost's own environment (Claude Code also gets `CLAUDE_CODE_EMIT_SESSION_STATE_EVENTS=1`), and leads its own process group, which cancellation signals with `SIGTERM` and then `SIGKILL` after 2 s (Verified: `apps/devhost/internal/devtools/chat_process.go:62-75`, `:104-124`).
13. **Native session.** After `initialize`, Codex has its configuration read (`config/read`, of which devhost keeps only the model) and gets `thread/start` with `{cwd, model}` or `thread/resume` with `{threadId}`; no approval policy, sandbox or permission mode is passed to either harness (Verified: `apps/devhost/internal/devtools/chat_sessions.go:147-186`; `apps/devhost/internal/devtools/chat_model.go:9-24`). The session becomes `idle`, is registered, is logged as started, and a monitor follows the process (Verified: `apps/devhost/internal/devtools/chat_sessions.go:187-251`).
14. **Socket attach.** The page opens `/__devhost__/ws/chat`; the server requires an `Origin`, the session's checkout must match the page's, and the full replay is written before live events (Verified: `apps/devhost/internal/devtools/chat_server.go:151-206`; `apps/devhost/internal/devtools/chat_journal.go:72-89`).
15. **Send command.** The server decodes the command, requires a command ID, re-checks the session's checkout against the page, then appends `"\n\nDevhost workflow instructions:\n"` and the current `[devtools.chat].prompt` to the text (Verified: `apps/devhost/internal/devtools/chat_server.go:234-258`). Without a configured prompt that is the built-in one: work in a dedicated Git worktree on a new branch, run checks, commit, merge into local `main`, remove the worktree and delete the branch (Verified: `apps/devhost/internal/manifest/chat.go:3-5`, `:12-13`, `:25-27`). The whole frame, instructions included, must fit in 8 MiB, and at most 16 sends wait per socket (Verified: `apps/devhost/internal/devtools/chat_server.go:212`, `:259-278`).
16. **Native send.** A closed or starting session refuses the send; the model is resolved and the send is a new turn or a steer (Verified: `apps/devhost/internal/devtools/chat_send.go:24-61`). Codex gets `turn/start`, or `turn/steer` with the expected turn ID, carrying `threadId`, input, `clientUserMessageId` and model; Claude Code gets `set_model` for a new turn and the message as streaming input (Verified: `apps/devhost/internal/devtools/chat_send.go:62-116`). A wait that times out is `unconfirmed` and is never retried (Verified: `apps/devhost/internal/devtools/chat_send.go:92-97`; `apps/devhost/internal/devtools/chat_process.go:235-263`).
17. **Acknowledgement.** The server answers with a `command_result` and its delivery state (Verified: `apps/devhost/internal/devtools/chat_server.go:291-308`); the page resolves the send, or marks it `unconfirmed` after 45 s, then clears the draft and the sent page context (Verified: `packages/devhost-ui/src/devtools/features/agentChat/createAgentChatClient.ts:27`, `:346-361`; `packages/devhost-ui/src/devtools/features/agentChat/hooks/useAgentChat.ts:128-130`; `packages/devhost-ui/src/devtools/features/agentChat/components/PageChat.tsx:178-183`).

The agent at work:

18. **Edits and commands.** The agent CLI reads, edits and runs commands in the checkout under its own permission configuration; devhost runs no Git command and inspects no file change (Verified: `packages/docs/src/content/docs/guides/annotations.md:87`; searched `apps/devhost/internal/devtools/chat_*.go`, tests excluded, for `git`, `undo`, `revert`, `checkpoint` and `stash`: no match). Every native frame is journaled, broadcast to attached pages and folded into the session status (Verified: `apps/devhost/internal/devtools/chat_sessions.go:317-458`).
19. **Approvals and questions.** A Codex server request or a Claude Code `control_request` is recorded as pending and the status becomes `requires_action` (Verified: `apps/devhost/internal/devtools/chat_sessions.go:348-361`, `:378-394`, `:427-429`). The page shows it above the transcript (Verified: `packages/devhost-ui/src/devtools/features/agentChat/layouts/AgentChatBody.tsx:8-14`; `packages/devhost-ui/src/devtools/features/agentChat/components/ChatApprovalRequest.tsx:36-82`); **Deny** sends the fixed message "Denied by the user." (Verified: `packages/devhost-ui/src/devtools/features/agentChat/readChatApproval.ts:39`), and a Codex file change without a diff offers only **Deny** (Verified: `packages/devhost-ui/src/devtools/features/agentChat/components/ChatApprovalRequest.tsx:55-69`). 20. **Follow-ups.** A message sent during a turn waits in the page's queue until the server acknowledges it, then reaches Codex as `turn/steer` and Claude Code as streaming input (Verified: `packages/devhost-ui/src/devtools/features/agentChat/hooks/useAgentChat.ts:167-197`; `apps/devhost/internal/devtools/chat_send.go:50-53`, `:71-87`).
21. **Stop.** **Stop Generating**, Escape or **Stop Turn** sends `interrupt`: `turn/interrupt` for Codex, `interrupt` with `cancel_queued` when Claude Code advertises it (Verified: `packages/devhost-ui/src/devtools/features/agentChat/hooks/useAgentChat.ts:218-225`; `apps/devhost/internal/devtools/chat_sessions.go:535-583`).

Results:

22. **Turn end.** `turn/completed` or a result sets the session `idle`, and compact chat shows the latest reply (Verified: `apps/devhost/internal/devtools/chat_sessions.go:406-415`; `packages/devhost-ui/src/devtools/features/agentChat/components/CompactChat.tsx:33-41`). The sent message shows the appended text afterwards, collapsed as **Workflow Instructions** and **Page Context** (Verified: `packages/devhost-ui/src/devtools/features/agentChat/components/ChatUserText.tsx:7-31`). What changed is known only from the agent's own reply: the session record holds ID, harness, checkout, native ID, status and error, and nothing about files, branches or commits (Verified: `apps/devhost/internal/devtools/chat_types.go:48-55`).
23. **The page after the edit.** The agent's working directory is the selected checkout of the routed service's repository, the one the page's services run from (Verified: `apps/devhost/internal/services/worktrees.go:403-441`; `apps/devhost/internal/devtools/chat_project.go:12-19`). An edit there reaches the page through the app's own hot reload; an edit in a separate worktree reaches it only after a merge into that checkout (Verified, observed in journey-agent-fix-01, where neither run fixed the page during the turn).

Failures:

24. **Process exit.** When the CLI exits, a running turn finishes as failed and the session becomes `error` with the exit error, which only the footer's status word reflects (Verified: `apps/devhost/internal/devtools/chat_sessions.go:227-251`; `packages/devhost-ui/src/devtools/features/agentChat/components/AgentChatPanel.tsx:225-230`; chat-compose-2-04).
25. **Journal failure.** A failed replay write sets the session to `error` and cancels the process (Verified: `apps/devhost/internal/devtools/chat_sessions.go:324-335`).
26. **Lost connection.** Pending sends settle as `unconfirmed` and are never sent again (Verified: `packages/devhost-ui/src/devtools/features/agentChat/createAgentChatClient.ts:86-89`, `:164-167`).
27. **Checkout switch or chat turned off.** Listing and attaching keep only sessions of the page's current checkout, and routes answer 404 while chat is off, while the hidden sessions keep running (Verified: `apps/devhost/internal/devtools/chat_project.go:30-38`; `apps/devhost/internal/devtools/chat_server.go:27-37`, `:96-111`; chat-checkout-switch-01, chat-approvals-08).

Ending, and what can be taken back:

28. **Close Conversation.** The server interrupts a running turn, drops pending approvals, closes the sockets with `1000` and stops the process group; the page then clears the transcript (Verified: `apps/devhost/internal/devtools/chat_server.go:72-89`; `apps/devhost/internal/devtools/chat_sessions.go:460-482`; `packages/devhost-ui/src/devtools/features/agentChat/createAgentChatClient.ts:313-332`). When the close request fails, the panel's action wrapper shows the server's raw response text (for a session the server no longer knows, Go's "404 page not found") as a red send error, and the conversation stays open (Verified: `packages/devhost-ui/src/devtools/features/agentChat/hooks/useAgentChat.ts:208-217`, `:303-306`; `packages/devhost-ui/src/devtools/features/agentChat/components/AgentChatPanel.tsx:171-175`, `:236-238`). This corrects chat-conversations-09's evidence, which says the failure shows nothing and surfaces as an unhandled rejection; its "cannot be closed" part stands.
29. **Resume.** Selecting a closed conversation starts a new session with `resumeId`; the closed record and its journal are dropped, so the earlier transcript leaves devhost (Verified: `packages/devhost-ui/src/devtools/features/agentChat/createAgentChatClient.ts:196-234`; `apps/devhost/internal/devtools/chat_sessions.go:205-207`, `:253-270`; chat-conversations-02).
30. **Stack stop.** Stopping the control server closes every session with `1001` "Devhost stopping", waits for them, and closes every journal (Verified: `apps/devhost/internal/devtools/server.go:530-531`; `apps/devhost/internal/devtools/chat_sessions.go:80-101`). Idle shutdown waits while any session is `starting`, `running` or `requires_action` (Verified: `apps/devhost/internal/devtools/chat_sessions.go:54-68`; `apps/devhost/internal/services/idle_timeout.go:127`).
31. **Undo.** devhost offers none for an agent's edits; the only Undo in chat is **Undo Drawing** (Verified: `packages/devhost-ui/src/devtools/features/agentChat/components/PageAnnotationToolbar.tsx:61-66`; searched `features/agentChat/`, tests and stories excluded, for `undo`, `revert` and `worktree`). Taking an edit back depends on Git in the checkout and on the agent CLI's own facilities (Hypothesis: holds when the checkout is a Git repository; the CLIs' own restore features were not examined through devhost's protocols).

## The contested behavior

**Every message sent from chat carries a built-in instruction to leave the page's checkout, commit and merge into local `main`; the page shows that instruction only after sending, and nothing in devhost limits, shows or records what the agent then changes (Verified).**

Supporting evidence:

- The built-in prompt applies whenever `[devtools.chat].prompt` is unset, and the server appends it to every non-empty send, after the page has shown only harness, model and conversation (Verified: `apps/devhost/internal/manifest/chat.go:3-5`, `:12-13`; `apps/devhost/internal/devtools/chat_server.go:252-258`; `packages/devhost-ui/src/devtools/features/agentChat/components/ChatSettings.tsx:46-54`). The public docs document it as the default (Verified: `packages/docs/src/content/docs/guides/annotations.md:85-96`; `packages/docs/src/content/docs/reference/chat-api.md:135-137`); the owner rule above replaces that default, which is why the behavior is contested: the documented contract says "worktree and merge", the findings (journey-agent-fix-01, with chat-approvals-06 recorded on it) say it defeats the page's own fix loop, and the owner decided for an explicit mode.
- The instructions become visible only on the sent message, collapsed as **Workflow Instructions**, with no word on where they come from (Verified: `packages/devhost-ui/src/devtools/features/agentChat/components/ChatUserText.tsx:7-31`).
- devhost passes no approval policy, sandbox or permission mode to either CLI, by contract, so whether the worktree, commit and merge steps ask first depends only on the person's CLI configuration (Verified: `apps/devhost/internal/devtools/chat_sessions.go:137`, `:160-168`; `apps/devhost/internal/devtools/chat_send.go:62-116`; `apps/devhost/AGENTS.md`, "Native chat boundary"; chat-checkout-switch-04).
- devhost runs no Git itself, so every worktree, branch, commit, merge, restore or deletion is the agent's own action (Verified: `packages/docs/src/content/docs/guides/annotations.md:87`).

Negative searches recorded as evidence:

- No Git, undo or file-change tracking exists in the chat backend: `apps/devhost/internal/devtools/chat_*.go`, tests excluded, has no match for `git`, `undo`, `revert`, `checkpoint` or `stash` (Verified).
- No approval or sandbox override exists: the same files mention permissions only in `--permission-prompt-tool=stdio`, which routes Claude Code's own prompts to devhost, and in parsing pending permission requests (Verified: `apps/devhost/internal/devtools/chat_sessions.go:137`, `:378-394`; `apps/devhost/internal/devtools/chat_discovery.go:14`).
- No mode, checkout name or change record reaches the page: `features/agentChat/`, tests and stories excluded, parses `projectRootPath` but renders it nowhere, and has no `mode` field or worktree reference (Verified: `packages/devhost-ui/src/devtools/features/agentChat/readChatServerFrame.ts:8`; `packages/devhost-ui/src/devtools/features/agentChat/types.ts:61`).
- No per-message record exists beyond the native transcript: the session record has six fields, none about changes (Verified: `apps/devhost/internal/devtools/chat_types.go:48-55`).

What this means in practice:

1. A bug pointed at on the page usually lives in the working tree the page runs, often as an uncommitted change. The built-in prompt sends the agent to a worktree made from committed `main`, so the fix does not reach the page during the turn: in one run the agent backed the person's diff up into an untracked folder in the project and ran `git restore` on their file (6 min 26 s, 4 approvals); in another it ended the turn without a fix (Verified, observed in journey-agent-fix-01).
2. With a CLI that asks before commands, each worktree, commit and merge step costs an approval the person never asked for (Verified, observed in journey-agent-fix-01 and in chat-checkout-switch-04's Claude Code run, which stopped at `git worktree add -b …`).
3. With a CLI configured never to ask, the same instructions run unasked: a message typed into a page can create a branch, commit, merge into local `main` and delete the branch with no card in chat (Hypothesis: holds when the CLI's configuration allows those commands without approval, as the review machine's Codex configuration does; inferred from devhost passing no policy, never run; chat-checkout-switch-04).
4. A completed default workflow moves local `main`, which other worktrees and the person's next pull build on, and deletes the branch that would have carried the change for review (Hypothesis: holds when the agent completes every step of the built-in prompt; agents did not in the recorded runs, journey-agent-fix-01).
5. Anyone who reaches the stack's HTTPS listener with a matching `Host` and `Origin` can start a session and send messages, because chat checks headers and never the client's address (Verified: `apps/devhost/internal/devtools/request_guard.go:22-71`; `apps/devhost/internal/devtools/chat_server.go:16-25`; network-exposure-01, P0, confirmed). The same client could presumably answer the session's approvals over the socket (Hypothesis: holds whenever it can attach, since `respond` checks only that the request is pending, `apps/devhost/internal/devtools/chat_sessions.go:493-524`).
6. After a checkout switch, or when chat is turned off, a working agent keeps editing the old checkout while no page can see or stop it (Verified: `apps/devhost/internal/devtools/chat_project.go:30-38`; `apps/devhost/internal/devtools/chat_server.go:27-37`; chat-checkout-switch-01, chat-approvals-08).
7. When a turn ends, the agent's prose is the only account of what changed; closing and resuming a conversation, or stopping the stack, also removes the transcript from devhost (Verified: `apps/devhost/internal/devtools/chat_types.go:48-55`; `apps/devhost/internal/devtools/chat_sessions.go:80-101`, `:253-270`; chat-conversations-02, chat-conversations-03).
8. Under **This checkout (live)**, the person's uncommitted edits and the agent's share one working tree, so an agent that restores, stashes or checks out a file can discard the person's work, as the agent in consequence 1 nearly did (Hypothesis: holds when the person has uncommitted changes in files the agent touches and the live mode's instructions do not forbid those Git commands; the stopgap for journey-agent-fix-01 sets that wording).

Reusable capabilities and their limits:

- **Per-send instructions.** The server already appends instructions to each send at one point and takes the current prompt on the next send of every session, so a mode can select its text there (Verified: `apps/devhost/internal/devtools/chat_server.go:252-258`; `apps/devhost/AGENTS.md`, "Native chat boundary"). Limit: the whole send frame, instructions and images included, fits in 8 MiB (Verified: `apps/devhost/internal/devtools/chat_types.go:11`; `apps/devhost/internal/devtools/chat_server.go:259-266`).
- **A per-message record that survives a reload.** The appended text travels in the native transcript, the journal replays it to every attaching page, and the page already splits it into a collapsed block (Verified: `apps/devhost/internal/devtools/chat_journal.go:72-89`; `packages/devhost-ui/src/devtools/features/agentChat/components/ChatUserText.tsx:7-31`). Limit: the journal lives until a closed conversation is resumed or the stack stops (Verified: `apps/devhost/internal/devtools/chat_sessions.go:80-101`, `:253-270`).
- **A stable message key.** Each send carries a browser UUID that becomes the native message ID and is never resent (Verified: `packages/devhost-ui/src/devtools/features/agentChat/createAgentChatClient.ts:334`; `apps/devhost/internal/devtools/chat_send.go:20`; `apps/devhost/internal/devtools/chat_types.go:23-26`).

### Other products

General knowledge, not re-checked for this note; each needs confirmation against the product's current documentation before a proposal relies on it.

- **Claude Code** (CLI reference linked from the annotations guide, `https://code.claude.com/docs/en/cli-reference`): permission modes range from asking before edits and commands, through accepting edits automatically and a read-only plan mode, to skipping every prompt; the interactive CLI keeps checkpoints of file edits that it can rewind within a session. Contribution: the policy is a parameter devhost could show, or pass, per conversation.
- **Hosted coding agents** (GitHub Copilot's coding agent, Cursor's background agents): work on their own branch in a separate environment and return a pull request for review. Contribution: the worktree mode's result is a reviewable branch, not a merge.
- **Editor agents** (Cursor, Windsurf, Copilot edits in VS Code): edit the open workspace directly and show each changed file with accept and reject before the person keeps the change. Contribution: the live mode's receipt is a per-file list with a way to take each change back.

## Open questions

Already in the pattern reference, cited instead of repeated: `O1` (decided: the edit mode), `O2` (decided: **Disable Reloads** sends in **This checkout (live)**), `O3` (the mode a message without page context inherits), `O11` (whether **Make tickets** shows the tickets before filing), `O12` (standing approvals from the browser) and `O13` (whether browser-started turns ask before acting by default). For `O13` this note adds the evidence that would close its backend part: devhost already runs Codex's `config/read` for every session and keeps only the model, and already reads Claude Code's `system/init`; whether either reports the effective approval policy, sandbox or permission mode is unchecked (**Reusable capabilities and their limits**).

1. **What "review before merge" means for the worktree mode.**
   - Unknown: whether **New worktree (review before merge)** stops after committing on its branch and waits for the person, or merges into local `main` by itself once checks pass, as today's built-in prompt does (Verified: `apps/devhost/internal/manifest/chat.go:5`). The owner rule calls the mode both "today's workflow" and "review before merge", and today's workflow has no review step.
   - Why it matters: it decides whether a worktree-mode message can still move local `main` before the person looks at the change, and what the turn's result offers (merge, open the worktree, discard).
   - Evidence that would close it: the owner's reading of the label; whether worktree-switch's picker lists a worktree the agent created, so the person can run the stack from it to review.
   - Proposed default: the mode's instructions end after the commit on the branch, reporting the branch and worktree path without merging; a follow-up that asks for the merge performs it.
   - Who decides: the product owner.
2. **What This checkout (live) lets the agent do with Git and the person's uncommitted work.**
   - Unknown: the limits the live mode's instructions set: whether they forbid commits, `git restore`, `stash`, `checkout` and `reset`, and what the agent does when the fix conflicts with an uncommitted change of the person's.
   - Why it matters: in this mode the person's and the agent's edits share one working tree (consequence 8), and a recorded run backed up and restored the person's file (Verified, observed in journey-agent-fix-01).
   - Evidence that would close it: the stopgap prompt for journey-agent-fix-01; one run per harness on a fixture with an uncommitted change in the target file and another in an unrelated file, recording every Git command the agent proposes.
   - Proposed default: edit files in place and leave every change uncommitted; never commit, stash, restore, reset or check out files; when a fix touches an uncommitted change, build on it and say so in the reply.
   - Who decides: the product owner, since the prompt is a public contract, with the stopgap's implementer.
3. **Changing the mode within one conversation.**
   - Unknown: what the agent is told when a message's mode differs from the conversation's earlier messages. The CLIs keep earlier messages in context, workflow instructions included, and the built-in prompt says "Reuse that worktree for related follow-ups" (Verified: `apps/devhost/internal/manifest/chat.go:5`).
   - Why it matters: conflicting instructions in context can send a live-mode follow-up into the earlier worktree, or leave uncommitted worktree changes behind (Hypothesis: holds when a conversation switches from the worktree mode to the live mode). `O3` sets which mode a follow-up inherits, not what a change of mode tells the agent.
   - Evidence that would close it: two-message runs per harness on a fixture, switching worktree to live and live to worktree, recording where each edit lands.
   - Proposed default: each mode's text states that it replaces earlier workflow instructions for this message; the composer says when the chosen mode differs from the conversation's previous message and names the earlier worktree when there is one.
   - Who decides: the product owner for the wording; Phase 7 for the composer's notice.
4. **What Make tickets does when the agent cannot file tickets.**
   - Unknown: devhost cannot tell whether the agent has a ticket skill or tracker access, since discovery reads only each CLI's availability and models (Verified: `apps/devhost/internal/devtools/chat_types.go:34-46`), and the mode's behavior without one is untested.
   - Why it matters: an agent without one may edit code anyway, or write ticket files into the checkout, which the mode exists to avoid (Hypothesis: holds when no ticket skill is installed). `O11` settles review before filing, not this fallback.
   - Evidence that would close it: one run per harness on a fixture without a ticket skill, sending a page-context message in **Make tickets**.
   - Proposed default: the mode's text says to change no files and, when tickets cannot be filed, to reply with the ticket drafts as text.
   - Who decides: the product owner.
5. **A record, and a way back, for what a turn changed.**
   - Unknown: whether devhost records per message which files the agent changed, and in which checkout or branch, and whether it offers any way back. Today it records nothing and offers nothing (Verified: steps 22 and 31), and the docs say devhost runs no Git commands itself (Verified: `packages/docs/src/content/docs/guides/annotations.md:87`).
   - Why it matters: the redesign's result step needs a source for "what changed" other than the agent's prose, and an undo for agent edits cannot come from devhost without running Git or reading the CLI's own records.
   - Evidence that would close it: whether the harness events already in the journal name every file change (Codex file-change items, Claude Code edit and write tool calls), measured on a recorded turn per harness; whether either protocol exposes the CLI's own edit checkpoints; the cost of a read-only `git status` on a large checkout, if the events are incomplete.
   - Proposed default: a per-turn list of changed files built from the harness events already in the journal, with no Git calls and no undo in devhost; the list names how to discard each change (live mode) or the branch to drop (worktree mode).
   - Who decides: the product owner, who owns the "devhost runs no Git commands itself" contract, with the backend owners confirming event coverage.
6. **What a resumable conversation list may keep after the stack stops.**
   - Unknown: what devhost may store on disk so that ended conversations stay resumable across a stop (this redesign's slice of chat-conversations-03). Today session records live only in memory and the replay files are freed at stop (Verified: `apps/devhost/internal/devtools/chat_sessions.go:15-23`, `:80-101`).
   - Why it matters: telling conversations apart needs a label, and the first message, the obvious one, would put message text on disk, which today's activity logs and browser storage deliberately never hold (Verified: `packages/docs/src/content/docs/guides/annotations.md:108`; `packages/docs/src/content/docs/reference/chat-api.md:165`).
   - Evidence that would close it: what each CLI reports as a conversation's title or summary in its own history; the owner's stance on message text at rest.
   - Proposed default: keep only harness, native session ID, checkout, model, the last message's mode, start and end times, and a title the CLI itself reports; no message text; kept as long as the stopped-stack record of `O15`.
   - Who decides: the product owner.
7. **Network reach while the mode is built.**
   - Unknown: when the loopback-only stopgap for network-exposure-01 ships relative to the stopgap for journey-agent-fix-01 and the mode control.
   - Why it matters: with header-only checks and a never-asking CLI, another machine on the network can have the agent run commands and edit files with no approval (consequences 3 and 5); the mode control changes neither.
   - Evidence that would close it: none beyond the confirmed finding; the open part is the order, and any later remote chat needs a per-page secret, a contract change.
   - Proposed default: the loopback-only stopgap ships first, no later than the journey-agent-fix-01 stopgap; chat stays loopback-only until a per-page secret exists.
   - Who decides: the product owner, whose answer on the stopgap's timing is pending.
