# Chat with a coding agent: proposed experience

Diagrams: [current](../agent-chat-current.html), [proposed](../agent-chat-proposed.html). [Wireframe](../wireframes/agent-chat.html). Research: [Chat with a coding agent: research](agent-chat-research.md).

Status: design proposal, not implemented behavior. The [shared UX pattern reference](../patterns.md) wins where this proposal disagrees with it.

Source revision: alexgorbatchev/devhost `edb5c0fc01cabae490e92ac23d4c785ec896c4ed`. Features: CHAT-01, CHAT-02, CHAT-03, CHAT-04, CHAT-05, CHAT-06, CHAT-07, CHAT-08, CHAT-09, CHAT-10, CHAT-11, CHAT-12, LOG-03. Redesign ticket: tracked privately.

Product rule: the product owner decided the chat edit mode (`O1`, owner decision q4, 2026-11-16): "the chat composer offers an explicit, visible choice of how the agent handles a message: **This checkout (live)** edits the checkout the page runs, so hot reload shows the change (the default when the message carries page context); **New worktree (review before merge)** is today's workflow, shown explicitly; **Make tickets** has the agent file tickets for the problem instead of editing [...]. Every sent message shows which mode applied; nothing commits or merges unless the worktree mode is chosen and shown." The owner's other rules make more of this flow intended: devhost never answers or pre-approves an agent's approval or question; **Delivery unconfirmed** and the refusal to resend a message are intended; chat never asks for API keys in the browser. `apps/devhost/AGENTS.md`, "Native chat boundary", adds that devhost passes the installed CLIs "the configured CLI authentication, settings, environment, and selected checkout" and must "not inject approval, sandbox, or system-prompt overrides". So a worktree, a commit or a merge is intended when the person chose **New worktree (review before merge)** and the message shows it; an edit to the running checkout is intended in **This checkout (live)**; an approval that waits until the person answers it is intended; and a CLI that never asks, because its own configuration says so, is the person's setting, not a defect. The gap is around them: today nobody chooses, because one built-in prompt, appended out of sight to every message, always picks the worktree-and-merge workflow; before **Send** the page names neither the agent, nor the checkout, nor the workflow, nor whether the agent asks first; the request the agent is waiting on hides its buttons under raw JSON; a switch, a close, a stop or turning chat off hides a conversation that still runs or remembers; and after a turn devhost keeps no record of what changed and names no way back (research note, "The contested behavior"). Until the product owner answers `O1`'s clarification, **New worktree (review before merge)** stops after committing on the worktree's branch and merges only when the person asks, the reading `O1` applies by default.

## Target experience

The person points at a broken header on the page, or presses Alt+Ctrl+C, and docked chat opens beside the notice stack with focus in the composer; the page keeps its scroll position and its state. Before typing a word they can read, in the composer row, who will answer and how: "Claude Code · Haiku 4.5", the mode "This checkout (live) · fix-nav ~/acme/.worktrees/fix-nav", whether that agent asks before it runs commands and edits, what devhost will add to the message behind "Added by devhost", and each mark of page context it carries. **Send** (or Enter) puts the message into the conversation at once with its delivery state and its mode line; nothing asks unless a second agent would edit the same files or a mark the message cites is gone. While the agent works, a status line names the turn's progress, "Claude Code is working · 12 s · 3 tool calls", with **Stop Turn** in a place of its own; a follow-up joins the running turn and says so. When the agent asks to edit a file, a card pinned above the composer asks "Edit src/header.tsx?" with the diff, a note field, **Deny**, **Allow Once** and **Stop Turn** all in view; the **Chat** button, the collapsed badge and a notice show "waiting for you" until the person answers, and the answer leaves a line in the conversation. The edit lands in the checkout the page runs, so the page's own hot reload shows the fix. The turn ends with its receipt under the reply: "Changed 2 files: src/header.tsx, src/nav.css", uncommitted, with **Copy Reverse Patch** and **Ask to Undo** as the way back; a worktree-mode turn names its branch and worktree, unmerged, with **Switch and Restart Stack** to try it; a **Make tickets** turn lists the tickets it filed. devhost runs no Undo of its own on the agent's edits: the outcome names the way back (`UNDO-5`), and a stopped turn or a closed conversation comes back with **Continue** or **Resume** (`UNDO-4`). Conversations are named by their first message, listed across every checkout of the stack, kept through switches, closes and stops, and resumable. Benchmarks: Cursor and Claude Code's IDE chat show the model and the mode in the input row before Send and list chats by title; Claude Code and Codex CLI show the diff or the exact command above the choice, let a refusal carry an instruction and mark an interrupted turn as interrupted, not failed; GitHub's Copilot coding agent and Cursor's background agents return a reviewable branch instead of merging; Cursor, Windsurf and Copilot edits list each changed file with a way to take it back; VS Code pins chat's input at every size and caps visible notifications. Competitor behavior is evidence here, never a requirement.

## Target steps

Today: 8 steps, two of them hidden: open **Chat**, open the gear's dialog to learn or change the harness and model, write, **Send** (the worktree-and-merge workflow appended out of sight), scroll a 90 px box past raw JSON to find **Allow Once**, answer, read the latest reply, then work out from the agent's prose, or from Git, what changed and where. Proposed: 5 steps: open chat (Alt+Ctrl+C), write with the recipient, mode and checkout named in the composer row, **Send**, answer the pinned card, read the turn's receipt with its changed files and its way back. The main path is steps 1, 5, 7 and 8, with steps 2 to 4 read in the composer row before **Send**; steps 6, 9 and 10 are the paths around it.

1. **Open chat (the cached agent catalog and the stack's conversation list, read only).** **Chat** on the bar, Alt+Ctrl+C on the page, or pointing at an element or finishing a drawing (page-context's entry points) opens docked chat with focus in the composer; pressed while chat is docked, either focuses the composer, and Escape there returns focus to the element that had it (`KEY-2`, `KEY-6`, `KEY-8`). Chat opens compact at the toolbar's edge beside the notice stack, never over it: the dock and docked chat shift inward past the minimap strip and the pinned log panel in `SURF-5`'s edge order, and an open toolbar panel, the running agents list included, paints above chat (`SURF-1`, `SURF-5`, `CC-1`). Opening reads the agent catalog devhost discovered for this stack and never starts an agent CLI by itself: discovery runs once, when chat first opens for the stack, and again only on **Refresh Agents** (`network-exposure-02`). The panel is a non-modal region labelled "Chat" that stays open when focus leaves it (`KEY-7`). Its header names the conversation the composer writes to by its title, the first line of its first message ("Fix the nav header"), then its agent and state word ("Claude Code · working"), or "New conversation" before the first **Send**; then the conversation list control, **New Conversation** (a text button, never a second + icon), **Expand Chat**, **Move Chat Panel** and **Close**, which hides the panel and stops nothing (`SEL-8`, `WORD-1`, `WORD-2`, `WORD-6`). Compact chat shows the person's latest message with its delivery state and the reply to it; **Expand Chat** shows the whole conversation.
   - Fit: in every chat state (compact, expanded, dragged, after a window resize) and at every acceptance viewport, the header, the composer row with **Send** and the mode control, and a pending decision card are inside the viewport: an expanded or moved panel sizes itself to the room between its top and the window's bottom edge, or moves up until the composer fits; a dragged panel never covers the bar's row; only the transcript scrolls (`SURF-6`, `SURF-9`). Narrower windows follow `O8`: below 900 px wide, docked chat takes the window's width less 16 px on each side and keeps the same order of header, conversation, card and composer. Chat's dragged position is the person's, saved per manifest on the control server through toolbar-shell's layout route, never in browser storage (`SURF-7`, `CC-5`).
   - Defaults: chat opens compact; whether it was open, its side, the selected conversation, the agent, the model and the unsent text come back per stack and page origin, never per checkout, so a reload and a worktree switch keep them (`SEL-11`, `CC-9`).
   - Keys: Alt+Ctrl+C opens chat or focuses its composer; Alt+Ctrl+B's cycle reaches the composer while chat is docked (`KEY-3`); **Move Chat Panel** moves with the arrow keys and Home returns it, as today (`KEY-12`); every hint comes from the binding's one definition, ⌃⌥C on macOS and Ctrl+Alt+C elsewhere, in `Button`'s `shortcut` prop with `aria-keyshortcuts` (`KEY-13`, `BAR-4`).
2. **Name the recipient (read only).** The composer row starts with the agent and model chip, "Claude Code · Haiku 4.5", a button whose accessible name is its text, which opens Chat Settings as a popover anchored to the chip, dismissed by a click outside or Escape with focus back on the chip (`SEL-8`, `SURF-2`, `KEY-6`). It is no longer a modal dialog, because 2.4's decision rule makes a small choice tied to one control an anchored popover and `KEY-7` keeps modal dialogs to the crash view and the Configuration window; `SEL-1`'s component primitive still names a Chat Settings dialog, a reading recorded for the reference's author. Chat Settings holds **Agent** and **Model**, each a combobox whose options show the catalog's description of each model; the first model option names what it resolves to, "Configured default (Sonnet 4.5)" when the CLI reports it, else "Configured default: set in your Claude Code configuration", so no option is an unexplained default; and **Refresh Agents** (`KEY-10`, `WORD-1`, `chat-compose-01`). An agent that is not installed stays listed, disabled, with "Not installed: devhost looks for claude on your PATH" as visible text and as its accessible description (`MENU-3`). Above the composer the recipient line names where the message goes: "To: Fix the nav header · Claude Code · Haiku 4.5", or, before the first message, "Send starts a new conversation with Claude Code · Haiku 4.5" (`SEL-8`). An open conversation's agent is fixed: choosing another agent never moves the next message silently; the line then reads "Send starts a new conversation with Codex · Fix the nav header keeps its agent and stays listed", and the earlier conversation keeps running (`SEL-8`, `chat-conversations-08`).
   - Defaults: the agent and model the person last chose on this stack; on a first visit, Codex when it is installed, else the first installed agent, named in the chip before anything is sent (`SEL-11`, `chat-checkout-switch-03`).
   - Keys: the chip is a Tab stop in the composer row; Enter or Space opens Chat Settings with focus in **Agent**; ArrowUp and ArrowDown move the highlighted option, Enter picks it and Escape closes the list, then the popover (`KEY-10`, `KEY-8`).
3. **Choose how the agent handles the message (read only until Send).** Beside the chip, the mode control shows the edit mode and the checkout it edits, "This checkout (live) · fix-nav ~/acme/.worktrees/fix-nav", the checkout named by its `SEL-4` label (`O1`, `SEL-8`, `SEL-4`, `WORD-10`). It is a select-only combobox (`KEY-10`) with three options in the owner's words, each with its effect as visible text and accessible description: **This checkout (live)** "Edits the files this page runs; nothing is committed"; **New worktree (review before merge)** "Works on a new branch in its own worktree and stops before merging"; **Make tickets** "Files tickets for the problem and changes no files" (`O1`, `O19`, `O21`, `WORD-3`). Under the row:
   - The approval line names whether the agent asks before it acts, as its own CLI is configured: "Asks before commands and edits (your Claude Code configuration)" in the neutral style; "Never asks: Codex runs commands and edits without approval · full disk access" in the warning style when the configuration never asks; "Approval behavior not read: your Codex configuration decides" when devhost cannot read it. devhost passes no approval policy, so the line only reports the person's setting (`REV-6`, `O13`, `chat-checkout-switch-04`).
   - "Added by devhost", collapsed, shows the instructions devhost will append: the chosen mode's own text, then the team's `[devtools.chat].prompt` when the manifest sets one (`O35`, `CC-10`, `WORD-10`). Nothing is appended out of sight (`journey-agent-fix-01`, `chat-approvals-06`).
   - When the chosen mode differs from the previous message's, one line says so before **Send**: "Previous message: New worktree (review before merge) in ~/acme/.worktrees/fix-nav-header" (`O20`).
   - Defaults: **This checkout (live)** when the message carries page context; otherwise the conversation's last chosen mode, and **This checkout (live)** for a conversation's first message (`O1`, `O3`). The `journey-agent-fix-01` stopgap ships first and makes the built-in instructions edit the checkout the page runs, so no release between the stopgap and this control commits or merges silently.
4. **Attach images and page context (read only).** **Attach Image**, a paperclip in the composer, and pasting add PNG and JPEG images; each shows as an uncropped thumbnail with its name and size ("screenshot.png · 1.2 MiB"), removable from the keyboard, and the composer counts the message against its limit as it grows: "Message 5.8 MiB of 8 MiB" (`WORD-5`, `WORD-8`, `chat-conversations-04`). An image that would push the message past 8 MiB, its instructions and page context included, is refused when it is pasted, with one sentence naming it: "screenshot-2.png (4.1 MiB) was not attached: the message would be 10.6 MiB of its 8 MiB limit." (`FAIL-2`). Page context sits under the composer as page-context's list, item by item: each mark's number, element and source file, and a mark whose element left the page flagged "#2 is no longer on this page" with **Select Again** and **Remove** (`REV-6`, `SEL-9`, `SURF-12`; page-context owns the list and its review, `page-context-07`). Page context tells the agent the page's URL, the page's service and its checkout (`SEL-3`). After an element pick or a drawing made with the annotation tools chat hosts, focus returns to the composer (`KEY-12`). Keys typed into the composer never reach the page's listeners, not even shortcuts the page listens for before devhost does (`KEY-5`, `CC-28`), and holding Alt alone (Option on macOS) in the composer starts Select Elements only from the first pointer move or after `O34`'s 300 ms hold, so a character typed with Option never starts it (`KEY-2`, `O34`). The unsent text stays in browser storage, and the pasted images and page context stay in the control server's draft record for this stack, page origin and conversation, so a reload devhost causes keeps them (`UNDO-2`, `CC-19`).
5. **Send (`send` with `mode` over `/__devhost__/ws/chat`, preceded by `POST /__devhost__/chat/sessions` for a new conversation; one write: asks the agent to act).** Enter in the composer or **Send** sends; Shift+Enter inserts a line break and Enter during input-method composition never sends (`KEY-9`). The message appears in the conversation at once as the person's, with "Not sent yet" until the server acknowledges it, then under it the mode line "Mode: This checkout (live) · fix-nav", "Added by devhost" collapsed and "Page context: 2 marks" collapsed; devhost writes the mode, the page context and the added text as records of its own into the session's journal, so every page and every reload shows them (`UNDO-8`, `WORD-10`, `CC-40`, `STATE-1`). Focus stays in the composer, the draft stays until the acknowledgement, then clears; images and page context leave the draft record with it (`UNDO-2`). A send without an acknowledgement after 45 s reads **Delivery unconfirmed**, "devhost did not hear back from Claude Code. It never sends a message twice; check the reply before you send it again.", and is never resent (owner rule; `FB-5`, `REV-12`). A **Send** never asks, except in two cases, each an in-place question above the composer that keeps the draft in the composer and shows nothing as working while it asks (`REV-6`, `REV-4`, `SURF-2`):
   - A second agent: when a message in **This checkout (live)** would start this conversation's agent in a checkout where an agent chat did not start works or waits: "Start a second agent in fix-nav ~/acme/.worktrees/fix-nav? Claude Code, which chat did not start, is working there, and both would edit the same files." with **Cancel** focused, which Enter takes, and **Start Second Agent**; **Cancel** and Escape leave the draft unsent with the neutral line "Not sent", never an error, return focus to the composer, and the next **Send** asks again while that agent works (`REV-3`, `REV-4`, `CC-14`, `chat-approvals-04`). It asks when the conversation's agent would start, never again for follow-ups while the same other agent works. In **New worktree (review before merge)** and **Make tickets**, which never edit the same files, the recipient line names that agent ("Claude Code, started outside chat, also works in this checkout") and **Send** sends.
   - A gone mark: "Send with #2 missing? Its element is no longer on this page." with **Select Again** focused and **Send Anyway** (`REV-6`, `SEL-9`).
   - A new conversation starts with the chosen agent and model in the page's checkout; the browser never names a directory, and its title becomes the first line of this message (`SEL-8`, `CC-38`).
6. **Follow the turn (the session's events, read only).** The reply streams into the transcript, which is `aria-busy` while it streams and never a live region; tool calls show as one line each in plain words, "Edited src/header.tsx", "Ran bun test · exit code 0" (`FB-9`, `WORD-4`). A status line above the composer names the turn's progress, "Claude Code is working · 12 s · 3 tool calls", adding "· 1 message not yet read" while follow-ups wait for the agent, with **Stop Turn** in it, a place of its own that **Send** never takes (`FB-1`, `WORD-5`, `STATE-1`, `KEY-11`, `WORD-2`). **Chat** on the bar shows a working agent with its spinner and the accessible name "Chat: Claude Code working" (`SURF-8`). A follow-up typed during the turn shows, beside **Send**, "Joins the running turn; the agent reads it at its next step", and sending it never interrupts or approves anything (`REV-6`). It appears in the transcript at once as the person's message: "Not sent yet", with **Take Back**, while it waits on this page for an earlier send's acknowledgement, which puts it back into the composer; then "Sent into the running turn · the agent reads it at its next step" once the agent's CLI has it, after which only **Stop Turn** cancels it, with the turn (`STATE-1`, `UNDO-4`, `chat-compose-2-02`). A turn the agent starts by itself, when a background command it started finishes, shows as "The agent continued on its own" above its reply, and compact chat keeps showing the reply to the person's message with "1 more reply from the agent" under it (`WORD-10`, `chat-conversations-06`); text the CLI adds, such as a loaded skill, shows as one collapsed line, "Skill loaded: programming", never as a message the person sent (`WORD-10`, `journey-agent-fix-05`).
   - Agents and the terminal: devhost starts every chat agent with `AGENT=1` and `DEVHOST_CHAT_SESSION` set to its conversation, so a devhost command the agent runs gets agent output (`devhost: ERR:` lines, absolute paths) and is reported as the agent's, "Restarted api · 2.6 s · from Claude Code, conversation Fix the nav header" (`REV-8`, `FB-11`, `ACT-1`, `WORD-4`, `agent-cli-journey-06`); the agent restarts a service with `devhost service restart api` and reads outcomes with `devhost status` and `devhost reload`, never through the browser's routes (`MENU-6`, `SEL-7`, `FB-11`, `CC-11`, `CC-23`; stack-run-stop builds them).
   - The stack's terminal and log print one line when a conversation starts or ends, one when its agent starts waiting, and one per turn outcome: "Chat · Claude Code (Haiku 4.5) in fix-nav · replied · changed 2 files · 29 s", never the delivery steps, model changes, usage or IDs, which stay in agent output and the log file (`FB-10`, `FB-7`, `WORD-9`, `chat-conversations-05`). These lines name a conversation by its agent, model and checkout label, or by the title the agent CLI itself reports (`O23`), never by its first message, because the stack's log is a file on disk and log lines never hold message text (`CC-40`); the page names the same conversation by its title. This is a reading recorded for the reference's author, since `WORD-4`'s example names an agent's conversation by its title; the pinned log panel shows these lines under devhost's own source in its filter (`SURF-13`; log-minimap owns the panel). Log lines never hold message text, page context, tool input or answers (`CC-40`).
7. **Answer the agent (`respond`, one write: answers one request, once).** When the agent asks to run a tool or asks a question, a decision card is pinned between the conversation and the composer, outside any scroll area, so every answer is visible without scrolling in compact chat at every acceptance viewport (`SURF-6`, `REV-9`). The card leads with a plain question naming the tool and its target, "Edit src/header.tsx?", then what will change: the checkout-relative path and a unified diff for an edit, in a region of capped height that scrolls on its own; the exact command, its working directory relative to the checkout and the agent's stated reason for a command ("Run bun test? In web/ · to check the header renders"); then a note field, "Note for Claude Code (optional)", **Deny**, **Allow Once** and **Stop Turn**, with the native request collapsed under **Details** (`REV-9`, `chat-approvals-01`, `chat-approvals-02`). A question shows its options and **Submit Answers** the same way. No answer is a default: an arriving card never takes focus from a field being typed in, and is announced once, "Claude Code waits for you: Edit src/header.tsx?" (`KEY-6`, `FB-9`). Several pending requests read "1 of 2 requests" and are answered in arrival order.
   - **Deny** sends the note with the denial: Claude Code receives it as the denial's message; Codex, whose answers carry no text, receives the decline and then the note as a message into the running turn, shown in the conversation as the person's message with its delivery state and without the instructions devhost adds; an empty note denies with no message (`REV-9`, `CC-16`, `chat-approvals-07`). devhost no longer sends "Denied by the user." on the person's behalf.
   - Each answer leaves a line where it was given, "You denied: Edit src/header.tsx · 13:23 · Use the existing NavLink", "You allowed once: Run bun test · 13:24", recorded in the session's journal and shown after every reload; a denied call reads "Denied" in the neutral style, never with the success check (`REV-9`, `UNDO-8`, `WORD-4`, `WORD-7`, `CC-40`, `chat-approvals-05`).
   - Waiting is a condition (`ACT-7`): **Chat** takes the waiting look, a shape distinct from the working spinner in both themes and in forced colors, never told by color alone (`ACT-13`), with the accessible name "Chat: Claude Code waiting for you"; the collapsed badge shows it in `ACT-7`'s order; the notice stack shows "Claude Code waits for you: Edit src/header.tsx? · Fix the nav header" with **Answer**, which opens docked chat with focus on the card's question in one activation, and stays in its one-line form beside the collapsed badge (`SURF-8`, `FB-8`, `REV-9`, `chat-approvals-03`). The running agents trigger and Watch Live Activity show the wait from the same state (running-agents). The condition clears when the request is answered, cancelled or its turn ends, from any tab, and its clearing is announced once (`ACT-7`, `FB-9`).
   - Standing approvals are not offered: the card has no "don't ask again"; a person who wants them sets them in the agent CLI's own configuration (`O12`).
   - Keys: the card is one Tab stop: Tab or Shift+Tab into it, from the composer included, focuses its question, named by the question and described by the change; ArrowUp and ArrowDown move between **Details**, the note, **Deny**, **Allow Once** and **Stop Turn** (in the note, ArrowLeft and ArrowRight move the caret); Tab leaves the card. Enter in the note denies with it, Shift+Enter inserts a line break, and Escape in the note returns to the card's question with nothing answered. No other key answers: **Deny**, **Allow Once** and **Stop Turn** act only when pressed, and Escape never answers (`REV-9`, `KEY-8`, `KEY-9`, `KEY-10`). `REV-9` lists the card's arrow stops without the note, which its own Deny note and 2.11's Enter and Escape rows need; the note's place between **Details** and **Deny** is a reading recorded for the reference's author.
8. **Read the receipt (the turn's end, read only).** When the turn ends, compact chat shows the reply to the person's latest message and, under it, the turn's receipt, built from the edit events in the session's journal with no Git command (`O22`, `UNDO-5`):
   - **This checkout (live):** "Changed 2 files: src/header.tsx, src/nav.css · not committed", with **Copy Reverse Patch**, the reverse of the agent's own edits, and **Ask to Undo**, which puts into the composer, unsent, "Undo the changes you made in your last turn to src/header.tsx and src/nav.css. Keep my own uncommitted changes."; when the agent ran commands, "Claude Code also ran 2 commands; files they wrote are not listed" (`UNDO-5`, `O19`, `O22`). devhost never commits, stashes, restores or reverts for the agent, and never offers a whole-file restore, which would also discard the person's own uncommitted changes (`UNDO-5`). The page's own dev server shows the change through its reloads.
   - **New worktree (review before merge):** "Committed on fix-nav-header in ~/acme/.worktrees/fix-nav-header · not merged", naming the worktree that holds the turn's edits from the stack's checkout list, with **Switch and Restart Stack**, which opens worktree-switch's checkout list with that worktree picked, so its switch button is `REV-2`'s second step and `REV-3`'s question applies; once switched, the receipt offers **Return to Configured Checkout**, after which the conversation takes messages again, a request to merge included (`UNDO-5`, `O1`, `SEL-8`, `SURF-15`). The merge happens only when the person asks for it in a message.
   - **Make tickets:** the agent's own list of the tickets it filed, by title and link, or its ticket drafts as text when it could not file them; "Changed no files", or, when it changed some anyway, "Make tickets changed 1 file: src/header.tsx" in the warning style with the live receipt's way back (`O11`, `O21`, `UNDO-5`).
   - The receipt is the turn's one outcome, shown in chat, where its progress showed; while chat is closed, **Chat** carries the turn instead: working, waiting for you, then "reply ready" until the person opens chat, and no activity line in the notice stack repeats it (`FB-1`, `FB-2`). A chat turn is not one of section 1's operations, which `FB-1`'s activity line reports, and a turn can run for many minutes, where an activity line would hold one of `FB-8`'s three places; this reading is recorded for the reference's author, and a waiting agent still raises its condition notice (`ACT-7`). The end is announced once with the reply's first sentence, or "reply ready", and the files changed: "Claude Code replied: The header now uses NavLink. Changed 2 files." (`FB-9`). The outcome holds the way back devhost names (`UNDO-5`) and the local undo of `UNDO-4` (**Continue**, **Resume**); devhost has no Undo control of its own for an agent's edits.
9. **Stop the turn (`interrupt`, one write: ends the turn and keeps the conversation).** **Stop Turn**, in the status line or on a decision card, or Alt+Ctrl+. in the composer and docked chat, ends the turn within a second; Escape never does (`KEY-8`, `KEY-9`, `UNDO-4`). While a card waits, the status line shows "The request above waits for your answer; its Stop Turn ends the turn" in place of its own **Stop Turn**, so the card's is the only one, and Alt+Ctrl+. stops nothing (`KEY-9`). The turn ends with a neutral line, "You stopped this turn after 29 s · 12 tool calls ran", with **Continue**, which starts a new turn in the same conversation; no red diagnostic, no "[Request interrupted by user]" shown as the person's message, no error state, and the terminal reads "Chat · Claude Code in fix-nav · stopped by you · 29 s", never "turn failed" (`FAIL-5`, `WORD-4`, `WORD-7`, `CC-24`, `chat-compose-2-03`). The draft stays; **Send** keeps its own place, so a second press after a stop cannot send it (`KEY-11`). A message sent into the turn that the agent's events never show it reading ends with "Not read: you stopped the turn first", and no such line appears under a message the agent answered (`STATE-1`).
10. **Manage conversations (the conversation list, read only; `close` and resume, one write each).** The conversation list opens from the header as a popover anchored to its control (`SURF-2`, `MENU-1`). It lists every conversation of the stack, this page's checkout first, then by last activity, each row naming its title, its agent and model, its checkout label, its start time and its state word with a cause where it has one ("Fix the nav header · Claude Code · Haiku 4.5 · fix-nav ~/acme/.worktrees/fix-nav · 14:02 · waiting for you"; "closed · Acme Shop stopped at 16:24"); the conversation ID sits behind **Copy ID** (`SEL-8`, `SEL-4`, `WORD-6`, `chat-conversations-01`). ## Backend and contract changes

**Backend** (the control server's chat routes and sessions in `apps/devhost/internal/devtools/chat_*.go` and the manifest's chat settings in `apps/devhost/internal/manifest/chat.go`, preserving: devhost never answers or pre-approves a request; **Delivery unconfirmed** and no resend of a command ID; the native chat boundary, which passes each CLI the person's own authentication, settings, environment and checkout and injects no approval, sandbox or system-prompt override; a page that sends only into its own checkout; the control guard on every chat route; activity lines without message text; and no Git command run by devhost):

1. **The edit mode on `send`.** `send` gains `mode` (`live`, `worktree` or `tickets`), required; a `send` without it is refused with an error naming the field. The server appends the mode's built-in instructions, then `[devtools.chat].prompt`, as today's labelled section of the user message; the manifest gains `[devtools.chat.modes.<mode>].prompt`, which replaces one mode's instructions, an empty string sending none for that mode; a manifest that sets `[devtools.chat].prompt` gets one warning naming the new keys on start and on each hot reload that keeps it. The live text ships first as the `journey-agent-fix-01` stopgap. Serves `journey-agent-fix-01` and `chat-approvals-06` (both resolved by the stopgap first), and this flow's mode control. Required. Contract: `CC-10`.
2. **devhost's records in the session's journal.** A `record` frame (`kind`: `mode`, `page-context`, `added-text`, `answer` with its note, `stop` with who stopped it, its duration and the tool calls that ran, or `delivery` for a `send`'s acknowledgement; the `commandId` or `requestId` it belongs to; a `sequence` shared with `event` frames), journaled beside the native events and replayed in `snapshot`; activity log lines keep only identifiers and outcomes. Serves `chat-approvals-05`, `chat-compose-2-02`, `chat-compose-2-03`. Required. Contract: `CC-40`.
3. **The Deny note.** `respond` gains `note`. For Claude Code, the deny's `message` is the note, empty when there is none; for Codex, the server sends the decline, then the note as a message into the running turn (`turn/steer`, or `turn/start` once that turn has ended), without the mode's instructions, and records both as `answer` and `delivery` records. devhost never writes a denial text of its own. Serves `chat-approvals-07`. Required. Contract: `CC-16`.
4. **The approval projection.** Each pending request carries what will change: the tool, the path relative to the checkout and a unified diff for an edit (from Claude Code's `Edit`, `MultiEdit` and `Write` input, or Codex's file-change item, saying when it carries no diff); the exact command, its working directory relative to the checkout and the agent's stated reason for a command; the native request kept for **Details**. The page builds this from the request it already receives (`readChatApproval.ts`, `readChatRequestChanges.ts`); no new route. Serves `chat-approvals-01`, `chat-approvals-02`. Required.
5. **[discuss]: The approval behavior.** The catalog publishes, per agent, whether its configuration asks before commands and edits, never asks, or could not be read, with the sandbox when the CLI reports one: from Codex's `config/read`, which devhost already runs for every session and of which it keeps only the model, and from Claude Code's `system/init` frame or settings. Whether either reports the effective approval policy is unchecked (research note); the backend owners confirm it on each CLI before the line ships, and the line reads "Approval behavior not read" until then. devhost still sends no approval or sandbox setting. Serves `chat-checkout-switch-04`. Recommended (`O13`).
6. **Sessions across the stack's checkouts.** The session list answers every session of the stack, the page's checkout first, each with its directory, checkout label, `title` (the first line of its first message, held in memory only), `agent`, `model`, last `mode`, `startedAt`, `lastActivityAt` and `state` (`working`, `waiting`, `idle`, `closed`) with its `cause`. The socket attaches to any session of the stack; `send` checks the session's directory against the page's and refuses another with an error naming that directory; `respond` and `interrupt` work for any session of the stack; resuming a conversation of another directory stays refused. The control server also publishes, per stack, its working and waiting conversations for the CLI's questions (`REV-7`). Serves `chat-checkout-switch-01`, `chat-conversations-01`. Required. Contract: `CC-38`.
7. **Chat off keeps running conversations reachable.** With `enabled = false`, the session list, the socket, `respond`, `interrupt` and close keep answering for sessions still running until they end; starting a session answers `404`; the notice names each running conversation. Serves `chat-approvals-08`. Required. Contracts: `CC-18`, `CC-38`.
8. **Close and resume keep the conversation.** Close ends the process and keeps the session's record and journal with `state` `closed` and the cause "by you"; resume starts a new process on the same native conversation under the same session ID and appends to the same journal and title. Serves `chat-conversations-02`. Required. Contract: `CC-38`.
9. **[discuss]: The conversation record after a stop.** Per manifest in the state directory, devhost keeps each conversation's agent, native session ID, checkout, model, last mode, start and end times and the title the agent CLI itself reports, never message text, removed with `O15`'s stopped-stack record; after the stack starts again the session list includes them as `closed` with their cause, and resume continues the CLI's saved conversation. What the record may keep is `O23`, which the product owner decides. Serves `chat-conversations-03` (this flow's slice), `chat-conversations-09`, `chat-compose-2-05`. Required. Contract: `CC-38`.
10. **A stop is a stop, an exit is an exit.** An interrupted turn ends `idle` with a `stop` record, never `error`: Claude Code's interrupt result and its "[Request interrupted by user]" frame are read as the stop. A CLI that exits publishes its exit code, or its signal by name with its status, its time and its last diagnostic lines (the 16 KiB already retained) as the conversation's `closed` cause. On macOS, a `killpg` that answers `EPERM` for a process group whose leader has exited and is not yet reaped counts as stopped (`apps/devhost/internal/devtools/chat_process.go:161-170`). Serves `chat-compose-2-03`, `chat-compose-2-04`, `chat-conversations-03`. Required. Contract: `CC-24` (roster CHAT-04).
11. **[discuss]: The turn's receipt.** For each finished turn, the server derives from the journal's events the files the agent changed (Claude Code's `Edit`, `MultiEdit` and `Write` tool calls, Codex's file-change items), the reverse patch of those edits from their old and new text, and the number of commands the turn ran; it names the checkout that holds the edits by matching their directory against the stack's checkout list, the read the Worktrees panel already makes, which gives the worktree-mode receipt its branch and worktree. No Git process runs. Whether every harness reports every edited path is unmeasured: the backend owners confirm it on one recorded turn per harness before the receipt ships (`O22`). Serves the receipt of every mode (`UNDO-5`). Recommended.
12. **The agent's environment.** Every chat agent process starts with `AGENT=1` and `DEVHOST_CHAT_SESSION` set to its session ID, added to the environment devhost already passes; no approval, sandbox or prompt flag changes. Serves `agent-cli-journey-06`. Required. Contract: `CC-13`.
13. **The guarded, cached catalog.** `GET /__devhost__/chat/harnesses` refuses, with `403`, a request whose `Sec-Fetch-Site` is `cross-site` or `same-site` or whose `Origin` names another host, and applies the stack's `Host` rule, as the config routes do for reads; it answers from a catalog cached per stack and checkout. `POST /__devhost__/chat/harnesses/refresh`, a state-changing request through the control guard, discovers again; concurrent discoveries join one in flight per agent. The page reads the catalog when chat first opens, never on a toolbar load. Which clients reach the route at all is the `network-exposure-01` stopgap's loopback rule, which names this route too. Serves `network-exposure-02`. Required.
14. **The draft record.** `/__devhost__/chat/draft` (`GET`, `PUT`, `DELETE`) keeps a conversation's unsent pasted images and page context (each pick's element path and offsets and each drawing's shape, never a screenshot) per stack, page origin and conversation, capped at 8 MiB, read under the config routes' `Host` rule, and removed when the send is acknowledged or the stack stops. Built with page-context, which owns the page context it holds. Required. Contract: `CC-19`.
15. **Activity lines for people.** The stack's human terminal output prints one line when a conversation starts or ends, one when its agent starts waiting, and one per turn outcome (replied, stopped by you, failed with its cause) with the agent, model, checkout label, files changed and duration; delivery steps, session and command IDs, model changes, usage and cost go only to agent output and the log file. Serves `chat-conversations-05`. Required.

## Recommended priority

**P1, with the `network-exposure-01` and `journey-agent-fix-01` stopgaps shipped first.** The realistic trigger is the first approval anyone meets: in the default compact chat every edit approval opens with **Deny** and **Allow Once** scrolled out of a 90 px box under raw JSON, so the agent blocks while the person reads only "Waiting for your response…" (`chat-approvals-01`); a switch or a close hides a waiting or finished conversation whose agent keeps running or remembers (`chat-checkout-switch-01`, `chat-conversations-02`); and a moved, expanded panel pushes **Send** off screen (`chat-compose-02`). The cost is work and trust rather than lost files: an agent left waiting holds its turn and the stack's idle shutdown, a hidden conversation keeps editing a checkout no page shows, and a stop that reads as a failure or a reply cut off by a dead process sends people to the terminal; the edits themselves can be taken back, but today only through Git and the agent's prose, because devhost records nothing per turn. Chat is used daily by anyone who uses it at all, far more often than **Disable Reloads**, whose request travels through this flow. Ship first the slice with no backend dependency: the decision card pinned with its answers in view, the waiting look on **Chat**, the panel's fit at every viewport, **Stop Turn** as a neutral stop with **Continue** and Escape no longer stopping a turn, the agent and model chip with the recipient line, **Attach Image** apart from **New Conversation**, follow-ups shown at once, the agent-started and skill-loaded markers, image sizes, and the failure sentences; ship the guarded, cached catalog (Backend 13) and `AGENT=1` (Backend 12) beside it, since neither changes what people see. Then ship the edit mode as one release: `send`'s `mode`, the three instruction texts with `O35`'s prompt keys, the mode control, "Added by devhost", the mode lines and the journal's records, after the `journey-agent-fix-01` stopgap has made the built-in instructions edit the checkout the page runs, so no release between them commits or merges silently and none labels a mode before its instructions exist; the approval line follows once Backend 5 is confirmed. Then the reach: sessions across checkouts, chat off keeping running conversations, close and resume keeping the conversation, the stop and exit records, the draft record with page-context, and, once `O23` is decided, the conversation record after a stop. Last, the turn's receipt with its reverse patch and the worktree's **Switch and Restart Stack**, after one recorded turn per harness confirms the edit events' coverage (`O22`), and the Deny note through Codex's steer. This flow depends on the foundations notices-and-feedback and toolbar-shell, which ship first or with the slice that needs them: notices-and-feedback provides the notice stack, the announcer and the lost-connection notice that this flow's waiting condition and blocked reasons use; toolbar-shell provides the dock and its corner order beside docked chat, **Chat** on the bar and the collapsed badge that read this flow's waiting state, the binding registry for Alt+Ctrl+C and Alt+Ctrl+., the layout route that keeps chat's position, the early key script and `Button`'s unavailable state.
