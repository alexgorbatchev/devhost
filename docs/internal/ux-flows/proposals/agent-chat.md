# Chat with a coding agent: proposed experience

Diagrams: [current](../agent-chat-current.html), [proposed](../agent-chat-proposed.html). [Wireframe](../wireframes/agent-chat.html). Research: [Chat with a coding agent: research](agent-chat-research.md).

Status: design proposal, not implemented behavior. The [shared UX pattern reference](../patterns.md) wins where this proposal disagrees with it.

Source revision: alexgorbatchev/devhost `190a8bb53e8cd903d2db0a92cb0886f29671607f` (Rust `main`). Features: CHAT-01, CHAT-02, CHAT-03, CHAT-04, CHAT-05, CHAT-06, CHAT-07, CHAT-08, CHAT-09, CHAT-10, CHAT-11, CHAT-12, LOG-03. Redesign ticket: tracked privately. Product decision `O64` records the Agent Chat changes the product owner shipped on `main` up to `bc33e2f1`: **Close Conversation** asks before it closes, the header names only the agent, and chat remembers whether it was expanded; the same commits made **Close Conversation**, **New Conversation** and **Share Tab** icon buttons in the composer row, which this proposal keeps.

Product rules: the product owner simplified the chat edit mode (`O1`, decided 2026-11-16, updated 2026-11-18): the chat composer offers an explicit, visible choice of two modes only — **This worktree (live)**, which edits whichever worktree the person has active (main's included), leaves every change uncommitted, and creates no additional worktree, commit or merge (the default when the message carries page context and for a conversation's first message, `O3`), and **Make tickets**, which asks the agent to file tickets for the problem instead of editing (`O11`) or to change no files and say it cannot make tickets when it lacks that capability (`O21`). Every sent message shows which mode applied; nothing commits, merges or creates worktrees. The owner's other rules make more of this flow intended: devhost never answers or pre-approves an agent's approval or question (while offering the agent CLI's own standing approval on the decision card when the CLI offers one so the person, never devhost, can grant it, `O12`); **Delivery unconfirmed** and the refusal to resend a message are intended; chat never asks for API keys in the browser; using devhost from another environment — another computer, a phone, or over a relay — is a primary use case (`HOLD-8`), so no protection confines chat to this machine, and this redesign owns the unified remote-authentication boundary (`O36`, decided 2026-11-25, with `O59`): local browsers and CLI agents stay trusted (relayed requests never count as this machine), and remote browsers sign in with one shared WebAuthn passkey under a single owned parent HTTPS domain (with phone support mandatory) or a one-time `devhost pair` fallback link, receiving a 30-day idle host-only `__Host-` session cookie. `apps/devhost/AGENTS.md`, "Native chat boundary", adds that devhost passes the installed CLIs the configured CLI authentication, settings, environment, and selected worktree and must not inject approval, sandbox, or system-prompt overrides. Every chat turn that changes code ends with the person seeing the change in the running app or with the one step left named (`FB-12`, `O56`, `O57`, `O58`). The gap is around these rules: today nobody chooses, because one built-in prompt, appended out of sight to every message, always picks a worktree-and-merge workflow; before **Send** the page names neither the agent, nor the worktree, nor the workflow, nor whether the agent asks first; the request the agent is waiting on hides its buttons under raw JSON; a switch, a close, a stop or turning chat off hides a conversation that still runs or remembers; unauthenticated network and relay clients can start agents; and after a turn devhost keeps no record of what changed and names no way back (research note, "The contested behavior").

## Target experience

The person points at a broken header on the page, or presses Alt+Ctrl+C, and docked chat opens beside the notice stack, compact or expanded as they last left it, with focus in the composer; the page keeps its scroll position and its state. Before typing a word they can read, in the composer row, who will answer and how: "Claude Code · Haiku 4.5", the mode "This worktree (live) · fix-nav ~/acme/.worktrees/fix-nav", whether that agent asks before it runs commands and edits, what devhost will add to the message behind "Added by devhost" (the team's prompt first, then the mode's instructions), and each mark of page context it carries. **Send** (or Enter) puts the message into the conversation at once with its delivery state and its mode line; nothing asks unless a second agent would edit the same files or a mark the message cites is gone. While the agent works, a status line names the turn's progress, "Claude Code is working · 12 s · 3 tool calls", with **Stop Turn** in a place of its own; a follow-up joins the running turn and says so. When the agent asks to edit a file, a card pinned above the composer asks "Edit src/header.tsx?" with the diff, a note field, **Deny**, **Allow Once**, the agent CLI's own standing approval when offered (**Allow for This Session**), and **Stop Turn** all in view — on desktop and on a 320 CSS px phone screen alike; the **Chat** button, the collapsed badge, a notice with **Answer**, and the app page's own browser tab title ("(1) waiting · Acme Shop") show the wait until the person answers, and the answer leaves a line in the conversation. The edit lands in the active worktree the page runs. When the turn ends, held reloads apply once unless the person is typing (or, after **Disable Reloads**, the receipt says "Reload to see the change" with **Reload Page**), and the receipt under the reply names what changed: "Changed 2 files: src/header.tsx, src/nav.css · not committed", with **Copy Reverse Patch**, **Ask to Undo**, and for any service whose `watch` paths changed, "api runs the old code until it restarts" with **Restart Changed**; a **Make tickets** turn lists the tickets it filed, or says it cannot make tickets while changing no files. devhost runs no Undo of its own on the agent's edits: the outcome names the way back (`UNDO-5`), and a stopped turn or a closed conversation comes back with **Continue** or **Resume** (`UNDO-4`). Conversations are named by their first message, listed across every worktree of the stack, kept through switches, closes and stops, and resumable. From a phone or another laptop over the network or a relay, the person signs in once per machine with their shared WebAuthn passkey (or a `devhost pair` link as fallback) and uses chat, approvals, and restarts as on `devbox`, while unauthenticated browsers see the app and one clear state: "Sign in with passkey or pair this browser to use devhost here". Benchmarks: Cursor and Claude Code's IDE chat show the model and the mode in the input row before Send and list chats by title; Claude Code and Codex CLI show the diff or the exact command above the choice, let a refusal carry an instruction, offer session-level standing approvals, and mark an interrupted turn as interrupted, not failed; Cursor, Windsurf and Copilot edits list each changed file with a way to take it back; VS Code pins chat's input at every size and caps visible notifications. Competitor behavior is evidence here, never a requirement.

## Target steps

Today: 8 steps, two of them hidden: open **Chat**, open the gear's dialog to learn or change the harness and model, write, **Send** (the worktree-and-merge workflow appended out of sight), scroll a 90 px box past raw JSON to find **Allow Once**, answer, read the latest reply, then work out from the agent's prose, or from Git, what changed and where. Proposed: 5 steps: open chat (Alt+Ctrl+C), write with the recipient, mode and worktree named in the composer row, **Send**, answer the pinned card, read the turn's receipt with its changed files and its way back. The main path is steps 1, 5, 7 and 8, with steps 2 to 4 read in the composer row before **Send**; steps 6, 9, 10 and 11 are the paths around it.

1. **Open chat (the cached agent catalog and the stack's conversation list, read only).** **Chat** on the bar, Alt+Ctrl+C on the page, or pointing at an element or finishing a drawing (page-context's entry points) opens docked chat with focus in the composer; pressed while chat is docked, either focuses the composer, and Escape there returns focus to the element that had it (`KEY-2`, `KEY-6`, `KEY-8`). Chat opens at the toolbar's edge beside the notice stack, never over it, compact on a first visit and afterwards compact or expanded as the person left it (`O64`): the dock and docked chat shift inward past the minimap strip and the pinned log panel in `SURF-5`'s edge order, and an open toolbar panel, the running agents list included, paints above chat (`SURF-1`, `SURF-5`, `CC-1`). Opening reads the agent catalog devhost discovered for this stack and never starts an agent CLI by itself: discovery runs once, when chat first opens for the stack, and again only on **Refresh Agents** (`network-exposure-02`). The panel is a non-modal region labelled "Chat" that stays open when focus leaves it (`KEY-7`). Its header names only the agent (`O64`): **Move Chat Panel**, which shows the agent's logo while it is idle, the working spinner while it works and `ACT-13`'s waiting shape while it waits for the person, then the agent's display name, "Claude Code" (never the raw `claude-code` ID), or "Agent Chat" before the first conversation; the state word stays in the heading's visually hidden status ("Claude Code · working"), and the heading spells it out only after an error or while reconnecting ("Claude Code · reconnecting"); then the conversation list control, **Expand Chat** (**Compact Chat** while expanded) and **Close**, which hides the panel and stops nothing (`SEL-8`, `WORD-1`, `WORD-2`, `WORD-6`, `ACT-13`, `O64`). The badge's waiting shape and the display name are this redesign's additions to the shipped agent-only header, and both keep it to the agent alone. The title of the conversation the composer writes to, the first line of its first message ("Fix the nav header"), shows in the recipient line above the composer (step 2) and in the conversation list, never in the header (`SEL-8`, `O64`). The composer row holds the conversation's icon actions beside **Send**, as `main` ships them: **Close Conversation** (a trash icon, while a conversation is open; step 10), **New Conversation** (a compose icon, distinct from **Attach Image**'s paperclip, available while a turn works or waits) and page-context's **Share Tab** (a screen-share icon, **Stop Sharing** while the tab is shared), each named by its tooltip and its accessible name (`WORD-2`, `chat-compose-03`). Compact chat shows the person's latest message with its delivery state and the reply to it; **Expand Chat** shows the whole conversation.
   - Fit: in every chat state (compact, expanded, dragged, after a window resize) and at every acceptance viewport (1600×1000, 1280×800, 900×900, and 1280×800 at 200% zoom, 640×400 CSS pixels), the header, the composer row with **Send** and the mode control, and a pending decision card are inside the viewport: an expanded or moved panel sizes itself to the room between its top and the window's bottom edge, or moves up until the composer fits; a dragged panel never covers the bar's row; only the transcript scrolls (`SURF-6`, `SURF-9`). Narrower windows follow `O8`: below 900 px wide, docked chat takes the window's width less 16 px on each side and keeps the same order of header, conversation, card and composer, and down to a **320 CSS px phone layout** docked chat, approval prompts (decision cards), and notices stack cleanly inside the viewport with zero horizontal overflow and >=24×24 CSS px tap targets so an authenticated phone (`O36`) can ask for a change, answer approvals, and see the change (`O8`, `SURF-9`). Below 900 px wide docked chat and the pinned log panel never sit side by side: the one opened earlier folds to its bar control, **Chat** still showing the turn's state (working, waiting for you, reply ready), and returns as it was, draft and scroll kept, when the later one closes; folding is not closing, and docked chat still closes only by its own **Close** (`SURF-5`, `KEY-6`). Chat's dragged position is the person's, saved per manifest on the control server through toolbar-shell's layout route, never in browser storage (`SURF-7`, `CC-5`).
   - Defaults: chat opens compact the first time; whether it was open, whether it was expanded or compact (`O64`), its side, the selected conversation, the agent, the model and the unsent text come back per stack and page origin, never per worktree, so a reload and a worktree switch keep them (`SEL-11`, `CC-9`, `O64`).
   - Keys: Alt+Ctrl+C opens chat or focuses its composer; Alt+Ctrl+B's cycle reaches the composer while chat is docked (`KEY-3`); **Move Chat Panel** moves with the arrow keys and Home returns it, as today (`KEY-12`); every binding is overridable per person in `~/.config/devhost/config.toml`'s `[devtools.shortcuts]` (`O17`, `CC-39`), and every hint comes from the binding's one definition, ⌃⌥C on macOS and Ctrl+Alt+C elsewhere, in `Button`'s `shortcut` prop with `aria-keyshortcuts` (`KEY-13`, `BAR-4`).
2. **Name the recipient (read only).** The composer row starts with the agent and model chip, "Claude Code · Haiku 4.5", a button whose accessible name is its text, which opens Chat Settings as a popover anchored to the chip, dismissed by a click outside or Escape with focus back on the chip (`SEL-8`, `SURF-2`, `KEY-6`). It is no longer a modal dialog, because 2.4's decision rule makes a small choice tied to one control an anchored popover and `KEY-7` keeps modal dialogs to the crash view and the Configuration window. Chat Settings holds **Agent** and **Model**, each a combobox whose options show the catalog's description of each model; the first model option names what it resolves to, "Configured default (Sonnet 4.5)" when the CLI reports it, else "Configured default: set in your Claude Code configuration", so no option is an unexplained default; and **Refresh Agents** (`KEY-10`, `WORD-1`, `chat-compose-01`). An agent that is not installed stays listed, disabled, with "Not installed: devhost looks for codex on devbox's PATH" (naming the stacks' machine via `O61`: `machineName` in `config.toml`, else the host name up to its first dot) as visible text and as its accessible description (`MENU-3`, `O61`). Above the composer the recipient line names where the message goes: "To: Fix the nav header · Claude Code · Haiku 4.5", or, before the first message, "Send starts a new conversation with Claude Code · Haiku 4.5" (`SEL-8`). An open conversation's agent is fixed: choosing another agent never moves the next message silently; the line then reads "Send starts a new conversation with Codex · Fix the nav header keeps its agent and stays listed", and the earlier conversation keeps running (`SEL-8`, `chat-conversations-08`).
   - Defaults: the agent and model the person last chose on this stack; on a first visit, Codex when it is installed, else the first installed agent, named in the chip before anything is sent (`SEL-11`, `chat-checkout-switch-03`).
   - Keys: the chip is a Tab stop in the composer row; Enter or Space opens Chat Settings with focus in **Agent**; ArrowUp and ArrowDown move the highlighted option, Enter picks it and Escape closes the list, then the popover (`KEY-10`, `KEY-8`).
3. **Choose how the agent handles the message (read only until Send).** Beside the chip, the mode control shows the edit mode and the worktree it edits, "This worktree (live) · fix-nav ~/acme/.worktrees/fix-nav", the worktree named by its `SEL-4` label (`O1`, `SEL-8`, `SEL-4`, `WORD-10`, `WORD-11`). It is a select-only combobox (`KEY-10`) with two options in the owner's words, each with its effect as visible text and accessible description: **This worktree (live)** "Edits the active worktree in place (main's included); nothing is committed"; **Make tickets** "Files tickets for the problem and changes no files" (`O1`, `O11`, `O19`, `O21`, `WORD-3`, `WORD-11`). Under the row:
   - The approval line names whether the agent asks before it acts, as its own CLI is configured: "Asks before commands and edits (your Claude Code configuration)" in the neutral style; "Never asks: Codex runs commands and edits without approval · full disk access" in the warning style when the configuration never asks; "Approval behavior not read: your Codex configuration decides" when devhost cannot read it. devhost passes no approval policy, so the line only reports the person's setting (`REV-6`, `O13`, `chat-checkout-switch-04`).
   - "Added by devhost", collapsed, shows the instructions devhost will append in `O35`'s order: the team's `[devtools.chat].prompt` first when the manifest sets one, followed by the chosen mode's own instructions (`live` or `tickets`), which state that they decide where the agent edits and whether it commits or merges whatever the guidance above says (`O35`, `CC-10`, `WORD-10`). Nothing is appended out of sight (`journey-agent-fix-01`, `chat-approvals-06`).
   - When the chosen mode differs from the previous message's, one line says so before **Send**: "Previous message: Make tickets" (or "Previous message: This worktree (live)") (`O20`).
   - Defaults: **This worktree (live)** when the message carries page context; otherwise the conversation's last chosen mode (**This worktree (live)** or **Make tickets**), and **This worktree (live)** for a conversation's first message (`O1`, `O3`). The `journey-agent-fix-01` stopgap ships first and makes the built-in instructions edit the active worktree in place, so no release between the stopgap and this control creates worktrees, commits or merges silently.
4. **Attach images and page context (read only).** **Attach Image**, a paperclip in the composer, and pasting add PNG and JPEG images; each shows as an uncropped thumbnail with its name and size ("screenshot.png · 1.2 MiB"), removable from the keyboard, and the composer counts the message against its limit as it grows: "Message 5.8 MiB of 8 MiB" (`WORD-5`, `WORD-8`, `chat-conversations-04`). An image that would push the message past 8 MiB, its instructions and page context included, is refused when it is pasted, with one sentence naming it: "screenshot-2.png (4.1 MiB) was not attached: the message would be 10.6 MiB of its 8 MiB limit." (`FAIL-2`). Page context sits under the composer as page-context's list, item by item: each mark's number, element and source file, and a mark whose element left the page flagged "#2 is no longer on this page" with **Select Again** and **Remove** (`REV-6`, `SEL-9`, `SURF-12`; page-context owns the list and its review, `page-context-07`). Page context tells the agent the page's URL, the page's service and its worktree (`SEL-3`, `WORD-11`). After an element pick or a drawing made with the annotation tools chat hosts, focus returns to the composer (`KEY-12`). Keys typed into the composer never reach the page's listeners, not even shortcuts the page listens for before devhost does (`KEY-5`, `CC-28`), and holding Alt alone (Option on macOS) in the composer starts Select Elements only from the first pointer move or after `O34`'s calibrated 400 ms hold, so a character typed with Option never starts it (`KEY-2`, `O34`). The unsent text stays in browser storage, and the pasted images and page context stay in the control server's draft record for this stack, page origin and conversation, so a reload devhost causes keeps them; on a `listeners-moving` HTTPS port change that changes the page's origin, the page hands its unsent text, pasted images and page context to the control server's draft record under the new origin so nothing is left behind on the old address (`UNDO-2`, `CC-19`).
5. **Send (`send` with `mode` and `pageContext` over `/__devhost__/ws/chat`, preceded by `POST /__devhost__/chat/sessions` for a new conversation; one write: asks the agent to act).** Enter in the composer or **Send** sends; Shift+Enter inserts a line break and Enter during input-method composition never sends (`KEY-9`). The message appears in the conversation at once as the person's, with "Not sent yet" until the server acknowledges it, then under it the mode line "Mode: This worktree (live) · fix-nav", "Added by devhost" collapsed and "Page context: 2 marks" collapsed; devhost writes the mode, the structured `pageContext` and the added text as `record` frames of its own into the session's journal, so every page and every reload shows them (`UNDO-8`, `WORD-10`, `CC-40`, `STATE-1`). Focus stays in the composer, the draft stays until the acknowledgement, then clears; images and page context leave the draft record with it (`UNDO-2`). A send without an acknowledgement after 45 s reads **Delivery unconfirmed**, "devhost did not hear back from Claude Code. It never sends a message twice; check the reply before you send it again.", and is never resent (owner rule; `FB-5`, `REV-12`). A **Send** never asks, except in two cases, each an in-place question above the composer that keeps the draft in the composer and shows nothing as working while it asks (`REV-6`, `REV-4`, `SURF-2`):
   - A second agent: when a message in **This worktree (live)** would start this conversation's agent in a worktree where an agent chat did not start works or waits: "Start a second agent in fix-nav ~/acme/.worktrees/fix-nav? Claude Code, which chat did not start, is working there, and both would edit the same files." with **Cancel** focused, which Enter takes, and **Start Second Agent**; **Cancel** and Escape leave the draft unsent with the neutral line "Not sent", never an error, return focus to the composer, and the next **Send** asks again while that agent works (`REV-3`, `REV-4`, `CC-14`, `chat-approvals-04`). While devhost's agent scan is incomplete it asks too, naming the agents it could not check instead of sending as if none ran: "Start a second agent in fix-nav ~/acme/.worktrees/fix-nav? Codex agents could not be checked there, so one may be working, and both would edit the same files." (`REV-3`, `CC-14`; running-agents owns the scan). It asks when the conversation's agent would start, never again for follow-ups while the same other agent works. In **Make tickets**, which edits no files, the recipient line names that agent ("Claude Code, started outside chat, also works in this worktree") and **Send** sends.
   - A cited mark that no longer exists: "Send with #2 missing? Its element is no longer on this page." for a mark whose element left the page, or "Send with #1 missing? It is not in page context." for a mark the person removed, page-context's sentence; each has **Select Again** focused, which picks that mark again under the same number, and **Send Anyway** (`REV-6`, `SEL-9`).
   - A new conversation starts with the chosen agent and model in the page's worktree; the browser never names a directory, and its title becomes the first line of this message (`SEL-8`, `CC-38`).
6. **Follow the turn (the session's events, read only).** The reply streams into the transcript, which is `aria-busy` while it streams and never a live region; tool calls show as one line each in plain words, "Edited src/header.tsx", "Ran bun test · exit code 0" (`FB-9`, `WORD-4`). A status line above the composer names the turn's progress, "Claude Code is working · 12 s · 3 tool calls", adding "· 1 message not yet read" while follow-ups wait for the agent, with **Stop Turn** in it, a place of its own that **Send** never takes (`FB-1`, `WORD-5`, `STATE-1`, `KEY-11`, `WORD-2`). **Chat** on the bar shows a working agent with its spinner and the accessible name "Chat: Claude Code working" (`SURF-8`).    - Agents and the terminal: devhost starts every chat agent with `AGENT=1` and `DEVHOST_CHAT_SESSION` set to its conversation, so a devhost command the agent runs gets agent output (`devhost: ERR:` lines, absolute paths) and is reported as the agent's, "Restarted api · 2.6 s · from Claude Code, conversation Fix the nav header" (`REV-8`, `FB-11`, `ACT-1`, `WORD-4`, `agent-cli-journey-06`); when an agent explicitly inspects or operates on the stack, it uses `devhost stack info` (short alias `devhost status`, `O62`), `devhost reload`, and `devhost service restart <name>` (`MENU-6`, `SEL-7`, `FB-11`, `CC-11`, `CC-23`; stack-run-stop builds them), never browser control routes, and devhost never asks the agent to restart services automatically at the end of a turn (`O58`).
   - The stack's terminal and log print one line when a conversation starts or ends, one when its agent starts waiting, and one per turn outcome: "Chat · Claude Code (Haiku 4.5) in fix-nav · replied · changed 2 files · 29 s", never the delivery steps, model changes, usage or IDs, which stay in agent output and the log file (`FB-10`, `FB-7`, `WORD-9`, `chat-conversations-05`). These lines name a conversation by its agent, model and worktree label, or by the title the agent CLI itself reports (`O23`), never by its first message, because the stack's log is a file on disk and log lines never hold message text (`CC-40`); the page names the same conversation by its title. The pinned log panel shows these lines under devhost's own source in its filter (`SURF-13`; log-minimap owns the panel). Log lines never hold message text, page context, tool input or answers (`CC-40`).
7. **Answer the agent (`respond`, one write: answers one request, once).** When the agent asks to run a tool or asks a question, a decision card is pinned between the conversation and the composer, outside any scroll area, so every answer is visible without scrolling in compact chat at every acceptance viewport and at the 320 CSS px phone layout (`SURF-6`, `REV-9`, `O8`). The card leads with a plain question naming the tool and its target, "Edit src/header.tsx?", then what will change: the worktree-relative path and a unified diff for an edit, in a region of capped height that scrolls on its own; the exact command, its working directory relative to the worktree and the agent's stated reason for a command ("Run bun test? In web/ · to check the header renders"); then a note field, "Note for Claude Code (optional)", **Deny**, **Allow Once**, the agent CLI's own standing approval when the CLI offers one (such as Claude Code's "don't ask again" or Codex's approval for the session, labelled **Allow for This Session** / the CLI's session-approval option, `O12`), and **Stop Turn**, with the native request collapsed under **Details** (`REV-9`, `O12`, `CC-16`, `chat-approvals-01`, `chat-approvals-02`). A question shows its options and **Submit Answers** the same way. No answer is a default: an arriving card never takes focus from a field being typed in, and is announced once, "Claude Code is waiting for you: Edit src/header.tsx?" (`KEY-6`, `FB-9`). Several pending requests read "1 of 2 requests" and are answered in arrival order.
   - Standing approval (`O12`): when the agent CLI offers a session standing approval for the request, the card exposes it beside **Allow Once**; the person — never devhost — grants it through the CLI's own option, never persisted across stack restarts, and later matching requests in the session are then answered by the CLI without prompting or a card (`REV-9`, `O12`, `CC-16`). No keyboard shortcut approves it (`KEY-9`).
   - **Deny** sends the note with the denial: Claude Code receives it as the denial's message; Codex, whose answers carry no text, receives the decline and then the note as a message into the running turn, shown in the conversation as the person's message with its delivery state and without the instructions devhost adds; an empty note denies with no message (`REV-9`, `CC-16`, `chat-approvals-07`). devhost no longer sends "Denied by the user." on the person's behalf.
   - Each answer leaves a line where it was given, "You denied: Edit src/header.tsx · 13:23 · Use the existing NavLink", "You allowed once: Run bun test · 13:24", or "You allowed for this session: Run bun test · 13:24", recorded in the session's journal and shown after every reload; a denied call reads "Denied" in the neutral style, never with the success check (`REV-9`, `UNDO-8`, `WORD-4`, `WORD-7`, `CC-40`, `chat-approvals-05`).
   - Waiting is a condition (`ACT-7`): **Chat** takes the waiting look, a shape distinct from the working spinner in both themes and in forced colors, never told by color alone (`ACT-13`), with the accessible name "Chat: Claude Code waiting for you"; the collapsed badge shows it in `ACT-7`'s order (`◆ dh · 1 waiting for you ▴`); the notice stack shows "◆ Claude Code is waiting for you · Fix the nav header" with **Answer** (and no **Dismiss**, aligning with notices-and-feedback and toolbar-shell), which opens docked chat with focus on the card's question in one activation, and stays in its one-line form beside the collapsed badge (`SURF-8`, `FB-8`, `REV-9`, `chat-approvals-03`); and devhost prefixes both devhost pages' and app pages' browser tab titles while the wait persists ("(1) waiting · Acme Shop" on an app page; "(1) waiting · Watch Live Activity · Acme Shop" on Watch Live Activity), tracking app title changes underneath and restoring the page's own title when cleared (`ACT-7`, `O16`). 11. **Use chat from another device or over a relay (`O36`, `O59`, `HOLD-7`, `HOLD-8`, `network-exposure-01`, `relay-previews-03`).** Using devhost from another computer, a phone, or through a relay is a primary use case (`HOLD-8`), so chat and every other gated control work identically for authenticated remote browsers while unauthenticated clients can reach only the app itself:
    - **Local trust and relay boundary:** a request counts as this machine only when its connection and every `X-Forwarded-For` hop are loopback (`apps/devhost/src/devtools/server.rs:344-361`), it did not arrive through devhost's relay connector (the connector marks every forwarded request in `apps/devhost/src/remote/proxy.rs:101-109` and Caddy strips that mark from direct connections; the connector's reverse listener in `apps/devhost/src/remote/transport.rs:188-192` stays bounded so relayed requests never bypass the mark — resolving `relay-previews-03`), its `Host` is one of the stack's hostnames or loopback, and no browser marks it cross-site or same-site.     - **One shared WebAuthn passkey with mandatory phone support (`O36`):** the person registers one WebAuthn passkey under a single owned parent HTTPS domain (ideally a subdomain used only for devhost that holds its relay hostnames, such as `devhost.acme.test` in these examples, so the Relying Party ID stays isolated from the apex domain and other sites). Because the passkey's public key record (`credential_id`, COSE public key, `rp_id`, `user_handle`, label; `signCount = 0` tolerated for synced keys) is non-secret, syncing that snippet in `~/.config/devhost/config.toml` (`CC-39`, safe in dotfiles) lets every devhost machine under that parent domain verify the same passkey with zero central server and zero shared secret. Phone support on iOS and Android is mandatory: it works with synced passkeys (iCloud Keychain / Apple Passwords, Google Password Manager, 1Password, Bitwarden) and cross-device hybrid/QR sign-in (caBLE), pairing directly with `O8`'s 320 CSS px phone layout for chat, decision cards and notices.
    - **Session cookies, revocation and fallback (`O59`, `O36`):** completing passkey sign-in on a machine's reserved hostname (or spending a one-time `devhost pair` link, 10-minute TTL, single use, also printed at start when reachable remotely) issues a host-only `__Host-` session cookie (`Secure`, `HttpOnly`, `SameSite=Strict`), stored in a mode-`0600` per-machine session store in the state directory and propagated per stack hostname via a reserved-host hop (the relay forwards the stack directory's reserved hostname). Sessions expire after 30 days without use and have no fixed lifetime (`O59`). `devhost pair` and `devhost passkey` list active sessions (auth method passkey or pair, browser and OS from user agent, created time, last used time and network, relayed or not — with no retired `O60` SSH-host column) and revoke one or all immediately; authenticated remote browsers also carry **Sign Out This Browser** (passkey) or **Unpair This Browser** (paired fallback) after a separator in the stack name menu. One-time `devhost pair` links remain available for first-time passkey enrollment bootstrapping, hostnames outside the shared HTTPS parent domain (`.localhost`, `.local`, LAN IPs, plain HTTP, or untrusted local CA), and lockout recovery.

## Backend and contract changes

**Backend** (the Rust control server's chat routes and sessions in `apps/devhost/src/devtools/chat/{mod,transport,session,process,journal,activity}.rs`, `apps/devhost/src/devtools/{server,request_guard,project_context}.rs`, `apps/devhost/src/remote/{proxy,transport}.rs`, `apps/devhost/src/config.rs`, and the manifest's chat settings in `apps/devhost/src/manifest/{types,validation}.rs`, preserving: devhost never answers or pre-approves a request itself; **Delivery unconfirmed** and no resend of a command ID; the native chat boundary, which passes each CLI the person's own authentication, settings, environment and worktree and injects no approval, sandbox or system-prompt override; a page that sends only into its own worktree; the control guard and `O36` auth check on every chat route; local loopback trust for local browsers and CLI agents; activity lines without message text; and no Git command run by devhost):

1. **The edit mode and `pageContext` on `send`.** `send` (`apps/devhost/src/devtools/chat/transport.rs:363-407`) gains `mode` (`live` or `tickets`), required (a `send` without it or with any other value is refused with an error naming the field), and optional structured `pageContext`. The server appends `[devtools.chat].prompt` first as team guidance, then the chosen mode's built-in instructions (`apps/devhost/src/manifest/types.rs:9,80-93`), which state they decide where the agent edits and whether it commits or merges whatever the guidance above says (`O35`), and renders structured `pageContext` into a labelled `Page context` section. The manifest gains `[devtools.chat.modes.<mode>].prompt` (`live` or `tickets` only; the `worktree` key is withdrawn under `O1`), which replaces one mode's instructions, an empty string sending none for that mode; a manifest that sets `[devtools.chat].prompt` gets one warning naming the new keys on start and on each hot reload that keeps it. The live text ships first as the `journey-agent-fix-01` stopgap. Serves `journey-agent-fix-01` and `chat-approvals-06` (both resolved by the stopgap first), and this flow's mode control. Required. Contracts: `CC-10`, `CC-40`.
2. **devhost's records in the session's journal.** A `record` frame (`kind`: `mode`, `page-context`, `added-text`, `answer` with its note or standing-approval choice, `stop` with who stopped it, its duration and the tool calls that ran, or `delivery` for a `send`'s acknowledgement; the `commandId` or `requestId` it belongs to; a `sequence` shared with `event` frames), journaled beside the native events (`apps/devhost/src/devtools/chat/journal.rs:1-60`) and replayed in `snapshot`; activity log lines keep only identifiers and outcomes. Serves `chat-approvals-05`, `chat-compose-2-02`, `chat-compose-2-03`. Required. Contract: `CC-40`.
3. **The Deny note and CLI standing approval.** `respond` (`apps/devhost/src/devtools/chat/session.rs:616-650`) gains `note` and forwards the person's choice of any CLI standing-approval option (`O12`, e.g. Claude Code's "don't ask again" or Codex's approval for the session, session-only, never persisted across restarts). For **Deny**, Claude Code receives the note as the denial's `message` (empty when there is none); Codex receives the decline, then the note as a message into the running turn (`turn/steer`, or `turn/start` once that turn has ended), without the mode's instructions, and records both as `answer` and `delivery` records. devhost never writes a denial text of its own. Serves `chat-approvals-07`, `O12`. Required. Contract: `CC-16`.
4. **The approval projection.** Each pending request carries what will change: the tool, the path relative to the worktree and a unified diff for an edit (from Claude Code's `Edit`, `MultiEdit` and `Write` input, or Codex's file-change item, saying when it carries no diff); the exact command, its working directory relative to the worktree and the agent's stated reason for a command; any standing-approval option the agent CLI offers for that request (`O12`); and the native request kept for **Details**. The page builds this from the request it already receives (`readChatApproval.ts`, `readChatRequestChanges.ts`); no new route. Serves `chat-approvals-01`, `chat-approvals-02`, `O12`. Required.

Serves `chat-checkout-switch-04`. Required (`O13`).
6. **Sessions across the stack's worktrees and deep link.** The session list (`apps/devhost/src/devtools/chat/session.rs:241-257`, `transport.rs:107-154`) answers every session of the stack, the page's worktree first, each with its directory, worktree label, `title` (the first line of its first message, held in memory only), `agent`, `model`, last `mode`, `startedAt`, `lastActivityAt` and `state` (`working`, `waiting`, `idle`, `closed`) with its `cause`. Required. Contract: `CC-38`.

Serves `chat-compose-2-03`, `chat-compose-2-04`, `chat-conversations-03`. Required. Contract: `CC-24` (roster CHAT-04).
