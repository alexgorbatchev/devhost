# Find a page element's source: proposed experience

Diagrams: [current](../component-source-current.html), [proposed](../component-source-proposed.html). [Wireframe](../wireframes/component-source.html).

Status: design proposal, not implemented behavior. The [shared UX pattern reference](../patterns.md) wins where this proposal disagrees with it.

Source revision: alexgorbatchev/devhost `190a8bb53e8cd903d2db0a92cb0886f29671607f`. Features: SRC-01; SRC-02 (highlight from the editor) and SRC-03 (editor choice) leave the roster under `O51`. Redesign ticket: tracked privately.

Product rule: the public docs set the contract this flow keeps, and the product owner's decisions narrow it. `guides/devtools.md` promises that "**Alt + right-click** on an element opens its React component's source file in your editor and copies the path. It needs a development build that exposes source locations, and opens the file in the selected worktree."; the product owner withdrew editor support completely on 2026-11-18 (`O50`, “drop this feature”; `O51`, “drop editors completely”; `O60` retired with it): devhost never starts or opens an editor, keeps no editor settings (`[devtools.editor]`, `DEVHOST_EDITOR`), builds no editor URL, command or remote editor link, asks no machine name for one, and keeps **Copy Path** (`SEL-11`, `MENU-4`, `SURF-15`, `CC-39` editor parts withdrawn). So opening a file is no longer part of this flow, and highlight from the editor, which exists only for an editor plugin publishing its cursor, leaves with it (`O51` removes `guides/react-highlight.md` with the editor docs). What stays is the element's source: which file, line and column render the element the person points at, shown in a menu with **Copy Path**, and the same lookup giving page context's marks their file. The gaps are around it: React 19, the current React, records its source locations in a form devhost never reads, so Alt + right-click takes the browser's menu and shows nothing, and marks reach the agent without a file; and nothing tells the person that a path was copied.

## Target experience

The person holds Alt and right-clicks a button on their React 19 page, or, with Select Elements latched on, walks the highlight to it with the arrow keys and presses Shift+F10. The element is outlined with its role and name before the click, by the same resolver Select Elements uses, and the source menu opens at once beside it, inside the window and clear of the toolbar's notices, with focus on its first item. Its first row names what it shows, "Source of \<h1>"; the line under it names the worktree the files are in, "Files in fix-nav ~/acme/.worktrees/fix-nav"; then one **Copy Path** item per source, the element first and each component that renders it after it, "Copy Path · \<h1>" beside "frontend/src/components/PlaygroundLayout.tsx:15:7", each with its non-default props. Enter copies that path, line and column, the menu closes, and the notice stack says "Copied path · frontend/src/components/PlaygroundLayout.tsx:15:7"; the person pastes it into their editor, terminal or agent. When the page records no source for the element, the same menu opens and says why, with **Copy Element Path**, so the gesture never ends in a dead click and the browser's own menu is never taken for nothing. The same lookup gives page context's marks their file, so an agent asked about "#1" gets "PlaygroundLayout.tsx" instead of searching for it. Nothing here writes to the stack and nothing opens: devhost has no editor integration, so there is no Open, no editor setting and no highlight from the editor's cursor, and a manifest or plugin written for today's editor features gets a plain warning or `404` instead of failing silently. Copying changes nothing devhost could take back, so there is no Undo. Benchmarks: click-to-component lists a component and its parents on Option+Right-click; React DevTools reads React 19's owner stacks and maps them through source maps without any build plugin; Chrome DevTools walks the DOM with the arrow keys and keeps "Copy" actions in its context menu; VS Code's "Copy Path" and "Copy Relative Path" copy without opening anything. Competitor behavior is evidence here, never a requirement.

## Target steps

Today: 3 steps on a React 18 page whose editor registered its URL handler (Alt + right-click, click the entry, which copies and opens the editor without a word, then look for the editor), and 1 dead step on React 19, where Alt + right-click shows nothing and takes the browser's menu with it. Proposed: 3 steps on both: Alt + right-click with the element outlined before the click, **Copy Path** on an item, read the outcome in the notice stack.

1. **Point at an element (`contextmenu` with Alt, or Shift+F10 in Select Elements; read only).** Holding Alt (Option on macOS) and right-clicking an element of the app page, outside devhost's own surfaces, opens its source menu; while Select Elements is latched on, Shift+F10 (⇧F10 on macOS) or the context-menu key opens it for the highlighted element (`KEY-12`, `MENU-1`; `keyboard-14`). Both resolve the element with the one resolver that Select Elements and holding Alt use, which page-context owns and which outlines the element with its role and name before the click, so the element shown is the element looked up (`SEL-9`; `selection-09`). devhost takes the browser's context menu only for Alt + right-click and always answers it: the source menu opens at once, also when there is no source to show (`MENU-3`, `KEY-2`; `selection-11`, `keyboard-02`). Alt pressed as part of a chord, or to type a character, never starts selection (`KEY-2`). A right-click without Alt stays the page's and closes an open source menu, and Alt + right-click inside devhost's own surfaces stays the browser's, as today.
   - Defaults: on wherever devhost injects its devtools into the page. Today `[devtools.editor].enabled = false` turns it off together with highlight from the editor; the reference removes `[devtools.editor]` completely, `enabled` included (`SEL-11`, `O51`), so a leftover table is warned about like any other leftover editor setting (step 5) and turns nothing off. Whether Alt + right-click gets a switch of its own, and under which key, is open (Backend 3, `[discuss]`).
   - Keys: Alt + right-click; in Select Elements, the arrow keys walk the highlight and Shift+F10 or the context-menu key opens the menu (`KEY-12`; the two 2.11 rows component-source owns).
2. **Find the element's source in the page's worktree (`inspectComponentElement`, in the page; read only).** The page reads the element's React source: the React DevTools extension's renderer interface first when it is installed, as today; then React 18's `_debugSource` and `__source`, as today; then, on React 19, the fiber's `_debugStack`, the stack React records where the JSX was created, whose first frame outside React is the JSX call site (`page-context-06`). Each frame's position is mapped back through the source map of the script or module the frame names, whether a script element, a module loaded through `import` or a chunk loaded later, read from a `SourceMap` response header or from the last `sourceMappingURL` comment whatever follows it. The owner chain is walked the same way, each owner's `_debugStack` included, and duplicates are dropped, so the menu lists the element and the components that render it. Paths are resolved in the page's worktree: the selected worktree of the repository the page's service runs from, with a path from another worktree of that repository rewritten to it, as today (`SEL-3`, `WORD-11`; `selection-03`). The same lookup gives page context's marks their source file, so on React 19 a mark reaches the agent with its file and page-context's row shows it, "#1 h1 Devtools playground · PlaygroundLayout.tsx:15", or "no source found" (`SEL-9`; `page-context-06`). It stays one shared module under `packages/devhost-ui/src/devtools/shared/` (today `reactSourceInspection.ts` and `symbolicateSourceLocation.ts`), which page-context's marks and this flow's menu both call; it adds no control route.
   - While a source map is read for the first time, the open menu shows "Finding the source of \<h1>…" where its items go, never an empty menu, with focus on the menu itself; when the items arrive, focus moves to the first of them (`STATE-1`, `KEY-6`).
3. **Read the source menu (`ComponentSourceMenu`, anchored at the element; read only).** The menu opens at the pointer, or at the highlighted element after Shift+F10, inside the viewport and never clipped (`SURF-9`). It is a transient layer above the page, placed in the page area on the side of the pointer away from the dock, so it covers neither the notice stack nor docked chat's header, composer or decision card; where that area is narrower than the menu, the menu narrows to it, down to 240 CSS pixels, and wraps its paths (`SURF-1`, `SURF-6`; `surfaces-01`). Alt + right-click lands outside an open toolbar panel, which closes as any click away closes it (`SURF-2`), so the menu never covers another devhost surface's controls. It takes pointer input only where it draws, and the outline of the element it opened on stays anchored to that element through scrolling, resizing and a hot update while it is open (`SURF-11`, `SURF-12`; `surfaces-10`, `surfaces-11`). Its first row is the target header, "Source of \<h1>", in bold, and names the menu for assistive technology (2.3 Accessibility). The line under it names the worktree the files are in by its `SEL-4` label, "Files in fix-nav ~/acme/.worktrees/fix-nav" (`SEL-4`, `WORD-11`; `selection-04`, `language-04`). Then one item per source: "Copy Path · \<h1>", a badge per non-default prop, as today, and the path relative to that worktree with line and column, "frontend/src/components/PlaygroundLayout.tsx:15:7"; a path longer than the menu is shortened in the middle, keeping the file name and line, with the full path in its tooltip and in the item's accessible name, "Copy Path · \<h1> · frontend/src/components/PlaygroundLayout.tsx:15:7" (`WORD-8`, `WORD-3`). No item, header or line names or opens an editor (`O51`). The menu's foot shows its keys from the binding definitions, "↑↓ Move · Enter Copy · Esc Close" (`KEY-13`; `keyboard-15`).
   - A menu with one source has one item and no group heading; with two or more, "Element and components" heads the items as a labelled group (`MENU-2`, 2.3 Accessibility).
   - The item reads **Copy Path**, as `WORD-3`'s title-style labels and `O50` and `O51` write it; `KEY-10` and this flow's section 4 lines still write "Copy path", which the pattern reference's author aligns.
   - Keys: focus moves into the menu on open, on its first item (`KEY-6`; `keyboard-10`); ArrowUp and ArrowDown move, Home and End jump, a letter jumps to the next item that starts with it, so typing c moves from one **Copy Path** item to the next, and Enter or Space copies (`KEY-10`, `KEY-8`; `keyboard-07`, `keyboard-13`). When Escape, Tab, Shift+Tab or one of its items closes it, focus goes where `KEY-5` and `KEY-6` send it for a surface opened with the pointer: to the page element that had focus before the right-click, which is the element itself when the click focused it; opened with Shift+F10, focus returns to the Select Elements toggle with the highlight still on the element (`KEY-12`). A click outside the menu closes it and acts on what it lands on, as any click on the page does, and devhost moves no focus after it. devhost never adds a `tabindex` to a page element to give it focus, because the devtools stay isolated from the page. This proposal reads `KEY-10`'s "the element it opened on" this way; settling the wording of `KEY-10`, `KEY-6` and 2.3's Accessibility paragraph is left to the pattern reference's author.
   - Inside the open menu devhost keeps every key; once it closes, the page's keys work again without a click on the page (`KEY-5`).
4. **Copy a path (`navigator.clipboard.writeText`, in the page; no devhost write).** **Copy Path**, by Enter, Space or a click, puts the item's path, relative to the worktree with its line and column, on the clipboard, closes the menu and shows the outcome notice "Copied path · frontend/src/components/PlaygroundLayout.tsx:15:7", announced once; it closes by itself after its reading time, 4.2 s for these 9 words, counted only while neither the pointer nor focus is in it and the page is visible, and one that arrives while the browser window is not focused waits until the window next gains focus (`FB-2`, `FB-3`, `FB-6`, `FB-9`, `WORD-4`, `O14`, `O53`; `feedback-02`, `feedback-03`, `language-11`; `source-and-minimap-02`). When the browser refuses the clipboard, a failure notice reads "Could not copy the path: the browser did not allow clipboard access. Select the path and press ⌘C", with the path as selected, selectable text in it ("Ctrl+C" outside macOS), and stays until dismissed (`FAIL-2`, `FB-6`, `KEY-13`; `feedback-07`, `language-09`). Copying never navigates the page and never opens anything.
   - Copying is an action of this page, not an operation of the stack: it writes no line in the stack's log and no operation record, which `FB-7` and `ACT-1` keep for operations; its notices and the announcer are notices-and-feedback's.
   - Copying reads the page and starts no service, so it never asks (`REV-1`) and stays available while another operation runs (`HOLD-3`).
5. **Leftover editor settings and cursor updates (manifest load and the control server; read only).** Everything that existed only to reach an editor is gone, and what was written for it fails visibly instead of silently (`O50`, `O51`):
   - A manifest that still has a `[devtools.editor]` table, with `ide`, `enabled` or both, keeps loading and running: devhost applies nothing from it and prints one warning per key naming file, line, column and key, "devhost.toml:31:1  devtools.editor.ide  is no longer used: devhost has no editor integration; remove it", at start and on every hot reload that keeps it; it never refuses the manifest, whatever the value (`FAIL-2`, `MENU-4`, `WORD-7`; `source-and-minimap-03`). Warning instead of refusing keeps every manifest written for today running, as the owner's rule that manifest settings never stop a running stack asks; the reference has no rule for retired keys yet, so this is proposed for it.
   - `POST /__devhost__/react-highlight/cursor` and `/__devhost__/ws/react-highlight` no longer exist and answer `404` like any unknown control route; no page draws an outline from a cursor or dispatches `devhost:react-highlight` (`source-and-minimap-08`, `source-and-minimap-09`, `source-and-minimap-10`).

Branches and edge states:

- **Shift+F10 in Select Elements.** The menu anchors at the highlighted element and, when it closes, focus returns to the Select Elements toggle with the highlight kept (`KEY-12`, `KEY-6`).
- **No source found.** The menu opens all the same, its first row reading "No source for \<h1>", with one sentence naming the cause and **Copy Element Path**, which copies the element path page context sends, "main > section.hero > h1", and reports "Copied element path · main > section.hero > h1", which closes after its floor of 4 s (`MENU-3`, `FAIL-2`, `O14`; `selection-11`; `page-context-06`). The causes: "No React component renders this element." when the element has no React fiber; "This page's React build records no source locations: React 18 needs the JSX development transform, and React 19 a development build." when its fiber records none; "Found \<h1> in index.js line 5294, but its source map could not be read (404)." when the map does not load, which adds a **Retry** item that reads the map once more and fills the menu in place (`STATE-4`). The browser's menu is never taken without this answer.
- **A source outside the stack's worktrees**, such as a linked package elsewhere on disk. The item shows its absolute path shortened with `~`, "~/src/ui-kit/src/Button.tsx:12:3", and **Copy Path** copies the absolute path with its line and column (`SEL-4`).
- **The repository switches.** The menu opens and works, and its worktree line names the worktree the page still shows with the operation in progress, "Files in main ~/acme · Switch and Restart Stack is running · 2 of 6 started", because reads stay available during service operations (`HOLD-3`, `SEL-4`); today the gesture silently falls through to the browser's menu. The page reloads into the new worktree when the switch ends, which closes the menu.
- **A deleted worktree.** With the page's selected worktree deleted, the menu opens all the same, its worktree line reading "The worktree ~/acme/.worktrees/fix-nav was deleted; its services still run from it", and **Copy Path** works; today the gesture silently falls through to the browser's menu. Returning to the configured worktree stays the Worktrees panel's, as worktree-switch specifies (`HOLD-4`, `SEL-4`).
- **The lost connection.** The lookup and **Copy Path** run in the page and need nothing from devhost, so they keep working; the lost-connection notice, notices-and-feedback's, says devhost is not reachable (`HOLD-2`).
- **The toolbar collapsed.** Alt + right-click works the same; a copy failure stays visible in the collapsed toolbar's one-line form beside the badge until dismissed, and successes close by themselves (`SURF-8`, `FB-8`).
- **A page opened from another environment.** The menu works the same in a browser on another machine, a phone or through the relay, signed in or not, because the lookup and **Copy Path** read only the page and send nothing to devhost (`HOLD-8`, `HOLD-7`).
- **The page's own modal dialog.** Alt + right-click on an element inside the page's dialog opens the menu inside the dialog's top layer, where the notice stack and the announcer already move, so its items take the keyboard and the pointer and its notices are heard (`SURF-11`, `FB-9`; `surfaces-10`). devhost's bar keeps its paused state. `SURF-11` names only the notice stack and the announcer as moving into the page's dialog; this proposal moves the source menu there too, and naming it in `SURF-11` is left to the pattern reference's author, with toolbar-shell, which owns the layering it uses.
- **A rejected configuration, or chat that cannot take a message.** Neither blocks anything in this flow (`HOLD-6`, `HOLD-5`).

## What changes versus today

- **Removed:** opening the file in an editor: the editor URL built for Cursor, VS Code, VS Code Insiders and WebStorm, and the entry button that copied and opened at once without a word (`O50`, `O51`); the editor settings, the `[devtools.editor]` table with `ide`, its four accepted values and `enabled`, and the editor name in the injected configuration (`O51`; replaced by a warning per leftover key, and Alt + right-click keeps no off switch until Backend 3 is settled); highlight from the editor: the cursor route `POST /__devhost__/react-highlight/cursor`, the `/__devhost__/ws/react-highlight` stream, the page's outline overlay and its `devhost:react-highlight` event, and the "Highlight source locations" guide with its demo film (`O51`); the cursor route's documented answers, success once received and `400` when malformed, which go with the route (it answers `404`); the dead click on React 19, where devhost took the browser's menu and showed nothing; swallowed clipboard errors; paths cut from the left; the source menu switched off without a word while the page's repository switches or its worktree is deleted.
- **Merged:** Select Elements, holding Alt and Alt + right-click resolve elements with one resolver (page-context's); marks and the source menu read one source lookup, now including React 19.
- **New:** React 19 source locations from `_debugStack` without a browser extension; source maps named by a `SourceMap` header or a trailing comment after other text; the "No source" menu with its cause, **Copy Element Path** and **Retry** for a map that did not load; **Copy Path** items with their outcome and failure notices; the target header and the worktree line; the menu keyboard model with type-ahead and its hint line; Shift+F10 in Select Elements; the menu inside the page's modal dialog; the warning for a leftover editor setting.
- **Changed:** an item copies its path and never opens an editor or navigates the page; Alt + right-click during a switch or with a deleted worktree opens the menu with its state instead of falling through to the browser's menu; the menu takes focus and returns it (`KEY-6`), where today it never takes focus and handles only Escape; a path is shortened in the middle, where today it is cut from the left; a manifest `ide` outside the four editors is warned about instead of refused.
- **Kept:** walking every safeguard of the current flow:
  - When the build exposes source locations, the menu lists the element and its component chain with their non-default primitive props and paths mapped back through the page's source maps, without duplicates.
  - The element looked up is the one under the pointer that Select Elements would pick (`SEL-9`).
  - A path from another worktree of the repository is rewritten to the selected worktree, so the copied path is the file the page runs (`resolveWorktreeSourcePath`).
  - The menu stays inside the window and closes with Escape, a click outside or a worktree switch.
  - Alt + right-click inside devhost's own surfaces stays the browser's, and a right-click without Alt stays the page's and closes an open menu.
  - The React DevTools extension's renderer interface still answers first when it is installed.
  - The source lookup runs in the page with no control route, so it reads nothing from devhost and writes nothing.
  - A manifest that names an editor keeps running.
  - The `[devtools.editor].enabled = false` off switch does not survive: the reference removes the table (`O51`), and Backend 3 decides whether a switch of its own replaces it.
