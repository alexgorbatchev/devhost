# Install devhost and the shared HTTPS proxy: proposed experience

Diagrams: [current](../first-run-setup-current.html), [proposed](../first-run-setup-proposed.html). [Wireframe](../wireframes/first-run-setup.html).

Status: design proposal, not implemented behavior. The [shared UX pattern reference](../patterns.md) wins where this proposal disagrees with it.

Source revision: alexgorbatchev/devhost `190a8bb53e8cd903d2db0a92cb0886f29671607f` (Rust `main`), against shared pattern reference revision 7. Features: SET-01, SET-02, SET-03, SET-04, SET-05, SET-07. Redesign ticket: tracked privately.

Product rule: `guides/managed-caddy.md`, "Trust the certificates", states the trust contract: "devhost cannot ask without a terminal or under `AGENT=1`, and the installation can be declined or fail. In each case devhost prints a warning instead, Caddy keeps running, and browsers reject its certificates until you run: `devhost caddy trust`". The owner's rules add that devhost never opens a browser, that human output and agent output (`AGENT=1`) differ on purpose, and that Caddy listening on every interface by default is documented. The owner decided four things this flow follows: on macOS, `bindHost = "127.0.0.1"` is honored from port 1024 upward, and below port 1024, port 443 included, Caddy keeps listening on every interface with a warning on every start, so existing setups keep starting (`O39`); a self-managed install updates devhost with a new built-in `devhost upgrade`, while dotfiles, package managers and local builds replace the binary their own way and run the shipped `devhost restart` (`O18`); `devhost caddy stop` prints its set and acts without asking, because it ends no agent's turn (`O33`); and devhost's pages name the machine that runs the stacks, devbox in these examples (`O61`). So a Caddy that runs with an untrusted certificate authority is intended, a start that never asks for a password without a person at a terminal is intended, and devhost leaving the browser's own certificate warning in place is intended; none of them is a defect. The gap is around them: `devhost caddy --help` teaches a setup order that fails, the warning never says why devhost did not ask and tells an agent to run the command itself, the command that changes the machine's trust never refuses an agent, `trust-remote` shows a hash nobody can check and installs at once, nothing removes a root devhost installed, a missing Caddy points at empty logs, a rerun of the download breaks a running Caddy on macOS, and `devhost caddy stop` takes every stack offline without naming one.

## Target experience

A person installs the binary and asks it what to do: `devhost --help`, `devhost caddy --help`, the Install page, the README and the agent skill all give one recipe, `devhost caddy download` (skipped when Caddy is on the `PATH`), `devhost caddy privileged-ports` on Linux, then `devhost caddy start`, and each says beforehand which step downloads and which asks for a password. The download says where it downloads from, shows its progress on one status line, checks that the file runs as Caddy and only then puts it in place, and ends with one outcome, "Installed Caddy 2.11.9 at ~/.local/state/devhost/caddy/caddy · 48 MiB · 9.4 s"; a rerun says whether anything changed, never touches the running Caddy's file, and says how to restart onto the new version. The start ends with "Started Caddy 2.11.9 from ~/.local/state/devhost/caddy/caddy · 1.2 s" only once Caddy listens, then proxy-settings' one line naming where it listens, who can reach it, its settings file and how to stop it: every interface and the network by default, this machine only on a loopback listener, and on macOS a loopback setting below port 1024 keeps every interface with a warning that names the fix (`O39`). When the system does not trust devhost's local certificate authority and a person is at the terminal, one line names the authority, the trust store and that the next prompt asks for the password; after it the start names what it trusted, its SHA-256 fingerprint and the command that removes it, `devhost caddy untrust`. Without a person, the start never asks: a warning that stands out says browsers will reject devhost's certificates, why devhost did not ask, and the command to run on a line of its own, and agent output tells the agent to ask the person, never to run it, because the trust commands refuse an agent. The last line names the stack directory in its page's words, "All stacks on devbox: https://devhost.localhost/", and the next command. If the authority stays untrusted, devhost's own pages and the toolbar say so in one sentence that names devbox, with the command to copy, and name `devhost caddy trust-remote` with devbox's SSH name for a browser on another Mac, since devhost cannot change the browser's warning and never opens a browser. Trusting another machine's authority shows its name, expiry and the fingerprint the other machine prints for comparison, says what the trust allows and asks `[y/N]` first. `devhost caddy stop` names every stack and serve session it takes offline, with their hostnames, and then stops Caddy without asking, because it ends no agent's turn: every service keeps running and `devhost caddy start` brings their routes back. A certificate install and a Caddy stop cannot be taken back by an Undo, so there is no Undo: each names its way back, `devhost caddy untrust` and `devhost caddy start` (`UNDO-5`). Later, the Install page's "Update devhost" section says how devhost itself updates: `devhost upgrade` for a release archive installed in a folder the person can write, or the dotfiles or package manager that installed it followed by `devhost restart`; neither touches Caddy, which updates with `devhost caddy download` (`O18`). Benchmarks: mkcert installs its root with one command, removes it with `mkcert -uninstall` and warns that the root key can intercept any secure request from the machine; Laravel Valet and Herd trust at install and ship an uninstall; ssh shows a key's fingerprint in the format `ssh-keygen -l` prints and asks yes or no before trusting it; Homebrew and rustup print the version and the transfer progress, and rustup writes a download beside the target and renames it into place; Caddy itself ships `caddy untrust`; `docker system prune` prints what it will act on before acting; rustup and Deno update their own binary with one command (`rustup self update`, `deno upgrade`). Competitor behavior is evidence here, never a requirement.

## Target steps

Today, following `devhost caddy --help` ("Download and trust it once, then start it before running a stack.") on a new Mac: 5 steps, one of them a dead end and the last a guess: `devhost caddy download` (50 MB with no progress, ending in a path), `devhost caddy trust` (refused: "Managed Caddy is not running. Run 'devhost caddy start' first."), `devhost caddy start` (a password prompt, ending in the Caddyfile's path), guess the stack directory's URL, then look up what to run next; `devhost --help` itself has no Quickstart on Rust `main`. Proposed: 3 steps, each ending in a stated outcome: `devhost caddy download` (or skip it), `devhost caddy start` (asks for the password once and names what runs, the stack directory's URL and the next command), open that URL.

1. **Read one setup recipe (`devhost --help`, `devhost caddy --help`, the Install page, the README, the skill; read only).** `devhost --help` gains a Quickstart, which reads, in order: `devhost caddy download` "once; skip when caddy is on your PATH", `devhost caddy privileged-ports` "Linux only: lets Caddy use port 443 without root", `devhost caddy start` "start the shared proxy; the first start asks for your password", then `devhost init` to write a starter `devhost.toml` (stack-run-stop's, `O52`), `devhost start` "run the stack in devhost.toml" and `devhost start web` "run web and what it depends on"; Caddy's steps come first and `devhost caddy trust` is not among them, because the first start already trusts the authority, so it becomes the repair command (`MENU-6`, `WORD-9`, `O52`; `first-run-setup-01`). stack-run-stop owns the lines from `devhost init` on (`stack-run-stop-12`, owned there). `devhost caddy --help` replaces today's "devhost sends every stack through one shared Caddy server. Download and trust it once, then start it before running a stack." and opens with "devhost routes every stack through one shared Caddy server. Download it once, then start it: the first start trusts its certificate authority, which asks for your password. Run devhost caddy trust only when a start could not.", followed by proxy-settings' line naming the devhost config file. The Install page, the managed-Caddy guide, the README's install block and the skill give the same order, and the README's line gains the comment "# the first start asks for your password to trust devhost's certificates" (a correction of the block's text, not a new section). Each subcommand's help line names the same command the docs and the output use, "the shared Caddy" in help and docs and "Caddy" in output, never "managed caddy" (`MENU-6`, `WORD-1`, `WORD-3`; `selection-15`, `language-01`, `language-17`), and says beforehand what downloads and what asks for a password (`WORD-9`; `review-05`): `start` "Start the shared Caddy; the first start asks for your password to trust its certificates", `stop` "Stop the shared Caddy; every stack goes offline until it starts again", `trust` "Trust Caddy's certificate authority on this machine (needs Caddy running; asks for your password)", `untrust` "Remove the certificate authorities devhost trusted on this machine (asks for your password)", `download` "Download Caddy from caddyserver.com into devhost's state directory", `print-root-cert` "Print Caddy's root certificate, or with --fingerprint its name, expiry and SHA-256 fingerprint", `trust-remote` "Trust another machine's Caddy certificate authority over SSH after showing its fingerprint (macOS; asks for your password)"; `privileged-ports` keeps the line proxy-settings words.
   - Defaults: the help's order is the docs' order; nothing in any help screen teaches a step that fails on a new machine.
   - Updating devhost later (`O18`): the Install page gains an "Update devhost" section after "Prepare Caddy". It reads: "A release archive installed in a folder you can write, such as ~/.local/bin, updates with devhost upgrade, which downloads the latest release, checks it against SHA256SUMS, replaces the binary and restarts every running stack and serve session in a new devhost supervisor running it. When dotfiles, a package manager or your own build installed devhost, or the folder needs sudo, such as /usr/local/bin, update it the way you installed it, then run devhost restart, which restarts every running stack and serve session in a new devhost supervisor running the new binary. Neither updates Caddy: run devhost caddy download again for that." Serve sessions restart with the stacks because one devhost supervisor per state directory runs both, and `devhost restart` starts each again in its new supervisor (`O18` revision 7, `O31`; `start_replaced_in_daemon`, `apps/devhost/src/daemon/client.rs:1251`; `apps/devhost/src/services/restart.rs:430-495`). The "Download the binary" section's "Any directory on your `PATH` works in place of `/usr/local/bin`." gains "devhost upgrade can replace it only in a folder you can write without sudo." The section's recipe keeps `sudo install … /usr/local/bin/devhost`, so a person who follows it takes the second path, `devhost restart` after reinstalling; whether the recipe should default to a folder writable without sudo, such as `~/.local/bin`, is open product owner item q85; until it is answered, the recipe's `/usr/local/bin` with `sudo` is the applied default (`CC-48`). stack-run-stop owns `devhost upgrade`'s and `devhost restart`'s behavior and output (`O18`, `CC-36`); this flow owns the Install page's words.
2. **Download Caddy (`devhost caddy download`, one write: the managed Caddy binary).** The first line says what it downloads and from where, "Downloading Caddy for macOS arm64 from caddyserver.com…" (`WORD-9`), then on a terminal one status line updates in place with what has arrived and the elapsed time, "Downloading Caddy · 12 MiB · 3 s", or "12 of 48 MiB · 3 s" when the server sends a length, and without a terminal one plain line every 10 MiB (`FB-10`, `STATE-1`; `feedback-15`, `first-run-setup-07`). caddyserver.com's download sends no length (checked on 2026-11-17), so the size shows as it arrives and in the outcome; `WORD-9` accepts this for a download of unknown length. devhost streams the body into a temporary file beside the binary (`caddy.download-<random>` in `~/.local/state/devhost/caddy/`), flushes it to disk, makes it executable, runs it once with `version` to read its version and to prove it is Caddy for this platform, and only then renames it over `caddy`; a rename gives the file a new inode, so a Caddy that runs from the old file keeps it, macOS checks the new file's signature from scratch and Linux accepts the replacement while Caddy runs (`FB-5`, `REV-11`; `first-run-setup-08`). The outcome is one line, verb first: "Installed Caddy 2.11.9 at ~/.local/state/devhost/caddy/caddy · 48 MiB · 9.4 s" (`FB-3`, `WORD-4`, `WORD-8`), followed, when a Caddy is also on the `PATH`, by "devhost uses it instead of the caddy on your PATH (2.10.0 at /opt/homebrew/bin/caddy)". Today it prints "Downloading Caddy for darwin-arm64 from https://caddyserver.com/api/download?os=darwin&arch=arm64...", reads the whole body into memory, writes it over the installed binary in place and ends with "Caddy downloaded to" and the path (`apps/devhost/src/caddy.rs:328-408`).
   - A rerun compares the new file's SHA-256 with the installed one: identical, it removes the temporary file and reads "The download matches the installed Caddy 2.11.9 · nothing changed · 9.1 s"; different, "Updated Caddy 2.11.8 → 2.11.9 at ~/.local/state/devhost/caddy/caddy · 48 MiB · 9.4 s" (`first-run-setup-07`).
   - While the managed Caddy runs from that file, the outcome adds what happens next: "The running Caddy keeps 2.11.8 until you restart it, which takes every stack offline for a moment:" and the command on its own line, `devhost caddy stop && devhost caddy start` (`WORD-8`, `UNDO-5`; `first-run-setup-08`). On Linux, a replacement of a binary that held the low-port grant ends with proxy-settings' line "Run devhost caddy privileged-ports again: the new Caddy cannot use ports below 1024".
   - Keys: Ctrl-C cancels the download, removes the temporary file and reads "Download cancelled · the installed Caddy 2.11.9 is unchanged", exiting 130 with no error tag, because a cancel is not a failure (`KEY-14`, `FAIL-5`; `keyboard-16`).
   - Agent output prints the start line and the outcome with absolute paths and no progress line, the same facts in its own layout (`WORD-9`, `FB-11`).
3. **Start Caddy (`devhost caddy start`, one write: starts Caddy).** Before it starts anything, devhost checks that a Caddy executable exists: the downloaded one, else `caddy` on the `PATH` (kept) (`first-run-setup-06`). It renders the routes and starts Caddy under the route lock, as today, and reports success only once Caddy listens: its admin API answers and its HTTPS listener accepts a connection (`FB-5`; `feedback-04`). The outcome is one line naming which Caddy runs, "Started Caddy 2.11.9 from ~/.local/state/devhost/caddy/caddy · 1.2 s", or "… from /opt/homebrew/bin/caddy (on your PATH) · 1.2 s" (`FB-3`, `WORD-4`; `feedback-02`, `language-11`, `language-17`), then proxy-settings' line, worded there and printed here, which says who can reach the proxy (`FB-10`, `O39`):
   - Default settings: "Caddy runs HTTPS on port 443 on every interface, reachable from your network · settings: ~/.config/devhost/config.toml · stop it with devhost caddy stop".
   - A loopback listener (`bindHost = "127.0.0.1"` with every port at 1024 or above, such as `httpsPort = 4443`): "Caddy runs HTTPS on 127.0.0.1:4443 and [::1]:4443, direct connections from this machine only; relay previews and SSH forwards still reach it · settings: ~/.config/devhost/config.toml · stop it with devhost caddy stop".
   - On macOS with `bindHost = "127.0.0.1"` and a port below 1024, port 443 included: the line names every interface, as Caddy then listens, and proxy-settings' warning follows it on every start: "Warning: on macOS, bindHost = "127.0.0.1" needs every port at 1024 or above, so Caddy listens on every interface on port 443, reachable from your network. Set httpsPort = 4443, or start Caddy from a privileged launcher." Nothing is refused and the start succeeds, so existing port-443 setups keep starting (`O39`, `WORD-7`). Today macOS drops the loopback bind on every port without a word (`apps/devhost/src/caddy/files.rs:503-510`).

   Then the trust step (step 4), and last, the stack directory in its page's words with the next command, "All stacks on devbox: https://devhost.localhost/ · next: devhost start in the folder with your devhost.toml", with the URL from the shared Caddy settings and the machine name `O61` resolves, because devhost never opens a browser and the terminal hands off by printing URLs (`SURF-15`, `O61`; `first-run-setup-07`). The Caddyfile's path leaves human output and stays in agent output (`WORD-9`); today the start ends with "managed caddy started with" and the Caddyfile's path (`apps/devhost/src/caddy.rs:186-191`). A start while Caddy already runs reads "Caddy 2.11.8 already runs (PID 9076) · nothing started", then the proxy line, and, when a download has since installed 2.11.9, "The installed Caddy is 2.11.9; restart it to use it:" with `devhost caddy stop && devhost caddy start` on its own line (`first-run-setup-08`). `devhost serve`, which starts Caddy the same way, prints the same lines; serve-folder owns its own session lines.
   - Defaults: the binary is the downloaded one when it exists, else the `caddy` on the `PATH`, as today; devhost never downloads Caddy on its own, and `devhost start` never starts it. Section 4's wireframe line asks to draw "a first `devhost start` that downloads Caddy and reaches the trust step", which no devhost command does (`guides/managed-caddy.md`: "It never downloads Caddy on its own."); the wireframe draws the download, then this start with its trust step, and this flow reports the wording to the reference's author.

4. **Trust the local certificate authority (the trust step of `devhost caddy start`, one write: the system trust store; asks every time, and only a person at a terminal can answer).** devhost checks Caddy's root certificate against the system roots, as today.    - When devhost does not ask, or the step does not succeed, the start still succeeds, Caddy keeps running (product rule), and one warning stands out from the lines around it: the `[WARN]` label and its text in the warning color on a terminal that shows color, never only a prefix (`FAIL-2`, `WORD-7`; `first-run-setup-02`). The warning repeats on every `devhost caddy start`, `devhost serve` and stack start while the authority stays untrusted, as today.
   - Agent output (`AGENT=1`) never asks and tells the agent what only a person can do (`REV-8`, `WORD-9`, `FB-11`; `first-run-setup-03`, `language-16`): "devhost: WARN: Browsers will reject devhost's HTTPS certificates: this machine does not trust devhost's local certificate authority (/home/dev/.local/state/devhost/caddy/storage/pki/authorities/local/root.crt). 5. **Open the stack directory (https://devhost.localhost/, read only).** With the authority trusted, the stack directory and every stack's hostname load without a certificate warning; the next step, `devhost start`, is stack-run-stop's. 7. **Trust another machine's authority (`devhost caddy trust-remote devbox`, one write: the macOS System keychain, after a question; macOS only, as today).** Under `AGENT=1` it refuses before `ssh` and `sudo`, as `devhost caddy trust` does (`REV-8`). 8. **Remove trust (`devhost caddy untrust`, one write: the system trust store and the System keychain; asks every time, and only a person at a terminal can answer).** devhost keeps a record of every root it installed from this state directory, local or fetched from another machine, with its name, SHA-256 fingerprint, source and trust store (`UNDO-5`; `first-run-setup-05`). `devhost caddy untrust` lists what it will remove before it asks (`SEL-1`, `BAR-2`): "Removing 2 certificate authorities devhost trusted on this Mac:", then one line each, "Caddy Local Authority - 2026 ECC Root · this machine's, from ~/.local/state/devhost · SHA-256 17:35:2E:…:35:D5 · system trust store" and "Caddy Local Authority - 2026 ECC Root · from devbox · SHA-256 4A:0C:…:9E:61 · System keychain", then "This asks for your password." before `sudo`; the outcome reads "Removed 2 certificate authorities · browsers warn on devhost's hostnames until devhost caddy trust" (`WORD-4`). The state directory's own root is found by its fingerprint even when it was installed before the record existed. ## Recommended priority

**P2.** The realistic triggers are ordinary for a first run and rare afterwards: every new user who follows `devhost caddy --help` first meets a refused step 2 (`first-run-setup-01`); every first start from an IDE button, a script or a coding agent leaves every hostname behind the browser's "Your connection is not private" with one plain line that has scrolled away (`first-run-setup-02`); a coding agent that follows today's agent-mode warning runs a command that changes the machine's root trust, which installs a root unseen wherever `sudo` does not ask (`first-run-setup-03`); `trust-remote` installs another machine's root after a hash nobody can check (`first-run-setup-04`); rerunning the download to update Caddy on macOS leaves a Caddy devhost can no longer stop or reload (`first-run-setup-08`); and `devhost caddy stop` silently takes every stack on the machine offline (`notices-and-feedback-04`). No data is lost: each state is recoverable by hand, but a silently installed root, an unremovable one and a Caddy that must be found and killed are hard to recover without knowing devhost's internals. It runs once per machine and per state directory, less often than daily flows such as starting a stack, which is P1.
