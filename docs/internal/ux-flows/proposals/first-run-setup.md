# Install devhost and the shared HTTPS proxy: proposed experience

Diagrams: [current](../first-run-setup-current.html), [proposed](../first-run-setup-proposed.html). [Wireframe](../wireframes/first-run-setup.html).

Status: design proposal, not implemented behavior. The [shared UX pattern reference](../patterns.md) wins where this proposal disagrees with it.

Source revision: alexgorbatchev/devhost `edb5c0fc01cabae490e92ac23d4c785ec896c4ed`. Features: SET-01, SET-02, SET-03, SET-04, SET-05, SET-07. Redesign ticket: tracked privately.

Product rule: `guides/managed-caddy.md`, "Trust the certificates", states the trust contract: "devhost cannot ask without a terminal or under `AGENT=1`, and the installation can be declined or fail. In each case devhost prints a warning instead, Caddy keeps running, and browsers reject its certificates until you run: `devhost caddy trust`". The owner's rules add that devhost never opens a browser, that human output and agent output (`AGENT=1`) differ on purpose, and that Caddy listening on every interface by default is documented. So a Caddy that runs with an untrusted certificate authority is intended, a start that never asks for a password without a person at a terminal is intended, and devhost leaving the browser's own certificate warning in place is intended; none of them is a defect. The gap is around them: the built-in help teaches a setup order that fails, the warning never says why devhost did not ask and tells an agent to run the command itself, the command that changes the machine's trust never refuses an agent, `trust-remote` shows a hash nobody can check and installs at once, nothing removes a root devhost installed, a missing Caddy points at empty logs, a rerun of the download breaks a running Caddy on macOS, and `devhost caddy stop` takes every stack offline without naming one.

## Target experience

A person installs the binary and asks it what to do: `devhost --help`, `devhost caddy --help`, the Install page, the README and the agent skill all give one recipe, `devhost caddy download` (skipped when Caddy is on the `PATH`), `devhost caddy privileged-ports` on Linux, then `devhost caddy start`, and each says beforehand which step downloads and which asks for a password. The download says where it downloads from, shows its progress on one status line, checks that the file runs as Caddy and only then puts it in place, and ends with one outcome, "Installed Caddy 2.11.9 at ~/.local/state/devhost/caddy/caddy · 48 MiB · 9.4 s"; a rerun says whether anything changed, never touches the running Caddy's file, and says how to restart onto the new version. The start ends with "Started Caddy 2.11.9 from ~/.local/state/devhost/caddy/caddy · 1.2 s" only once Caddy listens, then proxy-settings' one line naming where it listens, its settings file and how to stop it. When the system does not trust devhost's local certificate authority and a person is at the terminal, one line names the authority, the trust store and that the next prompt asks for the password; after it the start names what it trusted, its SHA-256 fingerprint and the command that removes it, `devhost caddy untrust`. Without a person, the start never asks: a warning that stands out says browsers will reject devhost's certificates, why devhost did not ask, and the command to run on a line of its own, and agent output tells the agent to ask the person, never to run it, because the trust commands refuse an agent. The last line names the stack directory's URL and the next command. If the authority stays untrusted, devhost's own pages and the toolbar say so in one sentence with the command to copy, since devhost cannot change the browser's warning and never opens a browser. Trusting another machine's authority shows its name, expiry and the fingerprint the other machine prints for comparison, says what the trust allows and asks `[y/N]` first. `devhost caddy stop` names every stack and serve session it takes offline, with their hostnames, and then stops Caddy without asking, because it ends no agent's turn: every service keeps running and `devhost caddy start` brings their routes back. A certificate install and a Caddy stop cannot be taken back by an Undo, so there is no Undo: each names its way back, `devhost caddy untrust` and `devhost caddy start` (`UNDO-5`). Benchmarks: mkcert installs its root with one command, removes it with `mkcert -uninstall` and warns that the root key can intercept any secure request from the machine; Laravel Valet and Herd trust at install and ship an uninstall; ssh shows a key's fingerprint in the format `ssh-keygen -l` prints and asks yes or no before trusting it; Homebrew and rustup print the version and the transfer progress, and rustup writes a download beside the target and renames it into place; Caddy itself ships `caddy untrust`; `docker system prune` prints what it will act on before acting. Competitor behavior is evidence here, never a requirement.

## Target steps

Today, following `devhost --help` on a new Mac: 5 steps, one of them a dead end and the last a guess: `devhost caddy download` (50 MB with no progress, ending in a path), `devhost caddy trust` (refused: Caddy is not running), `devhost caddy start` (a password prompt, ending in the Caddyfile's path), guess the stack directory's URL, then look up what to run next. Proposed: 3 steps, each ending in a stated outcome: `devhost caddy download` (or skip it), `devhost caddy start` (asks for the password once and names what runs, the stack directory's URL and the next command), open that URL.

1. **Read one setup recipe (`devhost --help`, `devhost caddy --help`, the Install page, the README, the skill; read only).** `devhost --help`'s Quickstart reads, in order: `devhost caddy download` "once; skip when caddy is on your PATH", `devhost caddy privileged-ports` "Linux only: lets Caddy use port 443 without root", `devhost caddy start` "start the shared proxy; the first start asks for your password", `devhost start` "run the stack in devhost.toml" and `devhost start web` "run web and what it depends on"; `devhost caddy trust` leaves the Quickstart, because the first start already trusts the authority, and becomes the repair command (`MENU-6`, `WORD-9`; `first-run-setup-01`). stack-run-stop adds the step that creates a `devhost.toml` before `devhost start` (`stack-run-stop-12`, owned there). `devhost caddy --help` opens with "devhost routes every stack through one shared Caddy server. Download it once, then start it: the first start trusts its certificate authority, which asks for your password. Run devhost caddy trust only when a start could not.", followed by proxy-settings' line naming the devhost config file. The Install page, the managed-Caddy guide, the README's install block and the skill give the same order, and the README's line gains the comment "# the first start asks for your password to trust devhost's certificates" (a correction of the block's text, not a new section). Each subcommand's help line names the same command the docs and the output use, "the shared Caddy" in help and docs and "Caddy" in output, never "managed caddy" (`MENU-6`, `WORD-1`, `WORD-3`; `selection-15`, `language-01`, `language-17`), and says beforehand what downloads and what asks for a password (`WORD-9`; `review-05`): `start` "Start the shared Caddy; the first start asks for your password to trust its certificates", `stop` "Stop the shared Caddy; every stack goes offline until it starts again", `trust` "Trust Caddy's certificate authority on this machine (needs Caddy running; asks for your password)", `untrust` "Remove the certificate authorities devhost trusted on this machine (asks for your password)", `download` "Download Caddy from caddyserver.com into devhost's state directory", `print-root-cert` "Print Caddy's root certificate, or with --fingerprint its name, expiry and SHA-256 fingerprint", `trust-remote` "Trust another machine's Caddy certificate authority over SSH after showing its fingerprint (macOS; asks for your password)"; `privileged-ports` keeps the line proxy-settings words.
   - Defaults: the help's order is the docs' order; nothing in any help screen teaches a step that fails on a new machine.
2. **Download Caddy (`devhost caddy download`, one write: the managed Caddy binary).** The first line says what it downloads and from where, "Downloading Caddy for macOS arm64 from caddyserver.com…" (`WORD-9`), then on a terminal one status line updates in place with what has arrived and the elapsed time, "Downloading Caddy · 12 MiB · 3 s", or "12 of 48 MiB · 3 s" when the server sends a length, and without a terminal one plain line every 10 MiB (`FB-10`, `STATE-1`; `feedback-15`, `first-run-setup-07`). caddyserver.com's download sends no length (checked on 2026-11-17), so the size shows as it arrives and in the outcome; this deviates from `WORD-9`'s "with the size" and is proposed as an exception below. devhost streams the body into a temporary file beside the binary (`caddy.download-<random>` in `~/.local/state/devhost/caddy/`), flushes it to disk, makes it executable, runs it once with `version` to read its version and to prove it is Caddy for this platform, and only then renames it over `caddy`; a rename gives the file a new inode, so a Caddy that runs from the old file keeps it, macOS checks the new file's signature from scratch and Linux accepts the replacement while Caddy runs (`FB-5`, `REV-11`; `first-run-setup-08`). The outcome is one line, verb first: "Installed Caddy 2.11.9 at ~/.local/state/devhost/caddy/caddy · 48 MiB · 9.4 s" (`FB-3`, `WORD-4`, `WORD-8`), followed, when a Caddy is also on the `PATH`, by "devhost uses it instead of the caddy on your PATH (2.10.0 at /opt/homebrew/bin/caddy)".
   - A rerun compares the new file's SHA-256 with the installed one: identical, it removes the temporary file and reads "The download matches the installed Caddy 2.11.9 · nothing changed · 9.1 s"; different, "Updated Caddy 2.11.8 → 2.11.9 at ~/.local/state/devhost/caddy/caddy · 48 MiB · 9.4 s" (`first-run-setup-07`).
   - While the managed Caddy runs from that file, the outcome adds what happens next: "The running Caddy keeps 2.11.8 until you restart it, which takes every stack offline for a moment:" and the command on its own line, `devhost caddy stop && devhost caddy start` (`WORD-8`, `UNDO-5`; `first-run-setup-08`). On Linux, a replacement of a binary that held the low-port grant ends with proxy-settings' line "Run devhost caddy privileged-ports again: the new Caddy cannot use ports below 1024".
   - Keys: Ctrl-C cancels the download, removes the temporary file and reads "Download cancelled · the installed Caddy 2.11.9 is unchanged", exiting 130 with no error tag, because a cancel is not a failure (`KEY-14`, `FAIL-5`; `keyboard-16`).
   - Agent output prints the start line and the outcome with absolute paths and no progress line, the same facts in its own layout (`WORD-9`, `FB-11`).
3. **Start Caddy (`devhost caddy start`, one write: starts Caddy).** Before it starts anything, devhost checks that a Caddy executable exists: the downloaded one, else `caddy` on the `PATH` (kept) (`first-run-setup-06`). It renders the routes and starts Caddy under the route lock, as today, and reports success only once Caddy listens: its admin API answers and its HTTPS listener accepts a connection (`FB-5`; `feedback-04`). The outcome is one line naming which Caddy runs, "Started Caddy 2.11.9 from ~/.local/state/devhost/caddy/caddy · 1.2 s", or "… from /opt/homebrew/bin/caddy (on your PATH) · 1.2 s" (`FB-3`, `WORD-4`; `feedback-02`, `language-11`, `language-17`), then proxy-settings' line, worded there and printed here, "Caddy runs HTTPS on port 443 on every interface, reachable from your network · settings: ~/.config/devhost/config.toml · stop it with devhost caddy stop" (`FB-10`). Then the trust step (step 4), and last, "Stack directory: https://devhost.localhost/ · next: devhost start in your project's folder" with the URL from the shared Caddy settings, because devhost never opens a browser and the terminal hands off by printing URLs (`SURF-15`; `first-run-setup-07`). The Caddyfile's path leaves human output and stays in agent output (`WORD-9`). A start while Caddy already runs reads "Caddy 2.11.9 already runs (PID 9076) · nothing started", then the proxy line, and, when a download has replaced the binary since, "The installed Caddy is 2.11.9; restart it to use it:" with `devhost caddy stop && devhost caddy start` on its own line (`first-run-setup-08`). `devhost serve`, which starts Caddy the same way, prints the same lines; serve-folder owns its own session lines.
   - Defaults: the binary is the downloaded one when it exists, else the `caddy` on the `PATH`, as today; devhost never downloads Caddy on its own.
4. **Trust the local certificate authority (the trust step of `devhost caddy start`, one write: the system trust store; asks every time, and only a person at a terminal can answer).** devhost checks Caddy's root certificate against the system roots, as today. When the system does not trust it and a person can answer (standard input is a terminal and `AGENT=1` is unset, as today), one line says what the step does and that it asks for the password, before the prompt (`REV-1`, `REV-8`, `WORD-9`): "Trusting devhost's local certificate authority adds Caddy Local Authority - 2026 ECC Root from ~/.local/state/devhost to the system trust store and asks for your password." sudo's prompt keeps the `caddy | Password:` label (kept). Success names what it installed, so the person can find it later among same-named roots of other state directories, and its way back (`UNDO-5`, `WORD-8`; `first-run-setup-05`, `language-18`): "Trusted Caddy Local Authority - 2026 ECC Root from ~/.local/state/devhost · valid until 2036-09-25", then "SHA-256 17:35:2E:25:00:A4:82:A9:…:06:B5:35:D5" on its own line, the full 32 bytes of the SHA-256 of the DER certificate in the form `openssl x509 -fingerprint -sha256` prints (the example abbreviates it), then "Remove it later with:" and `devhost caddy untrust` on its own line. devhost records every root it installs (step 8's record).
   - When devhost does not ask, or the step does not succeed, the start still succeeds, Caddy keeps running (product rule), and one warning stands out from the lines around it: the `[WARN]` label and its text in the warning color on a terminal that shows color, never only a prefix (`FAIL-2`, `WORD-7`; `first-run-setup-02`). It reads "Browsers will reject devhost's HTTPS certificates: this machine does not trust devhost's local certificate authority.", then the cause in one sentence, then "Trust it from a terminal:" and `devhost caddy trust` on its own line, which therefore never wraps mid-command (`WORD-8`). The cause names what happened: "devhost did not ask for your password because standard input is not a terminal.", "The password was not accepted: sudo: 3 incorrect password attempts.", "You cancelled the password prompt.", "Caddy could not install it: <Caddy's first error line>." and, for a stack that joins the running Caddy, "devhost start never asks for your password." The warning repeats on every `devhost caddy start`, `devhost serve` and stack start while the authority stays untrusted, as today.
   - Agent output (`AGENT=1`) never asks and tells the agent what only a person can do (`REV-8`, `WORD-9`, `FB-11`; `first-run-setup-03`, `language-16`): "devhost: WARN: Browsers will reject devhost's HTTPS certificates: this machine does not trust devhost's local certificate authority (/home/dev/.local/state/devhost/caddy/storage/pki/authorities/local/root.crt). Installing it needs the person's password. Ask the person to run devhost caddy trust in a terminal; do not run it yourself."
   - Keys: Ctrl-C at the password prompt skips trust: devhost keeps running, Caddy keeps running untrusted, the warning prints with "You cancelled the password prompt.", and the start exits 0, because Caddy runs (`KEY-14`, `FAIL-5`).
5. **Open the stack directory (https://devhost.localhost/, read only).** With the authority trusted, the stack directory and every stack's hostname load without a certificate warning; the next step, `devhost start`, is stack-run-stop's. While the authority stays untrusted, devhost cannot change the browser's warning page, so every page devhost renders says so where the person lands once past it (`MENU-5`, `STATE-4`; `first-run-setup-02`): the stack directory, the Caddy 404, the status pages (starting, recovery, the stopped stack's page) and the file listing put one line at the top, before their heading in reading order: "This machine does not trust devhost's local certificate authority, so your browser warns on each devhost hostname and blocks a page's requests to another one. Run devhost caddy trust in a terminal, then reload.", with **Copy** (accessible name "Copy devhost caddy trust", outcome "Copied devhost caddy trust"). This one sentence is the condition's reason on every page and in every criterion. It is one shared component in both style entries, the status pages' stylesheet and the devtools Shadow DOM stylesheet (`SURF-14`), rendered by its owners: stack-directory's directory and Caddy 404, startup-and-recovery's status pages, serve-folder's file listing. No line shows while the system trusts the authority.
   - On app pages, the toolbar shows the same sentence as a condition notice with **Copy** while the authority is untrusted, ordered with the other conditions of the notice stack (`FB-8`, group 3) and announced once politely when the condition starts or ends while the page is open (`FB-9`); it never takes focus (`KEY-6`), and dismissing it follows notices-and-feedback's rules for every condition notice (`SURF-8`, `UNDO-3`). The reference's list of conditions has no such entry, so the notice is proposed as an exception to `ACT-7` below; until the reference accepts it, the full pages and the terminal carry the condition alone.
   - Keys: full pages use the document's standard keys (`KEY-1`); **Copy** is an ordinary button and a Tab stop, and in the notice stack it is a Tab stop after the notice's text (`KEY-4`).
6. **Repair trust later (`devhost caddy trust`, one write: the system trust store; asks every time, and only a person at a terminal can answer).** At a terminal, with Caddy running and the authority untrusted, it prints step 4's line before the prompt and step 4's outcome after it; with the authority trusted it reads "Caddy Local Authority - 2026 ECC Root from ~/.local/state/devhost is already trusted · nothing changed" (kept, in words). With Caddy stopped it refuses with nothing changed: "devhost caddy trust needs Caddy running, because Caddy creates its certificate authority when it starts. Start it, which also trusts the authority:" and `devhost caddy start` on its own line (`FAIL-2`, `MENU-5`; `first-run-setup-01`). Under `AGENT=1` it refuses before any `sudo`, exits 1 and prints one line: "devhost: ERR: devhost caddy trust changes this machine's certificate trust, so only a person can run it. Ask the person to run devhost caddy trust in a terminal." (`REV-8`, `CC-13`; `first-run-setup-03`, `review-05`). Without a terminal and without `AGENT=1` (a provisioning script), it runs only when `sudo` needs no password (`sudo -n true` succeeds, or devhost runs as root); otherwise it refuses before `sudo` with "devhost caddy trust needs your password, and standard input is not a terminal to ask it in. Run it in a terminal." and exits 1, so a script never hangs on a prompt nobody sees.
7. **Trust another machine's authority (`devhost caddy trust-remote devbox`, one write: the macOS System keychain, after a question; macOS only, as today).** Under `AGENT=1` it refuses before `ssh` and `sudo`, as `devhost caddy trust` does (`REV-8`). Otherwise it fetches the certificate over SSH, naming the command it runs, "Fetching devbox's root certificate: ssh devbox devhost caddy print-root-cert", then prints what it would trust (`REV-8`, `WORD-8`; `first-run-setup-04`): "devbox's root certificate: Caddy Local Authority - 2026 ECC Root · valid until 2036-09-25", the fingerprint on its own line, "SHA-256 4A:0C:91:7B:E2:5D:0F:33:…:C8:9E:61", the full SHA-256 of the DER certificate, "Compare it with devhost caddy print-root-cert --fingerprint on devbox.", and what the trust allows, "Trusting it lets anyone who can read devbox's devhost state issue certificates this Mac accepts for any website." Then it asks, the set first and the question last, in one line ending in `[y/N]`: "Add it to the System keychain? This asks for your password. [y/N]" (`REV-4`, `SURF-2`; `surfaces-13`, `review-17`). Only y or yes adds it: an empty answer, end of input or anything else reads "Not trusted: nothing changed." and exits 1 with no error tag (`REV-4`, `FAIL-5`); `--yes` skips the question, for scripts (`CC-13`). After the password, it reads "Trusted devbox's Caddy Local Authority - 2026 ECC Root · SHA-256 4A:0C:…:9E:61" with "Remove it later with:" and `devhost caddy untrust`, and records the root (step 8) (`UNDO-5`). On devbox, `devhost caddy print-root-cert --fingerprint` prints "Caddy Local Authority - 2026 ECC Root · valid until 2036-09-25 · SHA-256 4A:0C:…:9E:61", the same value, so the person compares two screens instead of trusting one (`first-run-setup-04`); without the flag the command prints the PEM certificate, as today.
8. **Remove trust (`devhost caddy untrust`, one write: the system trust store and the System keychain; asks every time, and only a person at a terminal can answer).** devhost keeps a record of every root it installed from this state directory, local or fetched from another machine, with its name, SHA-256 fingerprint, source and trust store (`UNDO-5`; `first-run-setup-05`). `devhost caddy untrust` lists what it will remove before it asks (`SEL-1`, `BAR-2`): "Removing 2 certificate authorities devhost trusted on this Mac:", then one line each, "Caddy Local Authority - 2026 ECC Root · this machine's, from ~/.local/state/devhost · SHA-256 17:35:2E:…:35:D5 · system trust store" and "Caddy Local Authority - 2026 ECC Root · from devbox · SHA-256 4A:0C:…:9E:61 · System keychain", then "This asks for your password." before `sudo`; the outcome reads "Removed 2 certificate authorities · browsers warn on devhost's hostnames until devhost caddy trust" (`WORD-4`). The state directory's own root is found by its fingerprint even when it was installed before the record existed. Under `AGENT=1` it refuses as `devhost caddy trust` does (`REV-8`); with nothing to remove it reads "devhost has not trusted any certificate authority from ~/.local/state/devhost · nothing changed" and exits 0. The Install page gains an "Uninstall devhost" section: stop every stack, `devhost caddy untrust`, `devhost caddy stop`, then delete the state directory and the binary, and on a Mac that ran `trust-remote` before this release, find the root in Keychain Access by its name and the fingerprint `trust-remote` printed.
9. **Stop Caddy (`devhost caddy stop`, one write: stops Caddy and takes every stack's routes offline; never asks).** It prints its set first, from the state directory's records (`SEL-6`, `BAR-2`, `WORD-5`; `selection-06`, `status-13`, `notices-and-feedback-04`): "Stopping Caddy takes 2 stacks and 1 serve session offline; their services keep running:", then one line each, "Acme Shop · main ~/acme · PID 81234 · detached · shop.localhost, docs.shop.localhost, +3", "Blog · main ~/blog · PID 82001 · foreground · blog.localhost" and "serve session ~/notes · notes.localhost", each stack named by its manifest's name with its checkout label (`SEL-4`, `WORD-1`). Then it acts at once, in a terminal and under `AGENT=1` alike, because stopping Caddy ends no agent's turn, no service and no conversation (`REV-1`, `REV-7`, `UNDO-4`; `review-03`, `review-04`); this differs from the slice text of `notices-and-feedback-04`'s assignment, "and asks first", as recorded under **Tickets resolved**. Before Caddy stops, devhost writes a stop record beside Caddy's PID file (by `devhost caddy stop`, when, and the origin: a terminal or an agent) and tells each running stack, so each stack's terminal and log can tell this stop from a Caddy that exited on its own, and its pages can say that the proxy is not reachable (`ACT-10`, `FAIL-5`, `HOLD-2`, `FB-7`; `feedback-06`, `feedback-11`, `status-04`): stack-run-stop prints "Acme Shop lost its proxy at 14:10 (devhost caddy stop); its services keep running" and "Acme Shop's routes answer again at 14:12", and notices-and-feedback words the page's notice, "devhost's proxy is not reachable. Start it with devhost caddy start", drawn over services shown as unknown, never down (`ACT-5`). The outcome reads "Stopped Caddy · 2 stacks and 1 serve session offline until devhost caddy start · 0.4 s" (`FB-3`, `WORD-4`), and with nothing running "Stopped Caddy · no stack or serve session was running · 0.3 s". `--dry-run` prints the set and "Dry run: Caddy keeps running; nothing changed", then exits 0 without acting (`SEL-6`, `CC-12`). Agent output lists the same set with each manifest's absolute path, PID and every hostname (`WORD-9`).
   - Defaults: no question and no `--yes`: the reference keeps questions for writes that end an agent's turn, and this one ends none (`REV-7`, `O33`).

Branches and edge states:

- **No Caddy executable.** `devhost caddy start` and `devhost serve` check before starting and stop with nothing started: "[ERROR] Caddy is not installed: devhost looked for ~/.local/state/devhost/caddy/caddy and for caddy on your PATH.", then "Install it with:" and `devhost caddy download` on its own line, exit 1; the exec error is devhost's, never printed under the `caddy` label, because Caddy never ran (`FAIL-2`, `MENU-5`, `WORD-7`; `first-run-setup-06`, `language-09`, `language-10`). Agent output: "devhost: ERR: Caddy is not installed: devhost looked for /home/dev/.local/state/devhost/caddy/caddy and for caddy on PATH. Run devhost caddy download, or install Caddy on PATH."
- **Caddy fails to start for another reason.** The failure names what Caddy said, from the output this attempt wrote, with the file it comes from: "Caddy did not start: listen tcp :443: bind: address already in use · from ~/.local/state/devhost/caddy/caddy.stderr.log"; a log file is named only when this attempt wrote to it, never one the attempt emptied (`FAIL-2`, `FAIL-3`; `first-run-setup-06`). The two port 443 cases keep their specific next steps (kept), worded with proxy-settings.
- **The devhost config file is rejected at start.** `devhost caddy start` names the file, line, column and key from the one structured error proxy-settings and config-editor build, and starts no Caddy: "~/.config/devhost/config.toml:4:13 caddy.httpsPort: expected a number. Caddy did not start; nothing changed." (`MENU-4`, `FAIL-2`, `WORD-8`; `selection-10`).
- **A failed, cut or wrong download.** A failure at any step removes the temporary file and leaves the installed binary untouched, and says so: "Download failed: no space left on device after 31 MiB · the installed Caddy 2.11.9 is unchanged", or "… · no Caddy is installed" on a first download; a network failure reads "Could not download Caddy from caddyserver.com: the connection timed out after 30 s · the installed Caddy 2.11.9 is unchanged. Try again, or install Caddy and put it on your PATH."; a file that does not run as Caddy reads "The download from caddyserver.com did not run as Caddy for macOS arm64 · the installed Caddy 2.11.9 is unchanged". The original error stays in agent output's one `ERR:` line (`FAIL-2`, `WORD-7`, `REV-11`; `first-run-setup-08`). devhost never retries a download, a trust or a stop by itself (`REV-12`).
- **A Caddy that does not answer.** When the admin API does not answer and the recorded Caddy PID still runs, `devhost caddy stop` never reports Caddy as not running and never forgets its PID: "Caddy (PID 62784) runs, but its admin API at 127.0.0.1:2019 has not answered for 3 s; stopping it by signal", then "Stopped Caddy (PID 62784) with SIGTERM · …", keeping the PID file until the process has exited; `devhost caddy start` refuses to start a second Caddy while it runs: "Caddy (PID 62784) already runs, but its admin API at 127.0.0.1:2019 has not answered for 3 s; it may be stuck in a reload. Stop it with:" and `devhost caddy stop` (`ACT-11`, `FAIL-2`; `status-14`). The patch for `stack-scale-09` builds this check; this flow words its lines.
- **A Caddy devhost did not start.** `start`, `stop` and `trust` keep refusing an admin API devhost did not start, in words: "A Caddy that devhost did not start already listens on 127.0.0.1:2019, this state directory's admin address. Stop it, or set DEVHOST_STATE_DIR for a separate devhost." (kept; `WORD-7`).
- **`devhost caddy stop` with Caddy stopped.** "Caddy is not running · nothing changed", exit 0, as today (kept).
- **A running stack that does not answer the stop's notice.** The stop waits at most 1 s per stack, never blocks on one, and names it in its set line: "Blog did not answer; its terminal may not say why its routes stopped".
- **A rejected manifest or a lost connection.** No write of this flow is made from a page, so neither blocks anything here (`HOLD-2`, `HOLD-6`); a page that loses its stream because Caddy stopped shows notices-and-feedback's reason above, and the trust line's **Copy** keeps working, because it copies text and writes nothing.
- **Another browser store.** devhost's check reads the system trust store; a browser with a store of its own (Firefox without enterprise roots) can still warn while devhost reports the authority trusted. 3. **The executable check and honest start failures.** `devhost caddy start` and the serve session's start resolve the executable before rendering anything and return "Caddy is not installed" with both places it looked; exec errors are devhost's, never Caddy's output; `runBackgroundCommand` keeps the previous logs until Caddy itself writes, and a start failure names a log only when this attempt wrote to it, quoting its last error line. Serves `first-run-setup-06`. Required.
4. **Start certifies the listener.** The start waits until the admin API answers and the HTTPS listener (the address proxy-settings records as applied) accepts a TCP connection, with the listener check bounded by Caddy's own start timeout, before printing the started line. Serves `first-run-setup-07` (`FB-5`). Required.
5. **The trust step's lines and causes.** `trustAfterStart` and `trust` print the line before the prompt with the root's subject and the state directory, read the certificate's subject, expiry and DER SHA-256 for the outcome, and return a cause with each untrusted result (no terminal, `AGENT=1`, declined, cancelled, Caddy's error, a joining stack) that the warning words; SIGINT during the trust command ends only that command, and the start reports the cause "cancelled". Serves `first-run-setup-02`, `first-run-setup-05`. Required.
6. **Agent refusals.** `devhost caddy trust`, `untrust` and `trust-remote` check `AGENT=1` before any `ssh`, `sudo`, `security` or Caddy trust command and exit 1 with one `ERR:` line; without a terminal, `trust` and `untrust` run `sudo -n true` (skipped as root) before anything privileged and refuse when it fails. Serves `first-run-setup-03`. Required. Contract: `CC-13`.
7. **`trust-remote`'s fingerprint and question.** It parses the fetched PEM, prints the subject, expiry and the SHA-256 of the DER bytes in uppercase hexadecimal pairs joined by colons, states what the trust allows, and asks `[y/N]` on the terminal before `sudo security add-trusted-cert`; `--yes` skips the question; anything but y or yes, end of input included, exits 1 with "Not trusted: nothing changed." Serves `first-run-setup-04`. Required. Contract: `CC-13`.
8. **[discuss]: `print-root-cert --fingerprint`.** The flag prints the subject, expiry and DER SHA-256 instead of the PEM text, so the fingerprint can be read on the machine that owns the root. `CC-13` does not name it: the reference's author must add it to `CC-13` beside `trust-remote`'s row. Serves `first-run-setup-04`. Required.
9. **`devhost caddy untrust` and the trusted-roots record.** Every install from this state directory (the start's trust step, `devhost caddy trust`, `trust-remote`) appends `{subject, sha256, source, store, installedAt}` to a record in the state directory (`<state>/caddy/trusted-roots.json`, written atomically); `untrust` lists the record's roots plus this state directory's own `root.crt` when the system trusts it, then removes each with the store's own command (Caddy's `untrust` for the local root, `sudo security delete-certificate -Z <sha1>` from the System keychain for a fetched one) and rewrites the record. Serves `first-run-setup-05`. Required. Contract: `CC-13`.
10. **[discuss]: The trust state for pages.** The stack directory and the Caddy 404, which Caddy serves as static documents, are rendered with the trust line when the check reads untrusted, and `devhost caddy start`, `trust` and `untrust` re-render them under the route lock after a change; status pages served by a stack's servers read the check when they render; the control server publishes the machine's trust state on `/__devhost__/ws/health` for the toolbar's condition notice, re-read when a page connects and when `trust`, `untrust` or `start` tell the running stacks that it changed (the same notice route as Backend 11). The static re-render reuses the one 2.10's Backend contract gives the stopped-stack record; the published state and the notice depend on the `ACT-7` exception below. Serves `first-run-setup-02`. Required for the full pages; the toolbar part waits for the exception.
11. **`devhost caddy stop`'s set, `--dry-run`, stop record and notice.** Before stopping, it reads every running stack's record and every serve session in the state directory (name, manifest, checkout label, PID, foreground or detached, hostnames) and prints the set; `--dry-run` stops there. It then writes the stop record beside the PID file (`{by: "devhost caddy stop", at, origin}`, the origin as `ACT-1` sees it: the terminal, or an agent named by `DEVHOST_CHAT_SESSION`), and tells each running stack through its control server on the loopback port `caddy.SetStackControlPort` records, waiting at most 1 s per stack, which is the call notices-and-feedback's Backend 3 names (each stack then sends `{"type": "proxy-stopping"}` to its pages) and from which stack-run-stop prints its line; `devhost caddy start` removes the record. ## Recommended priority

**P2.** The realistic triggers are ordinary for a first run and rare afterwards: every new user who reads `devhost --help` first meets a refused step 2 (`first-run-setup-01`); every first start from an IDE button, a script or a coding agent leaves every hostname behind the browser's "Your connection is not private" with one plain line that has scrolled away (`first-run-setup-02`); a coding agent that follows today's agent-mode warning runs a command that changes the machine's root trust, which installs a root unseen wherever `sudo` does not ask (`first-run-setup-03`); `trust-remote` installs another machine's root after a hash nobody can check (`first-run-setup-04`); rerunning the download to update Caddy on macOS leaves a Caddy devhost can no longer stop or reload (`first-run-setup-08`); and `devhost caddy stop` silently takes every stack on the machine offline (`notices-and-feedback-04`). No data is lost: each state is recoverable by hand, but a silently installed root, an unremovable one and a Caddy that must be found and killed are hard to recover without knowing devhost's internals. It runs once per machine and per state directory, less often than daily flows such as starting a stack, which is P1. This redesign depends on the notices-and-feedback foundation, which ships first or with the slice that needs it: it provides the outcome model this flow's lines follow and the page's lost-connection notice. Seams, with no blocker in either direction: proxy-settings (the listener line and `privileged-ports`), stack-run-stop (the stacks' proxy lines, the Quickstart's manifest step, `CC-12`'s other half and `CC-30`), stack-directory and startup-and-recovery (rendering the trust line) and serve-folder (its trust step and session lines); the `stack-scale-09` patch, which builds the PID check whose lines this flow words, is recommended to land before `devhost caddy stop`'s slice (Backend 12). Ship first the slice with no product decision and no dependency, which closes the two ways an agent or a rerun can harm the machine: the trust commands' refusal under `AGENT=1` with the agent-mode warning, and the atomic download (Backend 1, 6). Then the words and the order: the help and docs recipe, the start's and download's lines, the warning's causes and the honest start failures (Backend 2 to 5). Then the trust round trip: `trust-remote`'s fingerprint and question, `print-root-cert --fingerprint`, `untrust` with its record and the uninstall docs (Backend 7 to 9), in one release, so no release prints a removal command that does not exist yet. Then `devhost caddy stop`'s set and stop record with stack-run-stop's proxy lines (Backend 11, after the patch of Backend 12). Last, the trust line on devhost's pages, and the toolbar's notice once the reference accepts its exception (Backend 10).
