# Edit the manifest and watch it apply: proposed experience

Diagrams: [current](../manifest-hot-reload-current.html), [proposed](../manifest-hot-reload-proposed.html). [Wireframe](../wireframes/manifest-hot-reload.html).

Status: design proposal, not implemented behavior. The [shared UX pattern reference](../patterns.md) wins where this proposal disagrees with it.

Source revision: alexgorbatchev/devhost `190a8bb53e8cd903d2db0a92cb0886f29671607f`. Features: MAN-03, MAN-04, MAN-05, MAN-06, MAN-07. Redesign ticket: tracked privately.

Product rule: `stacks/hot-reload.md` states the contract: "While a stack runs, saving `devhost.toml` or any included manifest applies the change without restarting devhost. Only the services the edit affects restart, and an invalid edit leaves the stack running as it was." The owner's rules add that every manifest setting applies through hot reload, never "restart to apply", and that a failed service leaving the rest of the stack running is the recovery contract. The contributor contract in `apps/devhost/AGENTS.md` ("compare effective injected environments, restart dependents and affected repository groups, and restore prior services/routes on failure") and the "What restarts" table of `stacks/hot-reload.md` make the repository-wide restart documented behavior, which `O9` (decided 2026-11-18) keeps. Under `O7` (decided 2026-11-25), external services (`managed = false`) never block worktree switches and need no switch warning. So a save that applies without a question, an edit that restarts every service of its repository, and a rejected edit leaving the accepted manifest running are intended, not defects. The gap is around them: nothing says what a reload restarted or why, its progress is a stack of spinners with every restart button dead, a rejection is a raw parser error with no file or line that a busy service scrolls away, the crash that caused it is one hover-only minimap row, a save missed by the file watcher leaves no timeout report, and an undo, a repeat or a second save during a reload print nothing at all.

## Target experience

The person saves `devhost.toml`, or an include, in any editor, or an agent or `git` writes it. They keep their place: no question asks anything (`REV-10`), and the stack's terminal prints one line naming what will restart and why, "Apply devhost.toml: restarting worker (changed), and api, web, docs, admin and search-index-rebuilder (same repository as worker)". Every open page of the stack shows the same reload as one activity line in the notice stack, "Apply devhost.toml · 2 of 6 restarted · 5 s", and the touched rows read "restarting · Apply devhost.toml" while every other row keeps its state; a **Restart** pressed meanwhile queues behind the reload when its service is outside the set, and says the service is already restarting when it is inside, instead of doing nothing. The reload ends with exactly one outcome line in the terminal and the stack's log, "Applied devhost.toml: restarted worker (changed), and api, web, docs, admin and search-index-rebuilder (same repository as worker) · 6 of 6 running · 16 s", certified only once every restarted service passed its health check (`O28`); a page whose own service restarted shows the same sentence as a notice that stays for its calibrated reading time (`O14`), pauses its countdown on arrival when the browser window is unfocused (`O53`), and is announced once. An edit devhost cannot apply never stops anything: the terminal reads "devhost.toml:12:8 not applied: services.api.port: expected a number. The stack still runs the accepted manifest." with the offending line under it, and every page shows the same rejection as a notice that names the file and line, never runs off the screen, and leads with **Edit** when the config editor is on, or the file and line with **Copy** alongside **Copy Error** when the config editor is off (`O51`). When a restarted service crashes, devhost restores the accepted manifest service by service and keeps the crashed service's own last lines in the notice. Fixing the file replaces the rejection with its outcome; undoing the edit prints "Configuration restored: devhost.toml matches the accepted manifest · nothing restarted"; saving the same failing change again prints one line saying it failed again and what it restarted and rolled back. A save that lands while a reload runs replaces it, and one line says so; a save that no reload reads within 5 s while the stack is idle ends unseen and directs the person to `devhost reload` (`O42`). An agent that edits the manifest runs `devhost reload`, which waits for the same outcome and exits with it, and reads stack state with `devhost stack info` (short alias `devhost status`, `O62`). There is no Undo save: the way back is to what runs (`UNDO-6`), and devhost's own rollback restores the accepted manifest when a restart fails (`UNDO-1`). Benchmarks: Vite and Next.js apply a config save at once and print what restarted; Tilt names the resource each file change updates and keeps a pending update visible; `nginx -t` with `nginx -s reload` and `systemctl reload` give a reload a checkable exit status; rustc and TypeScript print `file:line:column` with the offending line and a caret; Kubernetes reports a rollback as an outcome of its own and keeps old replicas serving until new ones are ready; VS Code's Problems panel jumps to the line and column. Competitor behavior is evidence here, never a requirement.

## Target steps

Today: an accepted save takes 4 steps, the last a guess: save, watch the toolbar drop to 0/6 with every **Restart** disabled and no reason, read `configuration reloaded:` and every URL in the terminal, compare PIDs or logs to learn what restarted. A rejected save takes 6: save, find `configuration reload rejected` among the services' output before it scrolls away, read the raw error, search the includes for the file it never names, find the line by hand, fix and save, then read nothing that confirms the fix. Proposed: an accepted save takes 3 steps: save, read the activity line naming the set, read the outcome line. A rejected save takes 4: save, read "not applied" with the file, line, column and offending line, **Edit** (or copy `file:line:column` when the config editor is off) and fix, read the outcome that replaces the rejection.

Examples use Acme Shop: 6 services in one Git repository, where worker depends on api. With worktrees on, the default, `O9`'s scope restarts every service of the repository; examples that restart fewer services, such as "restarted api (changed) and worker (depends on api)", have worktrees off (`[worktrees].enabled = false`), where the scope is the changed services and their dependents.

1. **Save a manifest file from any editor (the manifest watcher, then the reload: one write, applied without a question).** A save of the root manifest or an include, from a text editor, the Configuration window, `git` or an agent, or a file that starts or stops matching an `includes` pattern, starts a hot reload 200 ms after the last write (`apps/devhost/src/services/watch.rs:20`), as today, and never asks first: a hot reload is reported, never reviewed (`REV-10`, `REV-1`; owner rule; `review-07`). The services runtime opens one operation record for it, kind `reload`, whose origin is "after devhost.toml changed on disk" for a save from outside devhost's UI, because the watcher cannot tell an editor's save from an agent's edit or a formatter, and the Configuration window's own operation ID for a save from that window (`ACT-1`, `WORD-4`). Its label on every surface is **Apply devhost.toml**, the file the save changed, and its outcome uses the same verb in the past tense, "Applied" (`WORD-2`, `WORD-1`; `language-07`, `language-08`).
   - Defaults: the restart scope is `O9`'s decided default, today's scope: the services whose definition or injected environment changed, every service that depends on one of them, and every service of the same repository when worktrees are on (`O9`, `SEL-11`; `selection-14`); the reload keeps the run's service selection, as `stacks/hot-reload.md` documents, so a service left out of the run stays not started and an added one starts only when the selection includes it (`SEL-7`; `selection-07`); every manifest setting applies through hot reload, never "restart to apply" (owner rule).
   - Unseen saves (`O42`): if a save is not read by any reload within **5 s** of the write on the server — counted **only while no operation (startup, a reload, a restart, or a worktree switch) holds the stack** — its record ends `unseen` and reports "devhost did not see this save; the stack still runs the accepted manifest. Apply it with devhost reload in ~/acme", never stalling indefinitely; a version superseded by a later save before any reload reads it ends as `replaced`, never `unseen` (`O42`, `FB-5`, `REV-12`). This bounds missed watcher events such as replaced symlinks (`manifest-hot-reload-10`) and symlinked manifests or `config.toml` files (`manifest-hot-reload-08`, which on Rust `main` affects macOS `notify` FSEvents as well as Linux `inotify` until config-editor's symlink-following watcher lands). config-editor's Backend 12 builds the timer and the record's `unseen` and `replaced` ends; this flow reports the same outcome for a save from another program in the terminal, the log and the notice stack (`O42`).
   - Seeing the reach beforehand: the Configuration window states it beside **Save** from the backend's check, config-editor's statement (`REV-10`), and `devhost reload --dry-run`, or `devhost reload --dry-run --stdin devhost.toml` with a candidate text that is not written yet, prints the same plan from the same check and changes nothing: "Dry run: Apply devhost.toml would restart worker (changed), and api, web, docs, admin and search-index-rebuilder (same repository as worker) · nothing applied" (`FB-11`, `CC-23`; Backend 11).
   - Other work: starting and restarting services ends nothing of an agent's, so a save asks about no agent (`REV-3`); the one question a save can meet is config-editor's, in the Configuration window, when the save turns the config editor off while other files hold drafts (`REV-10`, `REV-3`).
   - Keys: none of its own; the save is the editor's. The notices this flow shows are reached as step 5 says.
2. **Check everything before anything stops (the reload's checks, read only).** devhost re-reads the root manifest and every include and validates the merged result, then claims new hostnames and fixed ports against other stacks, as today, and now also probes each new or changed fixed port on its bind host, both loopback addresses included, and names the program that listens there (`REV-11`; `review-01`, `review-07`). A failed check refuses the reload with nothing stopped and names the check and what holds it: "devhost.toml:12:8 not applied: services.api.port: 127.0.0.1:4000 is already in use by python3 (PID 4242). Choose another port or stop that program. The stack still runs the accepted manifest." (`FAIL-2`, `WORD-7`, `HOLD-6`; `manifest-hot-reload-05`, `error-pages-06`). A service that was failing before the save and whose definition the save does not change is never a condition of the reload's success: it keeps failing with its recovery page, and the rest applies (`REV-11`, `UNDO-1`, `FAIL-1`; `status-06`); the `error-pages-01` stopgap ships that part first.
   - The plan names each service with its reason, from one plan function that the reload, the Configuration window's check and `devhost reload --dry-run` share: changed, which reads "changed"; depends on a changed service, "depends on api"; same repository, "same repository as worker"; added, "added"; removed, "removed" (`SEL-1`, `SEL-11`, `FB-3`; `selection-01`, `selection-14`).
   - The plan also names what the save changes beyond restarts: toolbar features turned off or on (toolbar-shell's outcome lines), turning the config editor off, or returning a repository to its configured worktree when `[worktrees].enabled = false` (`SEL-11`, `FB-3`, `WORD-11`). Adding or removing an external service (`managed = false`) in a repository never disables worktree switching and produces no switch-block warning (`SEL-5`, `ACT-9`, `O7`; `status-11`, `manifest-hot-reload-2-03`).
3. **Watch the reload restart its set (the reload: one write; it stops and starts the restart set, and rolls back on failure).** The stack's terminal prints one line when the reload starts, naming every service it restarts with its reason: "Apply devhost.toml: restarting worker (changed), and api, web, docs, admin and search-index-rebuilder (same repository as worker)"; while it runs, it prints no exit line for the services it stops, because those stops are steps of the reload, never exits waiting for a restart (`FB-10`, `FAIL-5`, `WORD-7`; `feedback-06`, `feedback-15`, `language-12`, `status-07`). Every open page of the stack shows its progress in one place: no devhost surface on the page started a save from an editor, so the notice stack shows one activity line, "Apply devhost.toml · 2 of 6 restarted · 5 s", updated at least once a second; a Configuration window that saved the file shows the same progress beside **Save** instead, as config-editor specifies, and never both (`FB-1`, `WORD-4`, `STATE-1`; `feedback-01`). Each touched service shows restarting with its step, stopping, then starting with "health check 2 s of 30 s", then running, on its Services row and on the collapsed trigger's counts: devhost stops the whole set, dependents first, then starts it in dependency order, so at "2 of 6 restarted" api and web run again, worker waits on its health check, docs, admin and search-index-rebuilder wait their turn as queued, and the trigger reads "2 of 6 running · 4 restarting"; every service outside the set keeps its own state: a reload never draws the stack as down and never counts a service it replaces as failed (`ACT-3`, `ACT-4`, `ACT-2`; `status-01`, `status-02`, `status-05`). The reload keeps every page's status stream open, so nothing is drawn unknown during it (`ACT-5`, `HOLD-2`; `status-04`).
   - While the reload runs, a **Restart**, **Start** or Restart Changed of a service outside its set queues behind it on every page, reading "queued behind Apply devhost.toml" with **Cancel Restart** or **Cancel Start**, as services-panel draws it; a **Restart** of a service the reload restarts is unavailable with "api is already restarting · Apply devhost.toml" (`REV-12`); and a stack-wide write (Restart Stack, a switch) is unavailable with the reason "Apply devhost.toml is running · 2 of 6 restarted" as visible text and as each control's accessible description, never a dead button (`HOLD-3`, `SEL-7`, `MENU-3`, `HOLD-1`; `selection-11`, `review-15`, `interrupted-operations-05`).
   - A restarted service with a `process` health check counts as started only once it has run for `O28`'s 1 s stability window after it spawned; one that exits within that time (any exit code, including 0) fails the reload with its exit code and last lines (step 5), and the reload rolls back (`FB-5`, `O28`; `feedback-04`).
   - The changed mark of a restarted service clears against its new launch, and a file saved after that launch marks it again (`ACT-8`; `status-09`).
   - On failure, the activity line and the touched rows turn to the rollback's own words, "Restoring the accepted manifest · 1 of 2 started · 12 s", while devhost restores service by service: every service that ran before runs again, a service that was failing before keeps failing, and the set is never stopped as one unit because one member fails (`UNDO-1`, `ACT-3`, `FAIL-1`; `feedback-05`, `feedback-12`, `status-06`).
4. **Read the outcome (the operation record on `/__devhost__/ws/health`, read only).** The reload ends with exactly one outcome line in the stack's terminal and in its per-manifest log, verb first: "Applied devhost.toml: restarted worker (changed), and api, web, docs, admin and search-index-rebuilder (same repository as worker) · 6 of 6 running · 16 s"; "Applied devhost.toml: restarted api (changed) and worker (depends on api) · 6 of 6 running · 3.1 s" (worktrees off); "Applied devhost.toml: nothing restarted · 0.2 s" (`FB-3`, `FB-10`, `FB-7`, `WORD-4`, `WORD-5`, `WORD-8`, `CC-22`; `feedback-02`, `feedback-15`, `language-11`, `language-18`). It is certified only once the reload that read this saved version ended with every restarted service in the state the line reports, a `process`-health service after `O28`'s 1 s (`FB-5`, `REV-12`; `feedback-04`). It names the page's own service first on that page (`REV-10`). It prints only the URLs the reload added, changed or removed, "New: https://extra.shop.localhost/ · Removed: https://old.shop.localhost/", never the whole list, which `devhost stack info` (short alias `devhost status`, `O62`) prints on request (`FB-10`, `CC-22`).
   - In the browser, the outcome replaces the activity line as an outcome notice on a page whose own service the reload restarted, its origin at the end: "Applied devhost.toml: restarted web (this page's service; same repository as worker), worker (changed), and api, docs, admin and search-index-rebuilder (same repository as worker) · 6 of 6 running · 16 s · after devhost.toml changed on disk"; on any other page the activity line ends, the rows show the result and the stack's log keeps the line (`FB-2`, `FB-6`, `FB-7`, `SEL-3`; `feedback-02`). The notice closes after its calibrated `O14` reading time (`1.5 s + 0.3 s` per word, counting runs of letters and digits, clamped `4–15 s` — `13.2 s` for this 39-word notice), paused while pointer or focus is in it or `document.hidden` is `true`; if it arrives while the browser window is unfocused (`document.hasFocus()` is `false`, as for an editor-saved reload), its countdown waits until the browser window next gains focus (`O53`), whereas a notice arriving while focused keeps counting and moving focus into an embedded iframe where `document.hasFocus()` stays `true` never pauses it (`FB-6`, `O14`, `O53`). Its accessible description says it is also in the log, and it is announced once in the polite region (`FB-6`, `FB-9`; `feedback-14`).
   - When the reload restarted the page's own service and its dev server then reloads the page, reload-control's **Reload blocked** holds that reload while **Hold Reloads** is on and names the restart that caused it, from this record; the outcome names work it ended or put out of reach: Configuration window drafts a save that turned the editor off left behind, with the setting that brings the editor back, page context the reload could not restore, a held reload it discarded (`FB-4`, `UNDO-2`; `feedback-13`).
   - Adding or removing an external service (`managed = false`) whose folder lies in a repository keeps worktree switching enabled, leaves the external service untouched and marked `external`, and emits no switch-block warning — the outcome reports only what changed or "Applied devhost.toml: nothing restarted · 0.3 s" (`SEL-11`, `SEL-5`, `ACT-9`, `O7`; `status-11`, `manifest-hot-reload-2-03`).
   - While the crash view is open over the page, minimized or not, for a service the reload restarts, the view shows the reload's progress and outcome in place of its recovery actions' progress, "Apply devhost.toml · restarting api (changed) and worker (depends on api) · 3 s", and when the exited service runs again the view closes by itself, as `SURF-3` says, with the outcome notice "api is running again · Applied devhost.toml: restarted api (changed) and worker (depends on api) · 6 of 6 running · 3.1 s" in the notice stack and focus returned where `KEY-6` sends it (`SURF-3`, `FB-2`, `KEY-6`; `surfaces-02`, `journey-crash-to-fix-06`).

The stack still runs the accepted manifest." The file is relative to the root manifest's folder, an include named as "admin/devhost.toml:3:1", a schema problem keeps the file and line of the setting it concerns through the include merge, a cycle starts with its setting ("devhost.toml:15:13 not applied: services.api.dependsOn creates a cycle: api -> web -> api"), and a close key is offered when one exists ("did you mean "serve"?"); the raw parser text and Rust error chain stay behind **Copy Error** and in agent output's one `devhost: ERR:` line (`MENU-4`, `FAIL-2`, `WORD-9`; `language-16`).
   - Every open page shows the rejection as one condition notice, ranked with failures at the top of the notice stack (`ACT-7`, `FB-8`; `feedback-09`, `feedback-10`): "Manifest file not applied: devhost.toml line 12, column 8, services.api.port: expected a number. Paths are shown once, shortened with `~` or relative to the root manifest, and wrap inside the notice with the full path in the tooltip and accessible name, so nothing runs past the window's edge at any acceptance viewport (`SURF-9`, `WORD-8`; `surfaces-09`). The notice never sits under an open toolbar panel or docked chat (`SURF-1`).

6. **Fix at the file and line, or undo, and save (Edit or Copy; the save is step 1 again).** **Edit** opens the Configuration window on the file at the line, the failing lines marked, with the rejection in its banner until a reload of that file is accepted, and, after a crash, the crashed service's last lines (`MENU-4`, `SURF-4`; `selection-10`, `surfaces-04`); config-editor owns the window and its **Edit** target (`config-editor-09`). With the config editor off, **Copy** copies `file:line:column` (confirming "Copied devhost.toml:12:8" without "also in the log", `O14`) and devhost launches no external editor (`O51`, `MENU-4`, `MENU-3`, `SURF-15`; `surfaces-15`). The person saves, and step 1 runs again; its outcome replaces the rejection instead of the notice vanishing (`FAIL-4`, `ACT-7`; `feedback-09`):
   - A fix: "Applied devhost.toml: restarted api (changed) and worker (depends on api) · 6 of 6 running · 3.1 s" replaces the rejection in the terminal, the log and on every page (`FAIL-4`, `FB-3`).
   - An undo to the accepted text, which restarts nothing: "Configuration restored: devhost.toml matches the accepted manifest · nothing restarted" (`FAIL-4`, `UNDO-1`; `manifest-hot-reload-04`), and the devhost config file's own, "Configuration restored: config.toml matches the running shared Caddy settings · nothing changed" (`proxy-settings-04`).
   - There is no Undo save: the Configuration window's **Restore Running Version** writes back what runs and applies like any save, and an accepted save is undone by undoing the text and saving again, which reports its own reload (`UNDO-6`, `REV-10`; `review-06`, `feedback-12`).
   - Keys: **Edit** opens config-editor's Configuration window with focus in its text at the line, and focus returns as `KEY-6` says when it closes (`KEY-6`, `SURF-4`).
7. **Read the outcome as an agent or a script (`devhost reload`, `devhost stack info --wait` / `devhost status --wait`, the stack's log; read only, or one write for `devhost reload`).** `devhost reload` applies the manifest on disk to the running stack via `POST /__devhost__/reload`, the same reload a save starts (a reload with nothing changed reads "Applied devhost.toml: nothing restarted"), waits for its outcome by the `operationId` it sent, prints the outcome line of step 4 or the rejection of step 5, and exits 0 when applied and non-zero when not applied or when a restarted service exited, naming it with its last output line; `devhost stack info --wait` and its short alias `devhost status --wait` (`O62`) wait for a running reload and report the last operation's outcome (plus manifest-reload rejection state and changed-file markers); under `AGENT=1` every rejection is one `devhost: ERR:` line holding every issue with absolute paths (`FB-11`, `WORD-9`, `O62`, `CC-23`, `ACT-1`; `feedback-16`, `language-16`, `status-15`, `agent-cli-journey-02`). Every stack writes its per-manifest log, a foreground stack included, so a reload's outcome is readable from another shell (`FB-7`, `CC-21`). stack-run-stop builds these commands; this flow specifies what they report.

Branches and edge states:

- **A second save while a reload runs.** A newer save that validates supersedes the reload in progress: devhost lets the stop or start in progress finish, starts the remaining services from the newest manifest only, never starts a service the newer save removed and never prints the replaced edit's URLs, and prints one line, "Replaced by a newer save of devhost.toml at 14:02:07; applying it", before the newer reload's own start and outcome lines; the replaced operation's record ends as replaced, and every page's activity line follows the newer one (`REV-12`, `FB-10`; `review-15`, `interrupted-operations-05`). A newer save that does not validate supersedes nothing: the reload in progress finishes with its own outcome, and the newer save's rejection follows it.
- **A save made in the Configuration window during a reload.** It waits for the reload and is reported with its own reload, or as "Replaced by your next save", which config-editor draws beside **Save** (`REV-12`).
- **A save the file watcher did not see (`O42`).** On Rust `main`, `InputWatch::update` (`apps/devhost/src/services/watch.rs:232-272`) watches each input's `file.parent()` without resolving symlinks via `notify` FSEvents on macOS and `inotify` on Linux, so edits through symlinked manifest, include or `config.toml` files now go unseen on macOS as well as Linux (`manifest-hot-reload-08`), alongside symlinks replaced by regular files (`manifest-hot-reload-10`). Until config-editor's symlink-following watcher lands, and for any remote/shared-folder write the OS watcher misses, `O42`'s 5 s unseen-save timer (counted only while no operation holds the stack) ends the save's record as `unseen` and prints "devhost did not see this save; the stack still runs the accepted manifest. Apply it with devhost reload in ~/acme", while any version overwritten by a newer save ends as `replaced` (`O42`, `FB-5`).
- **A save while a service is already crashed.** The crashed service, unchanged by the save, keeps failing with its recovery page; the save applies to the rest and its outcome counts it: "Applied devhost.toml: restarted worker (changed) · 5 of 6 running · api still exited" (`REV-11`, `UNDO-1`, `FAIL-1`). The `error-pages-01` stopgap ships this first.
- **A save that restarts the page's own service while Hold Reloads is on.** The page never reloads; **Reload blocked** names the restart that asked for the reload, as reload-control words it; the outcome notice shows on that page (`FB-2`, `FB-4`).
- **A rejection about a worktree that is gone.** A rejection names the manifest path it was read from, relative to that worktree's root, and clears when the stack accepts a configuration from any worktree: a switch or a Return to Configured Worktree that succeeds records an accepted manifest and clears it, and no page shows a rejection for a file the stack no longer watches (`FAIL-4`, `HOLD-4`, `ACT-7`, `WORD-11`; `status-10`, `worktree-switch-08`). A rejected edit never makes its worktree unavailable (`HOLD-6`).
- **The lost connection.** A rejection or an outcome notice stays through the outage, and the page reads the reload's state again from the published record when the stream returns; notices-and-feedback owns the lost-connection notice. A save from an editor is not a page write, so it still applies while a page is disconnected; the Configuration window's **Save** is unavailable then, as config-editor draws it (`HOLD-2`, `ACT-5`, `FB-6`).
- **Remote browsers and chat that cannot take a message (`O36`, `O38`, `O54`, `HOLD-7`, `HOLD-8`).** A disk save from any editor on the host applies regardless, and this flow sends no chat message (`HOLD-5`). In the browser, under `HOLD-8`, `O36`, `O38` and `O54`, authenticated remote browsers (signed in with the shared-domain WebAuthn passkey or `devhost pair` fallback) use **Edit** and save through the Configuration window just like local browsers; an unauthenticated remote browser sees the unauthenticated toolbar state ("Sign in with passkey or pair this browser to use devhost here", `HOLD-7`, `O36`) and receives no configuration file contents (`O38`).
- **A rejected configuration and the stack's other actions.** Every action stays available; a control that starts services from the running manifest (Restart Stack, Start, Restart, Restart Changed) names the change not applied in its reach line, "uses the accepted manifest; devhost.toml line 12 is not applied", services-panel's line (`HOLD-6`).
- **A reload stopped by a stack shutdown.** Ctrl-C or `devhost stop` during a reload cancels it: shutdown owns the cleanup and launches no restoration, as today, and the reload's record ends cancelled, never failed (`FAIL-5`).
- **A lost response or a repeated request.** `devhost reload` and the Configuration window read the reload's outcome from its record by the `operationId` they sent and never send the save or the reload again; a request repeated with that ID returns the record and runs nothing (`REV-12`, `ACT-1`).
- **Agents at work.** A reload asks about no agent, because starting or restarting services ends nothing of an agent's; chat sessions stay connected through it, as `stacks/hot-reload.md` documents (`REV-3`).

## Backend and contract changes

**Backend** (the services runtime in `apps/devhost/src/services/`, the manifest reader in `apps/devhost/src/manifest/` and the control server in `apps/devhost/src/devtools/`, preserving the owner rule that every setting applies through hot reload without a question, the checks before anything stops, the accepted manifest running while an edit is rejected, the rollback, `O9`'s restart scope, `O7`'s non-blocking external services, one operation at a time per stack, the run's selection, and every page's status stream):

1. **One plan with reasons.** `affected_services` and `expand_dependents` (`apps/devhost/src/services/stack/runtime.rs:804-832,1232-1275`) return each affected service with its reason (`changed`, `dependsOn` naming the dependency, `sameRepository` naming the service that pulled the repository in, `added`, `removed`), plus non-restart changes such as toolbar feature toggles or a return to the configured worktree (never emitting an external-service worktree-switch block under `O7`); the same function serves the reload, `Runtime::check_config` (`apps/devhost/src/services/stack/runtime.rs:217-262`, which today validates without computing the restart set) and `devhost reload --dry-run`. Serves `manifest-hot-reload-01`, `config-editor-05`, `manifest-hot-reload-2-03`. Required. Contract: `CC-37`.
2. **The reload as an operation record.** The reload opens an operation record (`ACT-1`) of kind `reload` with its file, its origin (`watcher`, or the page ID and `operationId` of a Configuration window save, or the CLI for `devhost reload`), its targets with their reasons, each target's step (`stopping`, `queued`, `starting`, `healthCheck` with `elapsedMs` and `timeoutMs`, `running`, `failed`) streamed on `/__devhost__/ws/health` at least once a second, its outcome (`applied`, `notApplied`, `restored`, `replaced`, `unseen`, `cancelled`), a `rollback` with its own steps and outcome, the content hash of every file version it read so a save's outcome resolves from the reload that read it (`REV-12`), or from config-editor's Backend 12 `unseen` end (`O42`), and its start and end times; the services-panel redesign builds the record and the rows that read it. Serves `manifest-hot-reload-01`, `interrupted-operations-05`, `journey-crash-to-fix-06`. Required. Contract: `CC-37`, `CC-25`.
3. **Supersede instead of queue.** While a reload runs, the watcher keeps the newest event (`InputWatch::poll` in `apps/devhost/src/services/watch.rs:278-310` keeps one `pending` instant, while the main loop in `apps/devhost/src/services/stack/runtime.rs:152-175` blocks on `reload_disk()` during a reload); when a newer save validates, the running reload stops launching services of the replaced manifest after the step in progress, the newer reload starts from the newest manifest only, and the replaced record ends `replaced` naming the newer one; a newer save that does not validate leaves the running reload alone. Serves `interrupted-operations-05`. Required.
4. **One structured error.** Manifest parsing (`apps/devhost/src/manifest/diagnostics.rs:5-51`), schema checks (`apps/devhost/src/manifest/validation.rs:116-148,1107-1111`), validation, claims, the port probe and start failures return `{file, line, column, key, message, excerpt, suggestion}`, the file relative to the root manifest's folder, keeping each setting's source file and line through the include merge (today `diagnostics::parse_error` prints `"Failed to parse <abs>: toml: line ..."` with neither column nor include-relative path, and `reject_unknown` carries only the key path); a cycle error (`apps/devhost/src/services/resolve.rs:124-150`) names `services.<name>.dependsOn`; `configuration[].error` on the health stream (`apps/devhost/src/services/stack/live.rs:157-179`) carries the object instead of the raw string, with the source manifest path it was read from; agent output (`apps/devhost/src/cliout.rs:234-261`, which today prints continuation lines with a bare `devhost:` prefix) joins every issue into one `devhost: ERR:` line. Serves `stack-run-stop-09`, `manifest-hot-reload-03`, `manifest-hot-reload-02`. Required. Contract: `CC-37` (the `config/validate` problems), `CC-23`.
5. **Probe fixed ports before stopping.** Before stopping anything, the reload probes each new or changed fixed port on its bind host, both loopback addresses included, for a listener the stack does not own (extending `claim_fixed_port_with_options` at `apps/devhost/src/caddy/routes.rs:158-229` and `Runtime::reserve` at `apps/devhost/src/services/stack/runtime.rs:995-1033`, which check claim files only today), and names the listening program and PID using `read_listening_process_ids_for_bind_host` (`apps/devhost/src/services/containment.rs:479-509`); when a health check fails on a fixed port, the failure checks who owns the port and names that program. Serves `manifest-hot-reload-05`, `error-pages-06`. Required.
6. **A crash's evidence kept with its rejection.** The rejection of a reload whose service exited carries that service's exit code or signal, time, frozen last output lines (services-panel's per-service lines, frozen at the exit, replacing the 512-line stack-wide ring at `apps/devhost/src/services/stack/live.rs:384-399` as the only store), and what devhost ran (command, folder, manifest file and line), for as long as the rejection lasts. Serves `journey-crash-to-fix-03`. Required.
7. **One outcome line for every finished reload.** The manifest and config watch handlers in `apps/devhost/src/services/stack/runtime.rs:152-200` and `LiveState::configuration_reloaded` (`apps/devhost/src/services/stack/live.rs:167-179`) classify every finished reload (`applied`, a new rejection, a repeated rejection with its count, `restored`) instead of suppressing identical error text via `error != last_manifest_error`, and log one line for every kind and both sources, the devhost config file included; `Runtime::apply`'s early return for a manifest equal to the accepted one (`apps/devhost/src/services/stack/runtime.rs:728-734`) reports `restored` when a rejection was pending; `log_service_urls` (`apps/devhost/src/services/stack.rs:2052-2074`, called at `apps/devhost/src/services/stack/runtime.rs:948`) prints only URLs added, changed or removed after a reload. Serves `manifest-hot-reload-04`, `manifest-hot-reload-07`, `proxy-settings-04`. Required. Contract: `CC-22`.
8. **A reload's stops are its steps.** Services a reload stops are published as restarting with the step `stopping`, and the exit watcher (`apps/devhost/src/services/stack/runtime.rs:85-95`) logs no exit for them; the same change serves worktree-switch's switch stops. Serves `journey-crash-to-fix-06`. Required. Contract: `CC-24`.
9. **A rejection belongs to the configuration it was read from.** A successful worktree switch or Return to Configured Worktree records an accepted manifest result (today `Runtime::switch_worktree` calls `self.apply(..., Change::Switch)` at `apps/devhost/src/services/stack/runtime.rs:567-573` without calling `configuration_reloaded`), so it clears a rejection, and the health stream never publishes a rejection for a file the stack no longer watches. Serves `worktree-switch-08`. Required.
10. **`O28`'s window for `process` health, and the report of `O42`'s unseen saves.** `wait_for_service_health` (`apps/devhost/src/services/health.rs:82-84`) waits `O28`'s decided 1 s stability window after spawn for `HealthKind::Process` instead of a single immediate `check_exited` check; any exit within 1 s fails the reload with its exit code and last lines and triggers rollback. Separately, config-editor's Backend 12 ends a written save that no reload read within `O42`'s decided 5 s idle-only window as `unseen` (or `replaced` when a newer save supersedes it); this flow prints and shows that outcome for a save from another program. Serves `config-editor-05`. Required.
11. **`devhost reload` and its dry run.** `devhost reload [--dry-run] [--stdin <file>]` calls `POST /__devhost__/reload` with a lowercase UUID `operationId` through the stack's control server, waits for its record and prints its outcome in both outputs with the exit codes `CC-23` gives; `--dry-run` reads Backend 1's plan and changes nothing; `devhost stack info --wait` (short alias `devhost status --wait`, `apps/devhost/src/services/stack_info.rs`, `O62`) reports the last operation, manifest-reload rejection state and changed-file markers; every stack writes its per-manifest log, a foreground stack included (`CC-21`). The stack-run-stop redesign builds the commands and the log; this flow defines what they report. Serves `agent-cli-journey-02`. Required. Contract: `CC-21`, `CC-23`, `CC-37`.
12. **Per-service rollback.** `Runtime::apply`'s failure path (`apps/devhost/src/services/stack/runtime.rs:871-913`) restores service by service instead of stopping and blocking the whole group at lines 893–899, and a service that was failing before the save and is unchanged by it is never a condition of the reload's or the rollback's success, as the `error-pages-01` stopgap ships first; while it restores, each touched service publishes the step `restoring`. Serves the rollback half of `journey-crash-to-fix-03` and builds on the stopgap. Required. Contract: none beyond the stopgap.

## Recommended priority

**P2, with the `error-pages-01` stopgap shipped first as a P0 fix.** The realistic trigger is every manifest save: with worktrees on, the default, one environment variable on one service restarts every service of its repository for about 16 s while the terminal prints the same `configuration reloaded:` line and URL list it prints for no restart at all (`manifest-hot-reload-01`); every typo or half-finished save from an editor or an agent is a raw parser error with no file or line that a busy service scrolls away in about a minute (`stack-run-stop-09`, `manifest-hot-reload-02`); and the most common fix, an undo, prints nothing, so the terminal keeps saying the edit was rejected (`manifest-hot-reload-04`). The costs are time and misread state rather than lost files: the accepted manifest keeps running and a failed restart rolls back, so a person who misreads a rejection debugs the wrong thing and a person who misreads the silence restarts the stack for nothing; the one path that takes healthy services down, a save while a service is already crashed, is the `error-pages-01` stopgap's to fix first. Manifest saves are less frequent than code edits and service restarts, which services-panel's P1 covers, and more frequent than switches. Ship first the slice that needs only the reload loop and the terminal: one outcome line for every finished reload (applied with each restart's reason, not applied, not applied again, Configuration restored), no exit lines for the reload's own stops, and no URL list after each reload; it needs no page change and closes `manifest-hot-reload-04`, `manifest-hot-reload-07` and the terminal half of `manifest-hot-reload-01`. Then the structured error with the port probe, which the terminal, the rejection notice (with **Edit** when config editor is on, or file and line with **Copy** when off, plus **Copy Error**), and config-editor's banner all read; then, once services-panel's operation record ships, the activity line, the rows, the queue behind a reload, supersede, the report of `O42`'s unseen saves (config-editor builds the timer), and the outcome notice (`O14`, `O53`); `O28`'s 1 s window ships in the same release as the not-applied report that names the exit and its last lines, so no release rolls back a save without saying why. Last, `devhost reload` (`POST /__devhost__/reload`) and its dry run with stack-run-stop, `O62`'s `devhost stack info` / `devhost status`, and the docs and skill text. Dependencies: this redesign is blocked by the services-panel and notices-and-feedback foundations, which ship first or with the slice that needs them (the terminal slice needs neither): services-panel provides the operation record, the published states, the per-service frozen output lines and the queue, and draws the rows this flow's reload touches; notices-and-feedback provides the notice stack, the announcer, `O14`/`O53` timing and the dismissal marker's model, and draws this flow's activity line, outcome and rejection notices.
