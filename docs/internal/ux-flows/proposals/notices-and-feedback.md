# How devhost reports operations and problems: proposed experience

Diagrams: [current](../notices-and-feedback-current.html), [proposed](../notices-and-feedback-proposed.html). [Wireframe](../wireframes/notices-and-feedback.html).

Status: design proposal, not implemented behavior. The [shared UX pattern reference](../patterns.md) wins where this proposal disagrees with it.

Source revision: alexgorbatchev/devhost `190a8bb53e8cd903d2db0a92cb0886f29671607f` (Rust main); the shared supervisor's stop path, stack IDs and stop order are cited at `bc33e2f1`. Features: TB-07. Redesign ticket: tracked privately.

Product rule: the owner's rules make several behaviors around feedback intended. A failed service leaves the rest of the stack running (`stacks/recovery.md`: "a service that crashes, times out, or returns errors does not take the stack down with it"); devhost never opens a browser; **Delivery unconfirmed** and the refusal to resend a chat message are intended; human output and agent output (`AGENT=1`) differ on purpose; and the one explicit exception to devtools host-page isolation is that devhost prefixes the app page's tab title while a waiting agent or a failure persists and restores the app's own title when cleared (`O16`, `ACT-7`). `guides/devtools.md` already states the principle this flow extends to the whole toolbar: the readouts "hide while the page has lost its connection to devhost, so a stale number never passes for a current one." So a stopped stack that the page cannot start by itself, a chat send that does not claim a delivery the agent never confirmed, and terminal lines laid out differently from the toolbar's are intended, not defects. The gap is around them: no two operations report their result the same way, a success says nothing, a failure vanishes within 0.2 s or never leaves, every notice interrupts a screen reader as an alert while no recovery is ever announced, a lost connection draws every service as crashed with live **Restart** buttons whose errors are the proxy's HTML, and closing one secondary port of a command-mode serve session paints healthy sibling ports as a false `0/3` outage.

## Target experience

The person presses **Restart** on api, **Restart Stack**, **Switch and Restart Stack**, **Save** or Alt+Ctrl+R. The control they pressed keeps focus and says what runs ("Restarting api…"); the surface that started the work shows each target's step with the elapsed time, and if they close that surface, or the work started in another tab, the terminal, an agent or a file saved on disk, one activity line in the notice stack beside the bar carries it instead: "Restart Stack · 2 of 6 started · 5 s". The work ends with exactly one outcome, where its progress was, in the words of the control that started it: "Restarted Acme Shop · 6 of 6 running · new automatic ports for api and web · 14 s". It is announced once, closes by itself after its calibrated reading time (`1.5 s + 0.3 s/word`, clamped `4–15 s` — 6.3 s for that 16-word sentence) once the pointer and focus leave it while the page is visible (pausing before counting if it arrived while the browser window was unfocused, `O14`, `O53`), stays readable in the stack's log, and the same line prints in the stack's terminal. A failure names its target, the cause in plain words, the evidence and the action that fixes it, and stays until the person dismisses it or the same operation succeeds, whatever the status stream does in between. Conditions that need the person (a crash, a manifest file not applied, a blocked repository, an agent waiting, a held reload, a lost connection or a closed command-mode port) are notices that start and end with the state that caused them, in one order, at most three at a time with **2 More**, adapting cleanly down to a 320 CSS px phone layout (`O8`); while a waiting agent or a failure persists, both app pages and devhost's own pages prefix their tab title and restore it when cleared (`O16`). When the stack stops, the page says so while it happens and after: "Stopping Acme Shop · 3 of 6 stopped", then "Acme Shop stopped at 16:24 by devhost stop. Start it with devhost start in ~/acme"; every service keeps its last known state drawn as unknown with the time it was last seen, never down, and every write is unavailable with that one sentence. When a single secondary port closes in a command-mode `devhost serve` session while sibling ports remain healthy, that tab shows a targeted port-closed notice with **Open** links to the remaining active URLs instead of a false `0/3` outage (`serve-command-05`). When the connection returns, the page says "Connected again · 6 of 6 running" once and clears what the outage raised. Most operations start or stop processes and cannot be taken back, so there is no Undo: each outcome says what changed, a failed Restart Stack or switch reports its own rollback, and every outcome stays in the log. Benchmarks: VS Code shows a task's progress where it started and in its status bar, caps visible notifications at three and keeps dismissed ones in its notification center, and VS Code Remote shows "Reconnecting…" over the last known state instead of an outage; GitHub Desktop keeps one progress line and turns it into the outcome; Vite prints "ready in" and "server connection lost, polling for restart"; `docker compose up --wait` and `kubectl rollout status` certify readiness, not a step; Kubernetes marks pods Unknown, not Failed, when it loses their node; the WAI-ARIA `status` and `alert` roles and WCAG 4.1.3 set what is announced and how politely. Competitor behavior is evidence here, never a requirement.

## Target steps

Today: 5 steps, the last a guess: press, watch a spinner that shows only while the panel stays open, see every service red for a second at the end of Restart Stack, see the count come back with no result, then reload or read the terminal to be sure. Proposed: 3 steps: press (the control keeps focus), follow the progress in place or as one activity line, read one outcome where the progress was. A failure adds one step taken in place: its lead action.

This flow is the progress and outcome foundation. It owns the notice stack, activity lines, outcome and condition notices, the announcer and the lost connection (TB-07), and it claims what the reference lists under "Work no flow owns" for it: the announcer and its move into the topmost modal (`FB-9`), the notice stack's order and **2 More** (`FB-8`), and the operation record's model and its readers (`ACT-1`). It ships five shared pieces that the other flows cite: the **notice stack component** (failure, condition, activity, success and neutral variants, built on the project's `Alert`, with the 320 CSS px phone layout of `O8`), the **announcer**, the **page-side operation store** (the IDs a tab sent, the outcomes read from the record, kept across reloads), the **shared request helper** (one sentence for any failed request, the original behind **Copy Error**), and the **outcome sentence builders**, which live in services-panel's shared module of state words and labels under `packages/devhost-ui/src/` with their Rust counterpart in `apps/devhost/src/cliout.rs` (`WORD-4`, `SURF-14`).

1. **Start an operation (`POST` with an `operationId`, one write).** Every write a page sends (a row's **Restart**, Restart Changed with its badge icon and Alt+Ctrl+R, **Start**, **Restart Stack**, **Switch and Restart Stack**, **Return to Configured Worktree**, **Save**, and **Send** in the Disable Reloads popover) carries an `operationId`, a lowercase UUID the page generates, and the page ID of this page load; the route answers `202 Accepted` with the operation record before the operation runs (`ACT-1`, `CC-37`, `WORD-11`). The page-side operation store keeps each ID the tab sent in `sessionStorage`, so only this tab treats the operation as its own and a page reload in the middle keeps following it (`ACT-1`). The pressed control keeps focus as the busy control, `aria-busy` and `aria-disabled`, never `disabled`, its label naming what runs ("Restarting api…", "Restarting Stack · 2 of 6 started"), drawn with toolbar-shell's unavailable and busy state of `Button` (`KEY-11`, `FB-9`, `WORD-4`). The announcer says the start once, in its polite region: "Restarting api" (`FB-9`).
   - Defaults: the operation's name is the label of the control or the command that started it, the same on every surface (`MENU-6`, `WORD-2`); a key or an icon acts on the set its control names and its outcome names that set (`SEL-1`): Alt+Ctrl+R is Restart Changed, on "api, web" when they are changed, else on its named fallback, the page's own service, "docs" on the docs page (`SEL-2`, `O4`).
   - Writes that ask first ask where their own flow says (`REV-1`); this flow adds no question, and no question ever sits in a notice: a decision lives in its panel, popover or dialog, and a notice carries one sentence and its actions (`REV-4`, `SURF-2`). The Disable Reloads popover anchors to the hot reload notice, which is a notice and never the question itself (`REV-5`, `O2`).
   - A key whose action is unavailable reports why instead of doing nothing: while Restart Stack runs, Alt+Ctrl+R shows the neutral notice "Restart Changed did not run: Restart Stack is running · 3 of 6 started", which closes after `O14`'s calibrated reading time (pausing for pointer, focus, hidden page, or unfocused arrival per `O53`) and stays in the log (`MENU-3`, `HOLD-3`, `FB-6`, `WORD-7`, `O14`, `O53`).
   - Keys: this step adds none; each control's own key starts it (2.11).
2. **Follow its progress in one place (`/__devhost__/ws/health`, read only).** While the surface that started the operation is open, that surface shows its progress: each target with its step (queued, stopping, starting, "health check 2 s of 30 s", running, failed), updated at least once a second, and the busy control with the elapsed time (`FB-1`, `ACT-3`, `STATE-1`). Whenever no open surface on the page shows the operation, because its surface closed or because it started in another tab, the terminal, an agent or a file saved on disk, the notice stack shows it as one activity line: the operation, its target, the targets done of the total and the elapsed time, joined by " · ", "Restart Stack · 2 of 6 started · 5 s", with its origin at the end when it came from elsewhere, "Restart api · health check 2 s of 30 s · from the terminal" (`FB-1`, `WORD-4`, `WORD-5`, `ACT-1`). Reopening the surface moves the progress back into it and removes the activity line, so progress shows in one place at a time. The rows the operation touches show restarting, starting or stopping on every surface, every other service keeps its own state, and starting one service never draws the running ones as down (`ACT-3`, `ACT-4`, `SEL-7`); services-panel draws those rows and dots from the published state (`ACT-2`). The step text and elapsed times update in place, outside every live region, so nothing ticks aloud (`FB-9`).
   - Closing a panel by Escape, a click outside it or Tab past its last control moves its operation's progress to the activity line (`KEY-7`, `KEY-8`).
   - An activity line has no Dismiss: it ends when its outcome replaces it (`FB-2`).
3. **Read one outcome where the progress was.** The outcome replaces the progress in the same place: in the surface that started the operation while it is open (a panel stays open through the progress and the outcome, `SURF-2`), otherwise as an outcome notice in place of the activity line, never both on one page (`FB-2`). It names the operation in the past tense, its target set, what changed and the time it took, then details after " · " (`FB-3`, `WORD-4`, `WORD-8`):
   - a row's **Restart**: "Restarted api · 2.6 s";
   - Restart Changed: "Restarted api and web · 4.1 s", or with its fallback "Restarted docs · 2.2 s", naming exactly the set it restarted (`SEL-1`, `SEL-2`);
   - **Restart Stack**: "Restarted Acme Shop · 6 of 6 running · new automatic ports for api and web · 14 s", counting of the stack's total (`ACT-6`, `WORD-5`);
   - a switch: both worktrees by their labels, "Switched to fix-nav ~/acme/.worktrees/fix-nav from main ~/acme · 6 of 6 running · 9.8 s" (`SEL-4`, `WORD-11`; worktree-switch words it);
   - a save or a file changed on disk: "Applied devhost.toml: restarted api (changed) and worker (depends on api) · 6 of 6 running · 3.1 s", or "Applied devhost.toml · nothing restarted · 0.4 s" (`REV-10`, `O9`; manifest-hot-reload and config-editor word it);
   - a chat Send: the outcome stays on the sent message in the conversation, naming the conversation it went to, "Sent to Fix the nav · Claude Code", and the delivery the agent confirmed, never more: without an acknowledgement the message keeps **Delivery unconfirmed** and is never resent (owner rule) (`SEL-8`, `FB-5`, `REV-12`; agent-chat draws it); chat's receipt stays the turn's one outcome (`FB-1`).
   - A success certifies the end state, never a step (`FB-5`): a start or restart once each target passed its health check with no leftover of a killed run answering in its place (`ACT-11`), a save once the reload that read that saved version ended with its services in the states the outcome reports (`REV-12`), a switch once the target worktree's services run (`WORD-11`), a stop once no process, route or port claim of the stack remains, a Disable Reloads request once its turn ended, its notice keeping "Request sent to Claude Code · working" until then (`O24`; reload-control words it). Until then the operation is in progress, and no surface infers a result by counting reloads or health messages (`ACT-1`).
   - It names the work the operation ended, discarded or left behind (`FB-4`): "· ended 1 conversation: Fix the nav (working)", "· 1 held reload discarded"; a conversation a stop ended stays listed and can be resumed (`UNDO-4`).
   - Lifetime (`FB-6`, `O14`, `O53`): a success outcome notice closes by itself after its calibrated reading time — `1.5 s + 0.3 s/word`, clamped to `4–15 s`, counting words as runs of letters and digits (not spaces, so paths are not undercounted) — for example `4 s` for "Restarted api · 2.6 s" (5 words), `6.3 s` for "Restarted Acme Shop · 6 of 6 running · new automatic ports for api and web · 14 s" (16 words), and `6.9 s` for "Applied devhost.toml: restarted api (changed) and worker (depends on api) · 6 of 6 running · 3.1 s" (18 words). The **Undo** replacement after dismissing a notice stays `4 s` (`O14`); keyboard **Dismiss** moves focus onto **Undo**, and pointer **Dismiss** keeps the smaller Undo replacement anchored under the pointer so its countdown does not start immediately. Both pause while the pointer or focus is in the notice or while the page is hidden (`document.hidden`). A notice that arrives while the browser window is unfocused (`document.hasFocus()` is `false` at arrival) pauses its countdown until the browser window next gains focus (reading `document.hasFocus()` at arrival and on `blur`, `focus`, and `visibilitychange`, never `blur` alone so embedded frames inside the app do not pause it); a notice that arrived while the browser window was focused keeps counting down as `O14` says even if the person switches windows while the page stays visible (`O53`). A success shown in the surface that started it stays until the person leaves that surface. Every action or link in a notice that closes by itself has an untimed equivalent: logged operation outcomes stay readable in the stack's log and carry "also in the log" in their accessible description (`FB-7`), while page-only outcomes with no log line (copying, sharing a tab, reconnecting, or a turn-end reload) omit "also in the log" (`O14`). Each outcome is announced once, in the polite region (`FB-9`).
   - An operation this page did not start gets an outcome notice only when it failed or its target set included the page's own service (`SEL-3`), ending with its origin as the backend saw it: "Restarted api · 2.6 s · from the terminal", "· from another tab", "· from Claude Code, conversation Fix the nav" for an agent devhost started, "· after devhost.toml changed on disk" (`FB-2`, `ACT-1`, `WORD-4`); otherwise its rows and the log show it. Outcomes name the stack, services and worktrees by name, never by an ID (`WORD-1`, `WORD-4`, `WORD-11`).
   - Across the page reload an operation causes (a switch, **Restart Stack** on a recovery page, or a turn-end reload under `O57`), the next page in the same tab reads the outcome from the record (or turn-end reload marker) by the ID the tab stored and shows it once (`FB-2`, `ACT-1`); focus starts on the control that started it when the new page shows it, else on the outcome's sentence (`KEY-6`). When a chat turn that changed files ends while **Hold Reloads** is on (and reloads have not been disabled under `O56`, and focus is not in a text field or chat's composer), devhost applies the held reloads once as its own reload and the reloaded page shows "Reloaded to show Claude Code's change" once, announced politely once (`O57`, `FB-2`, `FB-9`, `FB-12`; closing after `O14`'s calibrated time without "also in the log"), while chat's receipt stays the turn's one outcome. No page greets its load with an older success: a page shows a success at load only for an ID this tab stored, and never one older than that success's own `O14` lifetime, while a failure not yet handled shows on every page that loads (`ACT-1`, `FB-6`, `O14`).
4. **Read a failure and recover in place (one write per retry).** A failure leads with the target and what happened in plain words, then the cause, the evidence and where to fix it, each once (`FAIL-2`, `FAIL-3`, `WORD-7`): "api exited with code 1 at 14:02 before its health check", its last output lines, the probe it failed or the program holding its port, and what devhost ran. It stays, in its surface and as a failure notice once that surface closes, until the person dismisses it with **Dismiss** (accessible name "Dismiss api's failure") or the same operation succeeds on the same target; status-stream messages, reconnects, closing the surface, switching files and page reloads never remove it, because the record keeps it (`FB-6`, `ACT-1`). Today's toolbar-wide error, which the status stream clears on every message, disconnect and reconnect, goes away: each failure is the outcome of its own operation (`notices-and-feedback-01`). Page-only failures with no backend operation (such as a blocked Redux popup or library launcher error from `third-party-devtools`) follow the same failure-notice form and assertive announcement without a log line.
   - Focus stays on the control that started the operation while that control exists, and the failure becomes its accessible description; when the outcome replaces the control (a confirmed question's place), focus moves to the outcome's sentence, a `tabindex="-1"` element named by it, never to an action, so a repeated Enter cannot start a second write (`KEY-11`, `FB-9`). The announcer says the failure once, in its assertive region, which carries failures only (`FB-9`).
   - Lead action by cause, first, with the others beside it (`MENU-5`): an exited service leads with **Restart**, with **Logs** and **Edit**, and **Edit** leads after a retry fails the same way; a stopped stack leads with its start command and **Copy** (`HOLD-2`); an unreachable external service with **Check Again**; a blocked worktree with **Return to Configured Worktree**, choosing another worktree and **Check Again** (`WORD-11`, `O43`); a manifest file not applied with **Edit**, or the file and line with **Copy** beside **Copy Error** while the config editor is off (`MENU-4`, `WORD-2`; editor integration is removed under `O51`). No failure is drawn without a way forward.
   - A response devhost cannot read never shows: no response body, markup, raw Rust error chain, Rust's transport error or the same path twice (`FAIL-2`, `SURF-9`, `STATE-4`). The shared request helper, used by every control request and by the configuration client, turns each failed request into one sentence: a JSON error from the control server keeps its message; a `403` from an unauthenticated remote browser reads "Sign in with passkey or pair this browser to use devhost here" (`HOLD-7`, `O36`); an HTML or other non-JSON answer from the proxy means the stack is not running, "Acme Shop is not running, so api was not restarted. Start it with devhost start in ~/acme"; a request that cannot connect means the proxy is not reachable, "devhost's proxy is not reachable. Start it with devhost caddy start"; any other answer names the operation and the status, "Restart Stack failed: devhost answered 500 · see the stack's log"; the original text stays behind **Copy Error** (`HOLD-2`, `WORD-7`, `journey-new-project-02`, `notices-and-feedback-01`).
   - A partial result counts every target and is never a plain success or failure (`FAIL-1`): "Restart Stack: 5 of 6 running · api exited with code 1 before its health check", styled and announced as a failure with api's lead actions; a rollback reports its own outcome in its operation's words, naming what it put back (`UNDO-1`): "Restored the services as they ran before Restart Stack: 5 of 6 running · api still fails".
   - A failure whose cause repeats updates its own report instead of adding another: "api exited with code 1 · 2 times, last at 14:05" (`FAIL-4`).
   - A deliberate stop, cancel or replacement is never a failure (`FAIL-5`, `WORD-7`, `CC-24`): services devhost stops for a restart, Restart Stack, a switch, a reload or a shutdown are steps of that operation; a service a person stopped reads "Stopped by you", "Cancelled the queued restart of worker" reports a cancel, and both take the neutral style, never the failure look and never the assertive region.
   - A write refused because the view was stale shows the refusal with the current state and redraws from it (`REV-13`): "worker was not restarted: devhost.toml no longer defines it"; an open question whose action becomes unavailable closes and says why (`HOLD-1`); a refused save keeps its draft (config-editor).

Each leads with `MENU-5`'s action for its cause (a condition whose target lives outside the browser, such as a terminal-started waiting agent, renders with **Dismiss** alone); the words of each are its owning flow's, and this flow owns the form, the order, the lifetime, the tab-title prefix and the announcements:

   - Order (`FB-8`, `ACT-7`): (1) what needs the person or blocks writes: the crash notice, failures, a configuration not applied, devbox not trusting devhost's local certificate authority (after a rejected configuration, `ACT-7`), a blocked repository, an external service not reachable, an agent waiting, the lost connection or closed command-mode port; (2) activity lines; (3) other conditions: **Reload blocked**, chat off with conversations still running, and the hot reload notice with a pending Disable Reloads request; (4) successes and neutral notices; newest first within a group. At most three notices show; the rest fold into one **2 More** control (title-style per `WORD-3`) that expands the stack in place, `aria-expanded="true"`, and reads **Show Fewer** while expanded. Example: with api's crash notice, a Restart Stack activity line, **Reload blocked** and two successes live, the stack shows the crash notice, the activity line and **Reload blocked**, then **2 More** (`FB-8`).
   - Place (`SURF-1`, `CC-1`, `SURF-9`, `O8`): the notice stack fills toolbar-shell's notice slot beside the bar, between the bar and every other devhost surface, in both corner placements; no toolbar panel, docked chat or the Configuration window covers it, so every notice's buttons answer native hit testing at every desktop/zoom acceptance viewport (`1600×1000`, `1280×800`, `900×900`, and `1280×800` at 200% zoom). Down to **320 CSS pixels** wide (phone layout, `O8`), notices span the viewport width minus 8 px horizontal insets on each side, stack cleanly above or below the compact bar with wrapped text and wrapped action rows (every action and **2 More** / **Show Fewer** at least 24×24 CSS px), never overflow horizontally, and stay unobstructed alongside mobile chat and approval prompts (`O8`, `SURF-9`, `FB-12`). The hot reload notice keeps its place and stays visible while the Disable Reloads popover is anchored to it, with its pending request naming the agent (`REV-5`, `O2`).
   - Tab title (`ACT-7`, `O16`): while a waiting agent or a failure persists, devhost prefixes the browser tab's title on **both app pages and devhost's own pages** (such as `"(1) waiting · Acme Shop"` or `"(1) failed · Acme Shop"`), tracking any title updates the app makes while prefixed, and restores the page's exact own title as soon as every waiting agent is answered and every failure is cleared or dismissed.
   - Dismissal (`SURF-8`, `UNDO-3`): dismissing a condition notice whose condition persists leaves a marker on the control that owns the condition until it ends: "1 not applied" on **Config** for a manifest file or the devhost config file not applied while the config editor is on, else on the stack name, which is always on the bar; the untrusted certificate authority's marker on the stack name; the held count on **Hold Reloads** for **Reload blocked**. A marker appears only once its notice is dismissed, because while the notice shows it is the one report (`FAIL-4`); activating the marker shows its notice again. The lost-connection and closed-port notices have no **Dismiss**: they are the reason every write on this page is unavailable, and the trigger shows the same state.
   - Collapsed toolbar (`SURF-8`, `FB-1`): every condition notice, failure and running operation's activity line keeps a one-line form beside the collapsed badge, its first clause and its lead action ("Manifest file not applied: devhost.toml line 12 · Edit", "Lost connection to devhost; retrying · Retry Now", "Restart Changed · web · 0 of 1 restarted · 2 s"); only successes stay out of sight there and in the log; toolbar-shell places the forms and draws the badge, whose look follows `ACT-7`'s order and never shows a routine restart as failed (`ACT-3`).
   - Form (`FB-9`, `ACT-13`): a notice carries no live role; it is a group named by its sentence, so inserting or updating one announces nothing by itself, and the announcer alone speaks. The project's `Alert` stops rendering `role="alert"` for every tone (`packages/devhost-ui/src/components/ui/Alert.tsx:27` today), and the copy-error line's nested `role="status"` goes (`packages/devhost-ui/src/devtools/shared/components/InlineNotice.tsx:100-107`). Each notice kind (failure, condition, lost connection, activity, success, neutral) has its own icon and its kind's word in its accessible name, distinct in forced colors, and meets 4.5:1 text and 3:1 control-boundary contrast in both themes (`ACT-13`). State words come from the shared state-words module, one word per state (`WORD-6`), and long paths wrap or shorten in the middle with the full path in the tooltip and accessible name (`WORD-8`, `SURF-9`).

## Backend and contract changes

**Backend** (the services runtime in `apps/devhost/src/services/`, the control server in `apps/devhost/src/devtools/` and terminal output in `apps/devhost/src/cliout.rs`, preserving the recovery contract, one operation at a time per stack, the accepted manifest, the documented reconnect back-off of 1 s up to 10 s, devhost's own reloads never being held, and the two output contracts):

1. **The operation record for every operation.** Every write route in `apps/devhost/src/devtools/server.rs` takes `operationId` (a lowercase UUID the caller generates) and the page ID each page load sends with every request, and answers `202 Accepted` with the record: `id`, `kind`, `targets`, `origin` (`page` with its page ID and hostname, `cli`, `agent` with the `DEVHOST_CHAT_SESSION` conversation when devhost started the agent, or `watcher` with the changed file), each target's `step` (with `elapsedMs` and `timeoutMs` while it waits on a health check) and `outcome` (`result`, `cause`, `evidence`), the work it `ended` (conversations with their state, drafts, held reloads), `startedAt` and `endedAt`; the record streams on `/__devhost__/ws/health` (`apps/devhost/src/devtools/streams.rs`) at least once a second while it runs and stays until the next operation of the same kind on the same target, and a failed outcome stays until it is handled. A request repeated with an ID the server holds returns that record and runs nothing again. services-panel's Backend 2 ships it first for `restart-service`, `restart-stack`, `start-service` and `stop-service`; this flow requires the same record for every other write: the `worktrees` `POST` (worktree-switch), `config/save` (config-editor), a hot reload from a file changed on disk with origin `watcher` (manifest-hot-reload) and the Disable Reloads request's chat send, which keeps its `commandId` (reload-control). Serves `notices-and-feedback-03`, `notices-and-feedback-01`, `keyboard-and-screen-reader-02`. Required. Contract: `CC-37`.
2. **Handling a failure.** `POST /__devhost__/operations/<id>/dismiss` in `apps/devhost/src/devtools/server.rs` (gated by the same `O36` control-API check as other stack writes) marks a failed outcome as handled for every page of the stack, so a dismissed failure returns neither on reload nor in another tab, and the record stays readable in the log; services-panel's row **Dismiss** calls the same route. Serves `notices-and-feedback-01`. Required. Contract: `CC-37`.
3. **The reason before a stream closes (including command-mode `port-closed`).** Before the control server closes page streams for a stop (`devhost stop`, Ctrl-C, SIGTERM, the idle timeout, a replacement by `devhost stack restart`, `devhost restart` or `devhost upgrade` under `O18`, or a stop from another stack's page, which records why beside the stopped stack's record, naming both stacks by stack ID and name, before it asks the shared supervisor over its socket to stop the stack, as `devhost stop` does today without signalling the supervisor, `apps/devhost/src/services/stop.rs:148-216`), it sends one final message on `/__devhost__/ws/health`: `{"type": "stack-ended", "reason", "by", "at", "folder", "startCommand", "survivors": [{"service", "pid", "port"}], "endedConversations": [{"title", "state"}], "replacedBy": {"command", "at", "stackId"}}`, and then closes with `1001`, as today (`apps/devhost/src/devtools/streams.rs:158-198`, triggered by `apps/devhost/src/devtools/server.rs:144`). `by` for a stop from another stack's page is `{"stackId", "stackName"}` of that stack; `survivors` lists a service's own process, whose PID is real. `replacedBy` names the replacing command, its time and the new run's stack ID, for example `{"command": "devhost restart", "at": "2026-11-26T14:02:11Z", "stackId": "stk-9f3c1a7e5b2d4c60"}`, never a PID: every stack reports the shared supervisor's PID, which an in-place `devhost stack restart` keeps, while every run gets a new stack ID (`apps/devhost/src/caddy/stacks.rs:23-36`, `116-141`; `R7-99`). Nothing reports a replacement on `main` today. ## Recommended priority

**P2.** The realistic trigger is ordinary and frequent: every successful Restart Stack and every **Start** end with the whole stack drawn red for about a second (`services-panel-2-04`, `stack-scale-06`); every tab left open through `devhost stop`, `devhost caddy stop`, an idle shutdown or a port change shows six crashed services with live **Restart** buttons whose errors are the proxy's HTML (`notices-and-feedback-02`, `journey-new-project-02`, `proxy-settings-03`); closing one secondary port in a multi-port `devhost serve -- <cmd>` session turns open tabs into a false `0/3` outage over WebSocket instead of linking to the remaining active URLs (`serve-command-05`); a restart that succeeds says nothing and one that fails is erased within 0.2 s (`notices-and-feedback-03`, `notices-and-feedback-01`); a screen-reader user hears every failure but never a recovery (`keyboard-and-screen-reader-02`). Nothing is lost: the cost is wrong restarts, such as another 14 s Restart Stack, time spent debugging healthy services, reloading to be sure, and red that people learn to ignore. It is met daily, as often as restarts and stops, but costs less than services-panel's P1 problems, which hold or stop work. Ship first the slice with no backend dependency: a lost connection drawn as unknown with every write unavailable, "Lost connection to devhost; retrying", **Retry Now** and "Connected again"; failures kept until handled; the shared request helper (including the `O36` unauthenticated sentence); `Alert` without a live role and the one announcer; the notice stack's order with **2 More**, the 320 CSS px phone layout (`O8`), calibrated `O14`/`O53` timing, and `O16` app tab-title prefixing.
