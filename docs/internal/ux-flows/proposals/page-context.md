# Point at the page and attach screenshots: proposed experience

Diagrams: [current](../page-context-current.html), [proposed](../page-context-proposed.html). [Wireframe](../wireframes/page-context.html).

Status: design proposal, not implemented behavior. The [shared UX pattern reference](../patterns.md) (revision 6) wins where this proposal disagrees with it.

Source revision: alexgorbatchev/devhost `190a8bb53e8cd903d2db0a92cb0886f29671607f` (Rust `main`). Features: CTX-01, CTX-02, CTX-03, CTX-04, CTX-05. Redesign ticket: tracked privately.

Product rules: the product owner decided how a message with page context is handled (`O1`, decided 2026-11-16, updated 2026-11-18): the composer offers two edit modes only, **This worktree (live)**, which edits whichever worktree the person has active (main's included), leaves every change uncommitted and creates no additional worktree, commit or merge, so the change shows in the running page, and **Make tickets**; **This worktree (live)** is the default when the message carries page context, and every sent message shows which mode applied. The owner's other rules make more of this flow intended: chat never asks for API keys in the browser; devhost never answers or pre-approves the agent's approvals, while the decision card offers the agent CLI's own standing approval when the CLI has one, so the person grants it (`O12`); **Delivery unconfirmed** with no resend is how a lost send ends; using devhost from another environment, a phone included, is a primary use case, so a browser signed in with the shared passkey or paired uses this flow as this machine does (`HOLD-8`, `O36`, `O8`); and devhost never starts an editor (`O50`, `O51`), so a pick's source is a file and line to read or copy. `guides/annotations.md` adds that devhost never sends video, only one image per message, and that a screenshot is optional. None of these is a defect. The gap is around them: page context loses its identity while the person works (numbers shift, drawings drift, a reload drops everything and keeps the draft that cites it), nothing shows what leaves the machine before Send, the keyboard and a single click cannot pick or draw, and the keys that end a pick also stop the agent.

## Target experience

The person points at the page from docked chat: **Select Elements**, or holding Alt alone (Option on macOS) and moving the pointer, outlines the element under the pointer with its role and name before the click, and a click adds a numbered mark on the element; **Arrow**, **Line** and **Box** draw with a drag or with two clicks and take the next number from the same counter. Numbers never shift or come back within a draft, so "make #3 match #2" keeps meaning what it meant. Every mark and drawing stays on the element it marks while the app re-renders, the layout moves or the agent's hot update lands, and one that loses its element says so in its row instead of framing something else. Under the composer, page context is a review of what will leave the machine: one row per item with its number, its element, its source file or "no source found", and the page's details once (the URL, the page's service and its worktree), each row expandable to the exact fields sent. A `#n` typed in the message that no longer matches a pick is flagged before Send, and Send asks only when the message cites a mark that is gone, with **Select Again** first. **Undo** and Mod+Z reverse the last page-context change, a cleared list included. With the tab shared, Send takes one screenshot with devhost's own surfaces hidden, shows the crop preview, and its busy button says each step; a closed picker leaves nothing behind, and a share that ends says so neutrally. The sent message records its mode and shows the page context it carried in the same readable rows, the raw data one press away. A reload devhost or the person causes, the one that applies an agent's change at the end of its turn included, brings back the draft with its marks where their elements still exist and lists the rest as lost. Escape only ever leaves a page-context mode and never stops the agent. A selection the person latched with **Select Elements** stays on until they end it: an Option character typed in the composer, an Alt shortcut or a switch to another window ends only a selection that holding Alt started. Keyboard users latch Select Elements, walk the page with the arrow keys, pick with Enter, and draw with Enter on two elements; on a phone, docked chat takes the phone's width and a tap picks. There is no Undo for a sent message; the outcome kind here is the work kept through reloads (`UNDO-2`) and the page-context undo history (`UNDO-7`). Benchmarks: Chrome DevTools and React DevTools resolve and highlight the element under the pointer before the click, and Chrome DevTools walks the DOM with the arrow keys; Figma and Linear keep comment pins numbered and anchored to what they mark, and Figma's undo reverses the last action, whatever it was; Cursor's Add to Chat puts context into the composer without sending it and lists what it attached; Claude Code and Cursor show the mode in the input row and mark an interrupt as an interrupt; VS Code's hot exit brings unsaved work back after a reload. Competitor behavior is evidence here, never a requirement.

## Target steps

Today: 7 steps on the main path, three of them guesses: open chat, pick (pointer only), check the list (numbers and names only), type `#n` from memory, Send, crop, then read raw JSON to learn what went. Proposed: 5 steps: point, review the rows the message carries, write and Send, crop when a tab is shared, read the sent record. The keyboard path is the same 5 steps, with no pointer.

1. **Point at elements (the page's own DOM, read only).** **Select Elements** sits first in a row of page-context tools at the top of docked chat, beside **Arrow**, **Line**, **Box**, **Undo** and **Redo**, so the tools follow the dock's corner and docked chat's placement instead of covering the app's header at the top centre of the page (`SURF-7`, `SURF-5`, `MENU-1`). Pressing it latches selection on; holding Alt alone starts it from the page or from the composer (`KEY-2`). Select Elements, holding Alt and Alt + right-click resolve the element under the pointer with one resolver and outline it with its role and name before the click (`SEL-9`). A click adds a mark with the next number of the draft, "#3", drawn on the element, and a row in page context (step 3); clicking a marked element again does nothing. The first mark opens docked chat when it is closed, with focus in the composer (agent-chat's entry). Each pick is announced politely once with its number and element, "Mark 3 added: button Add to cart" (`FB-9`, `SEL-9`).
   - Alt-hold: selection starts only on the first pointer move while Alt alone is held (a change of position past a few pixels of jitter, never a `pointermove` without movement), on a pointer press while Alt alone is held, or once Alt alone has been held for 400 ms, `O34`'s provisional value, kept as one page constant until human holds are measured (`O34`). Any other keydown before that, Shift, a dead key and input-method composition included, cancels it without drawing anything, so Alt+Ctrl+R, Alt+Shift+D, a page's own Alt shortcut and a character typed with Option never start it. A pointer press while Alt alone is held picks the element under the pointer and never reaches the page, so Option+click never follows or downloads a link. Arrows pressed while Alt is held do nothing and never reach the browser's Back and Forward (`KEY-2`, `KEY-12`, `O34`; `keyboard-and-screen-reader-07`). Alt still belongs to the page's own fields while the person types there.
   - How a selection ends: the selection records whether holding Alt or the toggle started it. One that Alt started selects only while Alt is held, so it ends when Alt is released, when the window loses focus, whose Alt release the page may never receive, and when a key that types is pressed (a keydown whose `key` is one character or `Dead`), so a hesitant Option chord's outline never outlives the character it typed (`KEY-2`, `O34`). One that the toggle latched stays on until Escape, the **Select Elements** toggle, another tool, closing chat or a send that takes a screenshot ends it (`KEY-12`, `KEY-8`): pressing and releasing Alt, a character typed with Option in the composer (Option+- on a US layout, Option+L on a German one), Alt+Ctrl+R, which still restarts, and a switch to another window and back leave it on, with its hint, its selection cursor and its pressed toggle, so the next click adds a mark and never reaches the page's own control (`page-context-11`).
   - Keyboard: with Select Elements latched (its toggle, or Enter on it), a highlight starts on the element that had focus before devhost took it, else the page's main landmark, else the body's first visible element; ArrowUp moves it to the parent, ArrowDown to the first child, ArrowLeft and ArrowRight to the siblings; Enter picks; Shift+F10 or the context-menu key opens the highlighted element's source menu, which component-source owns (`KEY-12`, `MENU-1`). Focus stays on the toggle, whose accessible description names the highlighted element, and each move is announced politely, "button Add to cart · in form Checkout · 2 of 5" (`KEY-12`, `FB-9`; `page-context-10`).
   - Focus: a pointer pick or drawing returns focus to the composer, where agent-chat puts it after a pick made with chat's tools, with the caret where it was; a keyboard-latched selection keeps focus on its toggle until Escape, as `KEY-12` says; no pick ever moves focus to the page element or the body (`KEY-6`, `KEY-12`).
   - Escape leaves the mode and does nothing else: in the composer, on the toggle and on the page alike, it never stops the agent's turn, which **Stop Turn** and Alt+Ctrl+. do (`KEY-8`, `KEY-9`; `keyboard-and-screen-reader-06`). With no mode active, Escape in the composer returns focus to the page element chat took it from (`KEY-8`). One devhost key handler checks the active page-context mode first, so the outcome no longer depends on which listener registered last.
   - Hint: while a mode is active, one line beside the pointer (or under the toggle in a keyboard-latched mode) names the mode by its tool label and its next step, with each key cap followed only by its outcome, drawn from the bindings' one definition: "Select Elements · click an element to add it", then the key cap Esc and "Finish"; latched from the keyboard, "↑ ↓ ← → Move · Enter Pick · Esc Finish" (`KEY-13`, `WORD-3`; `page-context-08`). The hint is sentence case and never says "Annotate" or spells Esc in words (`WORD-1`, `WORD-3`).
   - Defaults: Select Elements off; it latches until Escape, its toggle or another tool, never until an Alt release; picks reach the page's own controls wherever devhost draws nothing (`SURF-11`; the empty strip above the toolbar is toolbar-shell's, `page-context-03`).
2. **Draw Arrow, Line or Box (the page's own DOM, read only).** A drawing tool stays armed until Escape or another tool, so three boxes take three drags, and its hint says so: "Box · drag, or click two corners", then Esc "Finish" (`KEY-13`; `page-context-04`, `page-context-08`). A drag draws as today; two clicks set the start and the end as a drag does, with a preview following the pointer between them, and Escape between them cancels the drawing in progress, its hint reading Esc "Cancel" (`KEY-12`; `page-context-10`). From the keyboard, the arrows walk the highlight as in Select Elements, Enter sets the start at the highlighted element and a second Enter the end, and Box boxes the highlighted element on one Enter (`KEY-12`). Each drawing takes the next number from the marks' counter and shows it on the page, "#4", and its row reads "#4 Box around button Add to cart" (`SEL-9`; `page-context-04`).
   - Anchoring: each mark and drawing is anchored to the element it marks as an offset to that element: a box to the smallest element that contains it, an arrow to the element under its head, a line to the elements under its ends; marks are re-measured on scroll, resize, layout change and DOM mutation, the re-render of a hot update included, within one frame (`SURF-12`; `page-context-02`). When its element leaves the page, the mark leaves the page too and its row reads "#4 is no longer on this page" with **Select Again** and **Remove**; it never floats over another element (`SURF-12`, `SEL-9`).
   - A finished drawing can be moved by its stroke, as today; the move is an action **Undo** reverses (step 4).
   - Marks and drawings paint beneath devhost's surfaces, so no mark covers the bar, the notice stack, a panel or docked chat (`SURF-1`).
3. **Review what the message carries (page context, read only).** Under the composer, page context lists every item in number order, one row each, and each row says what it sends (`SEL-9`, `REV-6`; `page-context-07`):
   - a mark: "#2 button Add to cart · ProductCard.tsx:42", or "#2 button Add to cart · no source found" when devhost resolved no source file, which component-source resolves on React 19 (`page-context-06`, related);
   - a drawing: "#4 Box around button Add to cart";
   - the page, once per message: "Page · /checkout?step=2 · web · fix-nav ~/acme/.worktrees/fix-nav", the page's URL, its service and its worktree label (`SEL-3`, `SEL-4`, `WORD-11`); a URL whose query or fragment is long is shortened in the middle with the full URL in its tooltip and accessible name (`WORD-8`);
   - with a tab shared and the camera on, "Screenshot of this tab, taken when you send".
   Each row expands to the exact fields that leave the machine for it (step 7's payload), so a person sees the full URL, the nearby text and the element path before Send. Hovering or focusing a row outlines its element or drawing on the page, and hovering a mark highlights its row (`SEL-9`; `page-context-04`). Each row has **Remove** (accessible name "Remove #2"); **Clear Page Context** removes every item and is undoable (step 4). Keys: each row's disclosure and its **Remove** are Tab stops in number order, and Enter or Space on the disclosure expands the row (`KEY-10`). While Select Elements or a drawing tool is on and nothing is picked or drawn yet, the list reads "No elements picked" with its next step, "Click an element, or use the arrow keys and Enter"; with no mode on and nothing picked, the list is absent, as today, and the tools row stays (`STATE-2`). Every row comes from the one page-context store the send reads, so the list and the payload cannot differ (`SEL-1`).
   - Removing a mark leaves every other number as it is, gaps allowed, and the next pick takes the next unused number, never a removed one; only **Select Again** on a number the message cites binds that number again (step 5) (`SEL-9`; `page-context-01`).
   - A `#n` in the message that no longer refers to a pick (removed, lost after a reload, or never made) is flagged under the composer before Send, "#3 is not in page context", with **Select Again**; Send stays available (`SEL-9`, `REV-6`; `page-context-01`, `journey-agent-fix-04`).
   - The list is part of docked chat, inside the composer's area; at every acceptance viewport, the 320 CSS pixel phone layout included, its rows scroll inside a bounded area and the composer, Send and the mode control stay in view (`SURF-6`, `SURF-9`, `O8`).
4. **Undo the last page-context change (local undo, no write).** One undo history per draft records every page-context action: add, move or remove a mark, draw, move or remove a drawing, and **Clear Page Context**. **Undo** reverses the last one, whatever it was, back to the start of the draft, and **Redo** reapplies it; each names what it will reverse in its tooltip and accessible description, "Undo Move #4 Box" (`UNDO-7`; `page-context-04`). Undoing a removal restores the item with its number. Mod+Z undoes and Mod+Shift+Z redoes while Select Elements or a drawing tool is active, or while focus is in devhost outside a text field; everywhere else they stay the app's own undo, and in the composer they stay the composer's text undo (`KEY-12`, `UNDO-7`). Send ends the draft's history.
5. **Write and Send (`send` on the chat socket, one write).** The composer names the recipient, the agent and model ("Claude Code · Haiku 4.5"), and the edit mode with the worktree it edits; with page context the mode starts at **This worktree (live)**, "This worktree (live) · fix-nav ~/acme/.worktrees/fix-nav", and the person can choose **Make tickets** instead (`O1`, `SEL-8`, `REV-6`, `WORD-10`, `WORD-11`); agent-chat owns that control and the conversation choice. Page context goes to the conversation the composer shows, also right after **New Conversation** (`SEL-8`). Send asks nothing, except when the message cites a mark that no longer exists: then the composer asks in place, verb first: "Send with #3 missing? Its element is no longer on this page." for a mark whose element left the page, agent-chat's sentence, or "Send with #3 missing? It is not in page context." for a number the person removed or never picked; **Select Again** is focused and enters Select Elements to pick #3 again under the same number, and **Send Anyway** sits beside it; Escape cancels the question, keeps the draft, leaves the neutral line "Not sent" and returns focus to **Send** (`REV-6`, `REV-4`, `SEL-9`, `UNDO-4`, `WORD-7`; `journey-agent-fix-04`, `page-context-01`). **Select Again** is the one way a number the message cites is bound again, so the text keeps meaning what the person wrote; this flow proposes it to the reference as a clarification of `SEL-9`'s "never reused". A picked element's fix then asks through the agent's own decision card, which agent-chat owns, pinned between the conversation and the composer with **Deny**, **Allow Once**, the agent CLI's own standing approval when it offers one (**Allow for This Session**) and **Stop Turn**, none focused or pre-selected; devhost never answers it (`REV-9`, `O12`).
   - While the send prepares (the capture and the crop, step 6), the page-context tools, rows and Undo are unavailable with one reason in the list's status line and as each control's accessible description, "Sending: page context changes wait until the message is sent" (`MENU-3`, `HOLD-1`); Select Elements stays focusable (`KEY-11`).
   - When chat cannot take a message (chat off, no agent CLI installed, the conversation disconnected), Send is unavailable with agent-chat's reason, and picks, drawings and the draft stay (`HOLD-5`).
   - Defaults: the mode **This worktree (live)** with page context (`O1`); the camera on once a tab is shared, as today.
6. **Attach a screenshot (`getDisplayMedia`, read only; the crop preview).** **Share Tab** opens the browser's picker; only a browser tab is accepted, and a window or whole screen ends with "Pick this browser tab: a window or a whole screen cannot show the page's marks." (`FAIL-2`). Closing the picker or choosing its Cancel leaves nothing: no line, no alert, and **Share Tab** is ready again (`FAIL-5`, `WORD-7`; `page-context-09`). A capture the system refuses reads, in the list's status line, "Your browser may not record the screen. Allow it in System Settings › Privacy & Security › Screen Recording, then choose Share Tab again." with the browser's own text behind **Copy Error** and a **Dismiss**; it stays through later sends until **Dismiss** or a share that succeeds, because a failure stays until it is handled (`FAIL-2`, `WORD-7`, `FB-6`; `page-context-09`). A share's outcomes read in the outcome grammar, verb first in the past tense: "Shared this tab · each message takes a screenshot while the camera is on" when it starts, and, when **Stop Sharing**, the browser's own sharing control or a reload ends it, the neutral "Stopped sharing this tab · from the browser's sharing control" or "Stopped sharing this tab · the page reloaded", never a failure (`WORD-4`, `FAIL-5`, `FB-4`, `UNDO-2`). These lines and every other page-context report show in the list's status line while docked chat is open; with chat closed, the report enters the one notice stack in its order (a failure with the failures, a success with the successes, a stopped share as a neutral notice, ○, below the failures), never a second stack or a toast of its own (`FB-8`, `FB-2`). A success or neutral notice there closes after its reading time, 1.5 s plus 0.3 s per word, at least 4 s and at most 15 s, counted only while the pointer and focus are outside it and the page is visible; one that arrives while the browser window is not focused, as when the person stops sharing from another window, starts counting when the window next gains focus (`FB-6`, `O14`, `O53`).
   - With the tab shared and **Include Tab Snapshot** (the camera) on, Send takes one screenshot: devhost hides its toolbar, chat and tooltips while keeping marks and drawings, waits until a captured frame shows them gone, for up to 10 s, and otherwise fails the send with the draft and page context kept, as today. Progress shows on the busy Send in the composer, which keeps focus: "Taking screenshot…", then "Crop the screenshot to continue" while the preview is open, then "Sending…" (`FB-1`, `KEY-11`, `STATE-1`).
   - The crop preview opens over the page with the frame: drag to select an area, or set Left, Top, Width and Height; the arrows adjust a crop field's value, Enter applies it and never shares; the crop fields' keys never reach the page (`KEY-9`, `KEY-5`). **Share Selected Area**, **Share Whole Tab** and **Cancel** end it; Escape or **Cancel** cancels the send, keeps the draft and page context, and leaves the neutral line "Not sent · your draft and page context stay" (`KEY-8`, `FAIL-5`, `WORD-7`). The preview stays a modal dialog over the page, the exception recorded under **Branches and edge states**; focus returns to Send when it closes (`KEY-6`).
   - Where the browser offers no tab capture (no `getDisplayMedia`, as on phone browsers), **Share Tab** stays in place, unavailable with "This browser cannot share a tab; attach an image instead" as its visible reason and accessible description, and agent-chat's **Attach Image** adds a screenshot the person took (`MENU-3`, `HOLD-1`, `O8`).
7. **Read the sent record (the session's journal, read only).** The message appears at once as the person's with "Not sent yet" until the acknowledgement, then its mode line, "Mode: This worktree (live) · fix-nav", with the instructions devhost added under a collapsed "Added by devhost", as agent-chat specifies (`WORD-10`, `UNDO-8`). Under it, "Page context: 2 marks, 1 drawing, 1 screenshot" is collapsed and expands to the same rows as step 3, each with the fields it carried, and **Show Raw** shows the exact data the agent received (`UNDO-8`, `FB-2`; `page-context-07`). Keys: the record's disclosure and **Show Raw** are Tab stops in reading order (`KEY-10`). devhost writes that page context as a record of its own into the session's journal, apart from the person's text, so every page and every reload shows it (`UNDO-8`, `CC-40`). Sending clears only the items that went out, and their undo history ends with them (`UNDO-7`).
   - What the agent receives for page context, once per message: the page's title and URL, its service and worktree label, the viewport's size, the scroll offsets and the device pixel ratio; with a screenshot, its size, its crop and its scale to CSS pixels, so a mark and a drawing can be placed on it; per mark, its number, element path, role and name, nearby text, bounds in page CSS pixels with horizontal scroll included, computed styles once, and its source file or that none was found; per drawing, its number, kind, the element path it is anchored to, its offsets and its page coordinates; no drawing IDs (`SEL-3`, `SEL-9`, `SURF-12`; `page-context-07`, `page-context-02`).
   - No outcome notice reports a send: the message itself is the receipt in the conversation, and agent-chat's delivery states apply (`FB-2`, `FB-5`).

Branches and edge states:

- **A reload devhost or the person causes.** The browser's reload, **Reload Now**, a worktree switch, Restart Stack on a recovery page, or an agent edit that reloads the page: the unsent text comes back from browser storage, as today, and the pasted images and page context from the control server's draft record for this stack, page origin and conversation (each pick's element path and offsets, each drawing's shape and anchor, never a screenshot) (`UNDO-2`, `CC-19`). Marks and drawings whose elements still resolve come back with their numbers; the rest stay listed with "#3 is no longer on this page", **Select Again** and **Remove**; the page announces once "Restored #1 and #2 after the reload · #3 is no longer on this page" (`UNDO-2`, `SEL-9`, `FB-4`, `WORD-4`; `journey-agent-fix-04`, `page-context-05`). A tab share always ends with the page, and the list says "Stopped sharing this tab · the page reloaded" (`UNDO-2`, `WORD-4`).
- **A turn ends while the page holds a reload.** When an agent's turn that changed files ends while Hold Reloads holds the page's reload, devhost applies it once as its own reload unless focus is in a text field, the composer included, because the next message is often typed as a turn ends; then nothing reloads and agent-chat's turn receipt leads with **Reload Now** and "The page reload this change needs waits for you" (`O57`, `FB-12`). A reload that runs is one devhost causes, so marks and drawings come back as above (`UNDO-2`); with reloads disabled through **Disable Reloads**, nothing reloads by itself (`O56`).
- **A worktree switch.** The switch's question names page context before the switch runs, "Page context: 3 marks · a mark whose element is gone after the reload is listed as lost; the tab share ends", read from this flow's page-context summary; whether and how the switch asks is worktree-switch's (`SEL-5`, `REV-3`). After the switch the draft record follows the conversation the composer shows, and a draft written for another worktree's conversation moves with **New Conversation** as agent-chat specifies (`SEL-8`).
- **A hot update re-renders the page.** Marks and drawings stay anchored through it, re-measured within one frame (`SURF-12`); reload-control's Hold Reloads keeps a full reload away while held.
- **The page's own modal dialog.** Picks and drawings keep working over the page's popovers and modal dialogs without closing them, as today; docked chat and its tools move into the dialog's top layer with the notice stack (`SURF-11`).
- **Annotations turned off.** With `[devtools.annotations].enabled = false`, chat shows no page-context tools, Alt-hold starts nothing and no page context is sent; the setting's description says so, "Element selection, drawings and page context for chat; turning it off removes them, chat stays" (`SEL-11`).
- **Chat closed.** Alt-hold still starts a selection on the page; the first pick opens docked chat with the mark in its list (agent-chat's entry). Closing chat ends an active mode; marks, drawings and the draft stay until Send or **Clear Page Context**.
- **Focus after a pick (proposed reading).** Section 4's line for this flow has Select Elements leave focus where it was (`KEY-6`, `keyboard-10`), while `KEY-12` keeps focus on the toggle in a keyboard-latched mode and agent-chat returns focus to the composer after a pick made with chat's tools. This proposal follows the last two: a pointer pick or drawing returns focus to the composer, a keyboard-latched selection keeps it on the toggle until Escape, and no pick focuses the page element; the reference's author settles the section 4 line.
- **Other write-blocking states.** While a service operation runs (`HOLD-3`), the page's worktree is unavailable (`HOLD-4`) or a configuration was rejected (`HOLD-6`), picking, drawing, the list, Undo and the draft stay available, because none writes, and Send follows agent-chat's rule for each. The Deny note keeps its keys from the page as the crop fields do (`KEY-5`); agent-chat owns the note.
- **From another environment.** A browser signed in with the shared passkey or paired uses every step of this flow as this machine does, the draft record included (`HOLD-8`, `O36`). Until it signs in, the app works and the toolbar shows its one state, "Sign in with passkey or pair this browser to use devhost here": chat with its page-context tools is unavailable with that reason, holding Alt starts nothing, so the page's own clicks reach the page, and the draft record refuses it (`HOLD-7`, `WORD-7`).
- **On a phone.** At 320 CSS pixels docked chat takes the window's width less 16 px on each side, with the tools row wrapping above the composer and the rows scrolling in their bounded area; **Select Elements** latches from its toggle and a tap adds a mark, the element outlined while the finger is down, because a touch screen has no hover; **Arrow**, **Line** and **Box** draw with two taps; holding Alt and the arrow keys do not apply; every tool and **Remove** is at least 24 by 24 CSS pixels (`O8`, `SURF-9`, `KEY-12`).
- **A send that fails or is cancelled.** A cancelled crop, a capture that cannot confirm devhost's surfaces are hidden, or a send the server refuses (over 8 MiB, an image that is not PNG or JPEG) sends nothing and keeps the draft and page context, as today; its reason shows where Send is, in words, with the original text behind **Copy Error** (`FAIL-2`, `UNDO-4`).
- **A lost response.** A send whose acknowledgement never arrives reads **Delivery unconfirmed** and is never resent (owner rule; `REV-12`); its page context stays in the draft record until a send is acknowledged, and the person decides whether to send again.
- **The lost connection.** Send is unavailable with the lost connection's reason (`HOLD-2`); picking, drawing, the list and Undo stay available, because none writes, and the draft record is written once the connection returns.
- **The crop preview's surface (proposed exception).** `SURF-3` calls the crash view devhost's only modal dialog over an app page, and 2.4's decision rule has no row for the crop preview. This proposal keeps it a modal dialog: it shows a frozen frame of the page that the person crops before the send continues, and the reference's own keys for it (Escape cancels the send, `KEY-1`'s crop fields) assume a send that waits on it. The exception is proposed for the reference: 2.4 gains it as a modal surface with `KEY-7`'s Tab cycle, or names another surface for it.
- **A message without page context.** Its mode follows agent-chat's default (`O3`); nothing in this flow changes it.

## What changes versus today

- **Removed:** renumbering marks when one is removed; the drawings' separate "1. box" numbering by list position; the tool switching itself off after one shape; **Undo Drawing**, which removed the newest shape and never a move; Escape in the composer stopping the agent's turn, and its dependence on listener order; Alt chords and Option characters starting Select Elements, and Alt's release or a window switch ending a selection the toggle latched; the "Annotate" label and the "Esc To Cancel/Finish" words beside the Esc key cap; the browser's raw rejection as a red alert after a closed picker; the fixed floating tools at the top centre of the page; page context appended to the person's text as one line of JSON; the drawing IDs and the second computed-styles format in what the agent receives; a reload silently dropping every mark and drawing.

## Recommended priority

**P2.** The realistic trigger is ordinary and frequent in this journey: the agent's own edit reloads the page while the person prepares the next message, now also at the end of a turn under `O57`, and every mark and drawing vanishes while the draft that cites them comes back, so the agent receives "#1" with nothing attached (`journey-agent-fix-04`); pruning one mark after writing renumbers the rest under the typed text (`page-context-01`); a validation message or a hot update moves the page and a box frames the wrong element (`page-context-02`); and pressing Esc to finish a pick, as the hint says, can stop the running turn mid-edit (`keyboard-and-screen-reader-06`). None loses files: the cost is a wasted or wrong agent turn, its approvals and, for paid agents, money, recoverable by marking again or sending again, which keeps it below the P1 flows that stop services or edit configuration.
