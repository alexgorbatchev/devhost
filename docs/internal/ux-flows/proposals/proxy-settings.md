# Change the shared proxy settings: proposed experience

Diagrams: [current](../proxy-settings-current.html), [proposed](../proxy-settings-proposed.html). [Wireframe](../wireframes/proxy-settings.html).

Status: design proposal, not implemented behavior. The [shared UX pattern reference](../patterns.md) wins where this proposal disagrees with it.

Source revision: alexgorbatchev/devhost `190a8bb53e8cd903d2db0a92cb0886f29671607f` (Rust `main`), against shared pattern reference revision 6. Features: SET-06, SET-08. Redesign ticket: tracked privately.

Product rule: the owner settled that Caddy listening on every interface by default is documented and intended, that every manifest setting applies through hot reload, never "restart to apply", and that using devhost from another environment is a primary use case (`HOLD-8`). `guides/shared-managed-caddy-settings.md` promises that when the devhost config file is saved, "Caddy moves to the new settings in one reload, including a new `adminAddress`." and "Services, routes, terminals, and chat sessions keep running." The owner decided three things this flow follows: on macOS, `bindHost = "127.0.0.1"` is honored from port 1024 upward, and below port 1024, port 443 included, Caddy keeps listening on every interface with a warning on every start and save, so existing setups keep starting (`O39`); no `publicUrl` reference or `DEVHOST_PUBLIC_URL` variable is added, so an HTTPS port change restarts no service (`O45`); and a browser in another environment uses every control, the Configuration window's **Save** included, once it signs in with the shared devhost passkey or pairs (`O36`, `O54`). So the default listener on every interface, a save that applies without a question, services that keep running through a move, and a rejected change that leaves the running shared Caddy settings in place are intended, not defects. The gap is around them: a loopback setting that silently does nothing on macOS, a held port reported as applied, open pages stranded on a port that closed, relay previews that break whenever Caddy is not on port 443 or moves, saves that never say what they changed, a routing change that drops the rest of the save, rejections that never say what keeps running, and stacks that miss a change another process applied. Who may use a stack's controls from another environment is `O36`'s check, which `agent-chat` owns; this redesign decides what the listener settings do and how every surface reports them. Routing settings in the devhost config file (`domainSuffix`, `[remote]`) apply to a running stack at its next start, as `guides/shared-managed-caddy-settings.md` documents today; the owner rule names manifest settings, so this redesign keeps that documented behavior and narrows it to the stacks a change affects, and whether these settings should apply live is open product owner item q84; until it is answered, this next-start behavior is the applied default.

## Target experience

The person who must move the proxy, because another program holds port 443, a Linux machine has no low-port grant, or they want the stacks off the network, types `devhost caddy --help` and reads where the shared Caddy settings live, with this environment's path: "~/.config/devhost/config.toml". `devhost caddy start`, `devhost start` and `devhost status` say what the proxy listens on in one line, "Proxy: HTTPS on port 443, every interface, reachable from your network · ~/.config/devhost/config.toml", so the listener's reach is never a guess; on macOS a loopback `bindHost` below port 1024 adds a warning naming the fix instead of silently listening everywhere. They edit the `[caddy]` table in any editor, or in the Configuration window from this machine or from a browser signed in elsewhere, which states before the save what it will do: "Saving moves the URLs of 3 stacks to port 4443: Acme Shop, Docs and Blog; no service restarts". Nothing asks. devhost checks the change before Caddy moves: a port another program holds or a stack directory hostname a stack already uses is refused with nothing moved, naming the file, the line, the key and what holds it, and saying what keeps running. A change that passes moves Caddy once for the whole machine; devhost tells every open page first, then certifies that the new listener answers. Each stack's terminal prints one line naming what changed and the URLs that moved, "Applied config.toml: HTTPS port 443 → 4443 · 1.4 s", and each open page keeps working on the old address with "Moving to port 4443" while the listeners move, then, once every listener answers, shows "Moved to https://shop.localhost:4443/" with **Open**, which keeps the page's path, query and fragment, while its toolbar follows its stack to the new address instead of drawing every service down. Relay previews keep answering, because a relayed page's public port stays 443 and the relay connector follows Caddy wherever it moves. A `domainSuffix` or `[remote]` change waits only for the stacks whose hostnames or relay it changes, which say so with the command that applies it, while the rest of the save applies everywhere. A setting is undone by saving the old value, which reports its own move; a rejected change is undone by **Restore Running Version** in the Configuration window or by any save that matches what runs, which clears the rejection on every page and every terminal: there is no Undo of its own. Benchmarks: Vite prints its local and network addresses at start and says how to expose it, so a dev server's reach is stated, never assumed; `nginx -t` and `caddy validate` check a configuration before a reload and keep the running one when it fails; Docker publishes `127.0.0.1:8080:80` on loopback only and `docker ps` shows the address each port is bound to; Tailscale's `serve status` says whether a service is reachable within the tailnet or from the internet; VS Code's Ports view shows each forwarded port's local address and whether it is private or public. Competitor behavior is evidence here, never a requirement.

## Target steps

Today: 6 steps, two of them guesses: search the CLI and the docs for where the setting lives, find the file through two environment variables, edit and save, read "Applied the shared Caddy settings from \<path\>." and every URL again in each terminal, find every open tab drawn as crashed, then work out the new address and type it. Proposed: 3 steps: read where the file is from `devhost caddy --help` or any start, save it with its reach stated, read one outcome per stack and press **Open** on each open page.

1. **Find where the shared Caddy settings live (`devhost caddy --help`, `devhost caddy start`, `devhost start`, `devhost status`; read only).** `devhost caddy --help` ends with "Ports, listeners and the stack directory hostname are shared Caddy settings in the devhost config file: ~/.config/devhost/config.toml", the path resolved for this environment (`DEVHOST_CONFIG_DIR`, else `XDG_CONFIG_HOME`, else `~/.config/devhost`, as today) and shortened with `~` (`WORD-1`, `WORD-8`, `SURF-15`; `language-02`, `proxy-settings-05`). `devhost caddy start` names what runs, its listener, the file and how to stop it, "Caddy runs HTTPS on port 443 on every interface, reachable from your network · settings: ~/.config/devhost/config.toml · stop it with devhost caddy stop", its listener part worded as the proxy line's in every variant below, with the macOS warning after it (`FB-10`; `feedback-02`), and `devhost start` and `devhost status` print the same facts as one proxy line, "Proxy: HTTPS on port 443, every interface, reachable from your network · ~/.config/devhost/config.toml" (`FB-10`, `FB-11`, `O62`; `proxy-settings-01`, `proxy-settings-05`). A loopback listener reads "Proxy: HTTPS on 127.0.0.1:4443 and [::1]:4443, direct connections from this machine only; relay previews and SSH forwards still reach it · ~/.config/devhost/config.toml", and with `http = true` the line adds "and HTTP on 127.0.0.1:8080 and [::1]:8080" after the HTTPS listeners (`O39`). Only `bindHost = "127.0.0.1"` changes on macOS; `"::1"` keeps today's behavior. This flow words the line; stack-run-stop prints it among its start and status lines, first-run-setup in `devhost caddy start`'s outcome, and serve-folder in a session's header. Terminal text says "this machine" for the machine the command runs on (`O61`). Agent output carries the same facts in its own layout with the absolute path (`WORD-9`, `FB-11`; `language-16`).
   - On macOS with `bindHost = "127.0.0.1"` and any listener below port 1024 (`httpsPort`, or `httpPort` while `http = true`, whose default is 80), the proxy line names every interface, as Caddy then listens, and one warning line follows it on every `devhost caddy start`, `devhost start`, `devhost status` and save of `config.toml`: "Warning: on macOS, bindHost = "127.0.0.1" needs every port at 1024 or above, so Caddy listens on every interface on port 443, reachable from your network. Set httpsPort = 4443, or start Caddy from a privileged launcher." Nothing is refused and no start fails, so existing port-443 setups keep starting (`O39`, `WORD-7`; `proxy-settings-01`).
   - Words: "devhost config file" for `config.toml` and "shared Caddy settings" for its `[caddy]` table, never "settings file", "global config", "machine config" or "proxy config" (`WORD-1`; `language-02`); `devhost start --help`'s `domainSuffix` paragraph names the devhost config file and its path the same way; stacks by name, with the worktree label when two share a name (`WORD-1`, `WORD-11`, `SEL-4`; `language-01`).
   - `devhost caddy privileged-ports` says what it does before it does it: its help line reads "Let Caddy listen on ports below 1024 without root (Linux; downloads Caddy if needed and asks for your password)", and on Linux a download it needs prints first-run-setup's download lines: what downloads and from where before it starts, "Downloading Caddy for Linux amd64 from caddyserver.com…", its progress as it arrives, and the size once known, "Installed Caddy 2.11.9 at ~/.local/state/devhost/caddy/caddy · 48 MiB · 9.4 s"; caddyserver.com's download sends no length, so neither the size nor the version is known before it, and this flow follows first-run-setup's proposed exception to `WORD-9`'s "with the size". Before `sudo` it prints "Granting Caddy ports below 1024 runs sudo setcap and may ask for your password", replacing today's "managed caddy privileged-port setup may prompt for your password because granting low-port bind capability is privileged." (`WORD-9`; `review-05`, `proxy-settings-05`). On macOS it no longer claims that no setup is needed: "macOS lets Caddy listen on ports below 1024 on every interface without setup. bindHost = "127.0.0.1" applies on macOS only from port 1024; use httpsPort = 4443 for loopback-only HTTPS." (`O39`). On Linux, `devhost caddy download` that replaces a binary holding the grant ends with "Run devhost caddy privileged-ports again: the new Caddy cannot use ports below 1024" on its own line (`WORD-8`, `WORD-9`; `proxy-settings-05`).
   - Under `AGENT=1`, `devhost caddy privileged-ports` refuses before any `sudo` with one line, "Ask the person to run devhost caddy privileged-ports in a terminal", as `REV-8` requires of every step that asks for a password, because a cached `sudo` ticket would otherwise let an agent change Caddy's capabilities silently (`REV-8`, `WORD-9`; `review-05`).
   - Keys: none; terminal output only.
2. **Change a setting, with its reach stated before the save (an editor, or the Configuration window and `/__devhost__/config/validate`; one write, applied through hot reload).** The person edits the `[caddy]` table, or `domainSuffix` or `[remote]`, in any editor and saves; nothing asks, because a save is reported, never reviewed (`REV-1`, `REV-10`; `review-03`, `review-06`). The Configuration window is config-editor's surface: off by default (owner rule), and with it on, it reads and saves from this machine and from a browser in another environment that signed in with the shared devhost passkey or paired; a browser that has not shows **Config** in the unauthenticated state, "Sign in with passkey or pair this browser to use devhost here" (`O36`, `O38`, `O54`, `HOLD-7`, `HOLD-8`). With "devhost config file · ~/.config/devhost/config.toml" picked under the machine's name, "devbox", the line "Changes here apply to every stack on devbox" sits under the header (`O61`), and beside **Save** one line states what saving the draft will do, from the backend's check of it (Backend 9; `REV-10`, `SEL-1`, `SEL-6`, `SEL-11`; `selection-06`, `review-03`, `review-06`, `language-01`). This flow gives each setting its words; config-editor draws the line:
   - `httpsPort`: "Saving moves the URLs of 3 stacks to port 4443: Acme Shop, Docs and Blog; no service restarts"; the stacks are listed by name in the line's tooltip and accessible description when there are more than two (`SEL-1`, `SEL-6`, `O45`).
   - `http` and `httpPort`: "Saving adds plain HTTP on port 8080 to 3 stacks: Acme Shop, Docs and Blog", or "Saving removes plain HTTP from 3 stacks".
   - `bindHost`: "Saving makes 3 stacks reachable only from devbox: Acme Shop, Docs and Blog; relay previews and SSH forwards still reach them"; the other way, in the warning style, "Saving makes 3 stacks reachable from devbox's network: Acme Shop, Docs and Blog" (`O39`, `O61`). On macOS, with any listener below port 1024, in the warning style: "Saving keeps 3 stacks reachable from devbox's network: on macOS, bindHost 127.0.0.1 needs every port at 1024 or above, such as httpsPort 4443" (`O39`). Browser surfaces say "devbox's network", because their reader may be elsewhere; the terminal says "your network" (`O61`).
   - `stackDirectoryHost`, a custom hostname removed so the directory returns to its default: "Saving moves the stack directory to https://devhost.localhost:4443/".
   - `stackDirectoryAllowRemote = true`, in the warning style: "Saving lets anyone on devbox's network read the stack directory without signing in, with every stack's URLs and raw configuration files; signed-in browsers read it already" (`O47`); while Caddy listens on loopback only, "Saving changes nothing while Caddy listens only on 127.0.0.1 and [::1]: other devices cannot reach the stack directory directly"; on macOS with `bindHost = "127.0.0.1"` below port 1024, where Caddy keeps every interface, the warning stands with the macOS note of `bindHost` above (`O39`).
   - `adminAddress`: "Saving moves Caddy's admin API to 127.0.0.1:2019; no URL changes".
   - `domainSuffix`: "Saving changes Blog's hostnames after its next start: blog.localhost → blog--devbox.example.com; Acme Shop and Docs keep theirs", naming only the stacks whose accepted manifest has a short host label; with none, "Changes no hostname that runs" (`proxy-settings-08`).
   - `[remote]` while a stack runs in remote mode: "Saving changes Acme Shop's relay settings after its next start; the rest applies now" (`relay-previews-08`).
   - Nothing that runs changes: "Changes nothing that runs".
   - When the save moves the address of the page the window is open on, the line adds "This page moves to port 4443; its unsent chat text and page context come along", because the page hands them to the control server before the move (step 5); nothing is discarded, so no question asks (`REV-3`, `UNDO-2`).
   - These are statements, never a question: **Save** stays available beside them (`REV-10`). The plan comes from `/__devhost__/config/validate`, which returns what saving would do (`CC-37`). Problems the check finds (Backend 2) show in the window's problem list on their line before the save, in the words of step 6 ("line 3: port 4443 is in use by nc (PID 77959) on 127.0.0.1"), and a draft the check refuses is not saved, as config-editor's save does today (`MENU-4`, `REV-11`). The statement and the problems are checked again whenever the running shared Caddy settings change, for example when another stack's start applied the file, so the line never describes settings that no longer run (`REV-13`; `review-14`).
   - Keys: the Configuration window's own (Mod+S saves, config-editor's row of the 2.11 keyboard map).
3. **devhost checks the change, tells open pages, then moves Caddy once (the apply; part of the one write).** Every running stack watches `config.toml`, as today, and the first to take the route lock every devhost process shares applies the change once for the machine; settings another process already applied are not applied twice (Kept). The `[caddy]` part always applies for the whole machine; `domainSuffix` and `[remote]` are decided per stack and never hold the rest of the save back (step 7). Before anything moves, devhost runs every check it can (`REV-11`; `review-07`, `feedback-04`): the file's validation, each problem with its file, line, column and key (Backend 1; `MENU-4`); a probe of each new listener port (`httpsPort`, and `httpPort` while `http = true`) on 127.0.0.1, ::1 and the bind host, which names the program and PID that hold it, Caddy's own current listeners excluded (Backend 2; `proxy-settings-02`); and a `stackDirectoryHost` that a running stack's service uses (Backend 2; `proxy-settings-04`). A failed check refuses the change with nothing moved (step 6).
   - When the change moves a listener (a port, `http`, or the bind host), the process that applies it first tells every running stack through its control server on the loopback control port the state directory records, and each stack sends each open page whose address changes the message `{"type": "listeners-moving", "origin", "operationId"}` with that page's own scheme and hostname on the new port (Backend 4; `HOLD-2`; `review-14`, `feedback-11`, `status-04`, `proxy-settings-03`). A stack that does not answer within 1 s never holds the move up. A page opened through a relay preview keeps its address, because its public port stays 443 whatever Caddy's port is, so it receives no `listeners-moving` (step 7).
   - Caddy then moves in one reload under the route lock, as today. On macOS, a loopback `bindHost` with every listener at port 1024 or above now listens on 127.0.0.1 and [::1] only, as on Linux; below 1024 Caddy keeps every interface and the warning of step 1 prints (Backend 3; `O39`, `proxy-settings-01`). Every configured route moves with it, the 24-hour routes of recently stopped stacks included, so a stopped stack's tab still opens its stopped-stack page over HTTPS at the new port, while an unconfigured hostname still gets no certificate (`O63`, `O15`). devhost then certifies the move on every address the bind host resolves to (127.0.0.1 and [::1] for every interface or `"127.0.0.1"`, [::1] alone for `"::1"`): a TLS handshake on the HTTPS listener reaches Caddy with the stack directory's hostname, which TLS serves because it is configured, and a plain request on the HTTP listener while `http = true` is answered by Caddy, within 5 s (Backend 6; `FB-5`; `feedback-04`, `proxy-settings-02`). Only then does devhost write the record of what Caddy runs; when the handshake fails, it reloads Caddy back to the running settings and the change is not applied, with its cause (step 6).
   - Services, routes, terminals and chat sessions keep running, and moving URLs never changes a service's state or restarts a service (`ACT-2`, `O45`; `status-01`). `adminAddress` moves with the reload, and `devhost caddy stop` and `devhost caddy trust` keep finding Caddy at the address it runs (Kept).
4. **Read the outcome in every stack's terminal and log (one line per stack).** Every running stack follows the record of what Caddy runs, whoever moved it: a save of `config.toml`, another stack's `devhost start`, a `devhost serve` session's start, or `devhost caddy start` (Backend 7; `proxy-settings-07`). When the record changes, the stack takes its URLs from it, publishes its state, and prints one outcome line in its terminal and log, then only what changed: the URLs that moved, labelled by service, and stack-run-stop's directory line (`FB-3`, `FB-7`, `FB-10`, `WORD-4`, `CC-22`; `feedback-02`, `feedback-03`, `feedback-05`, `feedback-15`, `language-08`, `language-11`, `proxy-settings-04`):

   ```text
   Applied config.toml: HTTPS port 443 → 4443 · 1.4 s · after config.toml changed on disk
   web    https://shop.localhost:4443/
   api    https://shop.localhost:4443/api/
   All stacks on devbox: https://devhost.localhost:4443/
   Proxy: HTTPS on port 4443, every interface, reachable from your network · ~/.config/devhost/config.toml
   ```

   - Each changed key is named with its old and new value in the person's words: "bindHost 0.0.0.0 → 127.0.0.1: direct connections from this machine only"; "stack directory moved to https://devhost.localhost:4443/"; "plain HTTP on port 8080", followed by each service's HTTP URL beside its HTTPS one ("web http://shop.localhost:8080/"), because a tunnel needs that address; "adminAddress 127.0.0.1:20197 → 127.0.0.1:2019" (`FB-3`, `WORD-4`; `proxy-settings-04`). A change of `bindHost` or a port adds the proxy line of step 1, and its warning when one applies (`O39`, `proxy-settings-01`). A loopback `bindHost` saved on macOS below port 1024 prints "Applied config.toml: bindHost 0.0.0.0 → 127.0.0.1 · nothing moved · 0.3 s · after config.toml changed on disk", then the proxy line and the warning.
   - Turning `stackDirectoryAllowRemote` on adds one warning line: "Anyone on your network can now read https://devhost.localhost/ without signing in, with every stack's URLs and raw configuration files." (`WORD-7`, `O47`; `proxy-settings-04`).
   - The origin ends the line as the record names it: "· after config.toml changed on disk" for a save, "· from the terminal (devhost start in ~/blog)" or "· from the terminal (devhost caddy start)" for a start that applied the file (`WORD-4`, `ACT-1`). A save that changes nothing that runs prints "Applied config.toml: nothing changed" (`FB-10`).
   - Agent output prints the same facts on one line in its own layout, with the absolute path and every changed key's old and new value (`WORD-9`, `FB-11`; `language-16`). The full URL list is never printed again; it prints at the first start and on request, `devhost status` (`FB-10`, `CC-22`, `O62`).

5. **Open pages follow the move (the page's status stream; read only, and one navigation the person chooses).** A page that receives `listeners-moving`, which carries the old and new address of each listener, keeps working on the old address while it answers and shows the activity line "◐ Moving to port 4443" (`FB-13`, `FB-1`, `WORD-4`). The page stops retrying the old address once the new one answers.
   - On `listeners-moving`, before its stream closes, the page hands its unsent chat text, pasted images and page context to the control server's draft record under the new address (`UNDO-2`), so **Open** brings them back; configuration drafts are kept per stack and file and are unaffected.    - Between the stream's close and the new address answering, every service keeps its last known state drawn as unknown with "last seen 14:02", never down or failed (`CC-26`); once the new address answers, the toolbar is live again from it, and its service links name port 4443 (`ACT-5`, `ACT-2`, `ACT-12`; `status-01`, `status-04`). notices-and-feedback draws the lost-connection state; this flow supplies the move's cause.
   - Every write on the old page (Restart, Restart Changed and its key, Start, Restart Stack, switches, Save, Send) is unavailable with one reason, said once in the notice and in each open panel's status line and given to each blocked control as its accessible description: "This page still uses port 443. A reload the page's dev server asks for meanwhile is a detail of this notice, never a **Reload blocked** whose **Reload Now** loads the closed port (notices-and-feedback's).
   - The Configuration window that saved the change shows the move beside **Save** while it runs, "Moving 3 stacks to port 4443…", then its outcome from the record once the new address answers: "Applied config.toml: moved the URLs of 3 stacks to port 4443 · 1.4 s", with "This page continues at https://shop.localhost:4443/admin?tab=2" and **Open**; focus moves to the outcome's sentence (`FB-2`, `FB-9`, `KEY-11`). ## What changes versus today

- **Removed:** the silent widening of `bindHost = "127.0.0.1"` to every interface on macOS, replaced by a loopback listener from port 1024 and an explicit warning below it; "Applied the shared Caddy settings from \<path\>." followed by every service URL again, replaced by one outcome line and only the URLs that moved; "shared Caddy settings rejected: \<error chain\>", replaced by step 6's line; the toolbar title "devhost config change not applied", replaced by "devhost config file not applied"; "managed caddy does not need privileged-port setup on macOS.", replaced by what applies; every service drawn down on a page whose port moved, and its endless retry of the closed address; the stack directory collision that names only a PID; a `domainSuffix` or `[remote]` change that refuses the whole save in every stack, replaced by a wait in the stacks it changes; a relayed page refused whenever Caddy is not on port 443.
- **Merged:** "Applied the shared Caddy settings", "shared Caddy settings rejected" and "devhost config change not applied" become one event, applied or not applied (`WORD-1`); each stack's private copy of the shared Caddy settings, each relay lease's captured backend and the record of what Caddy runs become one record that every URL, link, list, the relay connector and the stack directory read.
- **New:** the devhost config file's path in `devhost caddy --help`, the proxy line at `devhost caddy start`, `devhost start` and `devhost status`, and its macOS warning below port 1024; the statement of each setting's reach beside **Save**; the checks before the move (held ports with their holder, a directory hostname in use); the certification of the new listener and the restore when it fails; `listeners-moving` and pages that follow their stack to the new address with **Open**; the change summary with each key's old and new value; plain-HTTP URLs printed while `http = true`; the remote-access warning; the restore line and the repeat count; the waiting-suffix and waiting-relay lines and notice with **Copy Command**; the connector's unreachable-Caddy line and its start self-check; privileged-ports' help line, its download and password notices, its refusal under `AGENT=1` and the re-run line after a download on Linux.
- **Changed:** on macOS, `bindHost = "127.0.0.1"` listens on loopback when every port is 1024 or above, and below that keeps every interface with a warning on every start and save, a documented behavior that changes (Project contracts); running stacks and relay previews follow a change that a start applied, where today only each stack's own watcher moved it; a held port is refused before the move, as the docs already promise; a rejection clears whenever `config.toml` matches what runs, from any path; a routing change waits only for the stacks whose hostnames or relay it changes; the relay connector holds no machine-wide lock per request.
- **Kept:** walking every safeguard of the current flow:
  - The devhost config file's location: `DEVHOST_CONFIG_DIR`, else `XDG_CONFIG_HOME/devhost`, else `~/.config/devhost` on every platform; a missing file leaves every setting at its default.
  - Every running stack watches `config.toml` with the manifest's debounce and applies one save at a time, without restarting services, routes, terminals or chat sessions (`REV-10`, `O45`, owner rule).
  - Caddy moves in one reload under the route lock every devhost process shares, including a new `adminAddress`; settings another process already applied are not applied twice; `devhost caddy stop` and `devhost caddy trust` find Caddy at the admin address it runs.
  - An invalid file, a claimed directory hostname or a reload Caddy refuses keeps Caddy on the settings it runs, and its files are rendered back for them; now a held port and an uncertified move do the same (`HOLD-6`, `REV-11`).
  - Validation names each bad key: unknown keys, ports outside 1 to 65535, an empty `adminAddress`, an unsupported `bindHost`, a `stackDirectoryHost` with a scheme, port or path; a `[caddy]` table in a manifest is rejected naming the devhost config file; now each with its line and column (`MENU-4`).
  - A repeated rejection is printed once, now with its count (`FAIL-4`).
  - Routing settings (`domainSuffix`, `[remote]`) apply to a running stack only at its next start, as documented; now only the stacks they change wait, and the rest of the save applies.
  - The config editor is off by default; it validates the same file before writing it and creates a missing file (owner rule). Saves now come from this machine and from browsers signed in elsewhere (`O54`), and an unauthenticated browser reads and saves nothing (`HOLD-7`).
  - The stack directory answers this machine and signed-in browsers (`O47`), and anyone on the network only with `stackDirectoryAllowRemote`, read-only, with same-origin checks; setting the option back to `false` withdraws anonymous access on reload.
  - Strict TLS for configured hostnames only: an unconfigured hostname over HTTPS gets no certificate, and recently stopped stacks keep their routes for 24 hours (`O63`, `O15`).
  - `bindHost` defaults to every interface, as documented (owner rule); a loopback `bindHost` on Linux listens on loopback only.
  - `devhost caddy privileged-ports` grants low ports on Linux with `setcap`, downloading Caddy first when needed; devhost sets up no `authbind` or firewall redirect.
  - `devhost caddy start` and every stack that starts apply the file's settings; Caddy keeps its settings until `devhost caddy stop`, and the next `devhost caddy start` reads the file again; a runtime-policy upgrade restarts Caddy once with its own line.
  - Only a person changes the machine's certificate trust, at a terminal (`REV-8`).

## Backend and contract changes

**Backend** (`apps/devhost/src/config.rs`, `apps/devhost/src/caddy.rs` and `apps/devhost/src/caddy/`, the stack runtime in `apps/devhost/src/services/stack.rs` and `apps/devhost/src/services/stack/runtime.rs`, the control server in `apps/devhost/src/devtools/`, the relay in `apps/devhost/src/remote/` and the CLI in `apps/devhost/src/main.rs` and `apps/devhost/src/cliout.rs`, preserving one Caddy reload under the route lock per change, no second apply of settings already applied, the running settings kept on every refusal, services, routes, terminals and chat sessions kept running, the config editor off by default, the default listener on every interface, strict TLS for configured hostnames only, and the admin address that `devhost caddy stop` and `devhost caddy trust` follow):

1. **Structured issues for the devhost config file.** `config::parse` (`apps/devhost/src/config.rs:143-218`) returns each issue with its file, line, column and key, the offending line and, for an unknown key, a close key when one exists, instead of "devhost config \<path\> is invalid:" followed by bare messages; human output and the toolbar build step 6's sentences from it, while the original text stays for **Copy Error** and agent output's one `devhost: ERR:` line. This is the devhost config file's half of `MENU-4`'s one structured error. Serves `proxy-settings-04`. Required.
2. **One check before every move.** A save, `devhost start`'s apply, `devhost caddy start` and the validate route run the same check before Caddy moves: each new listener port probed on 127.0.0.1, ::1 and the bind host, naming the program and PID that hold it, with Caddy's own current listeners excluded (manifest-hot-reload builds this probe for fixed service ports, `REV-11`); a `stackDirectoryHost` checked against every running stack's claimed hostnames, naming the stack, the service and the manifest file and line, in place of "stack directory hostname \<host\> is already claimed by PID \<pid\>" (`apps/devhost/src/caddy/files.rs:195-214`); and a service hostname that `stackDirectoryHost` reserves refused at start with the devhost config file's path, line and key. A failed check moves nothing. Serves `proxy-settings-02`, `proxy-settings-04`. Required.
3. **A loopback listener on macOS from port 1024 (`O39`).** `render_caddyfile` (`apps/devhost/src/caddy/files.rs:497-534`), whose `"127.0.0.1" if cfg!(target_os = "macos") => ""` drops the bind on every port today, renders `default_bind 127.0.0.1 [::1]` on macOS when every enabled listener port is 1024 or above, as on Linux, and keeps every interface below that; the resolved listeners and whether the macOS warning applies are part of the record (Backend 7) that the proxy line and the warning read. `start_failure`'s macOS hint (`apps/devhost/src/caddy.rs:621-645`), which tells people to leave `bindHost` out, gives the same fix as the warning. Ships with the agent-chat redesign (`O39`, `O36`). Serves `proxy-settings-01`. Required.
4. **Pages told before the move.** Before reloading Caddy to settings that change a listener port, `http` or the bind host, the applying process calls each running stack's control server on the loopback control port the state directory records, with the operation ID and the new settings; each stack sends `{"type": "listeners-moving", "origin", "operationId"}` on `/__devhost__/ws/health` (`apps/devhost/src/devtools/streams.rs:138-169`) to each page whose origin changes, with that page's scheme and hostname and the new port, and answers; the applier waits at most 1 s per stack. Relayed pages, whose public origin does not change, receive none. Each stack also keeps the drafts it holds per page origin (`UNDO-2`'s chat draft record) under the new origin, so a page opened there finds the unsent text and page context its old page handed over. notices-and-feedback's Backend 3 names this message beside `stack-ended` and `proxy-stopping`. Serves `proxy-settings-03`. Required. Contract: `CC-26`.
5. **The status stream from the old address.** The control server accepts a `/__devhost__/ws/health` upgrade from a page of one of the stack's hostnames on the HTTPS or HTTP port it served before the last move, because that stream takes no commands; every write keeps today's origin check (`apps/devhost/src/devtools/server.rs:200-217`, `apps/devhost/src/caddy/devtools_origin.rs:17-60`), so a page left on the old address can read its stack's state and the move's record, never write, and `O36`'s check still applies to a client that is not this machine. The backend owners confirm this against the control API's security model when they build it. Serves `proxy-settings-03`. Required.
6. **The move certified, and restored when it fails.** After the reload, devhost certifies each new listener on every address its bind host resolves to (127.0.0.1 and [::1], or [::1] alone for `"::1"`): a TLS handshake on the HTTPS listener with the stack directory's hostname as the server name, which configured-hosts-only TLS serves (`O63`, `apps/devhost/src/caddy/files.rs:539-552`), requiring Caddy's certificate, and a plain HTTP request on the HTTP listener answered by Caddy, within 5 s; otherwise it reloads Caddy to the running settings, as `apply_managed_settings` already renders them back after a refused reload (`apps/devhost/src/caddy/routes.rs:509-535`), and reports the change not applied with the cause; only a certified move writes the record of what Caddy runs. The reload re-renders every configured route on the new port, `O63`'s stopped-stack routes included. Serves `proxy-settings-02`. Required. Contract: `CC-27`.
7. **One record of what Caddy runs, followed by every stack.** The record `write_applied_settings` writes (`applied.json`, `apps/devhost/src/caddy/files.rs:47-60`) gains the operation ID, the origin (a save of `config.toml`, `devhost start` or a `devhost serve` session with its folder, `devhost caddy start`), the time, the resolved listeners and the `config.toml` text the settings were read from; every running stack watches it beside `config.toml` and, when it changes, replaces its copy (today `apply_shared` keeps one per stack, `apps/devhost/src/services/stack/runtime.rs:671-716`), publishes its state, prints its outcome line and clears its devhost config file rejection when the running settings equal `config.toml`; `collect_manifest_service_urls`, `log_service_urls` (`apps/devhost/src/services/stack.rs:2034-2073`) and the toolbar's service links read their ports from it, as the stack directory already does; **Show Differences** and **Restore Running Version** read its text. Serves `proxy-settings-07`, `proxy-settings-04`. Required.

Required. Contract: `CC-37`, `CC-23`.

After the relay lease is taken, the stack sends one guarded no-op through the connector's own loopback listener and fails its start with a named cause when its own public origin is refused. Serves `relay-previews-01`. Required.
15. **The connector follows the record.** A lease stops capturing Caddy's address at start (`apps/devhost/src/services/stack.rs:2002-2032`); the connector reads the backend address from the record of what Caddy runs (Backend 7) whenever it changes, so a move by any stack, start or session reaches every preview; when it cannot reach Caddy, the remote stack prints one line naming the address it tried and the fix. Serves `relay-previews-08`. Required.
16. **The connector's request path.** The connector keeps the lease table in memory, reloaded within 250 ms of a change, instead of taking the exclusive state lock and rereading every lease on each request (`apps/devhost/src/remote/proxy.rs:39-47`, `apps/devhost/src/remote/state.rs:72-100`), and reuses one keep-alive TLS client per backend with its root certificate cached, instead of a new connector and handshake per request (`proxy.rs:72-75`, `apps/devhost/src/remote/proxy/backend.rs:24-53`). ## Recommended priority

**P1.** The realistic triggers are two deliberate settings. A person on shared Wi-Fi sets `bindHost = "127.0.0.1"` on macOS to keep unreleased apps, admin panels and manifests private, and every stack stays reachable from the network while devhost says nothing (`proxy-settings-01`). A person on a Linux machine without the low-port grant, or following the docs' 4443 example, enrolls it for relay previews, and every relayed toolbar reads the stack as down while every control answers `403` (`relay-previews-01`). The other triggers are rarer and cost time rather than data: moving `httpsPort` turns every open tab of every stack red with no new address (`proxy-settings-03`), a port that a local dev server holds on loopback is reported applied while IPv4 clients reach that server (`proxy-settings-02`), a `domainSuffix` change refuses the whole save in every stack (`proxy-settings-08`), a move leaves previews on a closed port (`relay-previews-08`), saves and rejections leave every terminal on a misleading last line (`proxy-settings-04`, `proxy-settings-07`), relayed module bursts queue (`relay-previews-07`), and apps on any port but 443 build public URLs that do not answer (`proxy-settings-06`). Nothing is lost in any of them, and a refused change keeps the running settings, but the exposure is silent until someone checks. Machine-wide settings change far less often than stacks start and stop, which keeps the rest of the flow below stack-run-stop.
