# Keep agent edits from reloading the page: proposed experience

Diagrams: [current](../reload-control-current.html), [proposed](../reload-control-proposed.html). [Wireframe](../wireframes/reload-control.html). Research: [Keep agent edits from reloading the page: research](reload-control-research.md).

Status: design proposal, not implemented behavior. The [shared UX pattern reference](../patterns.md) wins where this proposal disagrees with it.

Source revision: alexgorbatchev/devhost `190a8bb53e8cd903d2db0a92cb0886f29671607f` (Rust `main`). The current-flow diagram and the research note stay at the pre-Rust revision `edb5c0fc`. Features: RLD-01, RLD-02. Redesign ticket: tracked privately.

Product rule: the product owner decided Disable Reloads on 2026-11-16, recorded as `O2` in the pattern reference: the label **Disable Reloads** stays, and pressing it opens a confirm popover anchored to the hot reload notice that names the agent and shows the exact, editable request written for the detected framework (Bun `development.hmr`, Vite `server.hmr`, Next.js and webpack switches), scoped to this worktree, with **Send** and **Cancel**, and offers **Hold Reloads** as the path without an agent. The request goes out in the **This worktree (live)** chat edit mode, which edits the worktree the person has active, main's included, and never creates another (`O1`). On 2026-11-18 the owner settled how later chat turns reach the page: **Disable Reloads** wins. Once a Disable Reloads request takes effect, devhost never reloads the page by itself after a later turn, and each turn that changed files ends with "Reload to see the change" and **Reload Page** (`O56`, reversing the recommendation). Until then, while **Hold Reloads** is on, a turn's end applies the reloads its edits caused once, unless the person is typing (`O57`). The owner's standing rules add that **Hold Reloads** also holding the app's own `location.reload()` is a documented limitation, and that devhost never answers or pre-approves an agent's approvals or questions. So a coding agent editing this worktree's dev server configuration at the person's request is intended, the hold catching the app's own reloads is intended, and the agent's approvals staying the person's to answer is intended; none of them is a defect. The gap is around them: today the request leaves on one click, unseen, generic and carrying devhost's worktree, commit and merge instructions; nothing afterwards says what the agent changed, whether reloads stopped or which restart the change still needs; and the hold itself can drop, hide or silently stop holding a reload.

## Target experience

The person opens an app page whose dev server reloads it when files change. With chat on, the notice stack beside the bar says "Vite reloads this page when files change" with **Disable Reloads** and **Dismiss**, while **Hold Reloads** on the bar, on by default, already keeps every script reload from replacing the page. Pressing **Disable Reloads** sends nothing: a popover anchored to the notice, titled "Ask Claude Code to turn off reloads?", names the agent and model, says that the request starts a new conversation and offers each open conversation of this worktree by its title instead, shows "This worktree (live) · main ~/acme" with no new worktree, commit or merge, and holds the request itself, written for Vite's `server.hmr`, editable, with focus in it. **Send** sends the text as edited; **Cancel**, Escape, Tab out of the popover or a click outside it send nothing and leave no conversation or process behind. After **Send** the notice keeps its slot as the request's progress, "Request sent to Claude Code · working · 40 s"; when the agent asks, it reads "Claude Code is waiting for you · Edit vite.config.ts?" with **Answer**, one activation from the decision card. When the turn ends, the same slot shows the result in place of **Disable Reloads**: what the agent changed and what devhost observed, "Request done: Claude Code changed vite.config.ts · Vite's client still loads until web restarts", with **Restart web**, never a claim the page cannot show. From that result on, reloads count as disabled for web in this stack, in every browser: a later chat turn that changes files never reloads the page by itself and ends with "Reload to see the change" and **Reload Page**, devhost's own reload, which goes through the hold. Throughout, the reloads the agent's edits cause wait on **Reload blocked**, which counts them, names the changed files under the page's service's watch paths and says when the page is already current; dismissing it leaves "2 held" on **Hold Reloads**, and turning the hold off keeps them as "2 reloads pending" with **Reload Now** instead of dropping them or reloading under the person. Before any request takes effect, a chat turn that changed files and ends while this page holds reloads its edits caused applies them once, as devhost's own reload, unless focus is in a text field, where **Reload blocked** keeps them with **Reload Now** and says the reload waits for the person. Dismissing the hot reload notice offers **Undo**, and **Show Reload Notice** in the Hold Reloads popover brings it back later. devhost cannot take back an agent's edit, so the request has no Undo of its own: its result lists the files the turn changed with **Copy Reverse Patch** and **Ask to Undo**, beside the agent's reply saying how to turn reloads back on, and the page's own work survives because no reload happens until the person chooses it. Benchmarks: Cursor's Add to Chat and Claude Code's IDE chat put text in front of the person with the model and mode before anything is sent, which the popover does for a request devhost writes; Vite's and Bun's documentation name `server.hmr` and `development.hmr`, which the request names instead of describing reloads in general; VS Code's "Reload Window" notifications let a change wait for **Reload Now** instead of reloading under the person, and its notification center keeps a dismissed notification reachable, as **Show Reload Notice** does; Gmail's **Undo** follows a dismissal; the Next.js dev indicator keeps its issue count on its collapsed badge, as the held count stays on **Hold Reloads**; Claude Code and Codex list the files a turn edited, which the result reuses for its way back.

## Target steps

Today: 6 steps on the main path, the last two a guess: read the notice; press **Disable Reloads**, which opens chat and sends an unseen, generic request at once; answer the agent's approvals in chat; press **Reload** on the **Reload blocked** that the agent's own manifest edit raised; read the notice back word for word; then find out alone that the dev server needs a restart, restart it from the terminal, or from the Services panel when a `watch` covers the edited file, and reload again. Proposed: 5 steps, every one in the notice's slot: read the notice; review the request in its popover; **Send**; follow the request and answer the agent in one activation; read the result and apply it with **Restart web**, after which the reload it causes waits on **Reload blocked** for the person's **Reload Now**. The path without an agent stays one step: **Hold Reloads** is on by default, and applying what it held is one press of **Reload Now**.

Visible text calls the dev server's mechanism reloads and never hot reloading, which names applying a manifest (`WORD-1`). **Disable Reloads** keeps its label (`O2`), and its accessible description says that an agent receives the request: "Opens a request for Claude Code to turn off reloads in this worktree; nothing is sent until you press Send" (`REV-5`). The notice is a card named by its sentence with no live role, so it is never announced on load: it is standing information, not news, and the announcer reads only its request's start and result (`FB-9`); every notice of the stack follows notices-and-feedback's component and announcer. It sits in `FB-8`'s third group, newest first,, with **Reload blocked**, below anything that needs the person (`FB-8`). While the toolbar is collapsed it keeps its one-line form beside the badge, "Vite reloads this page", which opens the popover of step 2 from there (`SURF-8`); while the page's own modal dialog is open it moves into that dialog with the notice stack and stays operable (`SURF-11`); toolbar-shell places both forms.

## Recommended priority
