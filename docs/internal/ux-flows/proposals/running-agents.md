# See the agents working in this checkout: proposed experience

Diagrams: [current](../running-agents-current.html), [proposed](../running-agents-proposed.html). [Wireframe](../wireframes/running-agents.html).

Status: design proposal, not implemented behavior. The [shared UX pattern reference](../patterns.md) wins where this proposal disagrees with it.

Source revision: alexgorbatchev/devhost `edb5c0fc01cabae490e92ac23d4c785ec896c4ed`. Features: AGT-01, AGT-02. Redesign ticket: tracked privately.

Product rule: the owner settled that **Watch Live Activity** lives on `http://127.0.0.1:<port>` on purpose and that devhost never answers or pre-approves an agent's approvals or questions; `guides/devtools.md` adds that the list "only reports: it cannot send anything to an agent", and that it "needs `[devtools.chat].enabled`". So a loopback-only activity page in its own tab, a list that cannot answer a terminal agent, and no agents shown while chat is off are intended, not defects. The gap is around them: with chat docked the list opens under the chat panel, its rows name agents by internal IDs and "." (`reload-and-agents-05`), the control vanishes at zero and when a scan fails, so "none" and "could not look" read the same (`reload-and-agents-09`), Watch Live Activity never says what a tool call touches or that an agent waits for the person (`reload-and-agents-06`), after the stack stops it says Reconnecting forever (`reload-and-agents-10`), and on a page opened from another computer its link opens that computer's own `127.0.0.1`, with nothing saying the page opens only on the stack's machine (`reload-and-agents-13`).

## Target experience

The person glances at the bar: the running agents trigger always sits in its place and counts the agents in this checkout, "2 · 1 waiting", in a waiting look of its own that differs from a working agent's spinner, and it says "0" with "No agents in this checkout" when none run, or that running agents are shown while chat is on. Opening it, from the pointer or as one arrow stop of the bar, shows an anchored list above docked chat, never under it: a status line naming the checkout, the count and when devhost last looked, then one row per agent in words people use. An agent chat started reads by its conversation and edit mode, "Claude Code · Fix the nav header · This checkout (live)", with **Answer** while it waits for the person, which opens its decision card in docked chat in one activation, and **Open Conversation** otherwise; an agent started in a terminal reads "Codex in a terminal · PID 83275" with its state, its folder in the checkout ("checkout root", never ".") and its last activity, and, when it waits, says to answer it in its terminal, because devhost never answers for anyone. When devhost could not list some agents, the trigger carries an incomplete mark and the list says which agents and what to do, with **Check Again**; it never claims there are none. After a switch, agents still working in the checkout the stack left stay listed under that checkout. **Watch Live Activity** opens in its own tab on the machine's loopback address; on a page opened from another computer it stays in its place, unavailable, saying that it opens only in a browser on the machine that runs the stack, so the page never sends its address to the viewer's own computer. The activity page names the stack and checkout it watches, groups entries under each agent with its state, and labels them Reply, Tool call, Result and Denied, each tool call with its command or file; an agent waiting for the person shows as waiting until it is answered, and when the stack stops the page says so, with the command that starts it again, and stops reconnecting. Nothing in this flow writes: the list and the page only report, so there is no Undo; the one way to act on an agent is the person's own answer in chat or in the agent's terminal. Benchmarks: VS Code's terminal list names each terminal by its process and keeps the list in place when it empties; Claude Code and Codex CLI show a tool call's command or file and diff before its result, which Watch Live Activity follows; GitHub Actions' live log keeps each step's command beside its output and says when a run was cancelled instead of spinning; Docker Desktop's container list keeps its empty state with a sentence instead of disappearing; htop and Activity Monitor tell two processes of one program apart by PID; Kubernetes reports Unknown rather than an empty list when it cannot see a node. Competitor behavior is evidence here, never a requirement.

## Target steps

Today: 6 steps to learn that an agent waits for the person: notice a count (only while one runs), close docked chat, open the list, decode "claude-code · project-37 · this chat" and "Waiting for approval · .", open Watch Live Activity, and scan raw event lines that never show the wait. Proposed: 3 steps: the trigger's waiting look, the agent's row, **Answer**, which lands on the decision card. Watching stays 3 steps (list, Watch Live Activity, read), but each entry now says what the tool touched.

Its accessible name counts in words, "Running agents: 2 agents · 1 waiting for you", and its accessible description names its scope, "this checkout" (`WORD-5`, `WORD-6`; `language-14`, `language-13`). Keys typed into the filter never reach the page (`KEY-5`).
3. **Go to a chat agent's conversation (one activation; the list sends nothing).** **Answer** opens docked chat on that conversation with focus on its decision card's question, in one activation, also for a conversation of another checkout of the stack, which agent-chat makes answerable from this page (`REV-9`, `SEL-8`, `CC-38`; `review-13`); **Open Conversation** opens docked chat on that conversation with focus in its composer, or, for a conversation of another checkout, on its transcript, which takes no message from this page (`SEL-8`, `KEY-6`).    - Entries group under each agent's heading, named as in the list, "Claude Code · Fix the nav header · PID 14625" or "Codex in a terminal · PID 83275", so two agents of one CLI never interleave unnamed; each heading carries the agent's state and since when, "working", "waiting for you since 14:10 · answer in the page's chat" for an agent chat started, "waiting for you since 14:10 · answer it in its terminal" for another, or "idle", from the same state the list shows (`SURF-8`, `ACT-6`, `ACT-7`, `REV-9`, `WORD-6`; `surfaces-06`, `status-12`).    - Keys: the page uses the document's standard keys and has no shortcuts of its own (`KEY-1`); **Retry Now** and **Retry** are ordinary buttons.

- **An incomplete scan.** When devhost cannot list one CLI's agents (a session folder it cannot read, a database it cannot query, the 10 s scan limit), the record keeps what the others found and says which agents it could not list; the trigger carries the incomplete mark with "at least 1" in its accessible name; the status line reads "Codex agents could not be listed: devhost cannot read Codex's session folder. - **The scan fails for every CLI.** The trigger shows the incomplete mark without a count, named "Running agents: could not be listed"; the list keeps the rows it last had, drawn as unknown with "last seen 14:02", under "Running agents could not be listed: the scan did not finish within 10 s. devhost tries again every 10 s." with **Check Again** and **Logs** (`STATE-3`, `STATE-4`, `HOLD-1`).

- **The lost connection.** When the page's status stream closes, the list keeps its last rows drawn as unknown with "last seen 14:02", the trigger keeps its last count drawn the same way, named "Running agents: 2 agents when last seen at 14:02", and the status line carries the one reason the backend sent: after a stop, "Acme Shop stopped at 14:32 by devhost stop. Start it with devhost start in ~/acme", otherwise "Lost connection to devhost; retrying" (`ACT-5`, `HOLD-2`, `STATE-3`; `feedback-11`). Notices-and-feedback owns that notice and **Retry Now**; **Answer** and **Open Conversation** still open chat, which names its own block.
- **A terminal agent waits for the person.** The trigger takes the waiting look, the collapsed badge follows `ACT-7`'s order, and the notice stack shows a condition notice in its first group, "Claude Code waits for you in its terminal · main ~/acme · since 14:10", announced once, with no answer of devhost's own; it clears by itself, announced once, when the agent's state leaves waiting, and **Dismiss** leaves the waiting marker on the trigger until then (`ACT-7`, `FB-8`, `FB-9`, `SURF-8`; `feedback-09`, `status-12`). An agent chat started gets agent-chat's waiting notice with **Answer** instead, never both.
- **After a switch.** After Switch and Restart Stack from main to fix-nav, an agent still working or waiting in main stays in fix-nav's list under "in main ~/acme"; a waiting one keeps the trigger's waiting look and its **Answer** (`SEL-5`, `CC-38`; `selection-05`). agent-chat keeps its conversation listed and answerable (`chat-checkout-switch-01`, agent-chat's), and worktree-switch names it before the switch (`chat-checkout-switch-02`, worktree-switch's).
- **A page opened from another machine.** The agents record says whether this browser runs on the stack's machine (`isLocalClient`, Backend 4): not on a computer or phone that reaches the stack over the network, nor through a remote preview relay. There the activity page can never open, because it answers only direct loopback requests, and a `127.0.0.1` link would open the viewer's own computer, sending the page's URL and chat target to whatever listens on that port, or failing (`reload-and-agents-13`). So **Watch Live Activity** stays in its place under the rows as an unavailable control, `Button`'s unavailable state, never a link: no `127.0.0.1` address is rendered on that page. "Watch Live Activity opens only in a browser on the machine that runs this stack." stands beside it, said once, and is its accessible description; it keeps its Tab stop and announces that sentence when focused, and activating it opens nothing (`MENU-3`, `HOLD-1`, `HOLD-7`, `SURF-15`). The sentence names the way forward: on the stack's machine the link opens the page in its own tab, as today. The rows and their hand-offs to chat are unchanged. This extends `HOLD-7`'s form, unavailable with the reason before the person tries, to a read that works only on the stack's machine (see **Proposed exceptions**).
- **The stack stops while Watch Live Activity is open.** Before closing the stream with 1001, the server sends why: the page stops reconnecting, its state reads "Stopped" and "Acme Shop stopped at 14:32 by devhost stop from a terminal. Start it with devhost start in ~/acme, then open Watch Live Activity from the running agents list on its pages.", and the entries already shown stay under "From the run that ended at 14:32" (`ACT-10`, `HOLD-2`, `STATE-3`, `SURF-15`; `status-13`). The idle timeout reads "stopped at 02:14 after 1 h idle", Ctrl-C "stopped from its terminal", and `devhost stack restart` "replaced by devhost stack restart at 14:32"; a replaced stack's new run listens on a new loopback port the old page cannot learn, so the page shows the run ended and how to come back instead of reconnecting, a proposed exception to `ACT-10` (see **Proposed exceptions**). Restart Stack, a switch and a hot reload keep the same control server, so the page stays live through them, as today.
- **The activity stream cannot start.** When the watcher cannot start (its state files or file watcher cannot be created), the server sends the cause before closing with 1011, and the page reads "Watch Live Activity could not start: devhost could not create its watcher's files." with **Retry**, never Reconnecting (`FAIL-2`, `STATE-4`, `WORD-7`).
- **A dropped connection with no close message.** When the control server dies without closing (killed), the page reads "Lost connection to devhost; retrying · next attempt in 8 s" with **Retry Now**, keeps its entries and retries after 1, 2, 4 and 8 s and then every 10 s, as today (`HOLD-2`, `ACT-5`, `STATE-3`).
- **Many agents.** The list's filter appears when its rows overflow, as step 2 says (`SURF-10`, `SEL-10`).
- **The page's own modal dialog.** The bar shows its paused state; an open list stays anchored and paused, inert, its rows kept, with the moved notice stack's line "Paused while this page's dialog is open", and resumes when the dialog closes; a terminal agent's waiting notice shows in the notice stack inside the dialog (`SURF-11`, `KEY-7`, `FB-9`).
- **Who can reach the agents routes from the network.** That exposure belongs to `network-exposure-01`, `proxy-settings-01` and `serve-folder-04`, which the product owner handles outside the reference; this redesign decides nothing about it, and Watch Live Activity keeps its loopback-only guard (`review-16`).

Proposed exceptions, recorded for the reference's author:

- `WORD-6`: an agent whose CLI records no state reads "state not reported", a phrase that is not a state, because `WORD-6`'s agent states (working, waiting for you, idle, closed) have none for it and any of them would claim what devhost does not know.
- `ACT-10`: Watch Live Activity treats a replaced stack as an ended run, because it lives on that run's own loopback port and cannot follow the new one; it never reconnects to a replacement.
- `HOLD-7`: its form, unavailable with the reason before the person tries, extends to Watch Live Activity, a read that works only on the stack's machine: on a page opened from another machine it stays in place, unavailable, with "Watch Live Activity opens only in a browser on the machine that runs this stack." beside it (`reload-and-agents-13`), as component-source and stack-directory draw their own actions that work only on this machine.
- `WORD-2`: **Answer** and **Open Conversation** are not in its list yet; they carry the meanings agent-chat's and reload-control's proposals give them and are proposed for the list with them.

## What changes versus today

- **Removed:** the control vanishing when no agent runs, when chat is off and when a scan misses every agent, and the sideways jump of the bar it caused; raw CLI IDs ("claude-code"), "." and the CLI's generated session name as an agent's name; "this chat" as the only link to chat; "Waiting for approval" and "Running, state unknown" as state words; Watch Live Activity's raw tokens (tool_call, assistant, run_started), tool output and denials labelled "user", replies shown as unrendered Markdown, and its Reconnecting forever after a stop; the "running agents scan failed" log line repeated on every request.
- **Merged:** the trigger, the list, Watch Live Activity's agent headings and the questions of worktree-switch, agent-chat and stack-run-stop read one agents record with one state per agent: an agent chat started takes its conversation's state, which knows a pending approval for every CLI, and any other agent the state its CLI records.
- **New:** **Answer** and **Open Conversation** on chat agents' rows; the conversation title and edit mode on chat agents' rows; PID and "in a terminal" on other agents' rows; agents of the stack's other checkouts after a separator; the waiting look on the trigger; the incomplete mark, its sentence, **Check Again** and **Logs**; "No agents in this checkout" and the chat-off sentence with **Edit**; the status line with the checkout label and when devhost last looked; a filter when the rows overflow; a condition notice for a terminal agent waiting for the person; the local-client flag on the agents record and, on a page opened from another machine, the sentence beside an unavailable **Watch Live Activity**; on Watch Live Activity, the stack and checkout in its heading and title, per-agent headings with state, each tool call's command, file or edit summary, the entry labels, rendered replies, the waiting state, the stopped, could-not-start and lost-connection states, and the "Waiting for you" title prefix.

## Backend and contract changes

**Backend** (the control server in `apps/devhost/internal/devtools`, preserving the loopback-only guard of Watch Live Activity, the rule that no transcript path, native session ID or tool input reaches the app's origin, one shared scan per 5 s, the chat-off `404`, and that devhost never answers or pre-approves an agent's request):

1. **The agents record.** `GET /__devhost__/agents` answers each agent with `harness` (the CLI's ID, which the shared words module turns into its product name), `pid`, `state` (`working`, `waiting`, `idle`, `not-reported`) and `since`, `checkout` (the `SEL-4` label: branch or "Detached" with the short commit ID, and the `~`-shortened path) with `isPageCheckout`, `subdirectory` (empty for the checkout root), `lastActivity`, `sessionName` when the CLI reports one, and, for an agent chat started, `conversation` (`id`, `title`, `mode`, `state` and `since` from the chat session, which wins over the scanner's state), replacing `isOwned`; it never adds a transcript path or a native session ID. Serves `reload-and-agents-05`. Required.
2. **Scan completeness and Check Again.** The response keeps what every other CLI found and adds `scan` (`complete`, `unlisted`: the CLIs it could not list, `cause` per CLI as a sentence without a path, `checkedAt`); `error` stays for older pages. `fresh=1` runs one fresh scan past the 5 s shared one, at most one at a time per control server. The scan logs one line when a CLI starts failing, with the full error, and one when it recovers, never one per request. Serves `reload-and-agents-09`. Required.
3. **Every checkout of the stack, and a read without a page.** The record lists the agents of the page's checkout first, then those of the stack's other checkouts (the main checkout and linked worktrees of each repository the stack runs, from the checkout list worktree-switch reads, cached until that list is read again), so a switch never hides an agent the stack left; without `pageURL`, a loopback client gets every checkout's agents, which stack-run-stop's multi-stack commands read through each stack's recorded control port. Serves `reload-and-agents-05`, and supplies `chat-checkout-switch-01`'s and `chat-checkout-switch-02`'s owners. Required. The agents route's part has no `CC-n` yet (**[discuss]** below); `CC-38` changes the session list beside it.
4. **The local-client flag.** The record carries `isLocalClient`, from the check config saves and the stack directory use (the client and every `X-Forwarded-For` entry are loopback), so the list knows whether Watch Live Activity can open in this browser; the toolbar builds the `127.0.0.1` link only when it is `true`, so a page opened from another machine never sends its URL and chat target to that machine's own loopback port. Remote previews, which main adds after this revision, reach Caddy through a relay whose local hop connects from loopback, so that check alone reads a relayed request as local (the hop refuses configuration writes itself for that reason); the hop marks every request it forwards as relayed, and the flag reports a marked request as not local. Serves `reload-and-agents-13`. Required.
5. **Readable activity entries.** Each activity message gains `kind` (`prompt`, `reply`, `tool-call`, `result`, `denied`, `turn-end`, `stopped`), `input` (a shell tool's command, a file tool's path, an edit's path with its added and removed line counts, cut at 4 KiB like `text`), and `conversation` (`title`, `mode`) for an agent chat started; it is sent only on the loopback activity stream. A `state` message carries each agent's state and since when from the agents record (item 1), sent when it changes, so the page shows a wait the transcripts never record. Serves `reload-and-agents-06`. Required.
6. **Why a stream ends.** Before closing the activity stream, the server sends `ended` (`stack`, `reason`: `stopped-terminal`, `stopped-ctrl-c`, `idle-timeout`, `replaced`, `chat-off`, with `at`, `startCommand` and `folder`), from the reason the stopping process records beside the stack's record (`ACT-10`, stack-run-stop's), then closes with 1001; or `failed` (`cause` as a sentence) before 1011. `openReconnectingWebSocket` passes each close's code and reason, and the messages before it, to its handlers, which notices-and-feedback's lost connection needs too, and stops reconnecting after `ended`. Serves `reload-and-agents-10`. Required. The reason comes from the stopped-stack record that `ACT-10`'s backend contract names; the messages have no `CC-n` yet (**[discuss]** below).
7. **The waiting condition for terminal agents.** The control server publishes, on the status stream, each agent outside chat that waits for the person, with its product name, checkout and since when, so the notice stack, the trigger and the collapsed badge read one attention state (`ACT-7`); agent-chat publishes its own conversations' waits. Serves the trigger and the notice of step 1. Recommended.

## Recommended priority
