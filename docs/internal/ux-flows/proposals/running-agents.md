# See the agents working in this worktree: proposed experience

Diagrams: [current](../running-agents-current.html), [proposed](../running-agents-proposed.html). [Wireframe](../wireframes/running-agents.html).

Status: design proposal, not implemented behavior. The [shared UX pattern reference](../patterns.md) wins where this proposal disagrees with it.

Source revision: alexgorbatchev/devhost `190a8bb53e8cd903d2db0a92cb0886f29671607f` (Rust `main`). Features: AGT-01, AGT-02. Redesign ticket: tracked privately.

Product rule: devhost never answers or pre-approves an agent's approvals or questions, and **Watch Live Activity** never opens on an app's hostname, because page scripts there could read transcripts; the owner decided that it opens on the stack directory's hostname, an origin no app shares, for this machine and for a browser in another environment that signed in with the devhost passkey or paired (`O55`, `O36`), while `http://127.0.0.1:<port>` keeps answering on this machine, though nothing links it. `guides/devtools.md` adds that the list "needs `[devtools.chat].enabled`" and only reports. So an activity page in its own tab off the app's hostname, a list that cannot answer a terminal agent, and no agents shown while chat is off are intended, not defects. The gap is around them: with chat docked the list opens under the chat panel, its rows name agents by internal IDs and "." (`reload-and-agents-05`), the control vanishes at zero and when a scan fails, so "none" and "could not look" read the same (`reload-and-agents-09`), Watch Live Activity never says what a tool call touches or that an agent waits for the person (`reload-and-agents-06`), after the stack stops it says Reconnecting forever (`reload-and-agents-10`), and on a page opened from another computer its link opens that computer's own `127.0.0.1` (`reload-and-agents-13`).

## Target experience

The person glances at the bar: the running agents trigger always sits in its place and counts the agents in this worktree, "2 · 1 waiting", in a waiting look of its own that differs from a working agent's spinner, and it says "0" with "No agents in this worktree" when none run, or that running agents are shown while chat is on. While an agent waits, the app page's browser tab reads "(1) waiting · Acme Shop" too, for an agent started in a terminal as for one chat started. Opening the trigger, from the pointer or as one arrow stop of the bar, shows an anchored list above docked chat, never under it: a status line naming the worktree, the count and when devhost last looked, then one row per agent in words people use. An agent chat started reads by its conversation and mode, "Claude Code · Fix the nav header · This worktree (live)", with **Answer** while it waits for the person, which opens its decision card in docked chat in one activation, and **Open Conversation** otherwise; an agent started in a terminal reads "Codex in a terminal · PID 83275" with its state, its folder in the worktree ("worktree root", never ".") and its last activity, and, when it waits, says to answer it in its terminal, because devhost never answers for anyone. When devhost could not list some agents, the trigger carries an incomplete mark and the list says which agents and what to do, with **Check Again**; it never claims there are none. After a switch, agents still working in the worktree the stack left stay listed under that worktree. **Watch Live Activity** opens in its own tab on the stack directory's hostname, never an app's, on the stack's machine and in a browser in another environment that signed in with the devhost passkey or paired alike; a browser that has done neither sees toolbar-shell's one sign-in state instead of the bar, and no page ever sends its address to the viewer's own `127.0.0.1`. The activity page names the stack and worktree it watches, groups entries under each agent with its state, and labels them Reply, Tool call, Result and Denied, each tool call with its command or file; an agent waiting for the person shows as waiting until it is answered, and when the stack stops the page says so, with the command that starts it again, and stops reconnecting. Nothing in this flow writes: the list and the page only report, so there is no Undo; the one way to act on an agent is the person's own answer in chat or in the agent's terminal. Benchmarks: VS Code's terminal list names each terminal by its process and keeps the list in place when it empties; Claude Code and Codex CLI show a tool call's command or file and diff before its result, which Watch Live Activity follows; GitHub Actions' live log keeps each step's command beside its output and says when a run was cancelled instead of spinning; Docker Desktop's container list keeps its empty state with a sentence instead of disappearing; htop and Activity Monitor tell two processes of one program apart by PID; Kubernetes reports Unknown rather than an empty list when it cannot see a node. Competitor behavior is evidence here, never a requirement.

## Target steps

Proposed: 3 steps: the trigger's waiting look, the agent's row, **Answer**, which lands on the decision card. Watching stays 3 steps (list, Watch Live Activity, read), but each entry now says what the tool touched.

## Recommended priority

**P2.** The realistic trigger is ordinary: chat is docked whenever its own agent runs, so the list opens under it and cannot be read without closing chat (`reload-and-agents-05`), and every row names the agent by an internal ID; an agent blocked on an approval never shows on Watch Live Activity, and a tool call shows only its tool's name, so a harmless read and a destructive command look alike until afterwards (`reload-and-agents-06`). Less often, a CLI devhost cannot scan makes the list look complete or vanish, which also lets chat start a second agent beside a working one without its question (`reload-and-agents-09`); a tab left open across a stop says Reconnecting forever (`reload-and-agents-10`); and on a page opened from another computer, Watch Live Activity opens that computer's own `127.0.0.1`, which fails or hands the page's URL to whatever listens there (`reload-and-agents-13`); remote use, a primary use case (`HOLD-8`), makes that trigger common, but its consequence is a tab that fails or a URL sent to a listener on the viewer's own machine, never lost work, so the finding stays P3. Nothing here loses data: the list and the page only report, so the cost is a person who misses an agent at work or waits on a dead tab, and the agent's own terminal and chat stay the ways to act. The feature is informational and used less often than chat itself, which is P1.
