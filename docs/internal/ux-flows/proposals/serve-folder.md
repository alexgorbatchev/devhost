# Serve a folder, port or command: proposed experience

Diagrams: [current](../serve-folder-current.html), [proposed](../serve-folder-proposed.html). [Wireframe](../wireframes/serve-folder.html).

Status: design proposal, not implemented behavior. The [shared UX pattern reference](../patterns.md) wins where this proposal disagrees with it.

Source revision: alexgorbatchev/devhost `190a8bb53e8cd903d2db0a92cb0886f29671607f`. Features: SRV-01, SRV-02, SRV-03, SRV-04, SRV-05, MAN-08. Redesign ticket: tracked privately.

Covers all three `devhost serve` modes — serving a folder (`--dir`), routing a running port (`--port`), and running a manifest-free command (`devhost serve "<command>"` or `devhost serve -- <command>`, foreground or `--detach`) — together with manifest `serve` services.

Product rule: the owner's rules make several behaviors of this flow intended. Caddy listens on every interface by default, as documented, so a served folder, port, or command is reachable by anyone who can reach that listener; on macOS, `O39` honors `bindHost = "127.0.0.1"` from port 1024 upward and below 1024 keeps listening on all interfaces with an explicit startup warning naming `httpsPort = 4443` or a privileged launcher. A server routed with `--port` runs outside devhost, which never starts, restarts, or stops it ("External services (`managed = false`) show status only"). Under `O40`, `devhost serve` keeps chat ON by default for folder and command sessions, stated explicitly on the first line, with `--no-chat` to turn it off, while a `--port` session still never hands an agent the shell's current folder; remote access to chat and control routes in serve sessions uses the shared `O36` passkey check (with `devhost pair` fallback and `O59`'s 30-day idle session cookie). devhost never opens a browser; human output and agent output (`AGENT=1`) differ on purpose. The gap is around them: the terminal never says what is served, where it listens, whether it is ready, how to stop it, or that chat is on; a `--port` session prints its URL as ready while nothing answers; a command-mode session hangs after post-readiness exit instead of tearing down routes and exiting with the command's exit code (and detached crashes print `waiting for a restart` while deleting routes into `ERR_SSL_PROTOCOL_ERROR`), models its own discovered ports as fake `external` `port-<port>` services with a broken **Restart Stack**, over-pads output and hides sessions from `devhost stop` / `stack info` / `stack find` / `stack list`, leaves closed secondary ports as false `0/3` outages, and obscures OS launch errors and `HEAD /` probe timeouts; the folder's page hides the folder behind its README and lists it in byte order; and a mistyped name leaves the file browser for a service recovery page.

## Target experience

The person runs `devhost serve --dir docs --domain notes.localhost`, `devhost serve --port 3000 --domain app.localhost`, or `devhost serve -- bun run dev` (foreground or `--detach`), and reads, without a 37-column invented prefix, what is served and whether chat is on, then the shared proxy line saying where Caddy listens: "Serving ~/acme/docs · chat on (pass --no-chat to turn it off)", "Proxy: HTTPS on port 443, every interface, reachable from your network · ~/.config/devhost/config.toml", then "Ready in 0.3 s: https://notes.localhost/ · Ctrl-C stops this session". A `--port` session keeps chat off (never handing an agent the shell's current folder) and says what it waits for instead of claiming it is ready: "Waiting for 127.0.0.1:3000 to accept connections · 12 s", then its ready line once the server answers. A command-mode session starts cleanly, surfaces OS launch errors and `HEAD /` probe timeouts directly, prints its foreground ready summary with a `Ctrl-C` cue (or `--detach`'s `Started`, URL, `Log:`, and `Stop: devhost stop --session <name>` without over-padding), appears first-class as `1/1` in the toolbar, `devhost stack info --session` (`devhost status --session`), and the Stack Directory with working **Restart Command**, labels added/aliased/removed ports and notifies open tabs on secondary port closure via WebSocket `port-closed` instead of a false `0/3` outage or `ERR_SSL_PROTOCOL_ERROR`, and tears down routes and exits with the command's exit code on foreground post-readiness exit (while detached crashes keep the hostname routed over valid local HTTPS to a recovery page with working **Restart Command**). Opening a served folder shows the folder itself: its name as the page's heading path, folders first, then files in natural, case-insensitive order, each row with its size and modified time, a filter, and the README rendered below the listing under its own file name, as on GitHub. A Markdown file renders with its front matter table, a visible error when the front matter does not parse, and GitHub's alerts as titled callouts; **Rendered** and **Source** switch this file's view only, and the URL keeps it without flash on load. A mistyped name stays in the file browser: "No file named on-cal.md in docs/guides", "Did you mean on-call.md?", and that folder's listing below. `Ctrl-C` or `devhost stop --session <name>` ends the session inside `O30`'s configurable `stopTimeout` with one outcome line naming what it removed and what keeps running, then the command that starts it again. A taken hostname names the session or stack holding it, its folder/port/command, its PID, and how to stop it. Serve sessions write nothing in the served folder, so there is no Undo: stopping is the way back, and the outcome prints the command that starts it again. Benchmarks: GitHub, GitLab, and Gitea list a folder with its README rendered below the file list, switch Preview and Code per file, show "Error in user YAML" above invalid front matter, and render `[!WARNING]` alerts as callouts; Caddy's `file_server browse` and Finder list folders first with sizes, dates, and natural order; Vercel's `serve` and Vite print the local and network addresses and a ready line; standard static directory listings prefix `./` to names whose first segment holds a colon. Competitor behavior is evidence here, never a requirement.

## Target steps

Today: folder sessions start with a 37-column `serve-<domain>` prefix that names neither the folder nor readiness, hide the folder behind its README, list files in byte order, turn mistyped names into service recovery pages, and shut down as "the stack"; `--port` sessions claim readiness before anything listens and hand the shell's folder to chat; command-mode `devhost serve -- <cmd>` sessions hang forever after post-readiness exit (or break TLS on detached crashes), split discovered ports into fake `external` services whose **Restart Stack** fails, omit `Stop:` on `--detach`, hide from `devhost stop` / `stack list` / `stack find` / `stack info`, and turn secondary port closure into false `0/3` outages. Proposed: 7 steps covering start, readiness and inspection, command-mode multi-port and exit lifecycle, folder browsing, Markdown reading, missing-file recovery, and stopping.

1. **Start a serve session (`devhost serve`, one write: it claims the hostname, routes it, starts devhost's file server or command, and starts the shared Caddy when it is not running).** `devhost serve --domain notes.localhost` serves the current folder, `--dir` another folder relative to it, `--port 3000` a server already listening on `127.0.0.1:3000`, and `devhost serve "<command>"` or `devhost serve -- <command>` runs a manifest-free command (with optional `--name`, `--detach`, and `-s`/`--startup-timeout`, generating a hostname when `--domain` is omitted in command mode; `--domain` stays required and bare for folder and `--port` sessions) (Kept). devhost's own lines carry the label `devhost`, as `reference/output.md` gives lines written before a manifest is read, never an invented stack name such as `serve-notes.localhost` and never over-padded `devhost | ` prefixes, so at 120 columns no line wraps because of its label (`WORD-1`, `WORD-9`, `serve-command-03`). The first line names what is served and chat, and the next is the proxy line every command that reports the shared proxy prints (`WORD-12`):
   - Folder: "Serving ~/acme/docs · chat on (pass --no-chat to turn it off)" (`FB-10`, `WORD-8`, `O40`).
   - Command: "Running `bun run dev` in ~/acme · chat on (pass --no-chat to turn it off)" (`FB-10`, `WORD-8`, `O40`).
   - Port: "Routing to 127.0.0.1:3000 · chat off" (`FB-10`, `WORD-8`, `O40`).
   - Proxy: "Proxy: HTTPS on port 443, every interface, reachable from your network · ~/.config/devhost/config.toml" (`WORD-12`, `FB-10`).
   - Listener resolution (`O39`): the listener is what the shared Caddy settings resolve to, owned by `proxy-settings`. On macOS, `bindHost = "127.0.0.1"` is honored from port 1024 upward ("Proxy: HTTPS on 127.0.0.1:4443 and [::1]:4443, direct connections from this machine only; relay previews and SSH forwards still reach it · ~/.config/devhost/config.toml"); below port 1024 (including default 443), Caddy keeps listening on all interfaces so existing port-443 setups continue starting without error, while printing proxy-settings' macOS warning on the line after the proxy line on every start, explaining macOS's privileged-port restriction and naming the fix (`httpsPort = 4443` or a privileged launcher) (`FB-10`, `WORD-12`, `O39`).
   - Words: a serve session is a serve session, named by its folder, its target address, or its session name and command (`WORD-1`): no line, page, stack directory card, or help text calls it a stack, a project, or a primary service or names it `serve-notes.localhost`, and `serve (primary)` and "shutting down the stack" go (`WORD-1`, `WORD-3`, `serve-folder-11`). Every devhost-wide words module and state word comes from `services-panel`'s shared module (`SURF-14`, `WORD-6`).
   - Chat (`O40`, `O36`): folder and command sessions keep chat ON by default, stated on the first line ("chat on (pass --no-chat to turn it off)"), and `--no-chat` turns chat off ("chat off") (`SEL-11`, `O40`, `serve-folder-04`). A `--port` session still never hands an agent the shell's current folder: its chat is off, `projectRootPath` is empty, and its chat routes answer `404` (`serve-folder-04`, `O40`). Remote access to chat and control routes in serve sessions uses the shared `O36` passkey check (with `devhost pair` fallback and 30-day idle `__Host-` cookie `O59`); local loopback access keeps working unchanged.
   - Caddy and trust: when the shared Caddy is not running, the session starts it, as today. Before the trust step's password prompt, the session says that it will ask for the password to trust devhost's local certificate authority (`WORD-9`); the prompt runs only when a person can answer it (standard input a terminal and `AGENT=1` unset), and never under `AGENT=1`, where one warning tells the agent to have the person run `devhost caddy trust` in a terminal (`REV-8`, `CC-13`). An install prints the root's name, its SHA-256 fingerprint, and `devhost caddy untrust`, which `first-run-setup` words (`REV-8`, `UNDO-5`).
   - Taken hostname refusal: refused before anything is routed, with exit status 1 and nothing left running (Kept). The refusal names the holder in the person's terms and the next step: for a folder or port serve session, "notes.localhost is already used by the serve session for ~/acme/docs (PID 49514, started 15:50)", then "Stop it with Ctrl-C in its terminal, or run:", then `kill 49514` on its own line (or `devhost stop --session demoapp` for a command session), then "Or choose another --domain." (`FAIL-2`, `WORD-7`, `WORD-8`, `serve-folder-03`). A stack holder is named by its name, its worktree label, and its root manifest, "shop.localhost is already used by Acme Shop (main ~/acme · ~/acme/devhost.toml, PID 50112)", with `devhost stop --manifest ~/acme/devhost.toml`, in `stack-run-stop`'s words (`SEL-4`, `FAIL-2`, `WORD-11`). The refusal never prints "from ." or an empty path.
   - Command startup diagnostics (`serve-command-07`): when spawning the command fails (such as a missing binary `ENOENT` or permission error), devhost surfaces the underlying OS launch error directly on the `[ERROR]` / `devhost: ERR:` line (for example, `Could not launch 'nonexistent-binary': No such file or directory`), never falling back to the internal `"command process is unavailable"` message (`FAIL-2`, `WORD-7`, `serve-command-07`). When a command listens on a port that fails HTTP readiness before the deadline, the timeout names the `HEAD /` probe that did not receive an HTTP response and suggests `--startup-timeout <duration>` (`FAIL-2`, `MENU-5`, `serve-command-07`). When `devhost serve --detach` fails before ready, it preserves `Failure.hint` so `[INFO] Read the full log in <path>` prints instead of being discarded, and calls the target `the serve session` rather than `the stack` (`FAIL-2`, `WORD-1`, `serve-command-07`).
   - CLI help and flags (`serve-command-08`): `devhost serve --help`'s Quickstart includes runnable command-mode examples (foreground `devhost serve -- bun run dev` and detached `devhost serve --detach --name demoapp -- bun run dev`) alongside folder and `--port` examples; `--startup-timeout` enables `.allow_hyphen_values(true)` so negative inputs like `--startup-timeout -5s` produce devhost's structured duration error instead of clap's unknown-flag rejection; and `-s` short-flag documentation aligns across `apps/devhost/src/cli.rs`, `start/serve.md`, and `reference/cli.md` (`WORD-9`, `FAIL-2`, `serve-command-08`).
   - Keys: `Ctrl-C` at any point of the start cancels it, removes what it claimed, stops any spawned command, and says so as a cancellation, not an error (`KEY-14`, `FAIL-5`).

2. **Read that it is ready and inspect running sessions (`devhost serve` ready output, toolbar, CLI inspection, and Stack Directory — read only).**
   - Folder ready line: prints once its route answers: "Ready in 0.3 s: https://notes.localhost/ · Ctrl-C stops this session" (`FB-5`, `FB-10`, `KEY-14`, `WORD-4`, `CC-22`).
   - `--port` waiting, ready, and reachability: a `--port` session is starting in the terminal until its port first accepts a connection: on a terminal it keeps one status line updated at least once a second, "Waiting for 127.0.0.1:3000 to accept connections · 12 s · start your server, or check the port number", and without a terminal it prints that line once; the ready line follows only once the port answers, "Ready in 14.1 s: https://app.localhost/ · Ctrl-C stops this session" (`FB-5`, `ACT-4`, `STATE-1`, `manifest-hot-reload-2-04`, `serve-folder-01`). It waits with no timeout because starting the server after the route is ordinary. The hostname is routed from the start, so a page opened meanwhile shows `startup-and-recovery`'s "127.0.0.1:3000 is not reachable" page with **Check Again**, never a disabled **Restart** or an empty log, and reloads into the app once the port answers (`ACT-9`, `MENU-5`, `MENU-3`). In the browser the target reads reachable or not reachable, never starting, failed, or exited (`ACT-9`). After the ready line, a target that stops answering prints one line, "127.0.0.1:3000 stopped accepting connections at 14:05; its page shows it as not reachable until it answers", and one when it answers again, "127.0.0.1:3000 accepts connections again · 14:06", never one line per check (`ACT-9`, `FAIL-4`, `FB-10`).
   - Command-mode foreground and `--detach` ready summary (`serve-command-03`):
     - Foreground `devhost serve -- <cmd>` stops printing pre-startup `Session:` / `Stop:` headers before the command even launches and stops over-padding the `devhost | ` label to match long synthetic service names; once the first HTTP port answers, it prints a clean ready summary: "Ready in 1.1 s: https://demoapp.localhost/ (-> 127.0.0.1:4001) · session demoapp · Ctrl-C stops this session" (`FB-5`, `FB-10`, `KEY-14`, `WORD-9`, `serve-command-03`).
     - Detached `devhost serve --detach -- <cmd>` prints its structured ready block in both human mode and `AGENT=1` with the session name, discovered URL(s), log path, and explicit stop command: `Stop: devhost stop --session demoapp` (`FB-10`, `FB-11`, `CC-30`, `serve-command-03`).
   - Toolbar and Services panel (`serve-command-02`, aligned with `services-panel` and `toolbar-shell`):
     - On a folder or port page, the toolbar names the session by its folder or port ("~/acme/docs ▾", shortened in the middle when long with the full label in its tooltip and accessible name) and its one service by the same label, a folder session's file server reading running and a `--port` target reachable or not reachable with its check and time (`WORD-1`, `WORD-8`, `ACT-2`, `ACT-9`, `SURF-14`); `toolbar-shell` draws the name and keeps placement per served folder (`SURF-7`, `CC-5`).
     - On a command-mode session page (`sessionKind: "command"`), the Services trigger counts `1/1` (one dot/summary for the command, never `2/2` with a synthetic `port-<port>` service); the Services panel renders a single command row showing the command string and all discovered HTTP URLs and local ports attached directly under it, with no `external` badge on its own ports and no repeated `Services` subsection heading; the footer omits **Restart Changed** and replaces **Restart Stack** with a working **Restart Command** button that sends a manifest-free restart (`operationId`, `202 Accepted`), restarts the command process, refreshes discovered routes, and reports its outcome instead of failing with "stack restart requires an accepted manifest" (`serve-command-02`, `ACT-2`, `ACT-6`, `MENU-2`, `MENU-3`, `CC-37`).
   - CLI inspection and discoverability (`serve-command-02`, `serve-command-04`, `O62`):
     - `devhost stack info --session <name>` (and short alias `devhost status --session <name>`, `O62`) presents the same first-class command session model — session name, command string, process state, PID, and discovered HTTP URLs/ports attached directly to the command without synthetic `external` `port-<port>` services (`serve-command-02`).
     - When no manifest stack is found for the current directory (or when running `devhost stop`, `devhost stack info` / `devhost status`, `devhost stack find`, or interactive `devhost stack list` while serve sessions are running), devhost surfaces matching running serve sessions or prints a clear next step pointing to `devhost stack list --sessions` and `--session <name>` (`devhost stop --session <name>`, `devhost stack info --session <name>`), while preserving machine-readable `devhost stack list` output for manifest stacks when non-interactive or scripted (`serve-command-04`, aligned with `stack-run-stop`).
   - Stack Directory (`serve-folder-11`, `serve-command-06`, `O61`, aligned with `stack-directory`):
     - `statuspage::Stack` carries `sessionKind` (`"manifest"` | `"command"` | `"dir"` | `"port"`) and optional `command` string so the directory page (`All Stacks on devbox`, `O61`) counts manifest stacks and serve sessions separately ("2 stacks · 3 serve sessions") and renders every serve session accurately without ever printing `serve-<domain>`, `External` on devhost-run servers/commands, a launch folder on `--port` cards, or `"Manifest-free file or port session"` (`WORD-1`, `WORD-5`, `WORD-8`, `ACT-2`, `ACT-9`, `serve-folder-11`, `serve-command-06`). Manifest stacks with one file read `1 file` rather than `1 files` (`serve-command-06`).

3. **Follow multi-port changes and command exits (command-mode runtime lifecycle).**
   - Multi-port discovery and removal (`serve-command-05`, aligned with `notices-and-feedback`):
     - In the terminal, each newly discovered HTTP port prints a labeled route addition (`Added route: https://demoapp-4002.localhost/ -> 127.0.0.1:4002`), the first port explicitly notes its primary hostname alias (`Primary URL https://demoapp.localhost/ aliases port 4001`), and a closed port prints a labeled removal (`Removed route: https://demoapp-4002.localhost/ (port 4002 closed)`) instead of dumping raw unlabeled URLs (`FB-10`, `WORD-9`, `serve-command-05`).
     - Before `refresh_command_routes` removes a closed secondary port's Caddy host block while the command and sibling port(s) remain healthy, the control server emits `{"type": "port-closed", "port": 4002, "session": "demoapp", "activeUrls": ["https://demoapp.localhost", "https://demoapp-4001.localhost"]}` on `/__devhost__/ws/health` and closes that port's stream normally. `packages/devhost-ui/src/devtools/shared/openReconnectingWebSocket.ts` delivers the event to its handler and stops retrying the removed hostname; the open tab renders the targeted notice `"Port 4002 closed · demoapp still runs on https://demoapp.localhost"` with **Open** links for the remaining active URLs, disables writes on that dead port with that reason, and never paints healthy sibling ports or the command as a false `0/3` outage (`ACT-5`, `HOLD-2`, `CC-26`, `serve-command-05`).
     - While the command session stays running, a closed secondary port's hostname keeps a session-scoped closed-port status response (HTTP `410 Gone` over valid local HTTPS under `O63`, removed when the session stops) listing the remaining active URLs so reloading that tab never drops into browser `ERR_SSL_PROTOCOL_ERROR` (`O63`, `serve-command-05`).
   - Post-readiness command exit (`serve-command-01`, **P0**):
     - **Foreground `devhost serve -- <cmd>`**: when the command exits after readiness — whether exit code `0` or non-zero — devhost immediately tears down its routes, hostname claims, and session record, prints one clear outcome line naming the command's exit code (or signal) and the removed URL(s), and exits with the command's own exit code (matching `start/serve.md:23`), never printing `devhost is waiting for a restart.` and hanging (`FAIL-3`, `FAIL-5`, `FB-10`, `serve-command-01`).
     - **Detached `devhost serve --detach -- <cmd>`**: never prints `waiting for a restart` while deleting Caddy routes into `ERR_SSL_PROTOCOL_ERROR`. When a detached command crashes (exits non-zero) after readiness, devhost keeps the session's hostname(s) routed over valid local HTTPS (`O63`) to a command-session recovery page showing the exit code, frozen last output lines, working **Restart Command** (which re-launches the command without a manifest and restores discovered routes), and the `devhost stop --session <name>` command to remove it (`ACT-2`, `FAIL-3`, `MENU-5`, `O63`, `serve-command-01`). When a detached command exits cleanly (`0`), devhost tears down its routes, hostname claims, and session record cleanly and logs the clean exit so no dead supervisor leaves broken TLS routes behind (`serve-command-01`).

4. **Open the folder (a page load, read only).** The page's heading comes first; when the machine does not yet trust devhost's local certificate authority, full file-browser pages render `first-run-setup`'s shared trust line under it as a condition banner: "devbox does not trust devhost's local certificate authority, so browsers warn on each devhost hostname and block a page's requests to another one. On devbox, run devhost caddy trust in a terminal, then reload; on another Mac, run devhost caddy trust-remote with devbox's SSH name there." (`FB-9`, `WORD-12`, `SURF-14`, `O61`). The page's one heading is the path itself: the served folder's name, then each folder down to the one shown, each ancestor a same-tab link and the shown folder plain text with `aria-current="page"`, "docs / guides"; the served folder's absolute path never appears on the page (`WORD-1`, `serve-folder-05`). Under it, one line counts what the folder holds, "3 folders · 12 files" (`WORD-5`). The tab title starts with the same path, "docs/guides · devhost". The listing is a table with Name, Size, and Modified columns: folders first, then files, each group in natural, case-insensitive order (`file2` before `file10`, `alpha` before `UPPER.TXT`), a folder's name ending in "/" beside a folder icon and a file's beside an icon of its kind, so neither is told by the icon alone (`ACT-13`, `serve-folder-07`). Sizes use binary units with one decimal under 10 ("2.1 MiB", "512 B"), folders show no size, and modified times are local and 24-hour: today's as "14:02", this year's as "Nov 15 14:02", older ones as "Nov 15, 2025" (`WORD-8`). Every name is a same-tab link built as a path relative to the folder with `./` in front, so "Re: meeting.md", "TODO:list.md", and a folder "notes:2026" open like any other name (`SURF-15`, `serve-folder-10`); rows carry no external-link arrow, because nothing on these pages opens a new tab (`SURF-15`, `serve-folder-07`). Rows are compact, at least 24 CSS pixels tall (`SURF-9`).
   - The filter: a search field labelled "Filter guides" above every non-empty listing filters the rows as the person types, by name, highlights the matched text, keeps folders before files, and says the count, "3 of 15 entries match "on"", announced politely; with no match it reads "No entry in docs/guides matches "xyz"" with **Clear Filter** (`SEL-10`, `STATE-2`, `WORD-2`).
   - A Markdown index: a folder holding `index.md`, `README.md`, or `readme.md`, in that order, shows its listing first and that file rendered below it, in a section headed by the file's name, "README.md", which links to the file on its own page, with step 5's view control; the folder's other entries, the files the README never links to included, are each one click from the folder's URL (`serve-folder-05`). A folder holding `index.html` still serves it unchanged, as a site (Kept).
   - An empty folder reads "docs/drafts is empty. Files added here appear when you reload the page." in the shared empty-state block, with no filter (`STATE-2`, `SURF-14`).
   - Keys: the full page keeps the document's standard keys and adds no shortcuts (`KEY-1`); Tab moves through the heading path's links, the filter, then each row's link in order; Escape in the search field clears it, as the browser does.

5. **Read a Markdown file (a page load, read only).** A `.md` file renders as GitHub Flavored Markdown without raw HTML or unsafe links, its YAML front matter as a table above it (Kept); its heading path ends with the file's name, and its tab title reads "release-checklist.md · docs/guides · devhost". Front matter that does not parse shows an error above its raw block, in the shared cannot-load style and never as an ordinary code sample: "Front matter is not valid YAML: line 1, column 8: flow sequence in block collection must be sufficiently indented and end with a ]", and valid YAML that is not a mapping reads "Front matter is a list, not a mapping of keys and values" (`FAIL-2`, `WORD-7`, `STATE-4`, `serve-folder-09`). GitHub's five alerts, `[!NOTE]`, `[!TIP]`, `[!IMPORTANT]`, `[!WARNING]`, and `[!CAUTION]`, render as callouts titled Note, Tip, Important, Warning, and Caution with an icon each, in the design system's state colors at 4.5:1 text contrast in both themes and distinct in forced colors, and the bracketed marker never shows (`ACT-13`, `serve-folder-09`).
   - The view control: two buttons, **Rendered** and **Source**, beside the heading path, the active one pressed (`aria-pressed="true"`), so the control shows the view and its labels are not actions (`SEL-11`, `WORD-3`, `serve-folder-08`). It applies to this file only: **Source** adds `?view=source` to this page's URL with `history.replaceState`, so a reload, the back button, and a shared link keep it, and every other file opens rendered; nothing is kept in browser storage, and the hostname-wide preference of today is removed (`SEL-11`, `serve-folder-08`). First-paint restoration preserves synchronous `flushSync` mounting (`packages/devhost-ui/src/statusPages/main.ts`) and server-rendered `<noscript>` fallback (`apps/devhost/src/statuspage.rs:185-193`) so loading a `?view=source` URL paints the source view immediately without flashing rendered HTML first. In the source view, each link target of the raw text (`[text](target)`, `<https://…>`, and bare URLs) is a link with the rendered view's sanitizing, so a relative link to another file opens it and a `javascript:` target stays text (`serve-folder-08`).
   - Keys: Tab reaches **Rendered** and **Source**, and Enter or Space presses one; the page adds no shortcuts (`KEY-1`).

6. **Recover from a missing file (a page load, read only).** A name that does not exist under the served folder, `/guides/on-cal.md`, is answered by devhost's file server with status 404 and a page inside the file browser: the heading path down to the nearest folder that exists, then the failure in words, "No file named on-cal.md in docs/guides", then up to three names of that folder closest to the missing one, ignoring case and at most two edits away, as same-tab links, "Did you mean on-call.md?", then that folder's listing (`SURF-16`, `MENU-5`, `FAIL-2`, `WORD-7`, `serve-folder-06`). A missing folder on the way reads "No folder named old in docs/guides". The page offers no **Restart**, no worktree list, no internal address, and no logs, because a typo is no service's failure (`MENU-3`, `MENU-5`, `WORD-11`), and its tab title starts with the failure, "Not found: on-cal.md · docs/guides · devhost" (`O16`). The same page answers for a CLI serve session and a manifest `serve` service; `startup-and-recovery`'s document injection never replaces it (`SURF-16`, `CC-4`, `O5`). ## Recommended priority

**P0** (elevated from P1 by `serve-command-01`, alongside P1 `serve-folder-04`, `serve-command-02`, and `serve-command-04`). Command-mode `devhost serve -- <command>` breaks its own documented foreground exit contract by hanging forever with `devhost is waiting for a restart.` after the child exits, and on detached crashes prints `waiting for a restart` while deleting routes into `ERR_SSL_PROTOCOL_ERROR` (`serve-command-01`, P0). Every `--port` session today hands the shell's current folder to chat (`serve-folder-04`, P1); command sessions misrepresent their own ports as fake `external` services with a failing **Restart Stack** (`serve-command-02`, P1); and serve sessions disappear from `devhost stop`, `stack info`, `stack find`, and `stack list` (`serve-command-04`, P1).
