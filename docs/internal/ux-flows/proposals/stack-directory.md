# Find running stacks and routes in the browser: proposed experience

Diagrams: [current](../stack-directory-current.html), [proposed](../stack-directory-proposed.html). [Wireframe](../wireframes/stack-directory.html).

Status: design proposal, not implemented behavior. The [shared UX pattern reference](../patterns.md) wins where this proposal disagrees with it.

Source revision: alexgorbatchev/devhost `edb5c0fc01cabae490e92ac23d4c785ec896c4ed`. Features: REC-06, REC-07. Redesign ticket: tracked privately.

Product rule: `guides/stack-lifecycle.md` states the directory's contract: "The page accepts local clients by default." and "It remains read-only and works without the devtools toolbar." The owner's rules add that devhost never opens a browser and that external services (`managed = false`) show status only, and the reference's recommended default `O10` keeps the stack directory "read-only with links". So a directory that starts, restarts and stops nothing, that answers only this machine unless `[caddy].stackDirectoryAllowRemote` is set, and that hands each action off to a stack's own pages or the terminal is intended, not a defect. The gap is around it: nothing leads to the page, its status words are its own guess (a crashed service gets the gray of a service left out on purpose, a service devhost never launched reads Starting for as long as the stack runs, a hung one reads Running in green), two checkouts of one project are indistinguishable, the page is a snapshot that forgets what just stopped, a stack whose devhost process is paused (Ctrl-Z in its terminal) holds every load of the page although another stack could serve it, when no stack answers it is one line of plain text, or Go's raw error when a stack record cannot be read, and the Caddy 404 never names the hostname that was asked for.

## Target experience

The person who wants to know what runs on this machine follows a link they already have: the URL `devhost start` prints after its ready line, **All Stacks on This Machine** at the end of the toolbar's stack name menu, or the same link on the Caddy 404 and on every status page; nothing is typed from the docs. The stack directory opens in the same tab and leads with what needs the person: the heading "Stacks on this machine", the totals "3 stacks · 1 failed · 1 with an agent waiting for you · 2 stopped recently", and a document title that starts "1 failed · 1 waiting for you", so a background tab says so too. Each card names its stack and its checkout, "Acme Shop · fix-nav ~/acme/.worktrees/fix-nav", so two checkouts of one project read apart, then the stack's state and count, "failed · 4 of 6 running · 1 exited · 1 not started", drawn with the toolbar's own state indicator and words, the ones `devhost status` prints. Each service row says why it is not running and since when ("exited with code 3 at 17:15", "failed its health check · since 17:14", "blocked", "not started · left out of this run"), and its way forward is one step away: the service's status page, which offers **Restart**, **Start** or the way back to a checkout, or the same action's terminal command beside it with **Copy**; an agent waiting for an answer is a link that opens its stack with chat on the question. The page updates in place every 2 s while it is visible, so a crash, a restart or a new stack shows without a reload, and a stack that stops moves to "Stopped recently" with when and why it stopped and the command that starts it again. Typing in the filter narrows cards and rows at once and highlights the match; Enter does nothing more, and **Refresh Stacks** is a control of its own. A rejected manifest edit shows as not applied, opening on the version the stack runs with the version on disk beside it. A mistyped hostname's page names the hostname and path that were asked for and leads with the close match, path kept: "Did you mean hotfix-shop.shop.localhost/checkout?". When no stack answers, after a crash or a kill from outside devhost, the directory still opens as devhost's page: it lists the stacks devhost last knew as unknown, each with the commands that start it again or stop what it left running, and turns live again by itself once a stack answers; a stack record devhost cannot read is named on the page in plain words, never shown as Go's error in the page's place. A stack whose devhost process is paused, after Ctrl-Z in its terminal or at a debugger's breakpoint, never holds the page: another running stack serves it within seconds, and the paused stack's card reads unknown, names its devhost process and says how to resume it: "If you pressed Ctrl-Z in its terminal, run fg there". The directory writes nothing, so there is no Undo: its links take the person where they chose, and the browser's Back returns. Benchmarks: Docker Desktop's Containers view lists every Compose project as "Running (3/6)", keeps stopped projects listed with their state, and words each container's state ("Exited (1)"); Tilt keeps each resource's own state and puts a failing resource first; k9s and VS Code's quick pick filter as the person types and highlight the match; Chrome's "Did you mean" on a mistyped address leads with the close hostname; GitHub Desktop and VS Code label a checkout by its branch first. Competitor behavior is evidence here, never a requirement.

## Target steps

Today: 5 steps and a lookup: find the hostname in the docs, type it (with the port when `httpsPort` is not 443), read gray badges and compare path tails to tell the stacks apart, type a query and press Enter to reload the whole page, then click a URL. A mistyped hostname: 3 steps and a guess: read a page that never names the hostname, compare every routed hostname letter by letter, click one and type the lost path again. Proposed: 3 steps: follow **All Stacks on This Machine** or the printed URL, read the card (or type to filter), open the service or the page that fixes it. A mistyped hostname: 1 step: the close hostname with the path kept.

1. **Reach the directory from where you are (links and printed URLs, read only).** Every surface that knows about stacks leads to the directory, because devhost never opens a browser (owner rule; `SURF-15`, `MENU-1`; `surfaces-15`, `selection-15`). The toolbar's stack name menu ends, after a separator, with **All Stacks on This Machine**, a link in the same tab; toolbar-shell draws the menu, and this flow defines where the item leads (`MENU-1`, `MENU-2`, `WORD-2`; `stack-directory-06`). The Caddy 404 (step 8), stack-run-stop's stopped-stack page and startup-and-recovery's status pages carry the same link; `devhost start` prints "All stacks on this machine: https://devhost.localhost/" after its ready line, and `devhost stack list` on a terminal and `devhost status` print it too (stack-run-stop's slice of `stack-directory-06`). Every link and printed URL is the directory's current address from the applied shared Caddy settings: `[caddy].stackDirectoryHost` when set, with the port when `httpsPort` is not 443 ("https://stacks.localhost:4443/"), read when the menu opens, so a directory that proxy-settings moved is never linked at its old address (`SURF-15`).
   - Defaults: the directory's hostname stays `devhost.localhost`; every link to it, and every link on it, opens in the same tab and carries no `target` (`SURF-15`). A link people saved with `?q=search` still opens the directory with that query in the filter (step 5).
   - While this machine does not trust devhost's local certificate authority, first-run-setup's one line sits at the top of the directory and of the Caddy 404, before their heading, with the command that fixes it (`first-run-setup-02`, first-run-setup's).

One line under the totals says once what the page cannot do and why: "This page is read-only: restart, start and stop services on their status pages, in the toolbar or in the terminal · updates every 2 s while open", ending "· readable from your network" while `stackDirectoryAllowRemote` is on (`MENU-3`, `MENU-6`, `O10`).
   - Groups: cards sit in a single column in three groups, each headed with its count and shown only when it holds a card: "Needs you" (a stack in the failed state, or with an agent waiting for the person), "Running" (every other live stack, starting, changing and stopping ones included) and "Stopped recently" (step 3) (`ACT-6`, `SEL-10`).    - Keys: the document's standard keys only; the page binds no key of its own (`KEY-1`). The filter and **Refresh Stacks** are the first Tab stops, then each card's links and actions in row order; cards and rows are not Tab stops, and each action's accessible name names its target ("Copy devhost service restart reports", "Check Again search") (`KEY-10`; `keyboard-13`).

   - Header: the stack's name as the card's heading, then its checkout label (`SEL-4`): "Acme Shop · main ~/acme", "Acme Shop · fix-nav ~/acme/.worktrees/fix-nav", "Acme Shop · Detached 1de9d7a ~/acme/.workspaces/hotfix-detached"; a stack whose repositories run from more than one checkout names each checkout over its repository's rows (`SEL-4`, `SEL-6`, `WORD-1`; `selection-04`, `selection-06`, `language-04`, `stack-directory-03`). Under it, the stack state word, then the summary with the states that need the person first: "failed · 4 of 6 running · 1 exited · 1 not started"; a changed service counts as running (`ACT-6`, `WORD-5`, `WORD-6`; `status-03`, `language-13`, `language-14`). A details line keeps the PID and how the stack runs as details, with local times: "PID 84244 · detached · started 17:03 · 12 min ago"; the ISO time is only in copyable details. The stack's folder appears once, in the checkout label, shortened with `~` and in the middle when long, with the full path in its tooltip and accessible name; the raw "Registered" timestamp and the absolute folder under every row go (`WORD-8`; `language-06`, `language-18`, `stack-directory-03`).
   - Rows: one per service of the manifest, services the run left out included in their place and counted (`SEL-7`, `ACT-6`; `selection-07`). A daemon service reads what its status check last found, never running by default (`ACT-2`; `stack-directory-09`). A changed service adds "changed: src/server.ts" as a detail (`ACT-8`; `status-09`). A service whose dependency failed stays running and names it: "running · depends on api, which exited" (`ACT-2`; `status-06`).    - Conditions: under the summary, one line per condition that needs the person, in `ACT-7`'s order, each with its way forward (step 6): a blocked repository once, "The saved checkout ~/acme/.workspaces/ui-polish was deleted; devhost started none of its 6 services" (`HOLD-4`, `HOLD-1`; `status-10`, `stack-directory-08`); a manifest file or the devhost config file not applied, "devhost.toml not applied · rejected at 17:12 · line 42: expected ']' · the stack runs the accepted manifest" (`ACT-7`, `HOLD-6`, `UNDO-6`; `status-12`, `language-08`, `stack-directory-05`); each agent waiting for the person (step 6). A failed or exited service shows in its row and counts in the summary, never as a second line (`ACT-7`; `status-12`).
   - Last operation: the stack's last operation's outcome, the sentence `devhost status` prints, in a quiet line: "Last: Restarted api · 2.6 s · 17:20 · from the toolbar", in the failure style while it failed: "Last: Restart Stack: 5 of 6 running · api exited with code 1 before its health check · 17:22" (`FB-2`, `FB-3`, `FB-11`, `ACT-1`, `WORD-4`; `feedback-02`, `status-15`).

Its hostnames are not links: for that time they answer stack-run-stop's stopped-stack page.
4. **Keep the view current (`GET /stacks.json` on the directory hostname, every 2 s while the page is visible; read only).** The page updates every card, row, summary, total and the title in place from each stack's published state while it is visible, without a reload; it reads nothing while the tab is hidden and reads at once when the tab shows again; a read starts 2 s after the previous one ended, so reads never overlap (`ACT-12`; `status-16`, `stack-directory-07`). A stack that starts appears, one that stops moves to "Stopped recently", and a crash, a restart or a switch shows as it happens (`ACT-3`, `ACT-10`). A stack whose devhost process does not answer holds neither a read nor a page load: the other cards keep updating, its card turns unknown at the next read, and another running stack serves the page when Caddy would have asked that one first (branch "A stack that does not answer"; `stack-directory-11`).
   - Announcements: the page's one announcer (`FB-9`) says once, per stack, each change that starts or ends a need of the person: "Acme Shop: reports exited with code 3", "Acme Shop: every started service runs again", "Blog stopped at 14:10 by devhost stop", "Claude Code is waiting for you in Acme Shop"; reports within one second merge into one announcement, failures go to its assertive region, and ticking times, counts and steps are never announced; updates never move focus (`FB-9`, `ACT-7`, `KEY-6`; `feedback-14`).
   - **Refresh Stacks**, a button of its own beside the filter, reads every stack at once: it keeps focus while busy, "Refreshing Stacks…" (`aria-busy`), then the status line reads "Updated 17:15:02" until the next update; it is never a side effect of filtering (`SEL-10`, `FB-1`, `FB-2`, `KEY-11`, `WORD-2`, `WORD-4`; `feedback-01`).
5. **Filter as you type (on the page, read only).** The field "Filter stacks and services" filters the cards on the page as the person types, with no form and no reload (`SEL-10`, `KEY-9`; `selection-13`, `keyboard-09`, `stack-directory-07`). It matches stack name, checkout label (branch, commit ID prefix and path), service names and hostnames, ignoring case, and never a manifest file's or the devhost config file's path, so a query cannot match every stack through a file they share (`SEL-10`). A stack whose name or checkout matches keeps every row; any other matching stack keeps only its matching rows, with one line under them, "4 more services hidden by the filter" (`SEL-10`, `BAR-3`, `WORD-5`). The matched text is highlighted, each group header counts what it shows, "Running · 1 of 2", and the totals line keeps counting the whole machine (`SEL-10`, `WORD-5`). Once typing pauses, the announcer says the number of matches politely, "1 stack matches "search"" (`FB-9`). No match reads "No stack or service matches "serch"" with **Clear Filter**, which empties the field and returns focus to it (`STATE-2`, `WORD-2`, `KEY-6`; `language-15`). The query is kept in the page's address as `?q=` without a reload, so a reload or a shared link keeps it.
   - Keys: the field keeps its own keys: Escape clears it as a search field does, and Enter does nothing more (`KEY-9`, `KEY-1`; `keyboard-09`). The directory is a full page with no toolbar and no shortcuts, so its field needs none of the toolbar's early key listener, and no key typed in it reaches anything but the field (`KEY-5`; `keyboard-05`).
6. **Open a service, or the page that fixes it (a link in the same tab; Check Again and Copy are reads).** A route link opens the app, or devhost's status page for a service that is not running, in the same tab (`SURF-15`). The directory stays read-only, so the lead action (`MENU-5`) of each state it draws is one step away: a link to the page that performs it and the terminal command that does the same, with **Copy** (`MENU-5`, `MENU-6`, `O10`; `selection-15`, `status-18`; this flow's proposed exception to `MENU-5`):
   - exited or failed: "Restart it on its status page, or run devhost service restart reports" (`CC-11`);
   - not started: "Start it on its status page, or run devhost service start admin" (`O10`, `CC-11`);
   - blocked, once per repository: "Return to the configured checkout or choose another on its status page", with **Check Again**, which reads that stack's checkout list again and stops nothing (`HOLD-4`, `HOLD-1`); a switch has no terminal command (worktree-switch's recorded `MENU-6` exception), so this line names none;
   - not reachable: "devhost checks search but cannot restart it: it runs outside devhost", said once, with **Check Again**, which runs that service's check now (`ACT-9`, `MENU-3`, `HOLD-1`);
   - starting, restarting, stopping or switching: no action; the row shows its progress (`MENU-5`);
   - stopped recently: the start command with **Copy** (step 3);
   - unknown, a stack that does not answer: while its devhost process runs, "Its devhost process (PID 4121) is running but did not answer within 2 s. If you pressed Ctrl-Z in its terminal, run fg there; a debugger may also have paused it.", with **Copy Error**; on the page Caddy serves when no stack answers, which cannot tell a paused process from one that ended, "If its devhost process is paused, run fg in its terminal; if it ended, devhost start in ~/acme starts it again and devhost stop there stops what it left running", each command with **Copy** (`ACT-5`, `ACT-11`, `STATE-4`; branches "A stack that does not answer" and "Loading the directory when no stack answers"; `stack-directory-11`).
   - **Check Again** keeps focus while busy ("Checking search…"), and its result replaces the row's state and time; **Copy** keeps focus and says "Copied devhost service restart reports" once through the announcer; when the browser refuses the clipboard, "Could not copy: the browser did not allow clipboard access" stays beside it with the command as selectable text (`KEY-11`, `FB-9`, `FAIL-2`, `WORD-7`). Read from another machine, **Check Again** is unavailable with "Check Again works only on this machine" beside it and as its accessible description (`MENU-3`, `HOLD-1`). No control on the page starts, restarts, stops or switches anything, so none asks and none waits for another operation (`REV-1`, `O10`).
   - An agent waiting for the person: "Claude Code is waiting for you · Fix the nav · fix-nav ~/acme/.worktrees/fix-nav · since 17:18" is a link that opens a page of that stack, in the same tab, with docked chat on that conversation's decision card, in one activation; the conversations of every checkout of the stack are listed, the configured checkout first; devhost never answers for the person, and the directory cannot (`ACT-6`, `REV-9`, `SURF-8`, `CC-38`; `status-12`).
   - Being read-only, the directory never acts on what it shows: a link reaches the hostname, which answers with its current state, and **Copy** copies the command from the latest read (`REV-13`; `review-14`).
7. **Read a stack's configuration (read only; Open in Editor and Copy are hand-offs).** **Configuration · 2 files** expands the stack's manifest files, each named by its kind and its path relative to the root manifest's folder: "Root manifest · devhost.toml", "Included manifest file · services/api.toml". The devhost config file, which every stack shares, is listed once at the foot of the page, "devhost config file · ~/.config/devhost/config.toml", never on every card (`WORD-1`; `language-02`). Each file states whether the stack runs it: "Applied 17:03", or "Not applied · rejected at 17:12 · line 42: expected ']'" from the rejection's structured error, with "the stack runs the accepted manifest"; the caveat printed on every card today goes (`MENU-4`, `UNDO-6`, `HOLD-6`, `WORD-1`; `selection-10`, `feedback-12`, `language-08`, `stack-directory-05`). A file's text shows with line numbers. With no editor set for the stack, **Open in Editor** is absent and the section says once how to set one (`MENU-3`); read from another machine, it is unavailable with "Open in Editor works only on this machine" beside it and as its accessible description (`MENU-3`, `HOLD-1`).

8. **Recover from a hostname with no route (the Caddy 404, read only).** A page load of a hostname that no live stack routes gets devhost's own page, never an app's, with status `404` (`SURF-16`; `surfaces-03`). It leads with the hostname and path that were asked for: the heading "No devhost route for hotfix-shpo.shop.localhost/checkout", before the status code in reading order (`FB-9`, `WORD-7`; `stack-directory-04`). Its lead action is the close hostname with the path and query kept, "Did you mean hotfix-shop.shop.localhost/checkout?", a link in the same tab, followed by **All Stacks on This Machine** (`MENU-5`, `SEL-10`, `SURF-15`; `selection-12`, `status-18`, `stack-directory-06`). Close means within two edits of a routed hostname (a letter added, removed or changed, or two neighbouring letters swapped), at most three, closest first; this proposal asks the product owner to settle that threshold. One sentence gives the next step instead of Caddy's wording: "If it belongs to a stack that is not running, start that stack with devhost start in its folder." (`WORD-7`, `STATE-2`). Below, "Hostnames on this machine" groups every routed hostname by stack and checkout ("Acme Shop · main ~/acme"), each with its service's name and its path routes ("shop.localhost · web", "shop.localhost/api · api"), each a link to its route.    - With no route on the machine, the page reads "No stack is running on this machine. Start one with devhost start in its folder." with **All Stacks on This Machine**, which lists what stopped recently (`STATE-2`).
   - A hostname whose stack stopped within `O15`'s time never reaches this page: stack-run-stop's stopped-stack page answers it (`ACT-10`, `CC-27`; `stack-run-stop-11`).
   - A request that is not a page load (a `fetch`, an API client, an agent's `curl`) gets `404` with a body under 2 KB instead of the page: one text line, "No devhost route for hotfix-shpo.shop.localhost. Did you mean hotfix-shop.shop.localhost?", or, under `Accept: application/json`, `{error, host, closeHostnames}` (`FB-11`, `SURF-16`); this answers startup-and-recovery's open item for that response.
   - Keys: the document's standard keys; the close hostname is the first Tab stop after the heading (`KEY-1`, `KEY-10`).

Branches and edge states:

- **A stack that does not answer.** When a stack's control server does not answer within 2 s, its card keeps its last known rows drawn as unknown, "unknown · did not answer within 2 s · last seen 17:15:02", never stopped or failed, with **Copy Error** holding the original error, never Go's error text in the card's place, while the other cards keep updating; a stack the page never read shows its name and checkout from its record with that sentence, and the totals count it, "1 unknown" (`ACT-5`, `STATE-3`, `STATE-4`, `FAIL-2`, `WORD-5`, `WORD-6`; `status-04`, `stack-directory-11`). The directory lists a stack as live only while its devhost process runs (`ACT-11`), so a live stack that does not answer has a process that is paused, stopped at a debugger's breakpoint or busy, and the card says how to resume it: "Its devhost process (PID 4121) is running but did not answer within 2 s. If you pressed Ctrl-Z in its terminal, run fg there; a debugger may also have paused it." (`MENU-5`, `WORD-7`; this flow's proposed exception to `MENU-5`). Such a stack never holds the page: Caddy's health checks skip it within about 3 s and another running stack serves the page, and a load that reached it before a check moves on to the next stack within 7 s (Backend 12 (e)). ## Backend and contract changes

**Backend** (the directory routes of the control server in `apps/devhost/internal/devtools/stack_directory.go`, the Caddy directory site and the unmatched-hostname page in `apps/devhost/internal/caddy`, and the snapshot in `apps/devhost/internal/services/stack_directory.go`, preserving access from this machine only unless `stackDirectoryAllowRemote` is set, GET and HEAD only, loopback-only snapshots with a 2 s deadline per stack, `no-store` and `no-referrer`, and a directory that writes nothing):

1. **The snapshot reads the published state.** `directoryServices` gives way to the published service state services-panel defines (its Backend 1: `state`, `cause`, `since`, `healthCheck`, the exit record with its last output line, `changedFiles`, an external service's check with its result and time, `failedDependency`, `routes` with a `link` only to an address that answers), daemon services included, and no state is a default. ## Recommended priority

**P2.** The realistic trigger is ordinary for anyone who runs more than one stack, or a worktree beside the main checkout: the directory draws a crashed service in the gray of one left out on purpose and calls a hung one Running in green, so it is least trustworthy exactly when something broke (`stack-directory-02`, `stack-directory-09`); a service devhost never launched reads Starting for as long as the stack runs (`stack-directory-08`); two checkouts of one project are indistinguishable cards, so people open the wrong checkout's app (`stack-directory-03`); a mistyped or stale hostname costs a letter-by-letter comparison and a retyped path (`stack-directory-04`); nothing leads to the page at all (`stack-directory-06`); and in the rare moment after a crash, when a person opens the directory to learn what still runs, it is one line of plain text, or Go's raw error when one stack record cannot be read (`stack-directory-10`); and while the stack Caddy asks first has its devhost process paused, by Ctrl-Z in its terminal or a debugger, every load of the page hangs with no page and no error although another stack could serve it, a rare trigger with a silent, indefinite cost (`stack-directory-11`). Nothing here loses work or changes a process: the directory is read-only, and the toolbar and the terminal carry the truth for the stack the person works in, so every cost is time and a wrong conclusion, and the flow ranks below the ones that restart, switch or edit. It is used less often than the Services panel and the terminal. Ship first the slice that needs no backend change: the filter on the page with **Refresh Stacks** of its own, the words (stack, serve session, the empty state), local times and shortened paths, the 404's requested hostname with its close hostnames and the path kept, its grouped list and its link to the directory, and **All Stacks on This Machine** once the toolbar's stack name menu exists. The directory site's health checks and ordered timeouts (Backend 12 (e)) are a small backend change that needs no other flow, so they can ship beside that slice. This redesign depends on services-panel, the foundation that ships first: its published service state and its shared state indicator and state words, in the status pages' stylesheet, carry the second slice: the rows' states with their causes, the summaries, totals and order, blocked and health-checked states, the checkout labels, the live path, and the page that answers when no stack does, with the reader that names a stack record it cannot read. Last come the stopped-stack listing with stack-run-stop's record, waiting agents with agent-chat's link, configuration applied and not applied with manifest-hot-reload's accepted text, **Check Again** and the 404's short response. Seams with no blocker in either direction: toolbar-shell draws **All Stacks on This Machine** and this flow defines where it leads; stack-run-stop prints the directory's URL, writes the stopped-stack record and the static pages this flow draws, and re-renders the directory site when a devhost command finds a stack's devhost process gone; startup-and-recovery's status pages link the directory and carry each service's lead action; agent-chat provides the link to a waiting conversation; manifest-hot-reload keeps the accepted text and the rejection's structured error; component-source provides the editor hand-off; first-run-setup puts its trust line on both pages; notices-and-feedback's announcer speaks the page's updates; worktree-switch's checkout list data gives the labels and makes the checkout read stop nothing; serve-folder names serve sessions; proxy-settings moves the directory and words its new address.
