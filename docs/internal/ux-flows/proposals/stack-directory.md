# Find running stacks and routes in the browser: proposed experience

Diagrams: [current](../stack-directory-current.html), [proposed](../stack-directory-proposed.html). [Wireframe](../wireframes/stack-directory.html).

Status: design proposal, not implemented behavior. The [shared UX pattern reference](../patterns.md) wins where this proposal disagrees with it.

Source revision: alexgorbatchev/devhost `190a8bb53e8cd903d2db0a92cb0886f29671607f` (Rust `main`). Features: REC-06, REC-07. Redesign ticket: tracked privately.

Product rule: `guides/stack-lifecycle.md` states the directory's contract: "The page accepts local clients by default." and "It remains read-only and works without the devtools toolbar." The owner decided that the stack directory stays read-only with links (`O10`), that a browser in another environment that signed in with the devhost passkey or paired reads it and presses **Check Again** as this machine does, while `[caddy].stackDirectoryAllowRemote` keeps meaning anyone may read it without signing in (`O47`, `O36`), that its hostname also serves Watch Live Activity for this machine and signed-in browsers, never an app's hostname (`O55`), that an unknown HTTPS hostname gets no certificate (`O63`), and that the pages name the machine by its machine name, "devbox" here (`O61`); devhost never opens a browser, and external services (`managed = false`) show status only. So a directory that starts, restarts and stops nothing, that refuses a client that is neither this machine, signed in nor admitted by that setting, that hands each action off to a stack's own pages or the terminal, and a mistyped HTTPS hostname that fails the TLS handshake are intended, not defects. The gap is around them: nothing leads to the page, its status words are its own guess (a crashed service gets the gray of a service left out on purpose, a service devhost never launched reads Starting for as long as the stack runs, a hung one reads Running in green), two worktrees of one project are indistinguishable, the page is a snapshot that forgets what just stopped, a stack whose devhost process is paused (Ctrl-Z in its terminal) holds every load of the page although another stack could serve it, when no stack answers it is one line of plain text, or a raw error when a stack record cannot be read, the plain-HTTP 404 never names the hostname that was asked for, and a serve session's card reads "Manifest-free file or port session".

## Target experience

The person who wants to know what runs on devbox follows a link they already have: the URL `devhost start` prints after its ready line ("All stacks on devbox: https://devhost.localhost/"), **All Stacks on devbox** in the toolbar's stack name menu, or the same link on the plain-HTTP 404 and on every status page; nothing is typed from the docs. The stack directory opens in the same tab and leads with what needs the person: the heading "Stacks on devbox", the totals "3 stacks · 1 serve session · 1 failed · 1 with an agent waiting for you · 2 stopped recently", and a document title that starts "(2) 1 failed · 1 waiting", so a background tab says so too. Each card names its stack and its worktree, "Acme Shop · fix-nav ~/acme/.worktrees/fix-nav", so two worktrees of one project read apart, then the stack's state and count, "failed · 4 of 6 running · 1 exited · 1 not started", drawn with the toolbar's own state indicator and words, the ones `devhost stack info` (`devhost status`) prints. Each service row says why it is not running and since when ("exited with code 3 at 17:15", "failed its health check · since 17:14", "blocked", "not started · left out of this run"), and its way forward is one step away: the service's status page, which offers **Restart**, **Start** or the way back to a worktree, or the same action's terminal command beside it with **Copy**; an agent waiting for an answer is a link that opens its stack with chat on the question. A serve session reads as one, by its folder, address or session name, with the command it runs. The page updates in place every 2 s while it is visible, so a crash, a restart or a new stack shows without a reload, and a stack that stops moves to "Stopped recently" with when and why it stopped and the command that starts it again. Typing in the filter narrows cards and rows at once and highlights the match; a mistyped hostname that matches nothing offers the close running hostname, path kept, so a typo that failed over HTTPS is one paste away from its page; Enter does nothing more, and **Refresh Stacks** is a control of its own. A rejected manifest edit shows as not applied, opening on the version the stack runs with the version on disk beside it. On plain HTTP, a mistyped hostname's page names the hostname and path that were asked for and leads with the close match, path kept: "Did you mean hotfix-shop.shop.localhost/checkout?". When no stack answers, after a crash or a kill from outside devhost, the directory still opens as devhost's page: it lists the stacks devhost last knew as unknown, each with the commands that start it again or stop what it left running, and turns live again by itself once a stack answers; a stack record devhost cannot read is named on the page in plain words, never as a raw error in the page's place. A stack whose devhost process is paused, after Ctrl-Z in its terminal or at a debugger's breakpoint, never holds the page: another running stack serves it within seconds, and the paused stack's card reads unknown, names its devhost process and says how to resume it: "If you pressed Ctrl-Z in its terminal, run fg there". From a laptop or phone in another environment, the same page opens on the directory's hostname under the remote or relay suffix once that browser signed in with the devhost passkey or paired; the same hostname serves each stack's Watch Live Activity there. The directory writes nothing, so there is no Undo: its links take the person where they chose, and the browser's Back returns. Benchmarks: Docker Desktop's Containers view lists every Compose project as "Running (3/6)", keeps stopped projects listed with their state, and words each container's state ("Exited (1)"); Tilt keeps each resource's own state and puts a failing resource first; k9s and VS Code's quick pick filter as the person types and highlight the match; Chrome's "Did you mean" on a mistyped address leads with the close hostname; GitHub Desktop and VS Code label a worktree by its branch first; Tailscale names a remote machine by a name the person chose. Competitor behavior is evidence here, never a requirement.

## Target steps

Today: 5 steps and a lookup: find the hostname in the docs, type it (with the port when `httpsPort` is not 443), read gray badges and compare path tails to tell the stacks apart, type a query and press Enter to reload the whole page, then click a URL. A mistyped hostname over HTTPS: a TLS error and a guess; over plain HTTP: 3 steps and a guess: read a page that never names the hostname, compare every routed hostname letter by letter, click one and type the lost path again. Proposed: 3 steps: follow **All Stacks on devbox** or the printed URL, read the card (or type to filter), open the service or the page that fixes it. A mistyped hostname: 1 step on plain HTTP (the close hostname with the path kept), 2 over HTTPS (type it into the directory's filter, follow the close hostname).

1. **Reach the directory from where you are (links and printed URLs, read only).** Every surface that knows about stacks leads to the directory, because devhost never opens a browser (owner rule; `SURF-15`, `MENU-1`; `surfaces-15`, `selection-15`). The toolbar's stack name menu holds **All Stacks on devbox** in its one group of toolbar items, after **Move to**, **Collapse** and **Reset to Manifest Default**, a link in the same tab; toolbar-shell draws the menu, and this flow defines where the item leads (`MENU-1`, `MENU-2`, `WORD-2`, `O61`; `stack-directory-06`). The plain-HTTP 404 (step 8), stack-run-stop's stopped-stack page and startup-and-recovery's status pages carry the same link; `devhost start` prints "All stacks on devbox: https://devhost.localhost/" after its ready line, and `devhost stack list` on a terminal and `devhost stack info` (`devhost status`) print it too (stack-run-stop's slice of `stack-directory-06`; `O61`, `O62`). Every link and printed URL is the directory's current address from the applied shared Caddy settings: `[caddy].stackDirectoryHost` when set, with the port when `httpsPort` is not 443 ("https://devhost.localhost:4443/"), read when the menu opens, so a directory that proxy-settings moved is never linked at its old address (`SURF-15`). On a page opened through the remote or relay suffix, the link names the directory's hostname under that suffix, "https://devhost.acme.test/", never `.localhost`, because that is the address the browser can reach (`HOLD-8`, `O47`).
   - Defaults: the directory's hostname stays `devhost.localhost`; every link to it, and every link on it, opens in the same tab and carries no `target` (`SURF-15`). A link people saved with `?q=search` still opens the directory with that query in the filter (step 5).
   - While this machine does not trust devhost's local certificate authority, first-run-setup's one line sits under the heading of the directory and of the plain-HTTP 404, in its one sentence: "devbox does not trust devhost's local certificate authority, so browsers warn on each devhost hostname and block a page's requests to another one.    - Conditions: under the summary, one line per condition that needs the person, in `ACT-7`'s order, each with its way forward (step 6): a blocked repository once, "The saved worktree ~/acme/.workspaces/ui-polish was deleted; devhost started none of its 6 services" (`HOLD-4`, `HOLD-1`; `status-10`, `stack-directory-08`); a manifest file not applied, "devhost.toml not applied · rejected at 17:12 · line 42: expected ']' · the stack runs the accepted manifest" (`ACT-7`, `HOLD-6`, `UNDO-6`; `status-12`, `language-08`, `stack-directory-05`); each agent waiting for the person (step 6). The directory is a full page with no toolbar and no shortcuts, so its field needs none of the toolbar's early key listener, and no key typed in it reaches anything but the field (`KEY-5`; `keyboard-05`).

The directory stays read-only with links (`O10`), so it shows the shared recovery view's cause and state words without that view's action buttons, and the lead action (`MENU-5`) of each state it draws is one step away: a link to the page that performs it and the terminal command that does the same, with **Copy** (`MENU-5`, `MENU-6`, `O10`; `selection-15`, `status-18`; this flow's proposed exception to `MENU-5`):

7. **Read a stack's configuration (read only; Copy is a hand-off).** **Manifest files · 2** expands the stack's manifest files, each named by its kind and its path relative to the root manifest's folder: "Root manifest · devhost.toml", "Included manifest file · services/api.toml"; one file reads "1 file", never "1 files". ## Recommended priority
