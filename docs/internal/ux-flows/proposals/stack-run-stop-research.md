# Start, find, stop and restart stacks from the terminal: research

Proposal: [Start, find, stop and restart stacks from the terminal](stack-run-stop.md). Shared patterns: [UX pattern reference](../patterns.md). Current flow: [diagram](../stack-run-stop-current.html).

Scope: the terminal journey from a project folder to a running stack and back to a stopped or replaced one: `devhost start [names]` in the foreground or with `--detach`, `devhost stack list` and `devhost stack find`, `devhost stop` with `--manifest` or `--worktrees`, `devhost stack restart` with or without `--all`, Ctrl-C and the idle timeout, and the supervisor's shutdown with the process containment every stop path runs through. None of these operations has an undo; the way back from a stop or a failed restart is starting the stack again (Verified: step 23 below).

Evidence: `alexgorbatchev/devhost` at `edb5c0fc01cabae490e92ac23d4c785ec896c4ed` (Go code, tests and the public docs under `packages/docs/src/content/docs/`; the reviewed build's product code is identical), and this flow's findings, cited by ID. "Verified" means read in code, tests or docs at that revision, or reproduced against the reviewed build by the finding cited beside the claim; "Hypothesis" means inferred and not tested, and each one says when it holds.

Product rules. The owner settled two behaviors of this flow for the review: "A failed service leaving the rest of the stack running is the recovery contract; detached startup stopping on a failure before readiness is also intended", and "Human and agent (`AGENT=1`) output differ on purpose." The public docs make the reach of the two bulk commands a documented contract: `devhost stop --worktrees` "stops every stack whose root manifest is in the current Git repository, including its linked worktrees" (`guides/stack-lifecycle.md:230`), and `devhost stack restart --all` "includes manifest stacks and standalone `serve` sessions in the same state directory", after which "The original foreground command exits" (`guides/stack-lifecycle.md:240`, `:244`). The same page promises what a stop leaves behind: `devhost stop` "kills whatever is left" (`:196`), and "If devhost cannot stop a service during shutdown, it exits non-zero and reports what is still running" (`:290`). The reach of both bulk commands is intended, not a defect, and so is a failed service that leaves the rest running. The gap is that neither bulk command shows which stacks it will stop or replace before acting, or what happened to each afterwards; that a stop can report success while the stack's services keep running; and that every stop path can signal processes that are no longer the stack's own (Verified: the sections below).

## Today's flow, step by step

**Entry points.** A terminal in a project folder runs `devhost start`, `devhost stop`, `devhost stack restart` or `devhost stack list|find`; find, stop and restart usually run from a second terminal or an agent's shell; Ctrl-C ends a foreground stack; the idle timeout ends any stack. The toolbar's Restart Stack, a service restart, a reload that restarts services and a worktree switch reach the same service-stop code and are owned by services-panel, manifest-hot-reload and worktree-switch. The CLI dispatches stop, restart, list and find in `apps/devhost/internal/app/run.go:48-90` and start in `:112-172` (Verified).

**Surface.** Two terminals: the supervisor's own (foreground start) or a log file (detached start and restart replacements), and the command terminal that prints only what its command did. Every line goes through `cliout` in the human or the `AGENT=1` format (Verified: `run.go:54`, `:69`, `:161-162`).

Start:

1. **Find the manifest.** `devhost start [names]`, `devhost stop` and `devhost stack restart` without `--all` use `--manifest`, `DEVHOST_MANIFEST` or the nearest `devhost.toml` found upward from the working directory; with none, they exit 1 with "Run devhost from your project folder, or pass --manifest \<path\>." (Verified: `apps/devhost/internal/app/run.go:298-310`, `apps/devhost/internal/manifest/resolve.go:15-33`; stack-run-stop-12).
2. **Validate before anything runs.** Start reads the manifest and its includes, validates the schema, checks the requested names, orders services by `dependsOn` and resolves ports; any failure exits 1 before a process starts (Verified: `run.go:118-139`; stack-run-stop-09, journey-new-project-04).
3. **Detached start only: lock, wait, launch.** `--detach` takes a per-manifest lock beside the log `<state>/logs/stack-<sha256 of the manifest identity>.log`, waits for an earlier start of the same manifest to settle, and, when that manifest's stack already runs, prints "Already running \<name\> (PID n)." and the log and exits 0 whatever names were asked for. Otherwise it launches `devhost start` again as a supervisor in a new session with closed input and output only to the log, and waits for readiness within a limit built from every service's health timeout and grace period (Verified: `apps/devhost/internal/services/detach.go:98-125`, `:130-158`, `:240-245`, `:398-417`; stack-run-stop-01, stack-run-stop-04; the product call is `O6` in the pattern reference).
4. **Register the supervisor.** The supervisor registers SIGINT, SIGTERM and SIGHUP handling, makes sure the managed Caddy configuration exists, deletes the records of stacks whose process is gone, writes its stack record `<state>/stacks/<PID>.json` with its start identity, deletes stale route registrations and fixed-port claims, starts the shared Caddy when it is not running, and applies the shared Caddy settings from `config.toml` to it (Verified: `apps/devhost/internal/services/stack.go:51`, `:216-232`, `:323-353`; `apps/devhost/internal/caddy/stack_record.go:59-96`).
5. **Claim ports and hostnames.** It claims every fixed port and hostname. A claim held by a live process of another manifest refuses the start; a claim whose owner is dead is replaced without a word; with `killZombies` (default `true`) a claim held by another live process of the same manifest is answered with SIGKILL to that claim's recorded owner, a devhost supervisor, never the service that holds the port (Verified: `stack.go:357-391`; `apps/devhost/internal/caddy/routes.go:191-203`, `:298-316`, `:1143-1157`; `apps/devhost/internal/caddy/zombie_cleanup.go:42-73`; interrupted-operations-02).
6. **Start the services.** Services start one by one in dependency order, each in its own process group with a private `DEVHOST_SERVICE_TOKEN` variable, and each waits for its health check before the next starts. Every service gets a process-tree tracker fed by one shared monitor that reads the whole process table every 200 ms: `ps ax -o pid= -o ppid=` on macOS, `/proc` on Linux, where devhost also makes itself a child subreaper and recognizes re-parented processes by the token (Verified: `stack.go:486-533`, `:1140-1149`; `containment.go:13`, `:64-75`, `:193-207`, `:248-260`; `containment_darwin.go:16-43`; `containment_linux.go:21-29`, `:72-88`; journey-new-project-03, process-containment-02).
7. **Print the outcome.** A foreground start prints every URL and the not-started list only after the slowest service is healthy; a detached start prints "Started \<name\> (PID n).", the URLs without service names, and the log path (Verified: `stack.go:544-545`; `detach.go:398-417`; stack-run-stop-03, stack-run-stop-04, stack-run-stop-10).

Run:

8. **Run and watch.** A service that exits prints "\<name\> exited with code N; devhost is waiting for a restart."; the idle timeout prints "Idle timeout of \<d\> reached. Automatically shutting down the stack..." and sends SIGTERM to every service (Verified: `stack.go:633-634`, `:644-651`; agent-cli-journey-03, interrupted-operations-04, stack-run-stop-11).

Find:

9. **List and find.** `devhost stack list` and `devhost stack find <query>` read four record sources (stack records, hostname claims, fixed-port claims, route registrations), keep an owner only while its PID runs with the recorded start identity, skip every record without a manifest path, which is every `devhost serve` session, and print `<PID>\t<manifest path>`. `find` matches a URL's hostname exactly, a path to a manifest file by identity, and anything else as a case-insensitive substring of a hostname, stack name or manifest path; a folder is never resolved to its manifest (Verified: `run.go:74-90`, `:280-292`; `caddy/owners.go:29-68`, `:158-181`; `caddy/stack_find.go:15-50`; `start/serve.md:68`; agent-cli-journey-01, stack-run-stop-08).

Stop:

10. **Choose the targets.** `devhost stop` resolves the manifest as in step 1, reads the live owners as in step 9, and targets every owner with the same manifest identity. With `--worktrees` it also targets every owner whose root manifest's folder has the same Git common directory (`git rev-parse --git-common-dir`), which is every linked worktree of the repository wherever it sits on disk, not only under `.workspaces/` (Verified: `apps/devhost/internal/services/stop.go:31-51`; `stop_worktrees.go:16-54`; `worktree_git.go:23-67`).
11. **Hint, or report nothing to stop.** Without `--worktrees` and with other stacks in the repository, it first prints "N other stack(s) run in this repository's worktrees. Run devhost stop --worktrees --manifest \<path\> to stop them all."; with no target it prints "No active devhost stack process found for manifest: \<path\>" and exits 0 (Verified: `stop.go:52-68`; stack-run-stop-06).
12. **Stop each target in turn.** It prints "Stopping N active stack process(es) associated with \<scope\>...", then for each target, one after another: "Stopping stack PID n: \<path\>" (with `--worktrees` only), SIGTERM to the supervisor PID read in step 10, a check every 100 ms for 15 s, then SIGKILL to the supervisor alone and a 1 s check. The first error ends the command and leaves the later targets untouched (Verified: `stop.go:70-83`, `:88-136`; interrupted-operations-01, stack-run-stop-07).

Supervisor shutdown (the backend sequence behind Ctrl-C, SIGTERM from `stop` or `restart`, SIGHUP and the idle timeout; Verified: `stack.go:51`, `:635-651`):

13. **Read one signal.** The supervisor prints "Received \<signal\>; shutting down the stack." and reads no further signals, so a second Ctrl-C does nothing (Verified: `stack.go:216-232`; interrupted-operations-03).
14. **Forward the signal.** It prints "Stopping service \<name\>..." and forwards the signal to every started service. Each signal first refreshes that service's process-tree snapshot, then signals the service's process group while its root process lives, then every tracked PID that still answers as alive (Verified: `stack.go:635-641`, `:1274-1306`, `:1803-1815`; `containment.go:93-118`; process-containment-01).
15. **Wait, then kill.** It sends SIGTERM to every service, then waits for each service in turn up to 10 s and sends SIGKILL to what is left, waiting up to 10 s again. A service counts as stopped only when its root has exited, no tracked PID answers as alive and, for a service with a port, 2 s have passed since its signal, with any late listener it owns signalled again; once the root has exited, each 10 ms check takes a fresh snapshot. "Stopped service \<name\>." prints for every service only after the slowest one (Verified: `stack.go:35-37`, `:266-271`, `:1227-1272`, `:1308-1331`, `:1879-1978`; `containment.go:14`, `:217-238`; interrupted-operations-03).
16. **Stop daemons, servers and chat.** It runs the stop commands of daemon-mode services, stops the document injection servers, withdraws the control port, rewrites the stack directory site through a Caddy reload, and stops the control server, which closes every chat session with "Devhost stopping" and deletes its replay journal (Verified: `stack.go:272-285`; `apps/devhost/internal/devtools/chat_sessions.go:80-100`; chat-conversations-03). The reload has no deadline and can hold the shutdown indefinitely (Verified: stack-scale-01).
17. **Release and unregister.** It releases its hostname claims, unregisters its routes, syncs each host's route file, releases its fixed-port claims and removes its stack record last, then prints "Stack stopped." only when cleanup raised no error; Ctrl-C exits 130 and SIGTERM 143 (Verified: `stack.go:233-245`, `:287-320`; `guides/stack-lifecycle.md:194`).

Restart:

18. **Lock and check.** `devhost stack restart [--manifest <path> | --all]` takes `<state>/restart.lock` without waiting, so a second restart fails at once, checks that its own executable can run before stopping anything, and reads every live stack record: with `--all`, every stack and serve session in the state directory, across every repository; otherwise the record with the manifest's identity (Verified: `run.go:61-73`; `apps/devhost/internal/cli/parse.go:387-401`; `restart.go:39-72`; `caddy/stack_directory.go:56-88`).
19. **Capture every launch first.** For each stack it reads the supervisor's arguments, working directory and environment from the operating system and opens `<state>/restart-<random>/<old PID>.log`; it refuses an ancestor of itself and any process that is not `devhost start` or `devhost serve`, and any capture failure ends the command before a stack is signalled (Verified: `restart.go:92-167`).
20. **Replace each stack in turn.** It prints "Restarting \<name\> (PID n); log: \<path\>", sends SIGTERM through a check that re-reads the stack record under the records lock and compares its registration and start identity, waits up to 15 s and never sends SIGKILL, launches `<this executable> <captured arguments>` in a new session with closed input, the captured environment (its private launch variables replaced by the new log path) and output to the restart log, and waits up to 30 s for the replacement to register a control port. A failure is collected and the next stack is attempted (Verified: `restart.go:82-89`, `:174-235`; `caddy/stack_occupant.go:59-94`; stack-run-stop-02, stack-run-stop-13).

Results:

21. **Results.** A started stack prints its URLs and has its record and routes registered. A stopped stack's own terminal ends with "Stack stopped." and exit 130 or 143, the stop command prints "Process n stopped cleanly.", and its hostnames answer the generic page "No active devhost route matched this hostname." A replaced stack prints "Restarted \<name\> (PID n); services may still be starting." in the restart terminal only (Verified: `stack.go:316-320`; `stop.go:111`; `apps/devhost/internal/statuspage/not_found.go:10-17`; `restart.go:224`; stack-run-stop-02, stack-run-stop-11).

Failures and undo:

22. **Failures.** Validation and claim failures exit 1 before any service starts (steps 2 and 5). A stack that takes longer than 15 s to stop has its supervisor SIGKILLed while its services, each in its own process group, keep running, and `devhost stop` exits 0; the next start replaces the dead owner's records without a word and can report ready while the old processes answer (Verified: `stop.go:117-130`; `stack.go:327-345`, `:1149`; `routes.go:191-206`; interrupted-operations-01, interrupted-operations-02). A restart whose stack is still stopping after 15 s exits 1 and starts no replacement (Verified: `restart.go:194-198`; stack-run-stop-13).
23. **Undo.** None. A stop or a restart cannot be reverted; recovery is running `devhost start` again with the same names and flags, which neither command prints, and a restart's captured launch lives only in that command's memory (Verified: `restart.go:37-38`; stack-run-stop-13).

## The contested behavior

**The terminal's stop and restart commands reach beyond the stack in front of the person in two ways, and neither is shown before it happens: `devhost stop --worktrees` and `devhost stack restart --all` act on every stack in their scope with no list first, and every path that stops a service also signals process IDs it recorded earlier without checking that they still belong to that service (Verified).**

Evidence:

- **`--worktrees` scope.** Each live owner's root manifest folder is resolved to its Git common directory and compared with the named manifest's; root manifests decide membership, so an included manifest or a service `cwd` never widens it, and a linked worktree anywhere on disk counts. The only line before each stop is "Stopping stack PID n: \<path\>" (Verified: `apps/devhost/internal/services/stop_worktrees.go:10-54`; `stop.go:76-79`).
- **`--all` scope.** Every live stack record of the state directory, serve sessions included, although `stack list`, `stack find` and `devhost stop` skip serve sessions; the only line per stack is "Restarting \<name\> (PID n); log: \<path\>" (Verified: `restart.go:62-69`, `:84`; `caddy/stack_directory.go:56-88` against `caddy/owners.go:55`; `start/serve.md:68`).
- **Service containment.** The tracker stores bare PIDs, adds every PID a snapshot shows under the service and removes none while the service runs; it prunes only inside `liveDescendantPIDs`, which only the signal and stop paths call, and only by liveness; it then signals every tracked PID that answers as alive. Liveness is `kill(pid, 0)` with EPERM counted as alive plus a zombie check on macOS, and a `/proc` stat read on Linux (Verified: `containment.go:40-48`, `:108-118`, `:217-260`, `:285-292`; `containment_darwin_process.go:13-26`; `containment_linux.go:31-42`). process-containment-01's probe ran the real launch, snapshot and shutdown code: two unrelated processes listed under a service in three snapshots received SIGTERM and then SIGKILL from a stack shutdown that returned no error (Verified: process-containment-01).
- **The supervisor, by contrast.** Every stack record, claim and registration carries its owner's start identity and counts only while it matches, and `stack restart` re-reads the record and compares the identity under the records lock immediately before its SIGTERM. `devhost stop` checks the identity when it reads the owners, then sends SIGTERM and, 15 s later, SIGKILL to the bare PID with no further check (Verified: `caddy/owners.go:55`, `:158-181`; `caddy/routes.go:163`; `caddy/stack_record.go:24`; `caddy/stack_occupant.go:59-94`; `stop.go:88-124`).

Negative searches:

- No preview, confirmation or dry run: `dry.?run`, `--yes`, `confirm`, `isatty`, `IsTerminal` and `prompt` match nothing in `apps/devhost/internal/cli/parse.go`, `services/stop.go`, `services/stop_worktrees.go` or `services/restart.go` (Verified).
- No process identity in the service tracker: `procid`, `StartIdentity` and `pidfd` match nothing in `services/containment*.go` except the Linux snapshot's `procid.ReadStat`, which parses each process's start time and keeps only its parent and state (Verified: `containment_linux.go:31-70`; `apps/devhost/internal/procid/procid_linux.go:24-31`).
- No Git writes: stop and restart run only `git rev-parse --show-toplevel` and `--git-common-dir`; `commit`, `checkout`, `reset`, `stash`, `push`, `branch`, `switch`, `merge`, `rebase` and `worktree add|remove|prune` match nothing in `stop.go`, `stop_worktrees.go`, `restart.go` or `worktree_git.go` except the parser of `git worktree list` output (Verified: `worktree_git.go:45-67`, `:83`).
- No continuation or summary after a failure in `stop --worktrees`: the loop returns on its first error, while `restart --all` collects failures and attempts the remaining stacks (Verified: `stop.go:76-83`; `restart.go:82-89`; `guides/stack-lifecycle.md:248`).

What this means in practice:

1. One `devhost stop --worktrees` run from any checkout stops the stacks of every linked worktree of the repository, including ones an agent or another terminal started, one after another with up to 15 s each before the supervisor is killed, and names none by stack name, branch or how it runs (Verified: `stop.go:74-83`; stack-run-stop-07).
2. When one of those stacks cannot be stopped, the command exits 1 naming that PID and every later stack keeps running unnamed (Verified: `stop.go:80-82`, `:118-135`). Hypothesis: rare; it needs a signal error other than "no such process" or a supervisor that survives SIGKILL for a second, such as one owned by another user or stuck in an uninterruptible kernel wait.
3. A stack that needs more than 15 s to stop is reported stopped ("Process n terminated.", exit 0) while its services keep running and answering its hostnames, invisible to `stack list` and `devhost stop`; under `--worktrees` every slow stack repeats this (Verified: `stop.go:117-130`; interrupted-operations-01, interrupted-operations-02).
4. One `devhost stack restart --all` replaces every stack and serve session in the state directory, across repositories. A foreground stack's terminal prints an ordinary shutdown and exits 143 (Verified: stack-run-stop-02). A serve session started in a terminal becomes a background process with closed input that `stack list`, `stack find` and `devhost stop` cannot see, and it keeps serving its folder after its terminal closes until its new PID, printed only in the restart output, is signalled by hand (Verified: `restart.go:142`, `:201-215`; `caddy/owners.go:55`; `guides/stack-lifecycle.md:244`; `start/serve.md:68`). Every serve session runs chat (Verified: serve-folder-04).
5. A replacement starts the launch selection again, so services started later through the toolbar stop and are not restarted (Verified: `guides/stack-lifecycle.md:242`; `cli/parse.go:423-425`).
6. A stack whose own shutdown takes longer than 15 s is left stopped with no replacement and exit 1; the 15 s ignores the shutdown's one-after-another 10 s waits (Verified: `restart.go:194-198`; `stack.go:1241-1250`; stack-run-stop-13).
7. A stack that stops, or hot reloads its manifest, while `restart --all` works through earlier stacks is refused with "stack ownership changed; refresh worktrees", an instruction for the toolbar's worktree picker, and counted as a failed restart; after a reload it keeps running the old executable (Verified: `caddy/stack_occupant.go:48-53`, `:75-85`; `caddy/stack_record.go:64-72` writes a new creation time on every registration; `services/manifest_registration.go:17-45`; `services/reload.go:100`). Hypothesis: each earlier stack opens up to 45 s (15 s to stop, 30 s to register), so it needs a long `--all` run and a stop or save inside it.
8. Every stop path can reach unrelated processes. On a machine whose PIDs wrap within the life of a service that forks short-lived children (about 14 minutes on the review machine), a later process that takes one of those PIDs receives the stop signal and, 10 s later, SIGKILL, and the stop still reports success. The paths are Ctrl-C, SIGTERM from `devhost stop` or `stack restart`, SIGHUP, the idle timeout, a service restart, a reload that restarts the service and a worktree switch (Verified: `containment.go:108-118`, `:217-260`; `stack.go:635-651`, `:1209-1250`, `:1274-1283`; process-containment-01).
9. A tracked PID now owned by another user answers EPERM, counts as alive, keeps the service "running" through both 10 s waits and fails the shutdown naming a process the service never had, while `devhost stop` SIGKILLs the supervisor at 15 s (Verified: `containment.go:285-292`; `stack.go:1845-1877`; `stop.go:117`; process-containment-01).
10. Signals reach a service's process group only while its root process lives; after the root exits only tracked PIDs are signalled, so a group member no snapshot saw is never signalled (Verified: `stack.go:1297-1305`; `containment.go:13`). The docs say so for macOS: devhost "can miss a process that detached" (Verified: `guides/stack-lifecycle.md:287`).
11. Stopping a stack ends every chat conversation of its control server and deletes their replay journals, and `devhost stop` names none of them (Verified: `chat_sessions.go:80-100`; `stop.go:74`; chat-conversations-03). Hypothesis: an agent turn in progress is cut off mid-task, possibly mid-edit; holds when the agent CLI does not finish its current tool call after its session closes (not tested).
12. One stuck stop holds every stack: the stop's Caddy reload has no deadline and holds the shared routes lock, so every other stack's route changes wait on it (Verified: stack-scale-01).
13. The supervisor PID itself is safe from reuse in practice: `stack restart` re-checks it immediately before signalling, and `devhost stop`'s window between its identity check and its signals grows by up to 15 s per earlier target (Verified: `stop.go:43-48`, `:76-83`). Hypothesis: harmless, because macOS and Linux hand out PIDs in increasing order and a window of seconds cannot wrap the PID space; it stops holding only on a machine that starts about 100,000 processes within that window.

Reusable capabilities and their limits:

- **Process start identity.** `internal/procid.StartIdentity` reads the kernel's start time to the microsecond on macOS and the boot ID plus the start time in clock ticks since boot on Linux; other platforms have none and fall back to the PID (Verified: `procid/procid_darwin.go:11-22`; `procid_linux.go:80-95`; `procid_other.go:10-14`). Hypothesis: Linux ticks are 1/100 s on common kernels (general knowledge), so a reused PID would need to start within 10 ms of the old process, which a PID wrap cannot produce.
- **Snapshot cost.** The Linux snapshot already parses every process's start ticks and discards them; the macOS snapshot is one `ps` run per 200 ms per supervisor, about 15% of a CPU core with about 850 processes (Verified: `containment_linux.go:44-70`; `containment_darwin.go:16-17`; process-containment-02).
- **Revalidated signals.** `StackOccupant.Signal` re-checks a stack's registration and start identity under the records lock before signalling; `stack restart` already uses it (Verified: `caddy/stack_occupant.go:59-94`; `restart.go:191`).
- **Budgets already in code.** A detached start waits a minute plus 20 s per service for a failed supervisor's cleanup; the shutdown allows each service 10 s before SIGKILL and 10 s after, one service at a time; `stop` and `restart` allow 15 s; a replacement gets 30 s to register (Verified: `detach.go:248-253`; `stack.go:35`, `:1241-1250`; `stop.go:17`; `restart.go:22`).
- **What a plan can show.** The stack record holds the name, manifest path and files, PID, start identity, URLs, readiness, control port and log path, and only detached starts and restart replacements have a log path, so a stack without one runs in a terminal. It holds no branch, service selection or launch arguments; restart reads the arguments from the operating system (Verified: `caddy/stack_record.go:15-26`; `services/launch_metadata_test.go:15-16`; `detach.go:24-28`; `restart.go:119-167`).

### Other products

General knowledge, not re-checked for this note:

- **Docker Compose.** `docker compose down` and `docker compose stop` act on one project, named by its folder or `-p`; each container gets SIGTERM and then SIGKILL after a timeout (`-t`, 10 s by default); containers are confined by control groups, so a stop never signals a process outside them; a second Ctrl-C during `docker compose up` forces the stop. `docker system prune` lists what it will remove and asks "Are you sure you want to continue? [y/N]" unless `-f` is given (Docker CLI reference: `docker compose down`, `docker system prune`) (general knowledge, not verified for this note).
- **systemd.** `systemctl stop` signals every process in the unit's control group (`KillMode=control-group`), waits `TimeoutStopSec` (90 s by default) and then sends SIGKILL to the group; membership comes from the kernel, not from PIDs collected earlier (man pages `systemd.kill(5)`, `systemd.service(5)`) (general knowledge, not verified for this note).
- **Linux pidfds.** `pidfd_open(2)` (Linux 5.3) returns a handle to one process and `pidfd_send_signal(2)` (Linux 5.1) signals through it, so a signal never reaches a later process with the same PID. macOS has no equivalent; comparing a process's start time read through `sysctl` is the usual check (man pages `pidfd_open(2)`, `pidfd_send_signal(2)`) (general knowledge, not verified for this note).
- **Git.** `git clean` refuses to delete without `-n` (dry run) or `-f`, and `git worktree remove` refuses a worktree with changes unless `--force` is given (man pages `git-clean(1)`, `git-worktree(1)`) (general knowledge, not verified for this note).
- **Plans before changes.** `terraform plan` and `kubectl delete --dry-run=client` print what a command would change before anything changes (Terraform and kubectl command references) (general knowledge, not verified for this note).

## Open questions

1. **Whether the bulk commands ask before acting.** Unknown: whether `devhost stop --worktrees` and `devhost stack restart --all` should ask for confirmation in an interactive terminal, or only print what they will affect and then act. Why it matters: one command stops or replaces stacks that other terminals and agents run, today without naming them first (Verified: consequences 1 and 4); a prompt guards against a mistyped flag but changes the documented post-upgrade step for every caller attached to a terminal, and agents run these commands too (Hypothesis: holds when installers or agents run `restart --all` with a terminal attached). Evidence that closes it: who runs these commands and how (an installer, an upgrade script, an agent shell, a person), and whether any documented script would block on a prompt. Proposed default: print the plan before acting (each stack by name, checkout and branch, PID, terminal or background, chat turns in progress) and each stack's outcome after, never prompt, and offer `--dry-run` that prints the plan and changes nothing; this warns at the point of choice instead of gating an intended action. Decides: the product owner.
2. **How long stop and restart wait for a stack to stop.** Unknown: the budget. Today both allow 15 s, while the shutdown itself gives each service 10 s before SIGKILL and 10 s after, one service at a time, and a detached start allows a failed supervisor a minute plus 20 s per service (Verified: `stop.go:17`; `stack.go:1241-1250`; `detach.go:248-253`). Why it matters: a budget below the stack's own need makes `devhost stop` orphan the services and report success, and `stack restart` leave the stack stopped (Verified: interrupted-operations-01, stack-run-stop-13); a longer budget makes a stuck stop wait longer before it says so. Evidence that closes it: stop durations measured on representative stacks (dev servers holding connections, compose-backed services, a database flush) as a calibration ladder, with the shutdown's waits run one after another as today and in parallel. Proposed default: the detached start's cleanup allowance, with progress lines while waiting, and never SIGKILL the supervisor while it is still stopping services, which is what the interrupted-operations-01 stopgap ships. Decides: the product owner; Phase 7 calibrates the number.
3. **Whether `stack restart --all` replaces sessions that run in a terminal.** Unknown: whether `--all` should replace foreground stacks and `devhost serve` sessions with background processes, as documented today (Verified: `guides/stack-lifecycle.md:240-244`; `reference/cli.md:15`, `:26`). Why it matters: a foreground terminal ends with exit 143 and loses its logs and Ctrl-C (Verified: stack-run-stop-02), and a serve session, meant to end with Ctrl-C, becomes a background file server with chat on that no devhost command lists or stops (Verified: consequence 4; serve-folder-03, serve-folder-04). Evidence that closes it: how people keep stacks and serve sessions while upgrading, and whether any upgrade path runs `restart --all` unattended. Proposed default: replace manifest stacks, foreground ones included, each saying in its own terminal that it was replaced and where its replacement logs; list serve sessions in the plan and leave them running, with the command that restarts each in its terminal. Decides: the product owner, as a change to the documented restart contract.
4. **What a stop does about agent turns in progress.** Unknown: whether `devhost stop`, `--worktrees` and `stack restart` should proceed, warn or wait when a chat turn runs in a stack they stop. Why it matters: a stop ends every conversation and deletes its replay journal without a word, while the idle timeout already counts a running turn as activity (Verified: consequence 11; `guides/stack-lifecycle.md:265`); an agent cut off mid-edit can leave a file half written (Hypothesis: holds when the agent CLI stops its current tool call when its session closes). Evidence that closes it: what Claude Code and Codex do with a tool call in flight when their chat session closes and their process group gets SIGTERM, tested against a disposable fixture. Proposed default: proceed without waiting, and name each conversation ended, with whether a turn was in progress, in the plan and in the outcome. Decides: the product owner; agent-chat owns keeping ended conversations resumable.
5. **Whether `stack find` resolves a folder to its stack.** Unknown: whether a query naming an existing folder, `.` included, should match the stack started from that folder's `devhost.toml`, as `devhost stop` resolves a folder, instead of matching as a substring (Verified: `caddy/stack_find.go:29-50`; documented in `reference/cli.md:14` and `guides/stack-lifecycle.md:214`). Why it matters: with worktrees under the main checkout, `stack find .` returns every worktree's stack, so a script that feeds the result to `devhost stop --manifest` targets the wrong stacks or breaks (Verified: stack-run-stop-08). Evidence that closes it: whether any documented or known script relies on a folder substring matching several stacks. Proposed default: an existing folder matches only the stack started from the `devhost.toml` in it; every other query keeps today's matching. Decides: the product owner, as a CLI contract change.
6. **What a second Ctrl-C does.** Unknown: whether a second Ctrl-C during a shutdown forces it. Why it matters: today it is ignored (Verified: `stack.go:216-232`; interrupted-operations-03), so people close the terminal or run `kill -9`, which orphans every service (Verified: interrupted-operations-02); forcing kills services that were still saving data (Hypothesis: holds for services with a long drain, such as databases). Evidence that closes it: which service types devhost's users run need their full drain to keep data, and how Docker Compose words its forced stop. Proposed default: the second Ctrl-C sends SIGKILL to every service still running and still releases the routes, claims and stack record, printing that it forced the stop and which services it killed. Decides: the product owner.

Already product decisions in the pattern reference, cited rather than repeated: `O6` (what `devhost start <names>` does when the stack runs without those services), `O10` (which lifecycle actions the browser offers; it still cannot stop the page's own stack) and `O15` (how long a stopped stack is remembered for the page its hostnames show) (Verified: section 5 of the pattern reference, revision 1).
