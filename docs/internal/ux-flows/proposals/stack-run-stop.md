# Start, find, stop and restart stacks from the terminal: proposed experience

Diagrams: [current](../stack-run-stop-current.html), [proposed](../stack-run-stop-proposed.html). [Wireframe](../wireframes/stack-run-stop.html). Research: [notes](stack-run-stop-research.md).

Status: design proposal, not implemented behavior. The [shared UX pattern reference](../patterns.md) wins where this proposal disagrees with it.

Source revision: alexgorbatchev/devhost `190a8bb53e8cd903d2db0a92cb0886f29671607f` (Rust `main`). Features: STK-01, STK-02, STK-03, STK-04, STK-05, STK-06, STK-07, STK-08, STK-09, STK-10, MAN-01, MAN-02. Redesign ticket: tracked privately.

Product rule: the owner's settled intents govern this flow: a failed service leaves the rest of the stack running (the recovery contract in `stacks/recovery.md`), and a detached start stops the stack on a failure before readiness; devhost never opens a browser; human output and agent output (`AGENT=1`) differ on purpose (`reference/output.md`); every manifest setting applies through hot reload, never "restart to apply". So a start that reports one failed service while five keep running is intended, a detached start that stops after a failure is intended, the terminal printing URLs instead of opening them is intended, and two output layouts are intended; none of them is a defect. The gap is around them: the terminal never says when a stack is ready or what a stop really stopped, stops and replacements report success while services keep running or the stack stays down, the commands that reach every stack act without showing their set, an agent cannot ask whether services are up or restart one, enabling `[remote]` takes stacks off `.localhost` and stalls 45 s on bad relay credentials, active serve sessions stay invisible to stack commands, and every error and line is worded for devhost's internals instead of for the person or the agent reading it.

## Target experience

The person types `devhost start` in their project. Each service's URL prints as soon as its route answers, labelled by service (showing both local and public preview URLs clearly labelled when `[remote]` is configured, keeping the stack running locally when the relay is offline), then one ready line names the primary URL and the time it took, "Ready in 4.2 s: https://shop.localhost/ · 6 of 6 running", followed by the stack directory's URL ("All stacks on devbox: https://devhost.localhost/") and the active proxy listener line; with `--detach` the terminal names the stack within a second and keeps one status line updated ("Starting Acme Shop · waiting for api · health check 2 s of 30 s · 3 s") until the same ready line. A start that cannot run says which file, line and key stop it and what to do, before any service starts, and a non-retryable relay auth, fingerprint, or reverse-port error fails fast within 5 s naming the cause and `connector.log` instead of timing out after 45 s. From any terminal or agent, `devhost stack info` — and its short alias `devhost status` — answers what runs: each service's state with its cause and since when, its URL, what changed, any rejected manifest edit, remote preview state, and the last operation's outcome, exiting 3 when a started service is not running; `devhost service restart api` restarts one service the way the toolbar does and prints its outcome, and `devhost logs -f` follows the stack's one log through every replacement. When no manifest stack runs and manifest-free `devhost serve` sessions are active, `devhost stop`, interactive `devhost stack list`, `devhost stack find`, and `devhost stack info` (`devhost status`) surface those sessions and print `--sessions` / `--session <name>` commands instead of returning empty or manifest-only errors. `devhost stop` names the stack and its worktree, not PIDs, runs foreground and daemon shutdown in parallel from `t = 0` with one termination signal per service and one shared process snapshot, keeps one line updated while services stop ("Stopping Acme Shop · 4 of 6 stopped · mail and worker still stopping · forced in 6 s · Ctrl-C forces them now"), says that Ctrl-C forces them, waits within a 30 s default budget (configurable `5s`..`10m`) without ever killing a stopping supervisor, and reports success only once no process, route or port claim of the stack remains, naming the conversations the stop closed and printing the command that starts it again. Commands that reach several stacks — `devhost stop --worktrees`, `devhost restart-all`, and `devhost upgrade` — print their set first with each stack's worktree, how it runs and the conversations it would close, act on every member and report each one, and ask `[y/N]` only when an agent's turn would end; `--dry-run` shows the set and changes nothing. `devhost upgrade` downloads the latest release, verifies `SHA256SUMS`, swaps a user-writable binary (clearly reporting read-only paths or externally managed installs without breaking them) and replaces running manifest stacks, while shipped `devhost restart-all` and project-scoped `devhost stack restart` keep one verb for dotfiles, package managers and local rebuilds and state clearly that they replace the running devhost supervisor process. A stack that ends prints why, and its configured HTTPS hostnames stay routed to the stopped-stack page over HTTPS for 24 hours with the command that starts it again. Processes cannot be un-stopped, so there is no Undo: every stop names its way back, the start command, and a replacement that cannot finish says what still runs and how to start it. Benchmarks: Vite's "ready in" line and its URL list printed once, with a key to print it again; `docker compose up --wait` and `kubectl rollout status` certify readiness, not a step; `docker compose ps --format json`, `tilt get` and `kubectl wait` give scripts a waitable, exit-coded state; `docker compose restart api` and `overmind restart` restart one service of a running project; Docker Compose names its force step and forces on a second Ctrl-C; systemd reports a unit stopped only when no process of its control group remains and keeps the exit cause; `docker system prune` and `terraform plan` print what they would change before changing it; rustc and TypeScript print `file:line:column` with the offending line. Competitor behavior is evidence here, never a requirement.

## Target steps

Today: 7 steps on the main path, two of them blind: `devhost start`, validation, the launch with no ready line, a blank detached wait, `stack list` or `stack find` (a PID and a path), `devhost stop` (PIDs; 15 s, then the supervisor is killed), a silent shutdown. Proposed: 4 steps: `devhost start` with its ready line, `devhost stack info` (`devhost status`), `devhost stop` with its parallel progress, its outcome. Every step below is the same in a foreground and a detached stack unless it says otherwise, and every line it shows exists in both outputs: human output as written here, agent output (`AGENT=1`) with the same facts, absolute paths, PIDs and identifiers, and every error on one `devhost: ERR:` line (`WORD-9`, `FB-11`, `CC-30`).

1. **Start a stack (`devhost start [names]`, one write).** devhost finds the root manifest from the current folder upward up to the first folder containing `.git` (stopping at the repository root, as `apps/devhost/src/manifest.rs` does today), `--manifest` or `DEVHOST_MANIFEST` (MAN-01), and checks everything checkable before any service runs: the manifest and its includes against the schema, every service's `cwd` before the worktree lookup, the requested names, and every hostname (including reserved hostnames such as `[caddy].stackDirectoryHost`) and fixed-port claim, including a leftover of an earlier, killed run of the same manifest (`REV-11`, `ACT-11`). Route `path` values use prefix matching (`O44`): `path = "/api"` routes `/api` and everything below it (matching `DEVHOST_PATH`'s documented public path prefix, while `"/api/*"` keeps working). The first line names the stack, its worktree and its size, "Starting Acme Shop from main ~/acme · 6 services", with the worktree label of `SEL-4` (branch, or "Detached" with its 7-character commit ID, then the path shortened with `~`), and names the worktree a repository runs from when it is not the configured one, as after an interrupted switch (`SEL-4`, `FB-10`, `WORD-11`). When `[remote]` is configured in `config.toml` and `--local` is not passed, remote previews are additive (`relay-previews-02`): devhost keeps local hostnames (`shop.localhost` or configured local `domainSuffix`) active alongside public preview hostnames, connects to the relay in parallel with service startup (`relay-previews-04`), prints both local and public URLs clearly labelled (`local` and `preview`), flags any public hostname that lacks a matching DNS record (`DNS not configured`), and keeps the stack running locally with the preview marked offline if the relay is unreachable; passing `--local` publishes nothing to the relay. Each service's URL prints, labelled, as soon as its route is published ("api https://shop.localhost/api/"), the primary service's first among those published together; then one ready line, "Ready in 4.2 s: https://shop.localhost/ · 6 of 6 running", "All stacks on devbox: https://devhost.localhost/" (the machine name from `O61`, with the port when it is not 443), the active proxy listener line (naming loopback-only or all-interfaces listeners, and on macOS with `bindHost = "127.0.0.1"` below port 1024 the explicit `O39` warning naming `httpsPort = 4443` or a privileged launcher), and in a foreground terminal "Ctrl-C stops Acme Shop" (`FB-10`, `FB-5`, `WORD-4`, `SURF-15`, `KEY-14`, `O39`, `O61`, `CC-22`). Ready is certified, never a step: the line prints only once every started service passed its health check, or for a `process` check or none still runs after `O28`'s 1 s time, with no leftover answering in its place (`FB-5`, `ACT-11`). While it waits, a slow service keeps today's waiting line, now with what the probe last saw: "Waiting for api · GET /healthz returned 404 Not Found · 12 s of 30 s" (`STATE-1`, `ACT-4`, `FAIL-3`). The full URL list prints at the first start and on request (`devhost stack info` / `devhost status`), never again after each later action (`FB-10`, `ACT-12`). The services the run left out are counted, "4 of 6 running · 2 not started: admin, mail", and a longer list collapses to its count and the command that lists it, "34 services not started · devhost status" (`WORD-5`, `ACT-6`). A foreground stack also writes the stack's per-manifest log (`FB-7`, `CC-21`).
   - Defaults: the manifest's selection (`alwaysStart`, then the named services and groups with their `dependsOn`), as today (STK-03); the primary service is the manifest's first routed service, as today.
   - Keys: Ctrl-C stops the stack gracefully; a second Ctrl-C forces it (step 10, `KEY-14`).
   - Words: stack, never project or process; worktree, never checkout as a noun (`WORD-11`); services by name; state words of `WORD-6`, never only a color (`ACT-13`); lines start with a capital letter unless they start with a name that keeps its own case, such as devhost or api, and only sentences end with a period (`WORD-3`); URLs, paths and commands are never broken across lines, a command to run sits on its own line without trailing punctuation, and URLs are OSC 8 links where the terminal supports them (`WORD-1`, `WORD-6`, `WORD-8`).
2. **A start that cannot run says where and what to do (`devhost start`, read only: nothing starts).** Every problem prints as `file:line:column  key  message` with the offending line and, for a key close to a valid one, the close key: "admin/devhost.toml:3:1 services.admin.hostname unknown setting; did you mean host?", every problem of every file at once, grouped by file relative to the root manifest, then "Nothing started. Fix the manifest and run devhost start again" (`FAIL-2`, `MENU-4`, `WORD-7`, `WORD-8`). A hostname (including a reserved stack-directory hostname) or port clash names every clash with the owning stack's name, worktree and the command that stops it; an unknown name separates services from groups and suggests the closest (`FAIL-2`). A missing `cwd` reads "devhost.toml:12:7 services.api.cwd folder api does not exist in ~/newapp", never a Git error (`FAIL-2`, `REV-11`). A health check that fails names what the probe saw: "api answers on 127.0.0.1:4000, but GET /healthz returned 404 Not Found · 6 tries · 30 s of 30 s. Set services.api.health.http to a path that answers 2xx, or remove it to use a TCP check" (`FAIL-3`, `WORD-7`). When `[remote]` is enabled and the relay rejects credentials, refuses a host-key fingerprint, or refuses the reverse port, devhost fails fast in under 5 s with a plain message naming the cause and the path to `connector.log` instead of waiting 45 s silently for `"wait for authenticated remote connector: timed out"`, retrying only transient network errors with progress lines while local services start in parallel (`relay-previews-04`, `FAIL-2`, `FAIL-3`). Because `path` uses prefix matching (`O44`), `path = "/api"` needs no warning; a manifest that starts with a `path` but no `host` (which routes nothing) or `watch` on an external service (which devhost ignores, `ACT-8`) prints a warning with file, line, column and key and keeps starting: "devhost.toml:9:8 services.api.path routes nothing without host", the ready line repeats the count ("· 1 warning: devhost.toml:9"), and `devhost stack info` (`devhost status`) lists it (`O44`, `FAIL-2`, `MENU-4`, `ACT-8`). Under `AGENT=1` every problem — manifest errors or fail-fast relay errors — joins one `devhost: ERR:` line, "devhost: ERR: devhost.toml was not accepted: /work/acme/admin/devhost.toml:3:1 services.admin.hostname: unknown setting, did you mean host?; …" (`FB-11`, `WORD-9`). When no manifest is found, the error names where the upward search stopped (`stack-run-stop-17`): inside a Git repository, "No devhost.toml in ~/newapp/sub up to the repository root ~/newapp" (and outside any Git repository, "No devhost.toml in ~/newapp or any parent folder"), then `devhost init` on its own line (`O52`, decided: writes a commented `devhost.toml` with one service guessed from `package.json`'s `dev` script, `Cargo.toml`, `go.mod`, or a `Procfile`, and refuses to overwrite an existing file) and the Quickstart URL (`STATE-2`, `O52`, `stack-run-stop-12`, `stack-run-stop-17`).
3. **Start detached (`devhost start --detach`, one write).** Within a second the terminal names the stack, "Starting Acme Shop in the background from main ~/acme · 6 services", then keeps one status line updated on a terminal, "Starting Acme Shop · 3 of 6 running · waiting for api · health check 2 s of 30 s · 7 s", or prints one line per change when output is not a terminal (`FB-10`, `STATE-1`, `ACT-4`). It ends with the same labelled URLs (local and preview when `[remote]` is configured, marking preview URLs offline if the relay is down, `relay-previews-02`, `relay-previews-05`) and ready line as the foreground, "All stacks on devbox: https://devhost.localhost/" (`O61`), "Log: devhost logs", and "Stops after 30 min without requests (idleTimeout)" when the stack has an idle timeout (`FB-10`, `SURF-13`, `ACT-10`). As today, a failure before readiness stops what it started (using step 9's unified parallel stop routine) and prints the log tail, now with the cause once, by service, with `FAIL-3`'s evidence (owner rule; `FAIL-1`, `O30`). Ctrl-C while it waits cancels the start: "Cancelled the start of Acme Shop: stopped web and api, which had started", with no error tag (`FAIL-5`, `KEY-14`, `WORD-7`). A second start of the same manifest keeps waiting for an unsettled first one, as today (`HOLD-3`), and if a running stack's relay preview is offline, repeat `start --detach` marks the remote preview URL offline instead of presenting it as healthy (`relay-previews-05`).
4. **Start services into a running stack (`devhost start [--detach] <names>`, one write).** When the manifest's stack already runs, devhost expands the requested names (groups, `dependsOn`, `alwaysStart`) and compares them with what runs. Services the run left out start into the running stack exactly as the Services panel's **Start** does, with what they depend on and without touching running services, and the command prints what it started: "Started admin in Acme Shop · https://admin.shop.localhost/ · 1.2 s" (`SEL-7`, `O6`, `FB-3`, `CC-7`). When everything asked for already runs, it says so and prints the requested services' URLs only: "Already running in Acme Shop: web, api · https://shop.localhost/" (`FB-10`). The start queues behind a per-service operation and is refused while the stack starts, stops or runs a stack-wide operation, naming it ("Not started: Restart Stack is running · 3 of 6 started") and exiting 1 (`HOLD-3`, `HOLD-1`, `CC-8`).
5. **Check what runs (`devhost stack info [--json] [--wait]`, short alias `devhost status [--json] [--wait]`, read only).** Extending shipped `devhost stack info` (`apps/devhost/src/services/stack_info.rs`, `GET /__devhost__/stack-info`) with `devhost status` as its short alias sharing one implementation and output contract (`O62`, `CC-23`), one command answers whether the stack's services are up, from the published service state and the operation record that every surface reads, never a guess of the CLI's own (`FB-11`, `ACT-1`, `ACT-2`). Human output: a header line with the stack, its worktree, its PID, foreground or detached, its stack state and its summary, "Acme Shop · main ~/acme · PID 84244 · detached · failed · 4 of 6 running · 1 exited · 1 not started · as of 14:02:31", the snapshot's time saying that the answer does not update (`ACT-6`, `ACT-12`, `WORD-5`, `WORD-11`); one line per service with its state word, its cause and since when, and its URL ("api exited with code 1 at 14:01 · devhost service restart api", "admin not started · left out of this run · devhost service start admin", "docs running · changed: docs/astro.config.mjs"), an external service's reachability with its check and its time and "runs outside devhost", never a restart (`ACT-2`, `ACT-8`, `ACT-9`, `WORD-6`, `MENU-5`); a starting service's health check with its time ("starting · health check 4 s of 60 s", `ACT-4`); a transition as the touched services' step ("restarting · Restart Stack", `ACT-3`); a rejected manifest file as "devhost.toml line 12 is not applied: …", with the stack still running the accepted manifest (`HOLD-6`, `O62`); a blocked repository once, as its sentence ("The worktree ~/acme/.worktrees/fix-nav was deleted; its services still run from it"), instead of its URLs (`HOLD-4`, `WORD-11`); when `[remote]` is configured, local and public URLs clearly labelled plus any offline preview state ("Remote preview: offline since 14:12 · relay.acme.test disconnected · local URLs keep running", `relay-previews-02`, `relay-previews-05`); then "Last operation: Restarted docs · 1.9 s · 14:00 · from a page on shop.localhost", "Log: devhost logs", the active proxy listener line, and "All stacks on devbox: https://devhost.localhost/" (`FB-3`, `FB-7`, `SURF-15`, `O61`). It exits 0 when every started service runs and 3 naming each one that does not ("1 started service is not running: api"); 1 stays a failure of the command itself (`FB-11`, `O62`). `--wait` first waits for a running operation to end, printing its progress line (`FB-1`, `FB-11`). `--json` prints the same facts with `WORD-6`'s identifiers (`not-started`, `not-reachable`), manifest-reload rejection state, changed-file markers, remote preview status, absolute paths and ISO times (`WORD-6`, `WORD-8`, `WORD-9`, `O62`, `relay-previews-05`). `--session <name>` inspects a manifest-free serve session; in a folder with no running manifest stack it says "Acme Shop is not running" (or names the `.git` search boundary when no manifest exists), prints within `O15`'s 24-hour window when and why it stopped and the command that starts it (`ACT-10`, `STATE-2`), and when one or more manifest-free serve sessions are running names them with `devhost stack info --session <name>` (`devhost status --session <name>`) and `devhost stack list --sessions` (`serve-command-04`). When the stack's devhost process runs but its control server does not answer, it prints what the stack's record holds marked with its age, says once "Acme Shop's devhost process (PID 84244) does not answer; its state is unknown, last seen 14:02", never an empty list or "not running", and exits 1 (`STATE-4`, `STATE-3`, `ACT-5`). Every state is a word, never only a color (`ACT-13`). Leftovers of a killed run are named here too (step 13).
6. **Find stacks (`devhost stack list`, `devhost stack find <query>`, read only).** `stack find` resolves a query that names an existing folder, `.` and `..` included, to the stack of the nearest `devhost.toml` from that folder upward, as `devhost stop` does, and keeps substring matching of hostnames, names and manifest paths for other words (`SEL-6`, `SEL-10`, `CC-34`). Human output on a terminal shows one line per stack, its name, its worktree label, its PID, foreground or detached, its summary, and any offline remote preview state ("Acme Shop fix-nav ~/acme/.worktrees/fix-nav PID 85102 · foreground · 6 of 6 running · preview offline"), so two stacks named Acme Shop read apart, then when manifest-free serve sessions are running a hint line naming them ("1 serve session running (~/acme/docs) · devhost stack list --sessions", `serve-command-04`), and "All stacks on devbox: https://devhost.localhost/" (`SEL-4`, `WORD-1`, `WORD-11`, `ACT-6`, `SURF-15`, `O61`, `relay-previews-05`); a stack with leftovers of a killed run is listed with them (step 13). When no manifest stacks run on an interactive terminal and serve sessions are active, `devhost stack list` says "No manifest stacks are running · 1 serve session running (~/acme/docs) · devhost stack list --sessions" instead of printing nothing (`serve-command-04`). Piped, or under `AGENT=1`, both `stack list` and `stack find` keep today's documented picker format, `<PID><TAB><manifest path>`, byte for byte (and `--sessions` keeps `<PID><TAB><session name>`), because scripts and shell completion read it, and detailed state lives in `devhost stack info` (`devhost status`, `O62`). No match says what was searched, and when a serve session matches the query it names that session and points to `devhost stack info --session <name>` ("No manifest stack matches \"docs\", but serve session \"docs\" is running · devhost stack info --session docs"); otherwise "No stack matches \"shopp\" · devhost stack list lists them all" (`STATE-2`, `SEL-10`, `serve-command-04`).
7. **Act on one service (`devhost service start|stop|restart <service|group>…`, one write per service).** The terminal becomes one of each service's stated entry points, beside its row in the Services panel, the crash view and the control API (`MENU-1`). These reach the running stack through its control server on the loopback port the state directory records, the way the toolbar does, foreground or detached, send an `operationId` and take their outcome from the operation record, so a lost response never sends the write again (`SEL-7`, `MENU-6`, `REV-12`, `ACT-1`, `CC-11`, `CC-37`). Each waits for health checks, printing the progress line, then one outcome per target: "Restarted api · 2.6 s", "Started admin and mail (admin depends on mail) · 3.1 s", "Stopped worker · it reads not started, stopped by you"; a failure prints the target, the exit with its time, its last output lines and what devhost ran, and exits 1 (`FB-3`, `FAIL-1`, `FAIL-3`, `WORD-4`). A restart of another service queues behind a running one, "worker queued behind Restart api", and runs after it; a restart of a service already restarting, or any of them while the stack starts, stops or runs a stack-wide operation, is refused with one sentence naming that operation, its progress and the way out, "Not restarted: Restart Stack is running · 3 of 6 started. Run it again when Restart Stack ends", and exits 1 (`HOLD-3`, `HOLD-1`, `SEL-7`, `CC-8`). A rejected manifest blocks nothing: "Restarted api from the accepted manifest · devhost.toml line 12 is not applied · 2.6 s" (`HOLD-6`). An external service is refused with why: "search runs outside devhost; devhost checks it but cannot restart it" (`MENU-3`, `ACT-9`). The crash line a running stack prints names the command instead of "waiting for a restart": "api exited with code 1 at 14:01" and, on its own line, `devhost service restart api` (`MENU-6`, `MENU-5`, `FAIL-5`). `devhost service restart --all` is the terminal form of in-process **Restart Stack** (restarting every managed service with new automatic ports, as the Services panel, crash view, recovery pages and `POST /__devhost__/restart-stack` do), and its help says "Restart Stack in the browser" (`CC-11`, owner item q86), while `devhost stack restart`, `devhost restart-all`, and `devhost upgrade` replace the running devhost supervisor process (`O18`, `MENU-6`). `devhost reload [--dry-run] [--stdin <file>]` applies, or checks, the manifest on disk against the running stack and prints what manifest-hot-reload's reload reports (`FB-11`, `REV-10`, `CC-23`).
8. **Read the stack's output (`devhost logs [-f] [service…]`, read only).** Every stack, foreground or detached, appends to one log per manifest, whose name no longer changes when the stack is replaced; each run starts with a header naming the command, the PID, the worktree and the time; lines carry their time; the file holds one format, which `devhost logs` renders for people, and failures carry `ERR:` as warnings carry `WARN:` (`FB-7`, `FB-11`, `WORD-11`, `CC-21`, `CC-23`). `-f` follows the log across replacements; service names filter it; `devhost logs --path` prints the file's path for tools. Every operation on the stack, from any origin, is one outcome line there with its time and origin ("· from a page on shop.localhost", "· from an agent", "· after devhost.toml changed on disk"), so outcomes the toolbar closed stay readable (`FB-7`, `ACT-1`).
9. **Stop a stack (`devhost stop [--timeout <duration>] [--session <name>]`, one write).** The command resolves the stack as today (any path to its manifest, `--manifest`, or `--session <name>` for a serve session) and first names it, its worktree and what the stop ends: "Stopping Acme Shop (main ~/acme, PID 84244) · 6 services · closes 1 conversation: \"Fix the nav\" (Claude Code, working)" (`SEL-6`, `SEL-4`, `FB-4`, `WORD-1`, `WORD-11`). It never asks: it acts on the one stack it resolved (`REV-7`, `REV-1`). Before it signals, it records why beside the stack's record ("stopped from a terminal"), so the stack's own terminal, its open pages and its hostnames can say so (`ACT-10`, `HOLD-2`). Inside the stack's shutdown coordinator, foreground services and daemon lifecycle stops run in parallel from `t = 0` (`O30`, `O41`): devhost takes one shared process snapshot at `t = 0` (`apps/devhost/src/services/containment.rs`), sends a single termination signal per managed foreground service (`interrupted-operations-06`, removing the duplicate `SIGTERM` sent today), gives all foreground services one shared parallel 10 s `SIGTERM` grace window plus up to 5 s post-`SIGKILL` verification (15 s foreground bound) with one shared 2 s late-listener port scan (100 ms tick), and runs all daemon `status` → `stop` chains in parallel from `t = 0` under `O41`'s shared 20 s per-daemon deadline (20.12 s ceiling; whole-process-group `SIGKILL` on timeout; a cut `status` read reported as "did not finish", never "not running"). Combined worst case (0.82 s dispatch + max(15.0 s foreground, 20.12 s daemon) + 4.7 s route/record cleanup tail) is 25.64 s — fitting inside `O30`'s **30 s default** `stopTimeout` with 4.36 s margin. `stopTimeout` is configurable from `5s` to `10m` with precedence CLI `--timeout <duration>` > `DEVHOST_STOP_TIMEOUT` > `devhost.toml` top-level `stopTimeout` (hot-reloadable) > `~/.config/devhost/config.toml` `stopTimeout` > `30s`; raising `stopTimeout` does not extend `O41`'s 20 s daemon cut, and when a running daemon sets `[services.<name>.lifecycle].stopTimeout` above 20 s, the stack's effective wait automatically widens to `max(configured stopTimeout, max_running_daemon_stopTimeout + 10s)` unless an explicit CLI `--timeout` caps the run (`O30`, `O41`, `CC-35`, `CC-39`). This one stop routine and deadline rule governs every caller: `devhost stop`, `devhost stop --worktrees`, `devhost stop --session`, `devhost stack restart`, `devhost restart-all`, `devhost upgrade`, `devhost start --detach` failure cleanup, Worktrees **Stop Stack**, and `devhost serve` sessions. While services stop, one status line names those still stopping, the time before devhost forces them and the key: "Stopping Acme Shop · 4 of 6 stopped · mail and worker still stopping · forced in 6 s · Ctrl-C forces them now" (`FB-10`, `KEY-14`, `ACT-3`). The caller never sends `SIGKILL` to a supervisor that is still stopping services; Ctrl-C while it waits, or a second `devhost stop` of the same stack, forces remaining verified service process trees and daemon stop groups at once (`ACT-11`, `ACT-14`, `KEY-14`, `O30`, `CC-35`). Success is certified: "Stopped Acme Shop · 6 services · 6.1 s · closed \"Fix the nav\" (Claude Code, was working)", only once no process, route or port claim of the stack remains, then "Start it again in ~/acme with:" and `devhost start` on its own line (`FB-5`, `ACT-11`, `FB-4`, `UNDO-5`, `WORD-4`). - **Monorepo scale.** At first start every URL prints once; afterwards a one-service start prints its own URL, and lists of more than about a screen collapse to a count and the command that lists them (`WORD-5`, `FB-10`).
- **Who can reach a stack's control server from the network.** Remote browser access is governed by `O36` (shared-domain passkey with phone support and `devhost pair` fallback, built by `agent-chat`) and `O37`; terminal commands in this flow run on this machine over the loopback control port recorded in the state directory.
