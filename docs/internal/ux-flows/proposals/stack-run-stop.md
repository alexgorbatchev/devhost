# Start, find, stop and restart stacks from the terminal: proposed experience

Diagrams: [current](../stack-run-stop-current.html), [proposed](../stack-run-stop-proposed.html). [Wireframe](../wireframes/stack-run-stop.html). Research: [notes](stack-run-stop-research.md).

Status: design proposal, not implemented behavior. The [shared UX pattern reference](../patterns.md) wins where this proposal disagrees with it.

Source revision: alexgorbatchev/devhost `edb5c0fc01cabae490e92ac23d4c785ec896c4ed`. Features: STK-01, STK-02, STK-03, STK-04, STK-05, STK-06, STK-07, STK-08, STK-09, STK-10, MAN-01, MAN-02. Redesign ticket: tracked privately.

Product rule: the owner's settled intents govern this flow: a failed service leaves the rest of the stack running (the recovery contract in `stacks/recovery.md`), and a detached start stops the stack on a failure before readiness; devhost never opens a browser; human output and agent output (`AGENT=1`) differ on purpose (`reference/output.md`); every manifest setting applies through hot reload, never "restart to apply". So a start that reports one failed service while five keep running is intended, a detached start that stops after a failure is intended, the terminal printing URLs instead of opening them is intended, and two output layouts are intended; none of them is a defect. The gap is around them: the terminal never says when a stack is ready or what a stop really stopped, stops and replacements report success while services keep running or the stack stays down, the commands that reach every stack act without showing their set, an agent cannot ask whether services are up or restart one, and every error and line is worded for devhost's internals instead of for the person or the agent reading it.

## Target experience

The person types `devhost start` in their project. Each service's URL prints as soon as its route answers, labelled by service, then one ready line names the primary URL and the time it took, "Ready in 4.2 s: https://shop.localhost/ · 6 of 6 running", followed by the stack directory's URL; with `--detach` the terminal names the stack within a second and keeps one status line updated ("Starting Acme Shop · waiting for api · health check 2 s of 30 s · 3 s") until the same ready line. A start that cannot run says which file, line and key stop it and what to do, before any service starts. From any terminal or agent, `devhost status` answers what runs: each service's state with its cause and since when, its URL, what changed, and the last operation's outcome, exiting 3 when a started service is not running; `devhost service restart api` restarts one service the way the toolbar does and prints its outcome, and `devhost logs -f` follows the stack's one log through every restart. `devhost stop` names the stack and its checkout, not PIDs, keeps one line updated while services stop ("Stopping Acme Shop · 4 of 6 stopped · mail and worker still stopping · 12 s"), says that Ctrl-C forces them, and reports success only once no process, route or port claim of the stack remains, naming the conversations the stop closed and printing the command that starts it again. Commands that reach several stacks, `devhost stop --worktrees` and `devhost stack replace --all` (today `devhost stack restart --all`), print their set first with each stack's checkout, how it runs and the conversations it would close, act on every member and report each one, and ask `[y/N]` only when an agent's turn would end; `--dry-run` shows the set and changes nothing. A stack that ends prints why, and its hostnames say so for a day with the command that starts it again. Processes cannot be un-stopped, so there is no Undo: every stop names its way back, the start command, and a replacement that cannot finish says what still runs and how to start it. Benchmarks: Vite's "ready in" line and its URL list printed once, with a key to print it again; `docker compose up --wait` and `kubectl rollout status` certify readiness, not a step; `docker compose ps --format json`, `tilt get` and `kubectl wait` give scripts a waitable, exit-coded state; `docker compose restart api` and `overmind restart` restart one service of a running project; Docker Compose names its force step and forces on a second Ctrl-C; systemd reports a unit stopped only when no process of its control group remains and keeps the exit cause; `docker system prune` and `terraform plan` print what they would change before changing it; rustc and TypeScript print `file:line:column` with the offending line. Competitor behavior is evidence here, never a requirement.

## Target steps

Today: 7 steps on the main path, two of them blind: `devhost start`, validation, the launch with no ready line, a blank detached wait, `stack list` or `stack find` (a PID and a path), `devhost stop` (PIDs; 15 s, then the supervisor is killed), a silent shutdown. Proposed: 4 steps: `devhost start` with its ready line, `devhost status`, `devhost stop` with its progress, its outcome. Every step below is the same in a foreground and a detached stack unless it says otherwise, and every line it shows exists in both outputs: human output as written here, agent output (`AGENT=1`) with the same facts, absolute paths, PIDs and identifiers, and every error on one `devhost: ERR:` line (`WORD-9`, `FB-11`, `CC-30`).

1. **Start a stack (`devhost start [names]`, one write).** devhost finds the root manifest from the current folder upward, `--manifest` or `DEVHOST_MANIFEST`, as today (MAN-01), and checks everything checkable before any service runs: the manifest and its includes against the schema, every service's `cwd` before the checkout lookup, the requested names, and every hostname and fixed-port claim, including a leftover of an earlier, killed run of the same manifest (`REV-11`, `ACT-11`). The first line names the stack, its checkout and its size, "Starting Acme Shop from main ~/acme · 6 services", with the checkout label of `SEL-4` (branch, or "Detached" with its 7-character commit ID, then the path shortened with `~`), and names the checkout a repository runs from when it is not the configured one, as after an interrupted switch (`SEL-4`, `FB-10`). Each service's URL prints, labelled, as soon as its route is published ("api    https://shop.localhost/api/"), the primary service's first among those published together; then one ready line, "Ready in 4.2 s: https://shop.localhost/ · 6 of 6 running", and "All stacks on this machine: https://devhost.localhost/" with the port when it is not 443, and in a foreground terminal "Ctrl-C stops Acme Shop" (`FB-10`, `FB-5`, `WORD-4`, `SURF-15`, `KEY-14`, `CC-22`). Ready is certified, never a step: the line prints only once every started service passed its health check, or for a `process` check or none still runs after `O28`'s time, with no leftover answering in its place (`FB-5`, `ACT-11`). While it waits, a slow service keeps today's waiting line, now with what the probe last saw: "Waiting for api · GET /healthz returned 404 Not Found · 12 s of 30 s" (`STATE-1`, `ACT-4`, `FAIL-3`). The full URL list prints at the first start and on request (`devhost status`), never again after each later action (`FB-10`, `ACT-12`). The services the run left out are counted, "4 of 6 running · 2 not started: admin, mail", and a longer list collapses to its count and the command that lists it, "34 services not started · devhost status" (`WORD-5`, `ACT-6`). A foreground stack also writes the stack's per-manifest log (`FB-7`, `CC-21`).
   - Defaults: the manifest's selection (`alwaysStart`, then the named services and groups with their `dependsOn`), as today (STK-03); the primary service is the manifest's first routed service, as today.
   - Keys: Ctrl-C stops the stack gracefully; a second Ctrl-C forces it (step 9, `KEY-14`).
   - Words: stack, never project or process; services by name; state words of `WORD-6`, never only a color (`ACT-13`); lines start with a capital letter unless they start with a name that keeps its own case, such as devhost or api, and only sentences end with a period (`WORD-3`); URLs, paths and commands are never broken across lines, a command to run sits on its own line without trailing punctuation, and URLs are OSC 8 links where the terminal supports them (`WORD-1`, `WORD-6`, `WORD-8`).
2. **A start that cannot run says where and what to do (`devhost start`, read only: nothing starts).** Every problem prints as `file:line:column  key  message` with the offending line and, for a key close to a valid one, the close key: "admin/devhost.toml:3:1  services.admin.hostname  unknown setting; did you mean host?", every problem of every file at once, grouped by file relative to the root manifest, then "Nothing started. Fix the manifest and run devhost start again" (`FAIL-2`, `MENU-4`, `WORD-7`, `WORD-8`). A hostname or port clash names every clash with the owning stack's name, checkout and the command that stops it; an unknown name separates services from groups and suggests the closest (`FAIL-2`). A missing `cwd` reads "devhost.toml:12:7  services.api.cwd  folder api does not exist in ~/newapp", never a Git error (`FAIL-2`, `REV-11`). A health check that fails names what the probe saw: "api answers on 127.0.0.1:22250, but GET /healthz returned 404 Not Found · 6 tries · 30 s of 30 s. Set services.api.health.http to a path that answers 2xx, or remove it to use a TCP check" (`FAIL-3`, `WORD-7`). A manifest that starts but routes nothing the way it reads prints a warning with its location and keeps starting, the ready line repeats the count ("· 1 warning: devhost.toml:9"), and `devhost status` lists it: "devhost.toml:9:8  services.api.path  "/api" matches only the exact path /api; write "/api/*" to route everything under it", and a `path` without `host`, which routes nothing (journey-new-project-01, a recommended default the product owner settles, Backend 15). So does `watch` on an external service, which devhost ignores (`ACT-8`; services-panel's conflict c4). Under `AGENT=1` every problem joins one `devhost: ERR:` line, "devhost: ERR: devhost.toml was not accepted: /work/acme/admin/devhost.toml:3:1 services.admin.hostname: unknown setting, did you mean host?; …" (`FB-11`, `WORD-9`). No manifest at all reads "No devhost.toml in ~/newapp or any folder above it", then the command that creates one on its own line, `devhost init`, and the Quickstart's URL (stack-run-stop-12, Backend 16, `STATE-2`).
3. **Start detached (`devhost start --detach`, one write).** Within a second the terminal names the stack, "Starting Acme Shop in the background from main ~/acme · 6 services", then keeps one status line updated on a terminal, "Starting Acme Shop · 3 of 6 running · waiting for api · health check 2 s of 30 s · 7 s", or prints one line per change when output is not a terminal (`FB-10`, `STATE-1`, `ACT-4`). It ends with the same labelled URLs and ready line as the foreground, then "Log: devhost logs", and "Stops after 30 min without requests (idleTimeout)" when the stack has an idle timeout (`FB-10`, `SURF-13`, `ACT-10`). As today, a failure before readiness stops what it started and prints the log tail, now with the cause once, by service, with `FAIL-3`'s evidence (owner rule; `FAIL-1`). Ctrl-C while it waits cancels the start: "Cancelled the start of Acme Shop: stopped web and api, which had started", with no error tag (`FAIL-5`, `KEY-14`, `WORD-7`). A second start of the same manifest keeps waiting for an unsettled first one, as today (`HOLD-3`).
4. **Start services into a running stack (`devhost start [--detach] <names>`, one write).** When the manifest's stack already runs, devhost expands the requested names (groups, `dependsOn`, `alwaysStart`) and compares them with what runs. Services the run left out start into the running stack exactly as the Services panel's **Start** does, with what they depend on and without touching running services, and the command prints what it started: "Started admin in Acme Shop · https://admin.shop.localhost/ · 1.2 s" (`SEL-7`, `O6`, `FB-3`, `CC-7`). When everything asked for already runs, it says so and prints the requested services' URLs only: "Already running in Acme Shop: web, api · https://shop.localhost/" (`FB-10`). The start queues behind a per-service operation and is refused while the stack starts, stops or runs a stack-wide operation, naming it ("Not started: Restart Stack is running · 3 of 6 started") and exiting 1 (`HOLD-3`, `HOLD-1`, `CC-8`).
5. **Check what runs (`devhost status [--json] [--wait]`, read only).** One command answers whether the stack's services are up, from the published service state and the operation record that every surface reads, never a guess of the CLI's own (`FB-11`, `ACT-1`, `ACT-2`, `CC-23`). Human output: a header line with the stack, its checkout, its PID, foreground or detached, its stack state and its summary, "Acme Shop · main ~/acme · PID 84244 · detached · failed · 4 of 6 running · 1 exited · 1 not started · as of 14:02:31", the snapshot's time saying that the answer does not update (`ACT-6`, `ACT-12`, `WORD-5`); one line per service with its state word, its cause and since when, and its URL ("api  exited with code 1 at 14:01 · devhost service restart api", "admin  not started · left out of this run · devhost service start admin", "docs  running · changed: docs/astro.config.mjs"), an external service's reachability with its check and its time and "runs outside devhost", never a restart (`ACT-2`, `ACT-8`, `ACT-9`, `WORD-6`, `MENU-5`); a starting service's health check with its time ("starting · health check 4 s of 60 s", `ACT-4`); a transition as the touched services' step ("restarting · Restart Stack", `ACT-3`); a rejected manifest file as "devhost.toml line 12 is not applied: …", with the stack still running the accepted manifest (`HOLD-6`); a blocked repository once, as its sentence ("The checkout ~/acme/.worktrees/fix-nav was deleted; its services still run from it"), instead of its URLs (`HOLD-4`); then "Last operation: Restarted docs · 1.9 s · 14:00 · from the toolbar", "Log: devhost logs" and the stack directory's URL (`FB-3`, `FB-7`, `SURF-15`). It exits 0 when every started service runs and 3 naming each one that does not ("1 started service is not running: api"); 1 stays a failure of the command itself (`FB-11`). `--wait` first waits for a running operation to end, printing its progress line (`FB-1`, `FB-11`). `--json` prints the same facts with `WORD-6`'s identifiers (`not-started`, `not-reachable`), absolute paths and ISO times (`WORD-6`, `WORD-8`, `WORD-9`). In a folder with no running stack it says "Acme Shop is not running" and, within `O15`'s time, when and why it stopped and the command that starts it (`ACT-10`, `STATE-2`). When the stack's devhost process runs but its control server does not answer, it prints what the stack's record holds marked with its age, says once "Acme Shop's devhost process (PID 84244) does not answer; its state is unknown, last seen 14:02", never an empty list or "not running", and exits 1 (`STATE-4`, `STATE-3`, `ACT-5`). Every state is a word, never only a color (`ACT-13`). Leftovers of a killed run are named here too (step 13).
6. **Find stacks (`devhost stack list`, `devhost stack find <query>`, read only).** `stack find` resolves a query that names an existing folder, `.` and `..` included, to the stack of the nearest `devhost.toml` from that folder upward, as `devhost stop` does, and keeps substring matching of hostnames, names and manifest paths for other words (`SEL-6`, `SEL-10`, `CC-34`). Human output on a terminal shows one line per stack, its name, its checkout label, its PID, foreground or detached, and its summary ("Acme Shop  fix-nav ~/acme/.worktrees/fix-nav  PID 85102 · foreground · 6 of 6 running"), so two stacks named Acme Shop read apart, then the stack directory's URL (`SEL-4`, `WORD-1`, `ACT-6`, `SURF-15`); a stack with leftovers of a killed run is listed with them (step 13). Piped, or under `AGENT=1`, both keep today's documented picker format, `<PID><TAB><manifest path>`, byte for byte, because scripts and shell completion read it, and the state lives in `devhost status` (this proposal's reading of `SURF-15` against `status-15`, recorded for the reference). No match says what was searched: "No stack matches "shopp" · devhost stack list lists them all" (`STATE-2`, `SEL-10`).
7. **Act on one service (`devhost service start|stop|restart <service|group>…`, one write per service).** The terminal becomes one of each service's stated entry points, beside its row in the Services panel, the crash view and the control API (`MENU-1`). These reach the running stack through its control server on the loopback port the state directory records, so they run only on this machine (`HOLD-7`), the way the toolbar does, foreground or detached, send an `operationId` and take their outcome from the operation record, so a lost response never sends the write again (`SEL-7`, `MENU-6`, `REV-12`, `ACT-1`, `CC-11`, `CC-37`). Each waits for health checks, printing the progress line, then one outcome per target: "Restarted api · 2.6 s", "Started admin and mail (admin depends on mail) · 3.1 s", "Stopped worker · it reads not started, stopped by you"; a failure prints the target, the exit with its time, its last output lines and what devhost ran, and exits 1 (`FB-3`, `FAIL-1`, `FAIL-3`, `WORD-4`). A restart of another service queues behind a running one, "worker queued behind Restart api", and runs after it; a restart of a service already restarting, or any of them while the stack starts, stops or runs a stack-wide operation, is refused with one sentence naming that operation, its progress and the way out, "Not restarted: Restart Stack is running · 3 of 6 started. Run it again when Restart Stack ends", and exits 1 (`HOLD-3`, `HOLD-1`, `SEL-7`, `CC-8`). A rejected manifest blocks nothing: "Restarted api from the accepted manifest · devhost.toml line 12 is not applied · 2.6 s" (`HOLD-6`). An external service is refused with why: "search runs outside devhost; devhost checks it but cannot restart it" (`MENU-3`, `ACT-9`). The crash line a running stack prints names the command instead of "waiting for a restart": "api exited with code 1 at 14:01" and, on its own line, `devhost service restart api` (`MENU-6`, `MENU-5`, `FAIL-5`). `devhost service restart --all` is Restart Stack's terminal command: it prints the statement Restart Stack shows in the Services panel, "Restarting all 6 services of Acme Shop with new automatic ports · took 14 s last time", then runs on that one command without a question, reports per-service progress and one outcome, and rolls back service by service on failure, "Restored the services as they ran before Restart Stack: 5 of 6 running · api still fails" (`MENU-6`, `REV-2`, `REV-7`, `UNDO-1`, `FAIL-1`, `BAR-2`; an exception to `REV-2`'s second step and services-panel's conflict c5, both recorded for the reference). `devhost reload [--dry-run] [--stdin <file>]` applies, or checks, the manifest on disk against the running stack and prints what manifest-hot-reload's reload reports (`FB-11`, `REV-10`, `CC-23`).
8. **Read the stack's output (`devhost logs [-f] [service…]`, read only).** Every stack, foreground or detached, appends to one log per manifest, whose name no longer changes when the stack is replaced; each run starts with a header naming the command, the PID, the checkout and the time; lines carry their time; the file holds one format, which `devhost logs` renders for people, and failures carry `ERR:` as warnings carry `WARN:` (`FB-7`, `FB-11`, `CC-21`, `CC-23`). `-f` follows the log across replacements; service names filter it; `devhost logs --path` prints the file's path for tools. Every operation on the stack, from any origin, is one outcome line there with its time and origin ("· from the toolbar", "· from an agent", "· after devhost.toml changed on disk"), so outcomes the toolbar closed stay readable (`FB-7`, `ACT-1`).
9. **Stop a stack (`devhost stop`, one write).** The command resolves the stack as today (any path to its manifest, `--manifest`) and first names it, its checkout and what the stop ends: "Stopping Acme Shop (main ~/acme, PID 84244) · 6 services · closes 1 conversation: "Fix the nav" (Claude Code, working)" (`SEL-6`, `SEL-4`, `FB-4`, `WORD-1`). It never asks: it acts on the one stack it resolved (`REV-7`, `REV-1`). Before it signals, it records why beside the stack's record ("stopped from a terminal"), so the stack's own terminal, its open pages and its hostnames can say so (`ACT-10`, `HOLD-2`). While services stop, one status line names those still stopping, the time before devhost forces them and the key: "Stopping Acme Shop · 4 of 6 stopped · mail and worker still stopping · forced in 6 s · Ctrl-C forces them now" (`FB-10`, `KEY-14`, `ACT-3`). The command waits as long as the stack's own shutdown needs, up to `O30`'s allowance (a minute plus 20 s per service: 3 min for 6), and never kills the stack's devhost process while it still stops services; Ctrl-C while it waits, or a second `devhost stop` of the same stack, forces the services still stopping at once, signalling only the verified process trees of the stack's services (`ACT-11`, `KEY-14`, `O30`, `CC-35`). Success is certified: "Stopped Acme Shop · 6 services · 6.1 s · closed "Fix the nav" (Claude Code, was working)", only once no process, route or port claim of the stack remains, then "Start it again in ~/acme with:" and `devhost start` on its own line (`FB-5`, `ACT-11`, `FB-4`, `UNDO-5`, `WORD-4`). A service devhost had to force reads "Force-stopped worker after 10 s: it ignored SIGTERM", never stopped (`FAIL-5`, `WORD-7`). If anything survives the allowance, the outcome names each survivor with its service, PID and port, "Acme Shop is not fully stopped: worker (PID 8820, port 22314) still runs", and exits 1 (`FAIL-1`, `ACT-11`). With nothing running, it says "Acme Shop is not running", then, after the result, names other stacks of the repository with the `--worktrees` command (`STATE-2`). `devhost stop` during a start cancels that start and says so in both terminals: "Cancelled the start of Acme Shop: 2 of 6 had started; stopped them" (`REV-12`, `FAIL-5`). Progress and outcome go to the stream `reference/output.md` names for them (`WORD-9`).
   - Defaults: the stack of the nearest `devhost.toml`; conversations close with the stack and stay listed, resumable after the next start, from agent-chat's record (`UNDO-4`, `O23`; agent-chat's conflict c5 words them "closed" with this cause).
   - Keys: Ctrl-C while it waits forces the rest (`KEY-14`).
10. **Stop a stack in its own terminal (Ctrl-C, one write).** The first Ctrl-C prints "Stopping Acme Shop · 6 services", then the status line of step 9 with "Ctrl-C again forces them"; services that had already exited are not stopped again and read "api had already exited with code 1 at 14:01" (`KEY-14`, `FB-10`, `FAIL-5`). The second Ctrl-C forces every service still stopping within a second, still releases the stack's routes, port claims and record, and prints "Force-stopped mail and worker after 4 s" and the outcome (`KEY-14`, `FAIL-5`, `ACT-11`). The stack's end line names the reason and the time ("Acme Shop stopped at 14:10: Ctrl-C in this terminal"), as every end does (step 12).
11. **Stop every stack of the repository (`devhost stop --worktrees`, one write per stack).** The command first prints its set, every stack whose root manifest is in this repository with its checkout label, PID, foreground or detached, and the conversations each would close, then acts (`SEL-6`, `SEL-4`, `REV-7`, `FB-4`):

    ```
    3 stacks of the acme repository run:
      Acme Shop  main ~/acme                         PID 84244 · detached
      Acme Shop  fix-nav ~/acme/.worktrees/fix-nav   PID 85102 · foreground · Claude Code working: "Fix the nav"
      Acme Shop  Detached 3f9c2a1 ~/review/acme      PID 85390 · detached
    ```

    Only when the set would end an agent's turn that works or waits for the person, the work `REV-3` protects, does it ask, naming those turns; a conversation still running in a stack whose chat was turned off counts the same, because turning chat off never ends it (`HOLD-5`). It asks when standard input and output are both a terminal and `CI` is unset: "Stop 3 stacks and end Claude Code's working turn in fix-nav? [y/N]"; an empty answer, end of input or anything but y or yes stops nothing (`REV-7`, `REV-4`, `O33`, `KEY-14`). Without a terminal, or under `AGENT=1`, it refuses with one line and exits 1: "devhost: ERR: stop --worktrees would end Claude Code's working turn in fix-nav (/work/acme/.worktrees/fix-nav); ask the person to run it in a terminal or to pass --yes", the same form `REV-8` gives the trust commands (`REV-7`, `REV-8`, `WORD-9`). `--yes` acts without the question and is the one flag that skips a devhost question; no command of this flow takes `--force` for it; `--dry-run` prints the set and exits 0 without acting (`REV-7`, `CC-12`). Each stack then stops as in step 9, with its own progress line. A stack that cannot be stopped never ends the run: the command attempts every stack of the set and ends with one line per stack, "Stopped Acme Shop (main ~/acme) · 4.1 s", "Acme Shop (Detached 3f9c2a1 ~/review/acme) was not stopped: its devhost process (PID 85390) belongs to another user", and exits 1 naming each stack that still runs (`FAIL-1`). A stack whose folder is gone is classified from the repository's worktree list, which still lists a removed worktree, and never by running Git in its missing folder; a stack of another repository is never touched and never blocks this one (`FAIL-2`, `REV-11`).
12. **A stack's end is stated (one end line; its hostnames, read only).** However a stack ends, its terminal and its log print one line naming the stack, the reason and the time: "Acme Shop stopped at 02:14 after 30 min without requests (idleTimeout)", "Acme Shop stopped at 14:10: devhost stop from another terminal", "… stopped from the Worktrees panel of Blog", "… replaced by devhost stack replace" (step 14) or "… every service exited" (`ACT-10`, `CC-27`). Open pages learn the reason before their status stream closes, so the toolbar's lost-connection notice reads "Acme Shop stopped. Start it with devhost start in ~/acme" (`HOLD-2`, `ACT-5`; notices-and-feedback words the notice). For `O15`'s time, 24 hours or until another stack claims the hostname or the shared Caddy stops, each of the stack's hostnames answers with the stopped-stack page instead of the generic 404: the heading "Acme Shop stopped", the sentence "Stopped at 02:14 after 30 min without requests (idleTimeout)", "Start it again in ~/acme with" and `devhost start` with **Copy**, and **All Stacks on This Machine**, which lists it as recently stopped (`ACT-10`, `STATE-2`, `STATE-3`, `UNDO-5`, `O15`, `CC-27`). The page is a full page that works without the toolbar, drawn with the shared status-page components and words in the status pages' stylesheet (`SURF-14`, `WORD-6`); it starts nothing and never opens a browser, because only a terminal starts a stack (owner rule; `O10`). No stack runs behind it, so it carries no toolbar: no panel, popover, question, paused state or key listener of devhost's appears on it (`SURF-2`, `SURF-11`, `KEY-5`). It fits every acceptance viewport, 1600x1000, 1280x800 and 900x900 in both themes and 1280x800 at 200% zoom, and reflows at 320 CSS pixels, narrower windows following `O8` (`SURF-9`, `O8`); its state is told by its heading and words, never only by color (`ACT-13`). Its keys are the document's own: Tab moves through the command's **Copy** and **All Stacks on This Machine** in reading order after the heading and the sentence, Enter and Space activate, Escape has no layer to close, and devhost adds no shortcut and no key hint, so no binding definition applies (`KEY-1`, `KEY-6`, `KEY-8`, `KEY-9`, `KEY-13`, `BAR-4`). **Copy** keeps focus after copying and the page's one polite region says "Copied devhost start" once (`KEY-11`, `FB-9`); the heading comes before any status code in reading order (`FB-9`). While the shared Caddy is stopped, every running stack's terminal prints one line that it lost its proxy and one when its routes answer again: "Acme Shop lost its proxy at 14:10 (devhost caddy stop); its services keep running" and "Acme Shop's routes answer again at 14:12" (`ACT-10`).
13. **Leftovers of a killed stack are found, named and stopped (`devhost start`, `devhost stop`, `devhost stack list`, `devhost status`).** When a stack's devhost process died first (kill -9, a closed terminal, a crash), its record keeps each service's process group, start identity, ports and hostnames, and the next devhost command that reads it finds the services still running (`ACT-11`). `devhost stack list` and `devhost status` name them: "Acme Shop is not running, but 2 services of its killed run still do: api (PID 8812, port 22310), worker (PID 8820)". Branches and edge states:

- **Output that is not a terminal.** The status lines of steps 1, 3, 9 and 14 print one line per change instead of rewriting one line; questions never appear, and step 11's refusal stands in for them (`FB-10`, `REV-7`).
- **Agent output (`AGENT=1`).** Every line of this flow has its agent form with the same facts and exit codes; every error is one `devhost: ERR:` line holding every issue, and where only a person can act it tells the agent to ask the person (`WORD-9`, `FB-11`, `CC-30`). Chat agents devhost starts run with `AGENT=1` and `DEVHOST_CHAT_SESSION`, so their commands are reported as theirs (agent-chat's slice, `agent-cli-journey-06`).
- **A script polls a service while it starts.** A request that is not a page load gets devhost's short `503` with `Retry-After` and a body naming the service and its phase, never Caddy's empty `502` or a 750 KB HTML page; startup-and-recovery builds it (`SURF-16`, `FB-11`, `agent-cli-journey-04`).
- **Another operation in progress.** Steps 4 and 7 queue behind a per-service operation and refuse a clash with a stack-wide one, naming it and its progress; `devhost stop` cancels a start (step 9) and waits for nothing else (`HOLD-3`, `REV-12`).
- **A lost response.** `devhost service` and `devhost reload` read their outcome from the operation record by the `operationId` they sent; a command interrupted while it waits can be followed with `devhost status --wait`, and nothing is sent twice (`REV-12`, `ACT-1`).
- **A rejected manifest or devhost config file.** Nothing is blocked: commands run the accepted manifest and say which line is not applied (`HOLD-6`).
- **A blocked repository.** `devhost status` and the running stack's terminal name it once with its sentence and remedy; `devhost service restart` of its services is refused with that sentence (`HOLD-4`, `HOLD-1`).
- **Chat that cannot take a message, saves from another machine, the page's own modal dialog, the toolbar's keys.** None blocks or changes a terminal command of this flow (`HOLD-5`, `HOLD-7`, `SURF-11`, `KEY-5`); the one browser surface this flow draws, the stopped-stack page, is a full page with the document's standard keys (`KEY-1`).
- **A daemon's lifecycle stop command is slow.** Its deadline (services-panel's recommended 20 s, conflict c2) fits inside `O30`'s 20 s per service, so step 9's allowance covers it; the progress line reads "mail · stop command 12 s" (`FAIL-3`, `O30`).
- **Monorepo scale.** At first start every URL prints once; afterwards a one-service start prints its own URL, and lists of more than about a screen collapse to a count and the command that lists them (`WORD-5`, `FB-10`).
- **Who can reach a stack's control server from the network.** That exposure belongs to `network-exposure-01`, `proxy-settings-01` and `serve-folder-04`, which the product owner handles outside this redesign; the `devhost service` commands use the loopback port the state directory records (section 1 of the reference).

## Backend and contract changes

**Backend** (the CLI in `apps/devhost/internal/cli` and `apps/devhost/internal/app`, terminal output in `apps/devhost/internal/cliout`, the services runtime in `apps/devhost/internal/services`, stack records in `apps/devhost/internal/caddy`, preserving manifest validation and claims before any service runs, the recovery contract, a detached start's stop on failure before readiness, signals only to verified processes, the two output contracts, and devhost never opening a browser):

1. **One stop routine.** `devhost stop`, `devhost stack replace`, `devhost stop --worktrees` and the Worktrees panel's **Stop Stack** (worktree-switch's caller) share one routine: it records the stop's reason beside the stack's record before it signals; the stack's shutdown sends SIGTERM to every service in reverse dependency order and waits for them concurrently, 10 s each before SIGKILL, publishing `stopping` with the services still stopping and the time left; a second signal or a second stop request forces the rest at once, signalling only verified process trees; the caller waits up to `O30`'s allowance (a minute plus 20 s per service), never SIGKILLs the stack's devhost process while it still stops services, and certifies the end only when no process, route or port claim remains, else returns each survivor (service, PID, port). Serves `interrupted-operations-03`, `stack-run-stop-06`, `stack-run-stop-13`, and builds on the `interrupted-operations-01` stopgap and the `stack-scale-01` patch. Required. Contract: `CC-35`, `CC-22`.
2. **The stop reason and the stopped-stack record.** Every stop writes its reason (a terminal, another stack's page with its name, the idle timeout with its duration, a replacement, killed, every service gone) and its time beside the stack's record; the stopping process, or the next devhost command that finds a killed stack's owner dead, writes a stopped-stack record per manifest in the state directory (name, hostnames, reason, time, folder, start command), and under the route mutation lock re-renders the unmatched-hostname page and the stack directory's `stacks.html` that Caddy serves while no stack runs, each embedding the stop times so entries older than `O15`'s 24 hours are hidden; the status stream sends the reason before it closes. Serves `stack-run-stop-11`. Required. Contract: `CC-27`.
3. **Leftover detection.** The stack record keeps each service's process group, the start identity of its root process (the identity the `process-containment-01` stopgap records), its ports and hostnames; `devhost start`, `devhost stop`, `devhost stack list` and `devhost status` find services of a killed run whose devhost process is gone, name them, and `devhost start` refuses before launching a service whose port or hostname a leftover holds; `devhost stop` signals only leftovers whose identity matches. Serves `interrupted-operations-02`. Required.
4. **Multi-stack sets.** `stop --worktrees` and `stack replace --all` build their set first and print it (name, checkout label, PID, foreground or detached, the conversations each would close, read from each stack's control server, with the turns that work or wait); `--dry-run` prints it and exits 0; the question, its refusal under `AGENT=1` or without a terminal, and `--yes`, as `REV-7` says; every member is attempted and reported, and the exit is non-zero naming each failure; `stop --worktrees` classifies stacks from `git worktree list --porcelain` of the named manifest's checkout and never runs Git in a missing folder. Serves `stack-run-stop-07`, `stack-run-stop-14`, `stack-run-stop-16`, `chat-conversations-03`. Required. Contract: `CC-12`.
5. **Replacement.** `devhost stack replace` (with `restart` as its alias) checks each stack's PID, start identity and root manifest immediately before its signal instead of its registration time, waits with step 9's routine, relaunches with the stack's current service selection from its control server, appends to the same per-manifest log, tells a foreground stack who replaced it (a control-server request before the signal) so it prints the handoff and exits 0, reconnects open pages, and lists serve sessions without replacing them. Serves `stack-run-stop-02`, `stack-run-stop-13`, `stack-run-stop-15`. Required. Contract: `CC-24`, `CC-31`, `CC-36`, `CC-35`.
6. **One log per manifest.** Every stack, foreground included, appends to its per-manifest log; each run writes a header (command, PID, checkout, time); lines carry their time and one format whatever `AGENT` the start ran with; failures carry `ERR:`; replacements keep the file; `devhost logs [-f] [--path] [service…]` renders and follows it. Serves `stack-run-stop-05`, `agent-cli-journey-05`. Required. Contract: `CC-21`, `CC-23`.
7. **`devhost status`.** Reads the published service state and the operation record that services-panel's redesign defines (its Backend 1 and 2) through the stack's control server, adds the stack's checkout, PID, how it runs, warnings and leftovers, prints human and JSON forms and exits 0, 3 or 1; `--wait` waits for the running operation's end. Serves `agent-cli-journey-01`. Required. Contract: `CC-23`.
8. **The `devhost service` commands.** `devhost service start|stop|restart <service|group>…` call `start-service`, `stop-service` and `restart-service` with an `operationId` (services-panel's Backend 2, 3 and 7), print progress and one outcome per target, and exit 1 on any failure; `devhost start <names>` against a running stack uses `start-service`. Serves `agent-cli-journey-03`, `stack-run-stop-01`. Required. Contract: `CC-11`, `CC-37`, `CC-7`.
9. **[discuss]: `devhost service restart --all`.** Restart Stack's terminal command, calling `restart-stack` with an `operationId`, printing `REV-2`'s statement first and running without a question; the reference names no terminal command for Restart Stack (services-panel's exception to `MENU-6`), and `CC-11` names services or groups only, so the reference's author must add `--all` to `CC-11` or record the exception. Serves `MENU-6`. Recommended.
10. **`devhost reload`.** `devhost reload [--dry-run] [--stdin <file>]` calls the reload route and `config/validate`, whose plan (each restart with its reason, starts, stops, moved URLs) manifest-hot-reload's redesign builds. Required. Contract: `CC-23`.
11. **Terminal lines from facts.** `apps/devhost/internal/cliout` builds every line of this flow from the operation record and the published state through one Go words module (labels, state words, outcome grammar, counts, formats), in both outputs: progress lines rewritten on a terminal and one line per change otherwise, the ready line, labelled URLs as routes publish, one outcome line per operation from any origin, devhost's own stops marked as steps, never breaking a URL, path or command across lines, OSC 8 links, commands on their own line, one `devhost: ERR:` line per agent-mode error. Serves `stack-run-stop-03`, `stack-run-stop-04`, `stack-run-stop-10`, `stack-scale-07`, `worktree-switch-04`, `agent-cli-journey-05`. Required. Contract: `CC-22`, `CC-30`.
12. **Structured manifest errors.** `apps/devhost/internal/manifest` keeps each setting's source file and line through the include merge and returns every problem as one structured error (file, line, column, key, message, the offending line, a close key), shared with manifest-hot-reload's rejections; `cwd` existence is checked before the checkout lookup. Serves `stack-run-stop-09`, `manifest-hot-reload-03`, `journey-new-project-04`. Required.
13. **The probe's last result.** The health wait keeps the last HTTP status, or the connection error, and its count, published with the starting state and printed in the waiting line and the failure. Serves `journey-new-project-03`. Required.
14. **Exit, daemon and proxy lines.** Each exit published with its code or signal, status, time and sender (services-panel's Backend 9) prints in the stack's terminal and log; a daemon that fails its health check for three polls, and recovers, prints one line each, with its status command's answer; each stack is told when the shared Caddy stops and when its routes answer again, and prints one line each. Serves `interrupted-operations-04`, `manifest-hot-reload-2-02`, `notices-and-feedback-04`. Required. Contract: `CC-24`.
15. **[discuss]: Route warnings.** Validation warns, naming file, line, column and key, for a `path` without a trailing `/*` ("matches only the exact path"), for a `path` without `host` (which routes nothing) and for `watch` on an external service (services-panel's conflict c4), on start and on each hot reload, never refusing a manifest that loads today; the ready line counts warnings and `devhost status` lists them. 16. **[discuss]: `devhost init` and the embedded skill.** `devhost init` writes a commented `devhost.toml` with one service guessed from `package.json`, `go.mod` or a `Procfile`, and refuses to overwrite; the no-manifest message offers it; `devhost skill` prints the skill embedded in the binary for its version, and `devhost skill --install` keeps today's install text. ## Recommended priority

**P1, with the `interrupted-operations-01` and `process-containment-01` stopgaps shipped first.** The realistic trigger is ordinary: a stack whose devhost process dies first (a closed terminal, `kill -9`, or `devhost stop`'s 15 s SIGKILL today) leaves its services answering its hostnames unseen, and the next `devhost start` reports ready while the old processes answer, so people debug code that is not running (`interrupted-operations-02`); a manifest that mounts the API with `path = "/api"` routes every API call to the static site while every surface reads healthy (`journey-new-project-01`); and an agent cannot ask devhost whether its services are up, so it guesses from a PID and a path (`agent-cli-journey-01`). Nothing here loses files, so the cost is time and wrong conclusions, except where a stop reaches other work: `stop --worktrees` and `stack replace --all` close other checkouts' conversations and stacks without showing them (`stack-run-stop-07`), and a stop signals processes it never verified, which the P0 stopgap fixes first. The terminal is where every stack starts and stops and where agents work, so this flow is used daily, as often as the Services panel. Ship first the slice with no backend dependency: the words and lines of `cliout` (the stop's and start's wording, the ready line from today's readiness events, wrapping that never splits a token, one `ERR:` line), `stack find`'s folder rule, structured manifest errors with the `cwd` check and the probe's last status, and the route warnings. Then the safety slice, built on the two stopgaps: the one stop routine with `O30`'s allowance, the second Ctrl-C, survivors named, leftover detection, `stop --worktrees` attempting every stack and classifying missing folders, and the replacement's wait, identity check and foreground handoff. Then the multi-stack set with `--dry-run`, `--yes` and the question, in one release with the documented upgrade step's `--yes`, so no post-upgrade script meets an unexpected question. Then the agent commands, which read services-panel's published state and operation record: `devhost status`, `devhost service`, `devhost reload`, and `devhost logs` with every stack writing its log; the crash line names `devhost service restart` only in the release that ships the command. Last, the stopped-stack record and page with the stack directory's recently stopped list. Seams, with no blocker in either direction beyond its dependencies on the foundations services-panel and notices-and-feedback, which ship first or with the slice that needs them: services-panel provides the published service state, the operation record, the start, stop and restart routes and exit records that `devhost status` and `devhost service` read, and this flow builds those commands for it; notices-and-feedback's lost-connection notice words the stop reason this flow sends; startup-and-recovery builds the `503` for scripts and shares the status-page components the stopped-stack page uses; stack-directory lists recently stopped stacks from this flow's record; agent-chat keeps the conversation records that `devhost stop` names and resumes, worded "closed" (its conflict c5); worktree-switch's **Stop Stack** calls this flow's stop routine and its switch lines name checkouts by label; manifest-hot-reload owns the reload plan `devhost reload` prints and the rejection words; first-run-setup owns `devhost caddy stop`'s set; serve-folder's sessions appear in `--all`'s set; proxy-settings words the devhost config file save summary.
