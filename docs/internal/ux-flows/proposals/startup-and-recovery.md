# Startup pages, crash recovery and app error pages: proposed experience

Diagrams: [current](../startup-and-recovery-current.html), [proposed](../startup-and-recovery-proposed.html). [Wireframe](../wireframes/startup-and-recovery.html).

Status: design proposal, not implemented behavior. The [shared UX pattern reference](../patterns.md) wins where this proposal disagrees with it.

Source revision: alexgorbatchev/devhost `190a8bb53e8cd903d2db0a92cb0886f29671607f` (Rust `main`). Features: REC-01, REC-02, REC-03, REC-04, REC-05, REC-08, LOG-02. Redesign ticket: tracked privately.

Product rule: `stacks/recovery.md` states the recovery contract: "a service that crashes, times out, or returns errors does not take the stack down with it. Its hostname shows what went wrong, with recent logs and a restart button, and the other services keep running." The owner's rules add that devhost never opens a browser, that external services (`managed = false`) show status only, that a detached start stopping on a failure before readiness is intended, that every manifest setting applies through hot reload, and that using devhost's pages from a browser in another environment is a primary use case, so no action on these pages is held to this machine (`HOLD-8`). So a failed service leaving the rest running, a hostname that answers with devhost's own page while its service is not running, an external service's page offering no **Restart**, and a page that waits for the person to open it are intended; none of them is a defect. The gap is around them: the toolbar's crash view covers devhost's own failure page and is a dead end that only reruns the failing command; the cause and the lines that explain it get lost; an app's own error (a framework's build overlay, an API's 404) is replaced by a page that leads with a restart that cannot fix it and re-requests the broken URL every second; a failed Restart Stack closes the view without a word; and scripts get an empty `502`. Replacing the app's own 404 and 5xx documents is documented today; the product owner decided to stop it (`O5`, decided 2026-11-18; `CC-4`).

## Target experience

The person opens a service's URL. While the service is not running, its hostname answers with one devhost status page per state, and the page says which state in its heading: "api is starting" shows the health check it waits on, "http://127.0.0.1:4001/ · 4 s of 60 s", what started this attempt and only this attempt's output, then reloads the tab into the app once the service is ready. When the start fails, the same tab becomes the recovery page, "api could not start", with one cause sentence, the evidence devhost observed (the exit code or signal and who sent it, the service's own last lines frozen at the exit and opened at the end, the probe it failed, a port another program holds, and what devhost ran: the command, its folder and the manifest file and line), the action that can fix the cause first, and **Edit** beside **Restart api**. No toolbar view opens over that page. Pressing **Restart api** keeps focus on the button while the page shows the restart's steps in place; success reloads the tab into the app, where the outcome "Restarted api · 2.6 s" shows once; a retry that fails the same way updates the one report, "api exited with code 1 · 2 times, last at 14:05", and **Edit** then leads, because rerunning the same command cannot help. With the app already open, an exit of the page's service or of a service it depends on opens the crash view over the app: the same shared recovery view, focused on its heading and described by the cause, with **Minimize** (and Escape) folding it into a crash notice so the page, Config, Services and Chat stay usable; it opens minimized while the person types or chat is in use, and it closes by itself when the service runs again, saying so once. **Restart Stack** runs there on one press with its reach named beside it, shows each service's step in the view, and ends in the view with one outcome, "Restart Stack: 5 of 6 running · api exited with code 1 before its health check", never closing silently. When the app itself answered (a framework's build error, an API's own 404), the page shows the app's own document, the framework's overlay with its file, line and code frame included, and a devhost notice naming who answered, "web answered 500 for GET / · main ~/acme", with **Retry** and a secondary **Restart web**; devhost re-requests that URL only when something changed (a restart, a recovery, a watched file saved), never on a timer. Scripts polling a starting or crashed service get a short `503` with `Retry-After` naming the service and its phase, never an empty `502`. Restarts cannot be taken back, so there is no Undo: devhost's own rollback restores what ran before a failed Restart Stack, service by service, and drafts and page context survive every reload this flow causes. Benchmarks: Vite and Next.js keep the server's own error response and draw their overlay over the app's page with the file, line and code frame, and the Next.js dev overlay collapses into a badge that reopens it; Laravel Herd and Valet pass an app's own error pages through; Docker Desktop shows "Exited (1)" with the container's own logs and a Start button, and keeps state and health apart ("Up 3 seconds (health: starting)"); Tilt leads a resource's page with the failing step, its command and its log scrolled to the end, and offers its trigger only for that resource; VS Code tasks print the command they run ("Executing task: …") before its output; Kubernetes keeps a pod Pending with a reason and reports ready replicas of the total; `kubectl wait` and `docker compose up --wait` give scripts a waitable state instead of an empty error. Competitor behavior is evidence here, never a requirement.

## Target steps

Today: 6 steps on the main path, two of them dead ends: open the URL, wait on a starting page that shows no progress and the previous run's output, meet a failure page with the toolbar's crash view drawn over it, search a log box that may have lost the cause, press **Restart** (focus falls to the page body), and retry the same failing command blind. Proposed: 4 steps: open the URL, watch the start's progress, read the cause on the recovery page and press its lead action in place, land in the app with the outcome. The crash path today is 3 steps that end in the same blind retry or in a silent stopped stack; proposed it is 3 steps that end in a stated outcome: the crash view with its cause and lead action, the action with its progress in the view, the outcome in the view or, after recovery, in a notice.

1. **Open a service URL (a page load, read only).** The person opens a hostname, alias or path route in a tab; devhost never opens one for them. Caddy sends page loads to the service's document injection server, which answers from the published service state (`ACT-2`, `CC-25`): while the service is not running it answers with one devhost status page per state, led by `MENU-5`'s action for its cause: starting (step 2), exited or failed (step 3), blocked by its worktree, needing setup, not started, an external service that is not reachable, or the stack stopped (Branches), while a hostname with no route keeps stack-directory's page (Branches, `O63`); when the service runs and the app answers, the app's own response passes through, its own 404 and 5xx documents included (step 7, `SURF-16`, `O5`, `CC-4`). devhost's file server answers a missing file with its own 404 inside the file browser, which this flow's replacement rule leaves alone (`MENU-5`, `SURF-16`; serve-folder draws that page). A request that is not a page load (an API call, a fetch, an asset, `curl`) gets the app's own response while the app answers; while the service is not running, Caddy hands it to devhost, which answers `503` with `Retry-After` and a short body naming the service and its phase, never Caddy's empty `502` (`SURF-16`, `FB-11`, `CC-4`): with `Accept: application/json`, `{"service":"api","stack":"Acme Shop","phase":"starting","retryAfter":1}`; otherwise one line, "devhost: api is starting in Acme Shop; retry in 1 s". Every status page is one shared recovery view rendered in the status pages' stylesheet and, for the crash view, in the devtools Shadow DOM stylesheet, with the same words, actions and log rendering on both (`SURF-14`); it keeps working without the toolbar and, without JavaScript, still shows the state, the cause, the service's details and its logs (Kept). While this machine's certificate authority is not trusted, first-run-setup's shared trust line comes first on every status page, rendered from its one component (`SURF-14`); then the heading names the service and the state, and comes before any status code in reading order (`FB-9`): "api is starting", "api is restarting", "api could not start", "api exited", "api is blocked", "admin is not started", "search is not reachable", with the HTTP status a secondary detail ("HTTP 503 while the service starts") outside the heading (`WORD-6`, `WORD-3`). Under the heading, one line counts the stack, "Acme Shop · 5 of 6 running · 1 starting", and names the worktree the service runs from with its `SEL-4` label (`ACT-6`, `WORD-5`, `SEL-4`). The document title starts with the heading's words, "api could not start · devhost", so a background tab says what failed, and while the failure persists `ACT-7`'s count prefixes it, "(1) api could not start · devhost", until the failure clears (`O16`, `ACT-7`). States are drawn with services-panel's shared service state indicator, shape and word, never color alone, the same in forced colors (`ACT-13`, `SURF-14`). The pages use the glossary's words, stack, service, worktree and status page, never project (`WORD-1`). Full pages reflow at 320 CSS pixels wide without horizontal scrolling; narrower windows follow `O8` (`SURF-9`).
   - Defaults: the page's service is the service of the route that answered (`SEL-3`); on a status page about api, Restart Changed's fallback, its key included, is api (`SEL-2`, `O4`).
   - Keys: the status page is a full page with the document's standard keys and no shortcuts of its own (`KEY-1`); every action is a button or a link in reading order.
2. **Wait while the service starts (the published state, read only).** The starting page reads "api is starting" and, under it, the health check it waits on with its elapsed time and its limit, "HTTP health check on http://127.0.0.1:4001/ · 4 s of 60 s", updated at least once a second, or the dependency it waits for, "waiting for db to pass its health check" (`ACT-4`, `STATE-1`, `WORD-6`, `WORD-8`). One line says what started this attempt and when, "Started by devhost start at 14:02:11", "Restart from the Services panel at 14:05:10" or "after devhost.toml changed on disk at 14:06:02" (`ACT-1`, `FAIL-3`). The log shows only this attempt's lines, opening at the end and following new lines while the reader is at the bottom; earlier attempts sit in a collapsed group labelled with how each ended, "Previous run, ended 14:01:58 with code 0", and every attempt starts with a divider naming its time and what started it, as the terminal separates them (`ACT-4`, `SURF-13`); an attempt with no output yet reads "No output from api since it started at 14:02:11" (`STATE-2`, `STATE-3`). A restart reads restarting, "api is restarting · stopping", then "starting", never failed or down (`ACT-3`); a first start and a restart share one look. **Restart api** stays in its place, unavailable, with the running operation and its progress as its visible reason, "Restart api is running · health check 4 s of 60 s", or "Starting Acme Shop · 2 of 6 started" while the stack starts (`HOLD-3`, `HOLD-1`, `MENU-3`). The page reads state live from the stack's health stream (`ACT-12`); once the service is ready, and only then, it requests its URL once and reloads the tab into the app at the same URL; a ready service whose leftover from a killed run answers in its place is never reported ready (`FB-5`, `ACT-11`). When it cannot read the stream, it backs off to checks at 1, 2, 5 and 10 s, then every 30 s, says when it last checked, and checks nothing while the tab is hidden (`ACT-12`, `STATE-4`).
   - Defaults: the current attempt's lines open at the end; earlier attempts collapsed (`SURF-13`).
   - Keys: Tab reaches the attempt line, **Logs** controls and the log, which is one focusable scrolling element; **Jump to Latest** carries the count of new lines when the reader scrolled up (`SURF-13`, `WORD-2`).
3. **Read the failure on the recovery page (the published state and the exit record, read only).** When the start fails, the same tab changes in place to the recovery page; it is the shared recovery view (`SURF-14`) and it never has the toolbar's crash view opened over it for the same failure (`SURF-3`, `CC-2`). Its heading names the service and the state, "api could not start" or "api exited", and one cause sentence follows in plain words, "api exited with code 1 at 14:02:31 before its health check" (`FAIL-2`, `WORD-7`, `WORD-8`). The evidence devhost observed sits under it, each piece once (`FAIL-3`): the exit code, or the signal by name with its status, the time and its sender, "terminated by SIGTERM (143) at 21:53:34, not sent by devhost"; the probe it failed, "http://127.0.0.1:4001/ answered 502 after 60 s of 60 s" or "nothing answered on 127.0.0.1:5173 after 30 s of 30 s"; a fixed port another program holds, "port 5173 is held by node (PID 4242)"; and what devhost ran, "Ran bun run src/server.ts in backend/ · devhost.toml line 14", the folder shown only when it differs from the stack's and relative to it (`FAIL-3`, `WORD-8`). The service's own last output lines follow, kept per service and frozen at its exit so other services' output never pushes them out, opened at the end with the exit summary pinned above them (`SURF-13`, `FAIL-3`); when older lines are no longer kept, the log says so and names the command that prints the stack's whole log (`devhost logs api`, stack-run-stop's) (`STATE-4`). The log is a labelled, focusable scrolling element, "api output", one element per line, terminal colors rendered as styles, never as escape codes, never a live region (`SURF-13`); a line over 2,000 characters folds to its first and last 300 characters with **Show All 50,138 Characters** and **Copy** (`SURF-9`); identical repeated blocks show once with their count, "×16" (`FAIL-4`). No page shows markup, a raw Rust error chain or the proxy client's raw error (`FAIL-2`). Actions, led by `MENU-5`'s action for the cause: **Restart api** first for an exit; **Edit**, which opens the service's definition (`MENU-4`, step 5); and the stack-wide **Restart Stack**, secondary, with its reach line (step 6). For a fixed port held by another program the lead is **Edit**, because **Restart Stack** cannot free a fixed port (`MENU-5`, `MENU-4`); for an automatic port another program took, **Restart Stack** leads, because it assigns a new port, as `stacks/recovery.md` documents (Kept). When worktrees are on, the shared worktree list sits below the actions, collapsed, with worktree-switch's **Switch and Restart Stack**, its reach line, its two steps and its question, the same as in the Worktrees panel; Enter in its find field highlights a worktree and never switches (`SEL-4`, `SEL-5`, `SURF-14`, `REV-2`, `REV-3`, `KEY-9`).
   - Defaults: the lead action has the primary style; every other action is secondary; a failed health check of a running process reads failed, an ended process exited (`ACT-2`, `WORD-6`).
   - Keys: Tab order: heading's cause, lead action, other actions, the log, the worktree list's disclosure; every action is a button (`KEY-10`).
4. **Restart the service in place (`POST /__devhost__/restart-service` with an `operationId`, one write).** **Restart api** runs on one press, because restarting one named service is not disruptive (`REV-1`); it hands off to services-panel's restart (`MENU-1`, `MENU-6`), whose terminal command is `devhost service restart api` (`CC-11`). The pressed button keeps focus, `aria-busy` and `aria-disabled`, never `disabled`, and reads "Restarting api…" (`KEY-11`, `FB-9`); the page shows the restart's steps in place, updated at least once a second: queued when another per-service operation runs ahead of it, stopping, starting, "health check 2 s of 60 s" (`FB-1`, `ACT-3`); the log starts the new attempt with its divider, "Restart from this page at 14:05:10" (step 2). The route answers `202 Accepted` with the operation's record before the restart runs; the page stores the operation ID in `sessionStorage` (`ACT-1`, `CC-37`). The restart succeeds only once api passes its health check, or, with a `process` health check or none, still runs after the time `O28` sets (`FB-5`). A lost response is read from the record by its ID and never posted again; a press based on state the server no longer holds, such as api already running again, is refused with the current state and the page redraws from it (`REV-12`, `REV-13`).
   - Success: the page requests its URL once and reloads the tab into the app; the app page shows the outcome once, "Restarted api · 2.6 s", read from the record by the stored ID, then closes it after `O14`'s reading time, which waits for the browser window's focus when the outcome arrives while it is not focused (`O53`); no page greets its load with an older success (`FB-2`, `FB-3`, `FB-6`, `WORD-4`). After that reload, focus starts on the outcome's sentence, never at the top of the document (`KEY-6`).
   - Failure: the page stays, and its report updates in place instead of adding a second one: the cause sentence, the new attempt's lines under their divider, and the count, "api exited with code 1 · 2 times, last at 14:05:12" (`FAIL-4`); when the attempt failed exactly as the one before, one line says so, "Restart ran the same command and failed the same way; it comes from devhost.toml line 14", and **Edit** leads (`MENU-5`, `MENU-4`). The failure is announced once, in the assertive region, never twice (`FB-9`); focus stays on **Restart api**, which takes the cause sentence as its accessible description (`KEY-11`).
5. **Edit the service's definition (opens the Configuration window, read only; its save is config-editor's write).** **Edit**, on the recovery page with the toolbar and the crash view alike, opens the Configuration window at the service's definition, "devhost.toml line 14, services.api.command", marked, with this failure's evidence in the window's banner (the exit with its time, the cause sentence and the frozen last lines, with **Show All Output**) and Save's reach beside **Save** (`MENU-4`, `SURF-4`, `REV-10`); from the crash view it first minimizes the view, and closing the window returns focus to the crash notice's **Expand**, which stands in for the minimized view's **Edit** (`SURF-3`, `SURF-4`, `KEY-6`). With the config editor off, or on a status page without the toolbar, **Edit** gives way to the file and line, "devhost.toml line 14", with **Copy**; devhost opens no editor, so no **Open in Editor** appears anywhere (`MENU-3`, `MENU-4`, `SURF-15`, `O51`). A save that fixes the definition applies through hot reload, which restarts api (owner rule; manifest-hot-reload reports it); the recovery page then reads restarting and, once api is ready, reloads into the app (step 2).
6. **Restart the whole stack from the crash view or a recovery page (`POST /__devhost__/restart-stack` with an `operationId`, one write).** **Restart Stack** keeps its operation's name as its label and, as the remedy on offer where the page's service is already down, runs on one press with its reach as a line beside it, "Restarts all 6 services with new automatic ports · main ~/acme · took 14 s last time"; its tooltip and accessible description list the 6 services by name and its terminal form, "In a terminal: devhost service restart --all" (`REV-1`, `REV-2`, `BAR-2`, `SEL-1`, `MENU-6`, `CC-11`, `CC-17`); while a manifest edit is rejected, the line adds "uses the accepted manifest; devhost.toml line 12 is not applied" (`HOLD-6`); while another operation runs, it is unavailable with that operation and its progress as its reason, and the control API refuses it with `409` naming that operation (`HOLD-3`, `CC-37`). Pressed, it stays in place as the busy control and keeps focus, "Restarting Stack · 2 of 6 started", and the view or page lists each service with its step (`FB-1`, `REV-4`, `KEY-11`). Restart Stack keeps every page's status stream and chat sessions connected (Kept, `HOLD-2`). This **Restart Stack** restarts every managed service inside the running stack, the same operation as services-panel's; it is distinct from shipped `devhost stack restart` (project-scoped), `devhost restart-all` (all stacks) and `devhost upgrade`, which replace the running devhost supervisor process (`MENU-6`, `O18`, `WORD-2`). The `devhost service start|stop|restart <service|group>…` commands are the terminal counterparts of this flow's per-service actions, and `devhost service restart --all` is this **Restart Stack**'s, whose help says "Restart Stack in the browser" (`MENU-6`, `CC-11`); stack-run-stop ships it with the other `devhost service` commands, and owner item q86 decides whether it ships at all, so this is the applied default until the owner answers.
   - Partial result: the view stays open and the outcome replaces the progress in it, never closing without a word: "Restart Stack: 5 of 6 running · api exited with code 1 before its health check", with api's lead actions beside it (`FAIL-1`, `FB-2`, `SURF-3`). Healthy services keep running: the `error-pages-01` stopgap ships first, and the per-service rollback restores what ran before, its own outcome naming what it put back, "Restored the services as they ran before Restart Stack: 5 of 6 running · api still fails", "Restoring the services as they ran before Restart Stack" while it restores (`UNDO-1`, `REV-11`). Focus moves to the outcome's sentence, never to an action (`FB-9`, `KEY-11`). The failure stays in the view, and in the crash notice while the view is minimized, until the person dismisses it or the same operation succeeds; notices-and-feedback's record keeps it after the view closes (`FB-6`).
   - Success: the services run again, so the crash view closes by itself (step 8) and the outcome shows as a notice in its place, "Restarted Acme Shop · 6 of 6 running · new automatic ports for api and web · 14 s" (`FB-2`, `FB-3`, `WORD-4`); on a recovery page the page reloads into the app and the outcome shows there, read from the record by its ID (`FB-2`, `ACT-1`), with focus on the outcome's sentence (`KEY-6`).
7. **See the app's own error with devhost's notice (the app's response passed through, read only; **Retry** requests the page once).** When the app answers a page load with a 404 or a 5xx, the tab shows the app's own document with the toolbar injected: a framework's build error keeps its overlay with the file, line and code frame, and an API's 404 keeps its own body (`SURF-16`, `O5`, `CC-4`). A notice names who answered, the request and the status: "web answered 500 for GET / · main ~/acme" or "api answered 404 for GET /api/v1/products · main ~/acme", with **Retry**, which requests the page once, a secondary **Restart web**, a link to the service's root, and one line saying when the page reloads by itself, "Reloads when web restarts or a watched file changes" (`MENU-5`, `SURF-15`, `WORD-4`). When worktrees are on, "Is this route in another worktree?" holds the shared worktree list collapsed; switching from it takes worktree-switch's two steps (`SEL-4`, `SEL-5`, `REV-2`). devhost never re-requests that URL on a timer: it reloads the page once per sign that the answer may have changed (the page's service restarted or became healthy, or a watched file of it changed, `ACT-8`), and that reload is held like any other while **Hold Reloads** is on (`SURF-16`, `ACT-12`, `UNDO-2`). The framework's own overlay keeps its own reload when the fix is saved, as it does without devhost. An answer that is empty or not HTML, which the toolbar cannot be injected into, gets a devhost document that shows the app's status and its body verbatim as text under the same notice, and for an empty 5xx the newest error lines of the service's log first (`SURF-16`, `FAIL-3`); `SURF-16` does not yet say what an empty or non-HTML answer shows, so this reading is this flow's proposed addition to that rule.
   - A page load the app accepts but drops without answering, while its health check passes, gets devhost's `502` page in words: "web closed the connection without sending this page", "web is not accepting connections on 127.0.0.1:4100" or "devhost could not get this page from web", then "web is running and passes its health check" and when the page will retry; the proxy client's error text, the method, the path and the time sit behind **Copy Error**, never in the message (`FAIL-2`, `WORD-7`, `error-pages-07`).
   - Defaults: the worktree list collapsed; **Retry** is the lead, **Restart web** secondary (`MENU-5`).
8. **Back in the app (the outcome: no Undo).** The tab shows the app again at the same URL and in the same tab: a status page reloads itself once the service is ready and its URL answers, and the crash view closes by itself once every exited service it shows runs again or leaves the run (`SURF-3`, `FB-5`). The announcer says once, politely, "api is running again" (`FB-9`); focus returns to the element that had it before the view opened, else the Services trigger, never the body (`KEY-6`). Restarts cannot be taken back, so there is no Undo: the outcome's undo is devhost's own, the rollback that restores what ran before a failed Restart Stack, service by service (`UNDO-1`), and the work kept through every reload this flow causes, chat's unsent text, pasted images and page context, which come back after the status page reloads into the app (`UNDO-2`).

Branches and edge states:

- **The page's service, or a service it depends on, exits while the app is open (the crash view).** The crash view opens as a modal dialog over the app page, because the page cannot work without its service; any other exit stays in the Services panel and never covers the app (`SURF-3`, Kept). It is the shared recovery view (`SURF-14`): heading "api exited", the cause sentence as the dialog's accessible description, the evidence, the log opened at the end with the exit summary pinned (`SURF-13`), and the actions in `MENU-5`'s order: **Restart api**, **Edit**, then **Restart Stack** with its reach line, and **Minimize** (`WORD-2`). **Minimize** shows its key, "Esc", in `Button`'s `shortcut` prop outside its accessible name, with `aria-keyshortcuts="Escape"`, read from the binding's one definition, in the platform's notation (`KEY-13`, `BAR-4`). Focus goes to its heading (`tabindex="-1"`), never a button, with the lead action as the next Tab stop (`KEY-6`). Tab and Shift+Tab cycle inside it, docked chat and the notice stack included, which stay operable inside its top layer while the page and the bar are inert (`KEY-7`, `SURF-3`); Alt+Ctrl+R is suspended while it is open (`KEY-1`, `KEY-2`). Escape or **Minimize** folds it into the crash notice, "api exited with code 1 at 14:02", whose **Expand** (accessible name "Expand api's failure") reopens it with focus on its heading; `WORD-2` names **Minimize** but no label for reopening, so **Expand** is this flow's proposed addition to it, and notices-and-feedback draws the notice that carries it; Escape never dismisses the failure, and the next exit opens it again by the same test (`KEY-8`, `SURF-3`, `CC-2`). While it is minimized, the page and the toolbar (Config, Services, Chat) respond.
- **The service exits while the person types or uses chat.** While focus is in a text field (the page's or devhost's), while docked chat holds a draft or a decision card, or while an agent of the page's worktree works or waits, the view opens minimized as the crash notice, announced once as a failure in the assertive region, and expands only when the person activates **Expand** (`SURF-3`, `FB-9`).
- **Several services exited.** The view's heading names one or two by name, "api and worker exited", else a count, "3 services exited"; each service gets its own cause, evidence and **Restart**, the services the page's service depends on first, because it needs them (`SEL-1`, `SEL-3`, `WORD-5`).
- **The page's own service fails a restart started in the Services panel.** The crash view opens over the panel and carries that restart's failure as its outcome: the panel closes under the modal, the row keeps its failed state, and no second failure notice is raised, as services-panel states for the same case (`FB-2`, `SURF-3`).
- **A deliberate stop.** Services devhost stops for an operation (a restart, Restart Stack, a switch, a reload, a shutdown, a failed health check) are steps of that operation and never open the crash view or a recovery page as an exit; a service a person stopped reads "not started · stopped by you"; one killed from outside names the signal, the time and that devhost did not send it (`FAIL-5`, `WORD-7`, `CC-24`).
- **The stack's terminal on a crash.** The stack's terminal and log print one line per exit, "api exited with code 1 at 14:02:31 · restart it with devhost service restart api", in place of "devhost is waiting for a restart", once stack-run-stop ships the `devhost service` commands (`MENU-6`, `FB-10`, `CC-11`); agent output carries the same line as one `devhost: ERR:` line (`FB-11`, `WORD-9`).

## Backend and contract changes

**Backend** (the document injection server, the recovery pages and the control server in `apps/devhost/src/devtools/`, the services runtime in `apps/devhost/src/services/`, the Caddy routes in `apps/devhost/src/caddy/` and the relay connector in `apps/devhost/src/remote/`, preserving the recovery contract, a single-service restart keeping its automatic port, external services as status only, the accepted manifest, status pages that work without the toolbar and without JavaScript, every page's status stream, configured-hosts-only TLS, and the app's own responses passing through untouched while it answers):

1. **Stop replacing the app's answers.** The document injection (`apps/devhost/src/devtools/document_injection.rs:316-342`, which today renders the recovery document for any 404 or 5xx page load) keeps a page load's own body and status when the app answers with a 404 or 5xx, injects the toolbar into an HTML body and tells it who answered (service, worktree `SEL-4` label, status, method and path); an empty or non-HTML answer to a page load is wrapped in a devhost document that shows the status and the body verbatim as text, with the service's newest error lines for an empty 5xx; devhost's file server's responses are never replaced. The `X-Devhost-Recovery: probe` request that today re-requests the URL once a second is removed. Serves `error-pages-03`, `error-pages-04`, `error-pages-05`, `serve-folder-06`. Required. Contract: `CC-4`.
2. **Proxy errors in words.** The reverse proxy's error response (`proxy_error_response`, `apps/devhost/src/devtools/document_injection.rs:399-428`, which today titles the page "<service> could not load" and puts the client's raw error in its message) classifies a refused connection, a closed or reset connection or EOF, and a body cut off while the toolbar is injected, publishes a sentence per class with the service's health, and keeps the client's error text, the method, the path and the time as the detail behind **Copy Error**. Serves `error-pages-07`. Required.
3. **A short status for requests that are not page loads.** Each host route (`render_service_handle`, `apps/devhost/src/caddy/routes.rs:772-809`, which today sends only `Sec-Fetch-Dest: document` and `X-Devhost-Recovery` requests to the document injection server and every other request straight to the app) gains a `handle_errors` for the reverse proxy's `502`, `503` and `504` on requests that are not page loads, which hands the request to the service's document injection server; it answers `503` with `Retry-After` and a body under 2 KB naming the service, the stack and the phase (starting, restarting, exited with its code and last output line, blocked, not reachable), as JSON under `Accept: application/json` and one text line otherwise, extending what `serve_recovery_page` (`apps/devhost/src/devtools/recovery.rs:60-103`) already answers a JSON client; a running app's own responses, errors included, still pass through untouched. On plain HTTP, the route-not-found site (`append_fallback`, `apps/devhost/src/caddy/files.rs:539-552`) answers a request that is not a page load with stack-directory's short `404` body instead of its HTML page (stack-directory's Backend 8, `CC-50`); and over HTTPS an unconfigured hostname gets no certificate (`O63`). Serves `agent-cli-journey-04`. Required. Contract: `CC-4`.
4. **Status pages read the published state live, and reload by sign.** Status pages read the stack's health stream (`/__devhost__/ws/health`) for their service's state instead of polling `X-Devhost-Recovery: status` every second, and the control server sends the page a reload sign when its service restarted, became healthy, or a watched file of it changed (`ACT-8`); without the stream the page backs off to checks at 1, 2, 5 and 10 s, then every 30 s, and checks nothing while hidden. The request that reads the server-rendered state stays internal and is listed as such in `reference/control-api.md` (services-panel's route-list test). Serves `error-pages-05`, `startup-recovery-02`. Required. Contract: `CC-25`.
5. **Per-service output, attempts and the exit record.** The control server keeps each service's output per service, never evicted by other services (for example its last 200 lines plus the complete output of its latest failed attempt, capped per service), instead of filtering the stack-wide 512-entry buffer by service name (`LiveState::recovery`, `apps/devhost/src/services/stack/live.rs:226-291`; the buffer at `:396`), marks each attempt's start with its time and its origin from the operation record, and says when older lines were dropped; services-panel's exit record (its Backend 9) carries the code or signal, the time, the sender and the last lines frozen at the exit. Serves `startup-recovery-03`, `services-panel-01`, `stack-scale-02`, `startup-recovery-02`, `stack-scale-03`. Required. Contract: `CC-24`, `CC-25`.
6. **What devhost ran, and the health check's progress.** The published service state (services-panel's Backend 1) carries the resolved command, its folder, the manifest file and line that define it, and the health check's target, elapsed time and timeout, and one structured error (file, line, column, key, message) for **Edit** (`MENU-4`). Serves `journey-crash-to-fix-04`, `journey-crash-to-fix-01`, `startup-recovery-02`. Required. Contract: `CC-25`.
7. **A daemon's status on transition.** When a daemon-lifecycle service's health check starts failing for three consecutive polls, the services runtime runs its `status` command once and publishes whether the daemon runs, with the health check's last result; the start and stop commands' output is labelled as such. An optional `lifecycle.log` whose tail the page shows is optional later. Serves `manifest-hot-reload-2-02`. Required (the verdict); optional later (`lifecycle.log`).
8. **States of their own for every cause.** The published state gives a service that the run left out, an external service and a blocked service their own states (`ACT-2`), replacing the "<service> is unavailable" fallback of `LiveState::recovery`, so the document injection answers each with its own page: Caddy routes a not-started service's hostnames to the document injection server, which answers "not started" with **Start** (`POST /__devhost__/start-service`, services-panel's route); an external service's page uses services-panel's **Check Again** route (its Backend 12, `POST /__devhost__/check-service`, a read that takes no `operationId`, which `CC-37` lists); a blocked repository's **Check Again** is the worktree-list read, which stops nothing (`HOLD-4`). Serves `manifest-hot-reload-2-04`, `serve-folder-01`. Required (external, blocked); recommended (not started, `O10`). Contract: `CC-25`, `CC-37`.
9. **The crash view keeps an operation's failure.** The crash view's selection keeps a service whose repository carries an operation's error instead of dropping it (`packages/devhost-ui/src/devtools/components/App.tsx:181-193`), and a stack-wide operation's failure is published as that operation's outcome in its record (`ACT-1`), never stored as a worktree block that turns the Worktrees trigger to "attention required"; the per-service rollback is services-panel's and manifest-hot-reload's, on the `error-pages-01` stopgap. Serves `error-pages-02`. Required. Contract: `CC-37`.

## Recommended priority

**P1, with the `error-pages-01` stopgap shipped first as a P0 fix.** The realistic trigger is every compile error and every crash during ordinary development: a syntax error's `500` hides the framework's own overlay behind a page that leads with a restart that cannot fix code (`error-pages-03`), a noisy neighbour pushes the lines that explain a crash out of the only log the page reads (`startup-recovery-03`), and a Restart Stack that one service fails closes the crash view without a word while the whole stack is down (`error-pages-02`; the outage itself is `error-pages-01`'s, which its stopgap fixes first). Nothing is lost on disk, so the cost is time and wrong actions rather than data: the person reruns the same failing command, restarts a healthy service, or reads a raw client error, scripts retry an empty `502` blind, and a reviewer on a phone reads `404 page not found` with no way to tell a stopped stack from a broken link (`relay-previews-06`, P2). This flow is hit more often than any lifecycle command, because every failure on a page goes through it.
