# Switch the stack to another checkout: research

Proposal: [Switch the stack to another checkout](worktree-switch.md). Shared patterns: [UX pattern reference](../patterns.md).

Scope: from the wish to run the stack from another checkout of a repository (the toolbar's **Worktrees** picker, or **Switch worktree** on a startup, recovery or app error page) to the stack running and reloaded in the target checkout, restored to the previous checkout after a failed start, or stopped and awaiting explicit recovery. The operations involved are the refresh (`GET /__devhost__/worktrees`, or the status page's `GET` with `X-Devhost-Recovery: worktrees`), the switch (`POST` of `repositoryId` and `path` to the same routes), stopping another stack that holds a checkout (`POST` with `stopOwnerId`), the saved selection that `devhost start` restores, and a service **Restart** while a repository is in recovery. There is no undo: the way back is a second switch (Verified, step 26).

Evidence: devhost `edb5c0fc01cabae490e92ac23d4c785ec896c4ed`, code and public docs (`packages/docs/src/content/docs/`), whose product code is identical to the reviewed build. 'Verified' means read in code or tests at that revision; 'Hypothesis' means inferred and not tested, stated with the condition under which it holds. Where a claim also rests on a review's live reproduction, the finding that reproduced it is named beside the tag. This note ran no stack and no browser.

## Owner-confirmed product rule

"Never propose that a worktree switch fall back silently to another checkout; missing selections stay stopped for explicit recovery." It is one of the owner's standing rules for this review, and the same contract appears in the app's contributor notes (`apps/devhost/AGENTS.md`, "Service supervision boundary": "Missing saved selections remain stopped for explicit recovery; never silently fall back or leave a partially switched group running.") and in the public docs (`stacks/worktrees.md`, "New and deleted worktrees": "devhost does not fall back to another checkout by itself").

It makes these behaviors intended, not defects (Verified): when the running checkout disappears, devhost stops that repository's services and keeps them stopped (`apps/devhost/internal/services/worktree_refresh.go:29-46`); a failed switch restores the checkout it left, never a third one (`apps/devhost/internal/services/runtime.go:399-408`); when that restore fails too, the repository stays stopped until someone picks a checkout (`apps/devhost/internal/services/reload.go:339-350`). Two neighbouring behaviors are documented contracts rather than owner rules, and are intended too (Verified): a switch stops every managed service of the stack (`stacks/worktrees.md:21`, "it stops every managed service"), and **Stop stack** stops another running stack so its checkout can be picked (`stacks/worktrees.md:38`; the pattern reference's `O10` keeps that action).

The stop-and-wait rule is intended; the gap is everything around it. Nothing states the switch's reach before the one-click press or in its result (Verified: steps 7 and 16, negative searches 2 and 3): every service of the stack, every conversation and agent left in the old checkout, and the run's service selection, which the switch drops against the docs (Verified, worktree-switch-11; a defect, not covered by the rule). **Stop stack** ends someone else's stack with no confirmation and no attribution (Verified: step 25, negative searches 2 and 4). And the recovery state that the rule produces leads with an action that cannot work instead of the explicit choice the rule asks for (Verified: step 23, worktree-switch-05).

## Today's flow, step by step

Go paths are relative to `apps/devhost/` (they start with `internal/`), UI paths to `packages/devhost-ui/src/`, docs paths to `packages/docs/src/content/docs/`. `WorktreePicker.tsx` and `WorktreeStatusPanel.tsx` are in `devtools/features/serviceStatusPanel/components/`, `useServiceHealth.ts` in `devtools/features/serviceStatusPanel/hooks/`, `RecoveryPage.tsx`, `RecoveryRepository.tsx` and `WorktreeOwner.tsx` in `statusPages/components/`.

### Entry points

1. **The toolbar's Worktrees button.** It shows the selected checkout's branch (or `Detached` and a 7-character ID) and turns its fork icon red when a repository is in error, blocked, or its selected checkout is unavailable; its accessible name is `Worktrees` (or the list of non-default branches), plus ", attention required" (`WorktreeStatusPanel.tsx:22-56`). (Verified)
2. **Opening the picker refreshes.** The picker requests `GET /__devhost__/worktrees` when it opens and focuses **Find worktree** once the list loads (`WorktreePicker.tsx:62-78`; `useServiceHealth.ts:95-101`); the control server runs the refresh, then answers with the whole health response (`internal/devtools/worktrees.go:34-46`). (Verified)
3. **Status pages.** Startup, recovery and app error pages carry a **Worktrees** section with **Refresh worktrees**, the checkout select and **Switch worktree**, whether or not the toolbar is on (`RecoveryPage.tsx:50-73`; `RecoveryRepository.tsx:22-72`). The page's first poll reads the worktrees through its own URL with the header `X-Devhost-Recovery: worktrees`, `GET` to read and `POST` to switch (`statusPages/hooks/useRecovery.ts:30-38`; `statusPages/createRecoveryClient.ts:9-18, 30-41`), and the service's document server hands those requests to the same handler (`internal/services/routes.go:56-58`; `internal/devtools/worktrees.go:11-16`). (Verified)
4. **`devhost start` restores the saved selection.** A new stack reads `active.json` for its root manifest path and, when it names a checkout other than the configured one, loads and runs that checkout's manifest (`internal/services/worktrees.go:59-66, 114-117, 280-314`; `internal/services/stack.go:145-163`; docs `stacks/worktrees.md:27`). No terminal line names the restored checkout (negative search under **The contested behavior**). (Verified)

### The surface

5. **The refresh behind every read.** devhost lists checkouts with `git worktree list --porcelain -z` (5-second timeout per Git command), loads each checkout's manifest and service directories, and marks it available, unavailable (with the stored error text as its reason) or in use (another live stack owns its manifest inputs) (`internal/services/worktree_git.go:16, 23-43, 69-105`; `internal/services/worktrees.go:193-250`; `internal/services/worktree_ownership.go:12-18`). A selected checkout Git no longer lists stays in the list as "Saved checkout is no longer registered with Git." (`internal/services/worktrees.go:244-246`). (Verified)
6. **Pick a checkout.** Rows show the branch, the `~`-shortened path and badges; **Find worktree** filters fuzzily by row label and path only (`WorktreePicker.tsx:43-51, 266-268`; worktree-switch-01). The unavailable and in use badges open a popover with the raw reason and, for an owner, its name, PID, manifest path, one **Open stack** link per routed URL and **Stop stack** (`WorktreePicker.tsx:141-183`; worktree-switch-02, worktree-switch-07). (Verified)
7. **Press Switch and restart stack.** The button is enabled once the list has loaded, nothing is busy or restarting, the repository is not blocked and an available checkout other than the selected one is picked (or the selected one while the repository has an error, then labelled **Retry**) (`WorktreePicker.tsx:53-60, 204-213`). One click posts the switch (`WorktreePicker.tsx:80-87`; `useServiceHealth.ts:102-107`). On a status page, **Switch worktree** submits the selected option (`RecoveryRepository.tsx:26-55`; `statusPages/hooks/useRecovery.ts:101-105`). Neither surface asks first. (Verified)

### The switch inside the backend

8. **The request.** The handler decodes `repositoryId` and `path` and calls the runtime (`internal/devtools/worktrees.go:48-64`), which runs the switch with the stack's lifecycle context, not the request's (`internal/services/stack.go:409`), so a closed tab does not cancel a switch in progress. (Verified)
9. **The lifecycle lock.** The switch takes the operation lock that restarts, reloads, service starts and refreshes share, and is refused while the stack is still starting or shutting down (`internal/services/runtime.go:143-151, 363-373`; `internal/services/reload.go:44-46, 72-74`; `internal/services/worktree_refresh.go:8-13`). (Verified)
10. **Remember the way back.** It reads the saved selection and the old selected path, and names the transition by folder base names (`internal/services/runtime.go:380-390`; worktree-switch-04). (Verified)
11. **Prepare and save.** `prepare` refuses a blocked repository, refreshes Git, validates the target (registered, available, directories present), loads the target's manifest and includes, and resolves its ports with no service selection; it then saves the target to `active.json` and marks the repository switching with the target selected, before any service stops (`internal/services/worktrees.go:316-365`; `internal/services/worktree_config.go:12-42`). A failure at this point logs "Worktree switch failed: a -> b: …" and stops nothing (`internal/services/runtime.go:391-395`). (Verified)
12. **Announce.** The terminal prints "Switching worktree: a -> b. Restarting stack." and the health stream publishes, so the toolbar's label already names the target while the old checkout still runs (`internal/services/runtime.go:396-397`; `WorktreeStatusPanel.tsx:31-35`; worktree-switch-09). (Verified)
13. **Apply the target as a stack restart.** The switch calls `applyConfiguration` with `worktreeSwitch` and `restartStack` set and no requested names (`internal/services/runtime.go:398`; `internal/services/reload.go:18-27`). It reserves the target's manifest files (`reload.go:100-111`); resolves the candidate, which with no requested names starts every service (`reload.go:119`; `internal/services/ports.go:213-224`; `internal/services/selection.go:52-59`; worktree-switch-11); rebuilds the repository groups from the target (`reload.go:128`; `internal/services/worktrees.go:47-123`); validates service directories (`reload.go:141`); marks every managed service affected, with changed and removed ones, their dependents and their repository groups (`reload.go:144-152`; `internal/services/reload_plan.go:7-54`); and claims the target's hostnames and fixed ports (`reload.go:173-176`). (Verified)
14. **Stop everything.** It publishes the affected services as restarting (`reload.go:186-209`), then stops them in reverse dependency order: watches and change markers off, then a daemon's stop command in the checkout that launched it, or SIGTERM to the service's tracked process tree, a 10-second grace period and SIGKILL (`reload.go:210, 278-284`; `internal/services/runtime.go:218-266, 425-432`; `internal/services/stack.go:35, 1209-1225`). The tracker can also signal unrelated processes that reused old child PIDs (process-containment-01). (Verified)
15. **Start everything in the target.** It installs the candidate and starts each service in dependency order with its watches, retrying automatic ports up to 3 times; then it replaces the Caddy routes, points the manifest watcher at the target's manifest and includes, and pushes the new settings to open pages (`reload.go:213, 225-249, 286-328`; `internal/services/retry.go:10`; `internal/services/runtime.go:273-342`). (Verified)
16. **Accept and report.** It records the target as the accepted configuration, drops retired services, marks the repository as running in the target, resets the idle timeout, releases the old claims and manifest reservations, and logs "worktree switched: a -> b", the service URLs and any stopped services (`reload.go:250-269`; `internal/services/worktrees.go:367-383`). A rejected-reload notice from before the switch is not cleared, because only the manifest watcher records reload results (`internal/services/runtime.go:106-124`; `internal/services/stack.go:627-632`; worktree-switch-08). (Verified)
17. **Reload the page.** The `200` answer reloads the page at the same URL (`useServiceHealth.ts:102-107`; `statusPages/hooks/useRecovery.ts:101-105`); a path that has no route any more shows the Caddy 404 with the routes that do (docs `stacks/worktrees.md:21`). (Verified)

### Results

18. **What follows the target.** Editor links and tool launches resolve into the selected checkout and are refused while it is switching or in error (`internal/services/worktrees.go:403-442`). Chat lists and drives only conversations started in the selected checkout, and the running agents list keeps only agents inside it (`internal/devtools/chat_project.go:12-19`; `internal/devtools/chat_server.go:96-111`; chat-checkout-switch-01, seen live). The page keeps its chat and toolbar state per checkout path and origin, so a checkout seen for the first time starts from the defaults (`devtools/shared/createDevtoolsSettingsStore.ts:13-23, 46`; chat-checkout-switch-03). (Verified)
19. **What the terminal says.** Besides the two switch lines, services the switch itself stopped can print "\<service\> exited with code 0; devhost is waiting for a restart." (`internal/services/stack.go:633-634, 885-897`; worktree-switch-04, seen live for the fixture's `serve` services). (Verified)
20. **A successful switch can land on a broken app.** Availability checks only the manifest and the service directories, so a fresh worktree without installed dependencies switches "successfully" and serves a 500 (`internal/services/worktrees.go:222-242`; worktree-switch-06, seen live). (Verified)

### Failures and recovery

21. **Start failure: the previous checkout comes back.** Rollback restores the watcher's previous inputs, stops the new services and reinstalls and starts the previous services and routes (`reload.go:214-224, 330-364`); the runtime then restores `active.json` and the old selected path and logs "Worktree switch failed: a -> b: …" (`internal/services/runtime.go:399-410`). The picker stays open with the error and the page does not reload (`WorktreePicker.tsx:83-86, 105-107`). (Verified)
22. **Restore failure: the repository stays stopped.** Services that do not come back are stopped and blocked with the error (`reload.go:339-350, 352-360`); restarting any of them retries the whole repository (`internal/services/runtime.go:180-190`; `internal/services/worktree_recover.go:5-52`; docs `stacks/worktrees.md:23`). (Verified)
23. **The running checkout is deleted.** The next refresh (opening the picker, a status page's first poll, **Refresh** or **Refresh worktrees**) stops that repository's services, blocks them with "Selected checkout \<path\> is unavailable; choose a checkout to recover repository \<name\>." and logs it; other repositories keep running (`internal/services/worktree_refresh.go:18-47`; docs `stacks/worktrees.md:47`). The status page then leads with **Restart \<service\>**, which retries the deleted checkout, and preselects the deleted checkout (`RecoveryPage.tsx:33-40`; `RecoveryRepository.tsx:39-46`; `internal/services/runtime.go:180-190`; worktree-switch-05, seen live). Only the toolbar offers **Return to configured checkout** (`WorktreePicker.tsx:214-231`). (Verified)
24. **The repository is blocked.** One external service (`managed = false`) in a repository blocks switching for all of its services (`internal/services/worktrees.go:110-112, 317-318, 342-344`; `WorktreePicker.tsx:108-110`; `RecoveryRepository.tsx:34, 47`; manifest-hot-reload-2-03; the pattern reference's `O7`). (Verified)

### Stopping another stack

25. **Stop stack.** From the in use popover or the status page's owner card, one click posts `stopOwnerId` (`WorktreePicker.tsx:89-101, 173-180`; `WorktreeOwner.tsx:59-68`; `internal/devtools/worktrees.go:56-61`). Under the operation lock, devhost re-reads the checkout's owners, then, under the stack-records lock, re-checks the stack record's ID (a hash of its PID, start identity, manifest path, registration time and manifest files) and the process's start identity before it sends SIGTERM; it waits up to 15 seconds, sends SIGKILL with the same checks and waits 1 more second (`internal/services/worktree_ownership.go:20-101`; `internal/services/stop.go:17`; `internal/caddy/stack_occupant.go:48-94`). The other stack's own shutdown stops its services, and its terminal names only the signal (worktree-switch-07). The picker then refreshes and the status page reloads (`WorktreePicker.tsx:97-100`; `statusPages/hooks/useRecovery.ts:101-105`). (Verified)

### Undo

26. **There is none.** devhost keeps each repository's configured, selected and running path and nothing else (`internal/devtools/worktrees.go:97-109`). The way back is another switch, which restarts the stack again and does not bring back a dropped service selection (worktree-switch-11, seen live). (Verified)

## The contested behavior

**A switch is a whole-stack restart whose reach nobody is shown: it stops every managed service of the stack, not only the repository being switched; it drops the run's service selection; it leaves conversations and agents running out of sight in the old checkout; and Stop stack, one click away in the same picker, ends another running stack. (Verified)**

Supporting evidence:

- **Scope.** With `restartStack` set, every managed service of the target is affected, whatever repository it belongs to (`internal/services/reload.go:144-151`). The docs say "it stops every managed service" (`stacks/worktrees.md:21`) and the contributor notes say "Services outside Git participate in full-stack switching" (`apps/devhost/AGENTS.md`, "Service supervision boundary"). A plain manifest edit, by contrast, restarts only the edited services, their dependents and their repository (`internal/services/reload_plan.go:7-54`; the pattern reference's `O9`). (Verified)
- **Selection.** The switch passes no requested names (`internal/services/runtime.go:398`), so the target starts every service and the emptied selection is carried on by later reloads and **Restart Stack** (`internal/services/reload.go:39, 78`); worktree-switch-11 reproduced it live. The docs promise the opposite: "The names you started with last for the whole run" (`guides/stack-lifecycle.md:183`). Startup has the same gap by another path: restoring a saved linked worktree resolves its manifest with no requested names (`internal/services/worktrees.go:297`) and replaces the run's manifest with it (`internal/services/stack.go:149-150`), after `devhost start <names>` resolved those names (`internal/app/run.go:137, 174`). (Verified; the startup path was read in code, not run)
- **Chat.** Chat resolves every route to the page's selected checkout (`internal/devtools/chat_project.go:12-19`), so conversations and agents in the old checkout drop out of the page while they keep running (chat-checkout-switch-01, seen live). (Verified)
- **Another stack.** **Stop stack** posts at once (`WorktreePicker.tsx:173-180`; `WorktreeOwner.tsx:59-68`) and signals the other stack's supervisor after re-checking its identity (`internal/caddy/stack_occupant.go:59-94`). (Verified)
- **Reads that stop services.** The refresh behind every `GET` stops a repository whose running checkout is gone (`internal/devtools/worktrees.go:34-38`; `internal/services/worktree_refresh.go:29-46`), and the control guard lets every `GET` through unchecked because it is not state-changing (`internal/devtools/request_guard.go:24-27`). (Verified)
- **Ordering of the saved selection.** The target is saved before anything stops (`internal/services/worktrees.go:360`) and restored only when the switch returns an error (`internal/services/runtime.go:399-400`). (Verified)

Negative searches, recorded as evidence (each run at the pinned revision; Verified):

1. devhost never writes to Git. Its only Git commands are `rev-parse --show-toplevel`, `rev-parse --git-common-dir`, `worktree list --porcelain -z` and `for-each-ref` (`internal/services/worktree_git.go:46, 54, 70, 110`; searched `runGit(` across `internal/services/`): no `worktree add`, `remove` or `prune`, no `checkout`, `stash` or `commit`. The parser ignores Git's `locked` and `prunable` fields (`internal/services/worktree_git.go:76-101`).
2. No confirmation precedes a switch or a **Stop stack** (searched `WorktreePicker.tsx`, `RecoveryRepository.tsx` and `WorktreeOwner.tsx` for confirm and dialog: no match).
3. The switch path never looks at chat or agents (searched `internal/services/runtime.go`, `internal/services/worktrees.go` and `internal/devtools/worktrees.go` for chat, session and agent: only the unrelated chat panel position helper, `internal/services/worktrees.go:454-465`).
4. A stopped stack is never told who stopped it: the stop request carries no sender (`internal/devtools/worktrees.go:18-22`), the stopped stack logs only "Received SIGTERM (signal 15); shutting down the stack." (`internal/services/stack.go:224, 656-670`), and nothing in `internal/` records a stop reason (searched for "stopped by", "stopReason", "requested by": no match).
5. Nothing prepares a new checkout: the manifest has no setup, prepare or install key (searched `internal/manifest/` for those keys: no match), and availability means a manifest that loads and directories that exist (`internal/services/worktrees.go:222-242`).
6. No startup line names a restored selection (searched the `cliout.Log` calls in `internal/services/` for worktree and checkout: only the switch lines, `internal/services/runtime.go:393-407`, and the refresh failure, `internal/services/worktree_refresh.go:46`).
7. No previous checkout is remembered for an undo: a repository's state is its configured, selected and running path (`internal/devtools/worktrees.go:97-109`).
8. The worktree routes never check for a local client. `isLocalClient` guards only config saves, the stack directory and **Watch Live Activity** (`internal/devtools/config_files.go:153`; `internal/devtools/stack_directory.go:36`; `internal/devtools/agent_activity.go:54`; searched `internal/devtools/` for `isLocalClient(`).

What it means in practice:

1. A stack whose services come from two repositories, or include services outside Git, stops and restarts all of them when one repository switches. A switch took 13 to 27 seconds in the review (worktree-switch-06, worktree-switch-09, worktree-switch-11). (Verified in code; timings seen live)
2. A run started with names (`devhost start web api`) starts every service of the target on its first switch, side-effecting workers included, waits on their health checks, and keeps them for the rest of the run (worktree-switch-11, seen live). If one of the left-out services cannot start in the target, every switch fails and restores the previous checkout (Hypothesis, from `internal/services/reload.go:225-226` and docs `stacks/worktrees.md:21`; holds when a service the person left out is broken in the target).
3. The documented remedy for a changed selection, stopping and starting again, does not bring the names back while a linked worktree is the saved selection: startup runs every service of the saved checkout (Verified in code: `internal/services/worktrees.go:297`, `internal/services/stack.go:149-150`; not run).
4. A conversation waiting for an approval, or still working, in the old checkout vanishes from chat and the running agents count while its agent keeps running there, and nothing warned before the press (chat-checkout-switch-01, seen live; chat-checkout-switch-02). (Verified)
5. One click on **Stop stack** ends another stack, and its owner sees only the signal (Verified: step 25, worktree-switch-07). The docs present that other stack as a parallel worktree (`stacks/worktrees.md:57-59`), so it is often another agent's or terminal's work (Hypothesis, holding where parallel stacks are started by agents or other terminals). The stop never reaches a process that merely reused the PID (Verified: `internal/caddy/stack_occupant.go:66-94`). If that stack needs more than 15 seconds to shut down, devhost kills its supervisor during cleanup and the remaining services keep running unseen (Hypothesis: the same 15-second budget and SIGKILL as `devhost stop`, `internal/services/worktree_ownership.go:60, 86-96`, whose effect interrupted-operations-01 reproduced for `devhost stop`; holds when the other stack's services need more than 15 seconds together, for example two services that ignore SIGTERM, each given its 10 seconds in turn by `internal/services/stack.go:1241-1250`).
6. Every switch stops every managed service through the process-tree tracker, which can signal unrelated processes that reused old child PIDs after a long run (process-containment-01, a P0 stopgap owned by stack-run-stop), so each switch exposes every service of the stack to it. (Verified in code)
7. A page load can stop services: a status page's first poll is a `GET` that runs the refresh (`statusPages/hooks/useRecovery.ts:30-38`), which only brings forward the stop the owner rule already asks for (Verified). Until some refresh runs, the deleted checkout's services keep running from a deleted directory (Hypothesis: nothing watches the checkout's folder; holds until the picker opens, a status page loads or someone presses **Refresh**).
8. A supervisor that dies during a switch (a crash, or `devhost stop` killing it after 15 seconds) leaves the target saved as the selection, so the next `devhost start` runs the target checkout without saying so (Hypothesis, from the ordering in `internal/services/worktrees.go:360` and `internal/services/runtime.go:399-400`; holds when the supervisor dies after the save and before the switch returns).
9. From another machine that reaches the HTTPS port, a client that sends no browser headers can switch the stack or stop another stack, and a `GET` returns absolute checkout paths, branches, PIDs and owner IDs (`internal/devtools/request_guard.go:22-42, 53-71`; `internal/devtools/worktrees.go:34-64`). (Verified in code, not run; the same class as network-exposure-01, which covers chat only)
10. No Git state changes: a switch, a refresh or a stop creates, moves or deletes no branch, commit, stash or worktree (negative search 1). Files in the checkouts change only through what the started services do. (Verified)

Reusable capabilities and their limits (Verified):

- **Identity-checked stop of another stack**: the record hash (PID, start identity, manifest path, registration time, files) and the process start identity are re-checked under the stack-records lock before SIGTERM and again before SIGKILL; it refuses this stack, reused PIDs and re-registered stacks (`internal/caddy/stack_occupant.go:48-94`). Budget: 15 seconds, then SIGKILL and 1 second more (`internal/services/stop.go:17`; `internal/services/worktree_ownership.go:79-96`).
- **Rollback to the previous checkout**: services, routes, watcher inputs and `active.json` (`internal/services/reload.go:214-224, 330-364`; `internal/services/runtime.go:399-410`). Automatic ports retry up to 3 times (`internal/services/retry.go:10`).
- **One operation lock** serializes switch, restart, reload, service start, refresh and stop of another stack (`internal/services/runtime.go:363-365`; `internal/services/reload.go:44-46, 72-74`; `internal/services/worktree_refresh.go:9`; `internal/services/worktree_ownership.go:51`).
- **The run's selection** already travels through reloads and **Restart Stack** (`internal/services/reload.go:39, 78`) and grows through **Start** (`internal/services/reload.go:44-70`); a requested name the manifest does not define selects nothing (`internal/services/selection.go:48-51, 77-80`), so carrying names into a target whose services are named differently starts only its `alwaysStart` services and their dependencies.
- **Per-service progress** during a switch: pending health for every affected service is published before the stop (`internal/services/reload.go:186-209`), which the toolbar's service dots already show (worktree-switch-09).
- **Agent awareness**: the running agents list and the chat session list can count what a switch hides (`internal/devtools/chat_server.go:96-111`), and starting a conversation beside a working foreign agent already asks first (`devtools/features/agentChat/createAgentChatClient.ts:187-195`).
- **Limits**: Git commands time out after 5 seconds (`internal/services/worktree_git.go:16`); a switch waits up to 10 seconds per service before SIGKILL, one service after another (`internal/services/stack.go:35, 1209-1225`; `internal/services/runtime.go:425-432`); the switch request body is capped at 64 KiB (`internal/devtools/worktrees.go:49`).

### Other products

General knowledge, not checked against these products' documentation in this note (no browser was used); evidence, never requirements.

- **Git** refuses `git worktree remove` on a worktree with modified or untracked files unless forced, reports `locked` and `prunable` worktrees in `git worktree list --porcelain`, and cleans entries whose folders are gone with `git worktree prune` (the git-worktree manual). devhost reads neither field (Verified, negative search 1).
- **Docker Compose** starts only the named services with `docker compose up <service>` and keeps projects apart by project name, so a second checkout runs as a second project instead of replacing the first.
- **Branch preview deployments** (Vercel, Netlify) give each branch its own URL instead of switching one environment between branches.
- **Editors** (VS Code, JetBrains IDEs) open another worktree in a new window instead of replacing the current one.

## Open questions

Already product decisions in the pattern reference, not repeated here: `O7` (whether an external service keeps blocking its repository's switch), `O5` (whether devhost keeps replacing the app's own 404, the page that today offers a switch for an app's 404), `O10` (**Stop stack** stays the browser's way to stop another stack), `O6` (adding services to a running stack, which question 1 meets) and `O9` (the restart scope of a manifest edit, the reload's counterpart to question 2). Consequence 9, the worktree routes answering other machines, is a defect recorded for a ticket, not a question.

1. **Does a switch keep the run's service selection, and what happens to names the target does not define?**
   - Unknown: whether a switch is part of "the whole run" for which the docs keep the names (`guides/stack-lifecycle.md:183`), when the target's manifest may define other services (`stacks/worktrees.md:25`).
   - Why it matters: today every switch, and every start that restores a linked worktree, runs every service (Verified: worktree-switch-11, consequence 3). Carried names that the target does not define select nothing (`internal/services/selection.go:48-51, 77-80`), so a target that renamed them starts only its `alwaysStart` services and their dependencies, possibly no routed page (Verified in code).
   - Evidence to close it: the owner's reading of the two docs passages; how often worktrees' manifests rename or drop services (the review fixture's checkouts had identical manifests: Verified, worktree-switch-11).
   - Proposed default: keep the run's names across switches and restored starts, and name every name the target does not define in the switch result.
   - Decides: the product owner; the backend owners confirm it against the stack lifecycle docs.
2. **Does a switch restart only the repository being switched?**
   - Unknown: whether restarting every managed service is required (services outside the repository depend on the switched ones through `dependsOn` or templates, which the reload's dependency expansion already finds: `internal/services/reload_plan.go:23-54`, Verified) or only the implementation's choice (`internal/services/reload.go:144-151`, Verified).
   - Why it matters: each switch takes 13 to 27 seconds, hides conversations and exposes every service to process-containment-01, including services that have nothing to do with the checkout (Verified: consequences 1, 4 and 6).
   - Evidence to close it: how many stacks span several repositories or run services outside Git; whether any such service reads the switched checkout other than through declared dependencies.
   - Proposed default: keep the whole-stack restart the docs describe (`stacks/worktrees.md:21`), and name every service it stops before the press and in the result.
   - Decides: the product owner with the backend owners.
3. **When does a switch ask before it acts?**
   - Unknown: which states justify interrupting a one-click switch: a working or waiting conversation in the old checkout (chat-checkout-switch-02), a foreign agent working there, a run whose selection the switch would widen while question 1 is open.
   - Why it matters: a hidden waiting approval blocks an agent that only the person can unblock (Verified: chat-checkout-switch-01, P1, seen live), while asking on every switch slows the common case (Hypothesis, holding while most switches happen with no agent at work).
   - Evidence to close it: how often switches happen while an agent works or waits, before and after the chat edit mode (`O1`) makes **This checkout (live)** the default for messages with page context.
   - Proposed default: one click when nothing is at stake; ask only when an agent in the old checkout is working or waiting, naming each one and its state.
   - Decides: the product owner.
4. **Does Stop stack confirm, and how does the stopped stack learn who stopped it?**
   - Unknown: whether a one-click stop of another stack is acceptable (`O10` keeps the action and says nothing about confirming it) and whether devhost tells the stopped stack why (a signal carries no sender: Verified, negative search 4).
   - Why it matters: the stopped stack often belongs to another agent or terminal, whose owner then cannot tell why it died (Hypothesis, consequence 5; the missing attribution is Verified, worktree-switch-07).
   - Evidence to close it: whether a stop reason the supervisor can read when SIGTERM arrives is feasible (for example a record beside its stack record in the state directory), and whether `devhost stop`, `stop --worktrees` and `stack restart --all`, owned by stack-run-stop, should share it.
   - Proposed default: keep **Stop stack** behind a confirmation that names the stack, its checkout and how many services it stops; the stopped stack's terminal names the stack that stopped it.
   - Decides: the product owner for the confirmation; the backend owners with stack-run-stop for the attribution.
5. **When does devhost notice that the running checkout is gone, and may a read stop services?**
   - Unknown: whether detection at refresh time (opening the picker, a status page's first poll, **Refresh**) is enough; until then services run from a deleted directory (consequence 7, Hypothesis).
   - Why it matters: the owner rule requires the stop; when it happens decides what the person meets first (a crash, a 500 or the recovery state: Hypothesis, consequence 7), and today a `GET` performs it (Verified, step 23).
   - Evidence to close it: what common development servers (Bun, Vite, Next.js) do when their working directory is deleted, measured in a disposable checkout; the cost of watching each selected checkout's folder.
   - Proposed default: keep detection at refresh time and the stop on that read, and have the recovery state say that the folder was deleted (worktree-switch-05).
   - Decides: the backend owners; the product owner if detection changes when services stop.
6. **May devhost prepare a new checkout before it switches to it?**
   - Unknown: whether devhost should run anything in a target before starting its services (worktree-switch-06 proposes an optional manifest setting), given that the manifest decides which commands run.
   - Why it matters: the first switch to a new worktree fails whenever the stack's dependencies live in ignored folders (Verified for the review's Bun stack, worktree-switch-06; Hypothesis for JavaScript, Python and Ruby stacks in general), and agents working in the **New worktree (review before merge)** mode create a worktree per task (Hypothesis, from `O1`).
   - Evidence to close it: the owner's view of a new manifest setting that runs commands on a switch (a contract change; like every setting it would apply through hot reload); how many stacks need more than their ignored dependency folders.
   - Proposed default: devhost runs nothing new on a switch, and the result names the failure's cause from the service log; a preparation setting is a separate contract decision.
   - Decides: the product owner.
7. **Which checkout does the next start run after an interrupted switch, and does it say so?**
   - Unknown: whether `active.json` should name the target before the switch has succeeded (consequence 8, Hypothesis), and whether `devhost start` should name the checkout it restored (negative search 6).
   - Why it matters: a person whose stack stopped mid-switch gets a different checkout on the next start (Hypothesis, consequence 8), with no line saying which (Verified, negative search 6).
   - Evidence to close it: in a disposable stack, kill the supervisor between the save and the end of a switch, start it again, and read `active.json` and the output.
   - Proposed default: the next start prints the branch and path of the checkout it restored; whether the save moves after the switch is the backend owners' call.
   - Decides: the backend owners.
