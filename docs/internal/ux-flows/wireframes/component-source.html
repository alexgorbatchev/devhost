Find a page element's source

TLDR: Alt + right-click always answers, on React 18 and React 19 alike, with a keyboard-reachable source menu that names the worktree and copies each file, line and column with a confirmation, while devhost no longer opens editors, keeps no editor settings and drops highlight from an editor's cursor.

1. Point at an element

Alt + right-click still opens the source of the element under the pointer, and Select Elements and holding Alt still pick elements as page-context specifies. What changes is that the element is outlined with its role and name before the click, the gesture always answers, and the keyboard reaches the same menu. Keys: Alt + right-click (Option on macOS); with Select Elements latched on, the arrow keys walk the highlight and Shift+F10 or the context-menu key opens the source menu (KEY-12, MENU-1).

  1. 1 Holding Alt outlines the element under the pointer with its role and name before the click, drawn dashed here, by the one resolver that Select Elements, holding Alt and Alt + right-click share, which page-context owns: the element shown is the element looked up (SEL-9).
  2. 2 Alt + right-click on the app page, outside devhost's own surfaces, opens the source menu at once, also when there is no source to show (step 3): devhost takes the browser's context menu only for this gesture and always answers it (MENU-3, KEY-2).
  3. 3 With Select Elements latched on, Shift+F10 or the context-menu key opens the source menu for the highlighted element. The toggle lists Shift+F10 in its tooltip and in aria-keyshortcuts, both drawn from the binding definition its handler reads (KEY-12, KEY-13, BAR-4).
  4. 4 Alt pressed as part of a chord, or to type a character, never starts selection (KEY-2).
  5. 5 The feature is on wherever devhost injects its devtools. Its one switch is [devtools.componentSource].enabled in the manifest, on by default, which turns off Alt + right-click and Shift+F10 in Select Elements and nothing else; [devtools].enabled = false removes it with the toolbar. [devtools.editor] is removed completely, but a leftover enabled = false still turns the menu off, with a warning naming the new key (step 5), so no one's off switch turns on with an upgrade (SEL-11, FAIL-6, CC-41, O51; Backend 3).

2. Find the element's source in the page's worktree

The lookup still runs in the page, still reads React's source metadata and the page's source maps, and still resolves paths in the selected worktree, as today. What changes is that React 19 development builds work without a browser extension, maps named by a SourceMap header are read, and page context's marks use the same lookup. It stays one shared module under packages/devhost-ui/src/devtools/shared/, which the source menu and page context's marks both call, and adds no control route.

  1. 1 While a source map is read for the first time, the open menu shows "Finding the source of <h1>…" where its items go, never an empty menu, with focus on the menu itself; when the items arrive, they fill in place and focus moves to the first of them (STATE-1, KEY-6).
  2. 2 On React 19, the page reads the fiber's _debugStack, the stack React records where the JSX was created, whose first frame outside React is the JSX call site; the React DevTools extension's renderer interface still answers first when it is installed, and React 18's _debugSource and __source come next, as today. The owner chain is walked the same way, each owner's _debugStack included, and duplicates are dropped, so the menu lists the element and the components that render it.
  3. 3 Each frame's position maps back through the source map of the script or module it names, whether a script element, a module loaded through import or a chunk loaded later, read from a SourceMap response header or from the last sourceMappingURL comment whatever follows it.
  4. 4 Paths resolve in the page's worktree: the selected worktree of the repository the page's service runs from, with a path from another worktree of that repository rewritten to it, as today (SEL-3, WORD-11).
  5. 5 The same lookup gives page context's marks their source file, so on React 19 a mark reaches the agent with its file, and page-context's row shows it, "#1 h1 Devtools playground · PlaygroundLayout.tsx:15", or "no source found" (SEL-9).

3. Read the source menu

The menu still lists the element and the components that render it, each with its non-default props as badges and its path, and still stays inside the window and closes with Escape, a click outside or a worktree switch, as today. What changes is that it names the element and the worktree, offers Copy Path per source instead of opening an editor, answers when it has no source, takes the keyboard, and keeps clear of devhost's other surfaces; no row names or opens an editor (O51). It is a transient layer above the page, at the pointer, or at the highlighted element after Shift+F10. Keys: focus starts on the first item; ArrowUp and ArrowDown move, Home and End jump, a letter jumps to the next item that starts with it, so c moves from one Copy Path item to the next, and Enter or Space copies; Escape, Tab or Shift+Tab closes it and returns focus to the page element that had focus before the right-click, the element itself when the click focused it, or, opened with Shift+F10, to the Select Elements toggle with the highlight kept; a click outside closes it and leaves focus where that click put it; devhost never adds a tabindex to a page element. Inside the open menu devhost keeps every key; once it closes, the page's keys work without a click (KEY-10, KEY-6, KEY-5, KEY-8, KEY-12). A rejected configuration or chat that cannot take a message blocks nothing here (HOLD-6, HOLD-5).

  1. 1 The first row is the target header, "Source of <h1>", naming the element the menu shows; the menu is named by it (2.3 Accessibility, KEY-10).
  2. 2 The line under it names the worktree the files are in by its worktree label (SEL-4, WORD-11).
  3. 3 One Copy Path item per source, the element first and each component that renders it after it: the name, a badge per non-default prop, as today, and the path relative to the worktree with line and column, which is also in the item's accessible name. With two or more sources, "Element and components" heads them as a labelled group; a menu of one source has no heading. Focus moves into the menu on open, on its first item; Enter or a click copies it, step 4 (KEY-6, MENU-2, WORD-3, WORD-8).
  4. 4 The foot shows the menu's keys from the binding definitions: "↑↓ Move · Enter Copy · Esc Close" (KEY-13).
  5. 5 The menu opens inside the viewport, never clipped, here beside a success notice drawn only to show the clearance, in the page area on the side of the pointer away from the dock, so it covers neither the notice stack nor docked chat's header, composer or decision card. It takes pointer input only where it draws, and the outline of the element it opened on stays anchored to that element while it is open. Alt + right-click lands outside an open toolbar panel, which closes as any click away closes it (SURF-1, SURF-2, SURF-9, SURF-11, SURF-12).
  6. 6 Where the page area beside docked chat is narrower than the menu, the menu narrows to it, down to 240 CSS pixels, and wraps each path onto its own line; a path longer than the menu is shortened in the middle, keeping the file name and line, with the full path in its tooltip and accessible name. Chat's composer, Send and the pending decision card stay clear (SURF-6, WORD-8).
  7. 7 When the page records no source for the element, the same menu opens, its first row reading "No source for <div>", with one sentence naming the cause and Copy Element Path, step 4. The causes: no React component renders the element; the page's React build records no source locations; or the source map could not be read, which adds Retry, reading the map once more and filling the menu in place. The browser's menu is never taken without this answer (MENU-3, FAIL-2, STATE-4).
  8. 8 While the page's repository switches, the menu opens and works, and its worktree line names the worktree the page still shows with the operation in progress, because reads stay available during service operations; today the gesture silently falls through to the browser's menu. The page reloads into the new worktree when the switch ends, which closes the menu (HOLD-3, SEL-4).
  9. 9 With the page's selected worktree deleted, the menu opens all the same with that state on its worktree line, and Copy Path works; today the gesture silently falls through to the browser's menu. Returning to the configured worktree stays the Worktrees panel's, as worktree-switch specifies (HOLD-4, SEL-4).
  10. 10 A source outside the stack's worktrees, such as a linked package elsewhere on disk, shows its absolute path shortened with ~, and Copy Path copies the absolute path with its line and column (SEL-4).
  11. 11 The lookup and Copy Path run in the page and send nothing to devhost, so they keep working while the status stream is lost and in a browser in another environment, signed in or not; the lost-connection notice, notices-and-feedback's and not drawn here, says devhost is not reachable (HOLD-2, HOLD-7, HOLD-8).
  12. 12 Alt + right-click on an element inside the page's own modal dialog opens the menu inside the dialog's top layer, where the notice stack and the announcer already move, so its items take the keyboard and the pointer and its notices are heard; devhost's bar keeps its paused state, with its one reason line in the moved notice stack, unchanged (SURF-11, FB-9).

4. Copy a path

Copying is the menu's one action. Today the one entry button copies the path and opens the editor at once and says nothing; now each item copies, says so, and opens nothing, because devhost has no editor integration (O50, O51). Copying is an action of this page, not an operation of the stack: it writes no line in the stack's log and no operation record, which FB-7 and ACT-1 keep for operations, and its notices and the announcer are notices-and-feedback's. It reads the page and starts no service, so it never asks and stays available while another operation runs (REV-1, HOLD-3). A copy changes nothing devhost could take back, so there is no Undo. Keys: typing c moves to the next Copy Path item; Enter or Space copies (KEY-10).

  1. 1 "Copy Path · <h1>" copies that source's path, line and column; the item is reached with the arrows or by typing c (KEY-10, WORD-3).
  2. 2 The path, relative to the worktree with its line and column, goes to the clipboard, the menu closes, and "Copied path · frontend/src/components/PlaygroundLayout.tsx:15:7" shows, announced once; it closes by itself after its reading time, 4.2 s for these 9 words, counted only while neither the pointer nor focus is in it and the page is visible, and one that arrives while the browser window is not focused waits until the window next gains focus. Copying never navigates the page (FB-2, FB-3, FB-6, FB-9, WORD-4, O14, O53).
  3. 3 When the browser refuses the clipboard, a failure notice says so and names the way forward, with the path as selected text in it, "⌘C" on macOS and "Ctrl+C" elsewhere, and stays until dismissed (FAIL-2, FB-6, KEY-13).
  4. 4 Copy Element Path in the "No source" menu copies the element path page context sends and reports it the same way, closing after its floor of 4 s (MENU-3, FB-2, O14).
  5. 5 With the toolbar collapsed, a copy failure stays in the collapsed toolbar's one-line form beside the badge until dismissed, while successes close by themselves (SURF-8, FB-8).

5. Leftover editor settings and cursor updates

Alt + right-click and Copy Path stay, as steps 1 to 4 show. What leaves is everything that existed only to reach an editor: opening a file, the editor choice and highlight from the editor's cursor, as the product owner decided (O50, O51). A manifest written for today keeps running, and an editor plugin built on today's cursor route gets a plain 404, so neither fails silently. Nothing here writes, so there is nothing to confirm or undo.

  1. 1 A manifest that still has a [devtools.editor] table, with ide, enabled or both, keeps loading and running and prints one warning per key naming file, line, column, key and what replaced it, at start and on every hot reload that keeps it; any value warns and none is refused. devhost applies nothing from the table except enabled = false, which turns the source menu off as [devtools.componentSource].enabled = false does, so no one's off switch turns on with an upgrade (FAIL-6, FAIL-2, MENU-4, WORD-7, O51).
  2. 2 POST /__devhost__/react-highlight/cursor and the /__devhost__/ws/react-highlight stream no longer exist and answer 404 like any unknown control route; no page draws an outline from a cursor (O51).
  3. 3 Opening a file in an editor is removed everywhere: devhost starts no editor and builds no editor URL, so a missing or unregistered editor can no longer fail without a word; every flow that offered an editor shows the file and line with Copy instead (O50, O51, MENU-4, SURF-15).
  4. 4 Highlight from the editor leaves with its route, its outline overlay, its event and its guide, which removes the missed elements, the stale start-time root after a switch and the script-only source maps that highlight suffered from (O51).
