1. Point at an element

Alt + right-click still opens the source of the element under the pointer, and Select Elements and holding Alt still pick elements as page-context specifies. What changes is that the element is outlined with its role and name before the click, the gesture always answers, and the keyboard reaches the same menu. Keys: Alt + right-click (Option on macOS); with Select Elements latched on, the arrow keys walk the highlight and Shift+F10 or the context-menu key opens the source menu (KEY-12, MENU-1).

  1. 1 Holding Alt outlines the element under the pointer with its role and name before the click, drawn dashed here, by the one resolver that Select Elements, holding Alt and Alt + right-click share, which page-context owns: the element shown is the element looked up (SEL-9).
  2. 2 Alt + right-click on the app page, outside devhost's own surfaces, opens the source menu at once, also when there is no source to show (step 3): devhost takes the browser's context menu only for this gesture and always answers it (MENU-3, KEY-2).
  3. 3 With Select Elements latched on, Shift+F10 or the context-menu key opens the source menu for the highlighted element. The toggle lists Shift+F10 in its tooltip and in aria-keyshortcuts, both drawn from the binding definition its handler reads (KEY-12, KEY-13, BAR-4).
  4. 4 Alt pressed as part of a chord, or to type a character, never starts selection (KEY-2).
  5. 5 [devtools.editor].enabled stays on by default; set to false, it turns off both Alt + right-click and highlight from the editor, and the docs' settings row names both (SEL-11).

2. Find the element's source in the page's checkout

The lookup still runs in the page, still reads React's source metadata and the page's source maps, and still resolves paths in the selected checkout, as today. What changes is that React 19 development builds work without a browser extension, modules loaded through import are searched, and page context's marks use the same lookup. It stays one shared module under packages/devhost-ui/src/devtools/shared/, which the source menu and page context's marks both call, and adds no control route.

  1. 1 While a source map is read for the first time, the open menu shows "Finding the source of <h1>…" where its entries go, never an empty menu, with focus on the menu itself; when the entries arrive, they fill in place and focus moves to the first of them (STATE-1, KEY-6).
  2. 2 On React 19, the page reads the fiber's _debugStack, the stack React records where the JSX was created, whose first frame outside React is the JSX call site; React 18's _debugSource and __source come first, as today, and the React DevTools extension's renderer interface stays the last fallback. The owner chain is walked the same way, each owner's _debugStack included, and duplicates are dropped, so the menu lists the element and the components that render it.
  3. 3 Each bundle position maps back through the page's source maps, read from script elements, from modules loaded through import and chunks loaded later, from a SourceMap response header, or from the last sourceMappingURL comment whatever follows it.
  4. 4 Paths resolve in the page's checkout: the selected checkout of the repository the page's service runs from, with a path from another checkout of that repository rewritten to it, as today (SEL-3).
  5. 5 The same lookup gives page context's marks their source file, so on React 19 a mark reaches the agent with its file, and page-context's row shows it, "#1 h1 Devtools playground · PlaygroundLayout.tsx:15", or "no source found" (SEL-9).

3. Read the source menu

The menu still lists the element and the components that render it, each with its non-default props as badges and its path, and still stays inside the window and closes with Escape, a click outside or a worktree switch, as today. What changes is that it names the editor, its source and the checkout, offers Copy Path apart from opening, answers when it has no source, takes the keyboard, and keeps clear of devhost's other surfaces. It is a transient layer above the page, at the pointer, or at the highlighted element after Shift+F10. Keys: focus starts on the first item; ArrowUp and ArrowDown move, Home and End jump, a letter jumps to the next item that starts with it, so c reaches Copy Path, and Enter or Space activates; Escape, Tab or Shift+Tab closes it and returns focus to the page element that had focus before the right-click, the element itself when the click focused it, or, opened with Shift+F10, to the Select Elements toggle with the highlight kept; a click outside closes it and leaves focus where that click put it; devhost never adds a tabindex to a page element. Inside the open menu devhost keeps every key; once it closes, the page's keys work without a click (KEY-10, KEY-6, KEY-5, KEY-8, KEY-12).

  1. 1 The title names the editor and where that choice comes from, here the person's devhost config file; step 6 shows the four forms (SEL-11, CC-39).
  2. 2 The line under the title names the checkout the files are in by its checkout label (SEL-4).
  3. 3 One entry per source: the element or component name, a badge per non-default prop, as today, and the path relative to that checkout with line and column. Focus moves into the menu on open, on its first item; Enter or a click opens it, step 4 (KEY-6, WORD-8).
  4. 4 After the entries, one Copy Path item per entry, "Copy Path · <h1>", step 5. With two or more sources, "Element and components" and "Copy" head the two groups; a menu of one source has no heading (MENU-2, WORD-3).
  5. 5 The foot shows the menu's keys from the binding definitions: "↑↓ Move · Enter Open · Esc Close" (KEY-13).
  6. 6 The menu opens inside the viewport, never clipped, in the page area on the side of the pointer away from the dock, so it covers neither the notice stack nor docked chat's header, composer or decision card. It takes pointer input only where it draws, and the outline of the element it opened on stays anchored to that element while it is open. Alt + right-click lands outside an open toolbar panel, which closes as any click away closes it (SURF-1, SURF-2, SURF-9, SURF-11, SURF-12).
  7. 7 Where the page area beside docked chat is narrower than the menu, the menu narrows to it, down to 240 CSS pixels, and wraps each path onto its own line; a path longer than the menu is shortened in the middle, keeping the file name and line, with the full path in its tooltip and accessible name. Chat's composer, Send and the pending decision card stay clear (SURF-6, WORD-8).
  8. 8 When the page records no source for the element, the same menu opens, titled "No source for <div>", with one sentence naming the cause and Copy Element Path, step 5. The causes: no React component renders the element; the page's React build records no source locations; or the source map could not be read. The browser's menu is never taken without this answer (MENU-3, FAIL-2, STATE-4).
  9. 9 While the page's repository switches, the menu opens and works, and its checkout line names the checkout the page still shows with the operation in progress, because reads and hand-offs stay available during service operations; today the gesture silently falls through to the browser's menu. The page reloads into the new checkout when the switch ends, which closes the menu (HOLD-3, SEL-4).
  10. 10 With the page's selected checkout deleted, the menu lists the sources with their paths and Copy Path, and each entry's Open is unavailable, drawn dimmed, focusable with aria-disabled, with the one reason sentence in the menu's status line and as each entry's accessible description. The menu offers the lead action, Return to Configured Checkout, a link that opens the Worktrees panel with that action focused, where it asks in place as worktree-switch specifies, and Check Again, which reads the checkout list once and stops nothing (HOLD-4, HOLD-1, MENU-3, MENU-5, REV-2, REV-4).
  11. 11 After the status stream closes, the lookup, Copy Path and Open through a URL handler keep working, because they run in the page; an editor that devhost launches is unavailable with "Lost connection to devhost; retrying" in the status line and as each entry's accessible description until the stream returns. The lost-connection notice's Retry Now, notices-and-feedback's, is the way forward (HOLD-2, HOLD-1).
  12. 12 A file opens on the machine that runs the stack, so on a page opened from another machine Open is unavailable with that reason, Copy Path works, and devhost's editor launch answers 403 (HOLD-7, MENU-3).
  13. 13 A source outside the stack's checkouts, such as a linked package elsewhere on disk, shows its absolute path shortened with ~; Copy Path works, and Open works through the URL handler; through devhost's editor launch it is unavailable with that reason in the status line and as its accessible description, because the launch opens only files inside the checkouts (MENU-3, HOLD-1).
  14. 14 Alt + right-click on an element inside the page's own modal dialog opens the menu inside the dialog's top layer, where the notice stack and the announcer already move, so its items take the keyboard and the pointer and its notices are heard; the paused bar is unchanged (SURF-11, FB-9). A rejected configuration or chat that cannot take a message blocks nothing here (HOLD-6, HOLD-5).

4. Open the file in the editor

Choosing an entry still hands its file, line and column in the checkout the page runs to the person's editor. What changes is that the notice stack says what happened, opening no longer copies anything by itself, and a failure says why in words. Opening reads a file and starts no service, so it never asks and stays available while another operation runs (REV-1, HOLD-3). Nothing here writes to the stack, so there is no Undo: opening a file changes nothing devhost could take back, it writes no line in the stack's log and no operation record, and its notice says what it did. Every Open in Editor that config-editor, manifest-hot-reload, proxy-settings, worktree-switch and startup-and-recovery offer with the config editor off calls the same editor hand-off, one function under packages/devhost-ui/src/devtools/shared/ (MENU-4).   2. 2 Once the editor's command took the file, a success notice reads "Opened PlaygroundLayout.tsx:15:7 in Cursor", announced once, and closes 4 s after the pointer and focus leave it (FB-2, FB-3, FB-6, FB-9, WORD-4, O14).
  3. 3 When the editor cannot start, a failure notice says so in words, is announced once in the assertive region and stays until dismissed, with Copy Path and Copy Error, which copies the original error (FAIL-2, WORD-7, FB-6).
  4. 4 Through the editor's URL handler, the notice reads "Sent … to Cursor · devhost cannot tell whether Cursor opened", never "Opened", because a page cannot see whether a URL handler ran; it reports no failure, so it closes as a success notice does (FB-5, FB-6, O14).
  5. 5 When devhost's answer to the launch is lost, the notice says Cursor may have opened the file, offers Copy Path and stays until dismissed; the page never sends the request again by itself, because a second launch can open a second window (REV-12, FB-6).
  6. 6 With the toolbar collapsed, a failure notice from opening or copying stays visible in the collapsed toolbar's one-line form beside the badge until dismissed, and successes close by themselves (SURF-8, FB-8).

5. Copy a path

Copy Path is new as its own item: today the one entry button copies and opens at once and says nothing. Each now does one thing and says so. Copying is an action of this page, not an operation of the stack: it writes no line in the stack's log and no operation record, which FB-7 and ACT-1 keep for operations, and its notices and the announcer are notices-and-feedback's. 6. Choose your editor

The four built-in editors keep their URL handlers, and a saved editor setting still reaches open pages with the next health message, through hot reload, without a reload or a restart, as a manifest ide change does today. What changes is whose choice it is: the person's, with the team's manifest as the default, and the menu's title says which one it used. Setting the editor is a setting the person saves, never an action in the menu.

  1. 1 devhost takes the editor from DEVHOST_EDITOR, else [devtools.editor].ide in the devhost config file, else [devtools.editor].ide in the manifest, which stays the team's default, else VS Code; the control server sends the page the merged value with its source, which the title names (SEL-11, CC-39).
  2. 2 A change in the devhost config file or the manifest applies through hot reload and reaches open pages with the next health message, and leaves devhost.toml untouched; DEVHOST_EDITOR is read when the stack starts, like every environment variable of the devhost process (SEL-11).

  4. 4 Beyond the four built-in editors, any editor with a URL handler works through a url template, in the manifest or the devhost config file, and any editor with a command through command, in the devhost config file only, because it runs a command on the person's machine and needs devhost's editor launch; a command in a manifest is rejected on save with its file and line (SEL-11).

7. Highlight the element under the editor's cursor

Highlight from the editor still reaches every open page of the stack and never another stack's, still compares with React's source metadata before the source maps, still answers success once it received a well-formed update and 400 for a malformed one, and outlines still sit below the toolbar, never block clicks and clear on {"locator": null}, on the next update and when the stream drops, as documented. What changes is that it finds the element the cursor sits in, compares with the checkout the page runs, also after a switch, and keeps the outline on its element. Nothing here writes to the stack, so there is no Undo. A cursor on a component tag, <PlaygroundLayout />, renders no element of its own: without React's source metadata the event says component-tag and nothing is outlined; with it, every element the component renders is outlined, as today.

  1. 1 An editor plugin or script publishes the cursor as file:line:column, as today.
