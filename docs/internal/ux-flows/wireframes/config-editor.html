TLDR: The Configuration window opens at the problem it was opened for, lists every problem on the line where the fix goes, states beside Save what saving will restart, reports each save's own outcome there, and keeps drafts and the way back to what the stack runs through reloads, disk changes and rejections.

Low-fidelity wireframe. Layout, names and numbers are illustrative; the redesign ticket's acceptance criteria are authoritative.

1. Turn the editor on

The editor stays off by default and is turned on by writing [devtools.configEditor] enabled = true in a manifest with any editor, as today; hot reload applies it and every config route answers 404 while it is off (owner rule). What changes is what Config says while the window is closed and what every problem report offers while the editor is off. Keys: Alt+Ctrl+B focuses the bar; Config is an arrow stop (ArrowLeft, ArrowRight, Home, End); Enter or Space opens the window (KEY-3, KEY-4).

  1. 1 Config appears on every open page of the stack with the next health message, without a page reload, as today. Its tooltip, toolbar-shell's words, says what it edits: "Edit this stack's configuration: its manifest files and the devhost config file" (WORD-1).
  2. 2 Config counts the files that hold drafts, "Config · 2 unsaved", and its accessible name lists them, so drafts kept on the control server are never invisible (ACT-7, UNDO-2).
  3. 3 While a manifest file or the devhost config file is not applied, Config keeps the not-applied look, told by its shape ◆ and the text "1 not applied", the marker notices-and-feedback words, in every tab until a reload of that source is accepted, also while the window is closed (ACT-7, SURF-8, ACT-13).
  4. 4 Collapsed, toolbar-shell's badge takes the rejected-configuration look in ACT-7's order, and the rejection's notice stays in one line beside it; its Edit opens the window at the problem (step 3) (SURF-8, MENU-4).
  5. 5 With the editor off, every surface that reports a manifest or devhost config file problem (the rejection notice, the crash view, a failed Services row) shows the file and line with Copy and Open in Editor, which hands off to the editor that DEVHOST_EDITOR, the devhost config file or the manifest names, at that line, and names the setting that turns the editor on; there is no Edit (MENU-3, MENU-4, SURF-15, SEL-11).
  6. 6 On a page opened from another machine, Config is unavailable with the reason "The configuration is available on this machine only" as visible text and as its accessible description, and the window does not open (MENU-3, HOLD-1, WORD-7). If the product owner keeps today's remote reads, the window opens there instead, with Save unavailable from the moment it opens and "Saving works only from this machine" (HOLD-7).

2. Open the Configuration window

Config still opens the Configuration window over the page, and closing it still keeps every draft. What changes is that the window is a real modal dialog (aria-modal="true", opened with showModal()): the page, the bar, the notice stack and docked chat are inert behind it and Tab never leaves it, where today focus wanders into the page. It never shows an empty, disabled box. Keys: focus starts in the text, where Tab and Shift+Tab indent and outdent; Escape in the text moves focus to File; outside the text, Tab cycles File, Revert, Save, Close and the banner's actions and back to the text; Escape outside the text, Close or a click on the backdrop closes the window with every draft kept, and focus returns to Config, or, when the window was opened with the pointer, to the page element that had focus before (KEY-5, KEY-6, KEY-7, KEY-8).

  1. 1 The header names the window, then the selected file's role, short path and the checkout whose manifest it edits; after a switch it reads "fix-nav ~/acme/.worktrees/fix-nav" (SEL-4).
  2. 2 The header actions File, Revert, Save and Close keep their size and stay in view whatever the body holds, at every acceptance viewport; only the text and the problem list scroll (SURF-9).
  3. 3 Drafts restored from the control server are named in one line under the header (UNDO-2, CC-19).
  4. 4 Focus moves to the file's text on open (KEY-6, SURF-4).
  5. 5 The hint line names the keys in the platform's notation, from each binding's one definition; elsewhere it reads "Tab indents · Ctrl+M Tab moves focus · Esc File list · Ctrl+S Save". Ctrl+M (⌥⇧M on macOS) switches Tab between indenting and moving focus (KEY-13, KEY-7).
  6. 6 The window's height stops above the notice stack, in either corner placement, so every notice's text stays visible beside it; the notices are inert while the window is open (SURF-1, SURF-4, SURF-9, KEY-7).
  7. 7 While an operation runs on the stack, one header line names it with its progress, and the text stays readable and editable (HOLD-3, HOLD-1).
  8. 8 The frame shows at once with "Loading devhost.toml…" where the text goes: the files route answers from a snapshot without waiting for the running reload, restart or switch (STATE-1).
  9. 9 A window that cannot load says once what failed and the next step, built from the cause the backend sent, never a response body; Copy Error holds the original text, and the same sentence is the accessible description of the unavailable Revert and Save. The header actions stay inside the window, and focus is inside it, so Escape closes it (STATE-4, FAIL-2, HOLD-2, HOLD-1, SURF-9).
  10. 10 Drafts and files the window already held stay readable, marked with their age (STATE-3, STATE-4).

3. Open the window at a problem

Edit in the rejection notice still opens the window, and Config still opens it from the bar. What changes is that every entry point to a problem (the rejection notice, the crash view, a failed Services row, Config while a service is exited) opens the file that holds it, at its line, with the context in a banner inside the window, from one structured error: file relative to the root manifest, line, column, key and message (MENU-4, SURF-4). Keys: focus starts in the text at the problem; the banner's actions are Tab stops after the header actions (KEY-6, KEY-7).

  1. 1 A rejection's banner names the file, line and key, words the cause key first and says the stack still runs the accepted manifest; it stays in the window until a reload of that source is accepted, also after the window closes and opens again. A rejection that no single file holds lists the files involved (FAIL-2, WORD-7, HOLD-6, ACT-7).
  2. 2 The window opens on admin/devhost.toml, not on the file shown last, scrolled to line 4 with the line marked ✕ in the gutter and the cursor at its column (MENU-4).
  3. 3 Edit in the crash view, on a failed Services row and Config while api is exited open api's definition with its evidence in the banner: the exit with its time and cause, its own last output lines frozen at the exit, and what devhost ran (FAIL-3, SURF-4).
  4. 4 Restart api, MENU-5's lead action for an exited service, hands off to the restart services-panel owns and shows its progress and outcome in the banner; Show All Output expands api's whole output in place. The window has no other log view: other services' output is read in the pinned log panel after the window closes with drafts kept (MENU-5, WORD-2, SURF-13).
  5. 5 The [services.api] header and its command line are marked in the gutter, and the File list marks devhost.toml "defines api, which exited" (step 4). A save that changes api's definition restarts it anyway, so the banner then reports that save's outcome for api.
  6. 6 Edit in the crash view first minimizes the crash view to its notice, which stays in the inert notice stack; closing the window returns focus to that notice (SURF-3, KEY-6). The crash view's own actions follow MENU-5, which startup-and-recovery owns, with Edit leading after a retry that failed the same way.
  7. 7 A report that needs the person while the window is open (a failure, a waiting agent, a rejected configuration) is announced once from inside the window, which holds the announcer, and shows as one line in its header; focus stays in the text, and the crash view opens minimized as its notice (SURF-4, FB-9, KEY-7, SURF-3).

4. Pick a file

File still lists the stack's root manifest, its includes and the devhost config file, and switching files still keeps each file's draft. What changes is that each option says what the file is and what state it is in, the list groups and filters them, and switching files keeps each file's last save outcome too (UNDO-2, UNDO-8). Defaults: the window opens on the file of the problem it was opened for, else the file shown last, else the root manifest. Keys: ArrowUp and ArrowDown move the highlighted file, Enter picks it, Escape closes the list and keeps focus on File (KEY-10, KEY-8).

  1. 1 File is a combobox whose field and list sit in one shadow tree; its options are grouped by role, "This stack" and "This machine", each header with its count (KEY-10, SEL-10, WORD-1).
  2. 2 Each option's role, short path and state ("unsaved", "applying", "applied", "not applied", "defines api, which exited") are text in the option and in its accessible description, never only on hover (WORD-8).
  3. 3 The devhost config file says that every stack on this machine shares it (SEL-11, WORD-1).
  4. 4 When the files outgrow the list, it gains a find field, focused on open, that filters by path and role as the person types and keeps the group headers with their counts (SEL-10, SURF-10).
  5. 5 A find with no match names what was searched, with Clear Filter (SEL-10, STATE-2).
  6. 6 A long path is shortened in the middle, with the full path in the trigger's tooltip and accessible name; the trigger never grows past its slot, so Revert, Save and Close stay in the window at every acceptance viewport (WORD-8, SURF-9).
  7. 7 With the devhost config file selected, a neutral line under the header says how far its changes reach (SEL-11).

5. Edit with every problem and the save's reach in view

Checks still run while the person types and never write, and completions still offer tables, keys and fixed-choice values, as today. What changes is that one check lists every problem a reload would find, each on the line where the fix goes and in plain words, and that the window states beside Save what saving will do (POST /__devhost__/config/validate, read only). Keys: Ctrl+Space (⌥I on macOS) lists completions; Enter breaks the line; Mod+S saves; CodeMirror's Alt chords stay inside the text, page-wide chords are suspended while the window is open, and keys typed into the text never reach the page's listeners in any phase (KEY-1, KEY-2, KEY-5, KEY-9, CC-28).

  1. 1 Beside Save, one line states what saving the draft will do, from the backend's check of it: each service it restarts and why (changed, depends on a changed service, same repository), the page's own service first; services it starts or stops; for the devhost config file, the stacks whose URLs move; a return to the configured checkout; the editor turning itself off (REV-10, SEL-1, SEL-11, O9).
  2. 2 Completions and problem tooltips open inside the viewport, above the cursor when the room below is short, and are never clipped by the window (SURF-9).
  3. 3 After each pause in typing, one check returns every problem in one list ordered by line: settings and values, dependency cycles, ports and working directories. Each is marked where the fix goes, worded key first and fix last, with the file relative to the root manifest, never an absolute path, a parser prefix or a Go error chain; a cycle marks the dependsOn line of each service in it. The list never covers the line holding the cursor (FAIL-2, WORD-7, WORD-8).
  4. 4 A problem in another file is listed with that file and Open, which shows it at its line; a problem with no position is listed without a marker, never on line 1 (MENU-4).
  5. 5 Only a TOML syntax error stops the later checks: it is marked at the end of the line it belongs to, and the list says the rest of the file waits for it.
  6. 6 These lines are statements, never a question: Save stays available beside each (REV-10, REV-1).
  7. 7 While the stack runs another operation, the check waits for it and the list says so instead of keeping old markers silently (HOLD-3, STATE-1).

6. Save

Save or Mod+S still writes the file at once, through every guard it has today: a browser on this machine only, the version the draft was based on (409 with the file on disk, draft kept), the reload's own checks (422 with the problems, draft kept), and an atomic write that keeps the file's mode and follows a symbolic link; the watcher still applies the write like any other (POST /__devhost__/config/save with an operationId, one write applied through hot reload). What changes is that the save gets its own operation record (202 Accepted) and shows its own progress beside Save (ACT-1, REV-12, CC-37). Keys: the pressed Save keeps focus; in the question, Enter takes Review Drafts; Escape, or a click elsewhere in the window that lands on no control, cancels it and returns focus to Save; a click on another control cancels it and that control acts; closing the window cancels it with the window (KEY-11, REV-4, KEY-8, KEY-6).

  1. 1 A save runs on one press, because a save is reported, never reviewed. The pressed button keeps focus, aria-busy and aria-disabled, never disabled, and names the save; beside it the progress updates at least once a second (REV-1, REV-10, KEY-11, FB-9, FB-1).
  2. 2 One row per touched service shows its step: stopping, starting, "health check 2 s of 30 s", running (FB-1, ACT-3, WORD-4).
  3. 3 While that file's save is in progress, its Save is unavailable with this reason as visible text and accessible description; Mod+S then announces the reason and sends nothing (MENU-3, HOLD-1).
  4. 4 A save made while another reload runs waits for it and says so, then is reported with its own reload, never with the one that was running (REV-12, HOLD-3).
  5. 5 A save that turns the config editor off while other files hold drafts asks in place: Save expands inside the window into one sentence naming the drafts it puts out of reach, a group labelled by that sentence (REV-3, REV-4, SURF-2). Without other drafts the same save runs on one press.
  6. 6 Review Drafts takes Save's place, focused and taking Enter, and shows admin/devhost.toml; the confirming Save Anyway sits beside it (REV-4, WORD-2).
  7. 7 From the moment the status stream closes, Save and Restore Running Version are unavailable with the one reason the backend sent, said once in the header with Retry Now, because the window makes the notice stack and its own Retry Now inert; drafts stay and are written to the control server with their revision when the stream returns (HOLD-2, ACT-5, HOLD-1, MENU-3).
  8. 8 The stack's terminal and its log print the same one outcome line for this save as for any save of the file, with its origin, in notices-and-feedback's words; a script or an agent that saves through the config route gets the same 202 record and reads the outcome from the health stream (FB-10, FB-7, FB-11).

7. Read the outcome beside Save

A rejected reload still keeps the stack on the accepted manifest, and the toolbar still shows the rejection, as today. What changes is that the outcome belongs to this save: it replaces the progress beside Save only once the reload that read this saved version ended, names each restart, and stays with its file (the operation record on /__devhost__/ws/health, read only; FB-2, FB-5, REV-12). There is no Undo save: the outcome phase holds devhost's rollback, which restores the accepted manifest by itself, and step 8's way back to what runs (UNDO-1, UNDO-6). Keys: focus stays on Save (KEY-11).

  1. 1 Success names each restarted service with its reason, the running count and the time, or "Applied devhost.toml: nothing restarted · 0.4 s"; a service with a process health check counts as started only after it stayed up for O28's 1 s. It is announced once in the polite region and stays while the window is open (FB-3, FB-5, FB-6, WORD-4, O28, O9).
  2. 2 When a restarted service fails, the reload rolls back and the progress says so (UNDO-1).
  3. 3 Not applied: the failing service with its exit, its own last output lines and what devhost ran, every touched service with its own result, and what the rollback restored. It is announced once in the assertive region, never as "Applied", and the cause sentence becomes Save's accessible description (FAIL-1, FAIL-2, FAIL-3, FB-9, KEY-11).

8. Recover a file that is not applied

A rejected reload still keeps the accepted manifest running and blocks nothing: Save, Restore Running Version and every toolbar action stay available (HOLD-6). What changes is that the window tells the version on disk apart from the version the stack runs and offers the way back to the second, and that a change on disk or in another tab never replaces a draft without a choice (Show Differences, read only; Restore Running Version, one write applied through hot reload). Keys: the banner's and the question's buttons are Tab stops after the header actions; in the Keep Mine question, Enter takes Cancel, and Escape, or a click elsewhere in the window that lands on no control, cancels it and returns focus to Keep Mine (REV-4, KEY-8).

  1. 1 A file whose last reload was not applied is a state of its own: the banner says that the file on disk differs from what the stack runs, and the text never reads as saved and applied (UNDO-6, HOLD-6, WORD-7).
  2. 2 The way back is to what runs: Show Differences and Restore Running Version. devhost never writes the running version back by itself, because the rejected text is the person's work (UNDO-6).
  3. 3 The lines that differ from the running version are marked ◆ in the gutter. Revert discards a draft and shows the version on disk, read again when it is pressed, never the version the window opened; it never asks, and Mod+Z in the text brings the discarded draft back (O29, UNDO-6).
  4. 4 Show Differences shows the running version beside the version on disk, read only, in the shared diff view.
  5. 5 Restore Running Version writes the running text back over the current disk version as an ordinary save (version-checked, checked, applied through hot reload, with progress and outcome beside Save) and reports what it restored; the rejection then clears from the window, Config and the toolbar notice, announced once. A repeated rejection with the same error updates its report, "· 2 times, last at 14:05". There is no Undo save: the editor's undo history survives a save, so an applied save is undone by undoing the text and saving again, which reports its own reload (UNDO-6, FAIL-4, ACT-7, REV-10).
  6. 6 Every reload record names the file versions it read, so the window learns of a change on disk within a second, without polling. With a draft, it says so at once and never replaces or drops the draft: Compare shows the disk version beside the draft, Keep Mine asks, and Use Disk Version loads the disk text (UNDO-3, REV-13). A save refused because the file changed meanwhile keeps the draft and offers the same choices.
  7. 7 Keep Mine asks in place, naming what it overwrites, with Cancel in its place, focused and taking Enter, and the confirming Keep Mine beside it; it then saves the draft over the disk version through the same checks (UNDO-3, REV-4).
  8. 8 A draft another tab changed meanwhile is never overwritten in either tab: each draft carries a revision, and the window offers Compare, Keep Mine, which asks the same way, and Use Other Version (UNDO-2, CC-19).
  9. 9 Without a draft, the disk text loads in place and the window says so (UNDO-3, WORD-4).
