Install devhost and the shared HTTPS proxy

TLDR: Help, docs and output teach one setup order (download, then start, whose first start trusts devhost's certificate authority only when a person is at the terminal), every command ends with one line saying what it did, who can reach the proxy and what comes next, the trust commands refuse agents, show what they install and name how to remove it, devhost caddy stop names every stack it takes offline before it acts, and the Install page says how devhost itself updates.

Low-fidelity wireframe. Layout, names and numbers are illustrative: acme.test hostnames stand for the default local hostnames the proposal uses (devhost.acme.test is the stack directory's). The redesign ticket's acceptance criteria are authoritative.

Docs › Install › Update devhosta new section after Prepare Caddy
Update devhost 7

A release archive installed in a folder you can write, such as ~/.local/bin, updates with devhost upgrade, which downloads the latest release, checks it against SHA256SUMS, replaces the binary and restarts your running stacks onto it.

When dotfiles, a package manager or your own build installed devhost, or the folder needs sudo, such as /usr/local/bin, update it the way you installed it, then run devhost restart-all, which restarts every running stack onto the new binary.

Both leave serve sessions running until you restart them. Neither updates Caddy: run devhost caddy download again for that. 8

1. Read one setup recipe

devhost caddy --help, the Install page, the managed-Caddy guide, the README's install block and the agent skill stay where they are, and devhost --help gains a Quickstart, which it lacks today. What changes is that all of them teach one order, and that order works on a new machine: download (skipped when Caddy is on the PATH), privileged-ports on Linux, then start, whose first start trusts the certificate authority. Today devhost caddy --help says "Download and trust it once, then start it", and that trust step fails because Caddy is not running yet. devhost caddy trust leaves the recipe and stays as the repair command (step 6). Reading help writes nothing. Keys: none; terminal and docs only.

  1. 1 The Quickstart's Caddy lines read download, privileged-ports and start, the docs' order; devhost caddy trust is not among them (MENU-6, WORD-9).
  2. 2 Each line says beforehand which step asks for a password; no help screen teaches a step that fails on a new machine (WORD-9).
  3. 3 Caddy's steps come first; stack-run-stop owns the lines from devhost init on, which writes a starter devhost.toml (O52).
  4. 4 devhost caddy --help opens with the recipe and says when devhost caddy trust is needed, followed by proxy-settings' line naming the devhost config file (MENU-6, SURF-15).
  5. 5 Every subcommand's line uses the name the docs and the output use ("the shared Caddy" in help and docs, "Caddy" in output, never "managed caddy") and says what downloads and what asks for a password; privileged-ports keeps the line proxy-settings words (WORD-1, WORD-3, WORD-9).
  6. 6 The Install page already gives this order and keeps it; the README's one install line gains the password comment, a correction of the block's text, not a new section. The managed-Caddy guide and the skill give the same order (MENU-6).
  7. 7 New: the Install page says how devhost itself updates. A release archive in a folder the person can write updates with devhost upgrade; dotfiles, package managers, local builds and folders that need sudo update their own way, then run devhost restart-all. stack-run-stop owns both commands' behavior and output; the "Download the binary" section adds that devhost upgrade can replace the binary only in a folder writable without sudo (O18).
  8. 8 Neither command updates Caddy, which keeps its own update: devhost caddy download, then a Caddy restart (step 2) (O18, UNDO-5).

2. Download Caddy

devhost caddy download still fetches the Caddy build for this platform from caddyserver.com into devhost's state directory; devhost still prefers that copy over a caddy on the PATH and never downloads Caddy by itself. What changes is that it says what it fetches, shows its progress, checks the file and only then puts it in place, so a rerun never breaks a running Caddy; today it holds the whole download in memory and writes it over the installed binary in place, ending with "Caddy downloaded to" and a path. One write: the managed Caddy binary. Keys: Ctrl-C cancels and keeps the installed binary (KEY-14).

  1. 1 Before anything arrives, one line says what downloads and from where (WORD-9; the size is not known yet, see the conflict above).
  2. 2 On a terminal one status line updates in place with what has arrived and the elapsed time, "12 of 48 MiB · 3 s" when the server sends a length; without a terminal, one plain line every 10 MiB (FB-10, STATE-1).
  3. 3 devhost writes a temporary file beside the binary, makes it executable, runs it once with version to prove it is Caddy for this platform, and only then renames it over the installed file. The outcome prints after that, verb first, with version, path, size and time (FB-3, FB-5, REV-11, WORD-4, WORD-8).
  4. 4 With a caddy also on the PATH, one line says which one devhost uses and which it leaves alone (WORD-9).
  5. 5 A rerun compares the new file's SHA-256 with the installed one and says whether anything changed; an identical download leaves the file and its inode as they were.
  6. 6 The rename gives the installed path a new file, so a Caddy running from the old one keeps it, macOS checks the new signature from scratch and Linux never answers "text file busy". The outcome says the running version stays until a restart and prints the restart command on its own line (FB-5, UNDO-5, WORD-8).
  7. 7 On Linux, replacing a binary that held the low-port grant ends with proxy-settings' line.
  8. 8 Every failure removes the temporary file, leaves the installed binary untouched and says so under the [ERROR] label, with a first download ending "· no Caddy is installed"; devhost never retries a download by itself (FAIL-2, WORD-7, REV-12).
  9. 9 Ctrl-C removes the temporary file and reports a cancel without an error tag, exit 130, because a cancel is not a failure (KEY-14, FAIL-5).
  10. 10 Agent output prints the start line and the outcome with absolute paths and no progress line; a failure keeps its original error on one devhost: ERR: line (WORD-9, FB-11).

3. Start Caddy

devhost caddy start still renders every stack's routes and starts Caddy under the route lock every devhost process shares, still uses the downloaded Caddy before the one on the PATH, and still never downloads Caddy; devhost serve starts Caddy the same way and prints the same lines. A first setup is devhost caddy download (step 2), then this start with its trust step (step 4); devhost start never downloads or starts Caddy and appears here only for its refusal and, in step 4, its trust warning; the reference's wireframe line for this flow asks for a devhost start that downloads Caddy, which no command does, so this page follows the product. What changes is that the start checks for a Caddy executable before starting anything, reports success only once Caddy listens, and ends by naming which Caddy runs, who can reach it and what to do next; today it ends with "managed caddy started with" and the Caddyfile's path. One write: starts Caddy. Keys: none here; at the trust step's prompt, step 4's.

  1. 1 The outcome names the version and the binary that runs, the downloaded one or the one "on your PATH", and prints only once the admin API answers and the HTTPS listener accepts a connection (FB-3, FB-5, WORD-4).
  2. 2 proxy-settings' line, worded there and printed here: where Caddy listens, who can reach it, the settings file and how to stop it. By default Caddy listens on every interface, as documented (FB-10, O39).
  3. 3 Last, the stack directory in its page's words, "All stacks on devbox", with its URL from the shared Caddy settings and the next command, because devhost never opens a browser; devbox is the machine name (machineName, else the host name up to its first dot). With the authority untrusted, step 4's trust step prints just before this line (SURF-15, O61).
  4. 4 Agent output carries the same facts with absolute paths, and the Caddyfile's path, which leaves human output (WORD-9, FB-11).
  5. 5 A loopback listener says that only direct connections from this machine reach Caddy, and that relay previews and SSH forwards still do (O39).
  6. 6 On macOS, a loopback setting below port 1024 still starts Caddy, on every interface, and one warning names the fix on every start; nothing is refused, so existing port-443 setups keep working. Today macOS drops the loopback setting on every port without a word (O39, WORD-7).
  7. 7 A start while Caddy runs names it by version and PID and starts nothing; after a download replaced the binary, it says how to restart onto the new version (UNDO-5, WORD-8).
  8. 8 With no Caddy executable nothing starts, and the error is devhost's: both places it looked and the command that installs Caddy, never under the caddy label and never pointing at log files this attempt emptied (FAIL-2, MENU-5, WORD-7).
  9. 9 Another failure quotes what Caddy said and the log it came from, named only when this attempt wrote to it; Linux's port 443 case keeps its next step, devhost caddy privileged-ports (FAIL-2, FAIL-3).
  10. 10 A rejected devhost config file names its file, line, column and key, and no Caddy starts (MENU-4, FAIL-2, WORD-8).
  11. 11 The route lock still refuses shared Caddy changes from a devhost older than the one that started Caddy; the refusal now names the update paths instead of "Upgrade this devhost instance" (FAIL-2, WORD-7, O18).
  12. 12 A stack still never starts a stopped Caddy: devhost start keeps today's refusal and names the command. Every human failure keeps today's [ERROR] label (WORD-7).

4. Trust the local certificate authority

The trust step is still part of devhost caddy start, and of a devhost serve that starts Caddy: devhost checks Caddy's root against the system roots and runs Caddy's own trust installation only when standard input is a terminal and AGENT=1 is unset, as today. Without a person, Caddy keeps running untrusted and the start succeeds (product rule). What changes is that the step says what it installs before the prompt, names what it trusted and how to remove it, and the warning says why devhost did not ask; today one sentence, "managed caddy local CA is not trusted, … Run 'devhost caddy trust' to trust it.", serves every cause and tells an agent to run the command. Terminal lines say "this machine" for the machine the command runs on (O61). One write: the system trust store; it asks every time, and only a person at a terminal can answer (REV-1, REV-8). Keys: Ctrl-C at the prompt skips trust (KEY-14).

  1. 1 One line before the prompt names the root, its state directory, the trust store and that the next prompt asks for the password (REV-8, WORD-9).
  2. 2 sudo's prompt keeps its caddy | label.
  3. 3 Success names what it installed and its expiry, then the full SHA-256 of the DER certificate in openssl's form (abbreviated here), so it can be told apart from same-named roots of other state directories, then the command that removes it on its own line; devhost records the root for step 8. There is no Undo: devhost caddy untrust is the way back (UNDO-5, WORD-8).
  4. 4 Without a person, one warning stands out from the lines around it: on a terminal that shows color, the [WARN] label and its sentence print in the warning color, never only a prefix (FAIL-2, WORD-7).
  5. 5 Its second line names the cause in one sentence.
  6. 6 The repair command prints on its own line, so it never breaks across lines, even at 80 columns (WORD-8).
  7. 7 Ctrl-C at the prompt ends only the trust command: devhost and Caddy keep running, the warning names the cancel, and the start exits 0, because Caddy runs (KEY-14, FAIL-5).
  8. 8 The warning repeats on every devhost caddy start, every devhost serve that starts Caddy and every stack start while the authority stays untrusted, as today, each time with its cause.
  9. 9 Agent output never asks and tells the agent to ask the person, never to run the command itself, because the trust commands refuse an agent (step 6) (REV-8, WORD-9, FB-11).

6. Repair trust later

devhost caddy trust stays the command that repairs an untrusted authority; it still needs Caddy running and still reports an authority that is already trusted instead of prompting. What changes is that it says why it needs Caddy and offers the start, prints step 4's lines, and refuses an agent before any sudo, so a cached sudo ticket never lets an agent install a root unseen; today it runs Caddy's sudo trust for an agent as for a person. One write: the system trust store; it asks every time, and only a person at a terminal can answer (REV-1, REV-8). Keys: none of its own; sudo's prompt reads the password.

  1. 1 At a terminal it prints step 4's line before the prompt and step 4's outcome after it, with the fingerprint and devhost caddy untrust (REV-8, UNDO-5).
  2. 2 An authority that is already trusted is reported in words, nothing changed, as today.
  3. 3 With Caddy stopped it refuses with nothing changed, says why and offers the start, which also trusts the authority, on its own line (FAIL-2, MENU-5, WORD-8).
  4. 4 Under AGENT=1 it refuses before any sudo, exits 1 and tells the agent to ask the person; untrust and trust-remote refuse the same way (REV-8, CC-13).
  5. 5 Without a terminal and without AGENT=1, as in a provisioning script, it runs only when sudo needs no password (sudo -n true succeeds, or devhost runs as root); otherwise it refuses before sudo and exits 1, so a script never hangs on a prompt nobody sees (REV-8).

7. Trust another machine's authority

devhost caddy trust-remote stays macOS-only, still fetches the root over SSH from a machine that has devhost on its PATH, and still installs it into the System keychain; print-root-cert without the flag still prints the PEM certificate. What changes is that it shows what it would trust and what that allows, and asks before it installs; today it prints a hash of the PEM text as "sha256" and installs at once. One write: the System keychain, after a question that only a person at a terminal can answer (REV-1, REV-8). Keys: only y or yes adds the root; Enter alone, end of input or anything else is No (REV-4, KEY-14); --yes skips the question, for scripts (CC-13).

  1. 1 It names the SSH command before running it (WORD-9).
  2. 2 What it would trust: the root's name and expiry, then the full SHA-256 of the DER certificate on its own line (abbreviated here), never today's hash of the PEM text (REV-8, WORD-8).
  3. 3 How to check it: the command that prints the same value on devbox.
  4. 4 What the trust allows, in one sentence.
  5. 5 The set first and the question last, on one line ending in [y/N] (REV-4, SURF-2).
  6. 6 The outcome names what it trusted and the command that removes it; devhost records the root for step 8. There is no Undo: devhost caddy untrust is the way back (UNDO-5).
  7. 7 On devbox, --fingerprint prints the name, expiry and the same fingerprint, so the person compares two screens instead of trusting one (WORD-8). CC-13 does not name the flag yet; the reference's author adds it beside trust-remote's row.
  8. 8 Any answer but y or yes, an empty one and end of input included, changes nothing and exits 1 without an error tag, because a No is not a failure (REV-4, FAIL-5).
  9. 9 Under AGENT=1 it refuses before ssh and sudo, as devhost caddy trust does (REV-8).
  10. 10 When devbox cannot be reached, it names the target, the command and its exit code, and what to check, with nothing trusted (FAIL-2).

9. Stop Caddy

devhost caddy stop still stops the shared Caddy, every stack's services still keep running, devhost caddy start still brings their routes back from the route files, and a stop while Caddy is stopped still changes nothing. What changes is that it names everything it takes offline before it acts, tells each running stack why its routes stop, and reports what it did; today it prints only "managed caddy stopped.". It acts without a question, in a terminal and under AGENT=1 alike, because stopping Caddy ends no agent's turn, no service and no conversation (REV-1, REV-7, O33); the reference's wireframe line for this flow still asks for a question here, against its own proposal line and O33. One write: stops Caddy and takes every stack's routes offline; there is no Undo: devhost caddy start is the way back (UNDO-5). Keys: none; it never reads standard input.

  1. 1 The set prints first: how many stacks and serve sessions go offline, and that their services keep running (SEL-6, BAR-2, WORD-5).
  2. 2 One line per stack and session: the stack's name, its worktree label, PID, foreground or detached, and its hostnames, a long list collapsed to "+3" (SEL-4, SEL-6, WORD-1, WORD-11).
  3. 3 Before Caddy stops, devhost writes a stop record beside Caddy's PID file (by devhost caddy stop, when, and from a terminal or an agent) and tells each running stack; the outcome counts what went offline and says how to bring it back (FB-3, WORD-4, UNDO-5).
  4. 4 --dry-run prints the set and changes nothing (SEL-6, CC-12).
  5. 5 Agent output lists the same set with each manifest's absolute path, the PID and every hostname (WORD-9).
  6. 6 The stop tells every stack at once and waits at most 1 s in total, however many stacks run; each stack that did not answer gets its own line after the set.
  7. 7 Each stack's terminal and log tell this stop from a Caddy that exited on its own, and say when the routes answer again; stack-run-stop prints these lines (ACT-10, FAIL-5, FB-7).
  8. 8 Its open pages show notices-and-feedback's lost-connection notice with this cause and the start command to copy, every service drawn unknown, never down, and every write blocked (HOLD-2, ACT-5).
