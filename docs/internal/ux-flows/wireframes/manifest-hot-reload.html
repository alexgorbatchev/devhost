1. Save a manifest file from any editor

Saving devhost.toml or an include from a text editor, the Configuration window, git or an agent still applies through hot reload 200 ms after the last write, without a question, and every manifest setting still applies this way, never "restart to apply" (owner rule; REV-10). What changes is that the save becomes one operation with one name on every surface, its reach can be read before the file is written, and a save no reload reads within 5 s while the stack is idle ends unseen with a remedy (O42). Keys: none of its own; the save is the editor's, and the notices it raises are reached as step 5 says.

  1. 1 A save of the root manifest or an include, or a file that starts or stops matching an includes pattern, starts the reload. The services runtime opens one operation record for it; a save from outside devhost's UI is recorded with the origin "after devhost.toml changed on disk", because the watcher cannot tell an editor's save from an agent's edit or a formatter. If no reload reads a written save within 5 s while no operation holds the stack, it ends unseen: "devhost did not see this save; the stack still runs the accepted manifest. Apply it with devhost reload in ~/acme" (REV-10, ACT-1, WORD-4, O42).
  2. 2 No page shows a question, a modal or a confirm(): a hot reload is reported, never reviewed. Its label is Apply devhost.toml, the file the save changed, on every surface, and its outcome reads "Applied". Starting and restarting services ends nothing of an agent's, so a save asks about no agent (REV-10, REV-1, REV-3, WORD-2, WORD-1).
  3. 3 The Configuration window states the reach beside Save, which stays available: config-editor's statement, read from the same plan the reload uses. Authenticated remote browsers (passkey or devhost pair, O36, O38, O54) save identically. The one question a save can meet is config-editor's, when the save turns the config editor off while other files hold drafts (REV-10, REV-3).
  4. 4 devhost reload --dry-run, with --stdin for text not written yet, prints the same plan from the same check and changes nothing. Defaults: the restart scope is O9's decided scope (the changed services, their dependents and, with worktrees on, every service of the same repository), and the reload keeps the run's service selection, so a service left out of the run stays not started (O9, SEL-11, SEL-7, FB-11, CC-23).

2. Check everything before anything stops

devhost still re-reads the root manifest and every include, validates the merged result, and claims new hostnames and fixed ports against other stacks before it stops a service, as today. What changes is that it also probes each new or changed fixed port on its bind host, both loopback addresses included, and a refusal names the check and what holds it. The plan names each service with its reason (changed, depends on a changed service, same repository, added, removed) and non-restart effects such as toolbar feature changes or returning to the configured worktree; declaring an external service never disables worktree switching (SEL-1, SEL-11, FB-3, O7). Keys: none; the checks run on the save.

  1. 1 A failed check refuses the reload with nothing stopped, every PID unchanged, as devhost's own block: the file, line, column and key, the program that holds the port with its PID, the way out, and that the stack still runs the accepted manifest (REV-11, FAIL-2, WORD-7, HOLD-6).
  2. 2 Every open page shows the same refusal as the rejection notice of step 5, with Edit first (or file and line with Copy when the config editor is off, O51); every service keeps running, because nothing stopped (HOLD-6, ACT-7, MENU-4).
  3. 3 When the holder starts listening only after the probe passed, the failed health check names it, never "Check the app's startup logs", and the reload rolls back (step 3) (FAIL-3, REV-11).
  4. 4 A service that was failing before the save and is unchanged by it is never a condition of the reload's success: it keeps failing with its recovery page, the rest applies, and the outcome counts it. The error-pages-01 stopgap ships this part first (REV-11, UNDO-1, FAIL-1).

3. Watch the reload restart its set

The reload still stops dependents first and starts services in dependency order, each after its health check, keeps automatic ports and the run's selection, and rolls back on failure, as today. What changes is that it names its set when it starts (using the settled label Apply devhost.toml across every surface), shows its progress in one place on every page, and never draws a service it replaces as failed. Keys: Cancel Restart is a Tab stop on the queued row, as services-panel draws it; no report here takes focus (FB-9, KEY-11, WORD-2).

  1. 1 One devhost line names every service the reload restarts with its reason. No exit line is printed for the services it stops: those stops are steps of the reload, never exits waiting for a restart (FB-10, FAIL-5, WORD-7, SEL-1).
  2. 2 No devhost surface on the page started this save, so the notice stack shows one activity line, updated at least once a second, on every open page of the stack; a Configuration window that saved the file shows the same progress beside Save instead, never both (FB-1, WORD-4, STATE-1).
  3. 3 The trigger's dots show 2 running and 4 restarting, and its accessible name reads "2 of 6 running · 4 restarting", never "0/6": devhost stops the whole set, dependents first, then starts it in dependency order, so services already started run again while the rest wait their turn. Every service outside the set keeps its own state, and the status stream stays open, so nothing is drawn unknown or down (ACT-3, ACT-4, ACT-2, ACT-5, HOLD-2, BAR-1).
  4. 4 Each touched row shows restarting with its step: stopping, queued for its turn, starting with its health check, then running. A restarted service with a process health check counts as started only once it has run for O28's decided 1 s window; one that exits sooner fails the reload with its exit code and last lines (step 5). Its changed mark clears against its new launch (FB-5, O28, ACT-8).
  5. 5 Restart on a service the reload is restarting is unavailable with "worker is already restarting · Apply devhost.toml" as visible text and as its accessible description (REV-12, HOLD-3, HOLD-1).
  6. 6 A stack-wide write, such as Restart Stack or a switch, is unavailable with "Apply devhost.toml is running · 2 of 6 restarted" as visible text and as its accessible description, never a dead button (HOLD-3, HOLD-1, MENU-3).
  7. 7 With worktrees off, a reload that restarts only worker leaves api outside its set: a Restart, Start or Restart Changed pressed meanwhile on api queues behind the reload on every page, with Cancel Restart or Cancel Start, instead of doing nothing (HOLD-3, SEL-7).
  8. 8 A newer save that validates supersedes the reload in progress: the stop or start in progress finishes, the remaining services start from the newest manifest only, nothing of the replaced edit is announced, its record ends replaced, and every page's activity line follows the newer reload. A newer save that does not validate supersedes nothing: the reload finishes with its own outcome, then the rejection follows (REV-12, FB-10).
  9. 9 On failure, the activity line and the touched rows turn to the rollback's own words while devhost restores service by service: every service that ran before runs again, one that was failing before keeps failing, and the set is never stopped as one unit (UNDO-1, ACT-3, FAIL-1).

4. Read the outcome

A reload still ends with the accepted manifest updated, routes changed in one Caddy reload, and retired hostnames and ports released before the outcome prints, as today. What changes is that it ends with exactly one outcome line that names what restarted and why, certified only once the reload that read the saved version ended with every restarted service in the state the line reports, and that the page whose service restarted says the same. When that service's dev server then reloads the page, reload-control's Reload blocked holds the reload while Hold Reloads is on and names the restart that caused it, and the outcome names work the reload put out of reach (FB-5, FB-4, UNDO-2). Keys: the outcome notice takes no focus; it closes after O14's calibrated reading time and pauses on unfocused arrival under O53 (FB-9, O14, O53).

  1. 1 Exactly one outcome line in the terminal and the per-manifest log, verb first: each restart with its reason, the count of the stack and the time, or "nothing restarted". Only the URLs the reload added, changed or removed follow it, after "New:" or "Removed:", never the whole list, which devhost stack info (short alias devhost status, O62) prints on request (FB-3, FB-10, FB-7, WORD-4, WORD-5, WORD-8, CC-22).
  2. 2 Under reversed O7, adding or removing an external service (managed = false) in a repository never disables worktree switching and emits no switch-block warning: an addition prints only its normal outcome ("Applied devhost.toml: nothing restarted · 0.3 s"), worktree switching stays enabled, and the external service stays untouched and marked external in Services (SEL-11, SEL-5, ACT-9, O7).
  3. 3 On a page whose own service the reload restarted, the outcome replaces the activity line as an outcome notice that names that service first and ends with its origin. It closes after O14's calibrated reading time (1.5 s + 0.3 s/word, clamped 4–15 s — 13.2 s for this 39-word notice), paused while pointer or focus is in it or the page is hidden; if it arrived while the browser window was unfocused (document.hasFocus() false, as for an editor save), its countdown waits until the window next gains focus (O53), while focus inside an embedded iframe never pauses it. Its accessible description says it is also in the log, and it is announced once in the polite region (FB-2, FB-6, FB-9, SEL-3, REV-10, O14, O53).
  4. 4 On any other page the activity line ends without a notice, the rows show the result and the stack's log keeps the line (FB-2, FB-7).
  5. 5 While the crash view is open over the page, minimized or not, for a service the reload restarts, the view shows the reload's progress in place of its recovery actions' progress; its Restart api stays in place, unavailable with its reason while the reload restarts api, and Edit stays available (SURF-3, FB-1, REV-12, HOLD-1).
  6. 6 When the exited service runs again, the view closes by itself, the outcome notice reports it in the notice stack, and focus returns to the element that had it before the view opened (SURF-3, FB-2, KEY-6).

5. Read a rejection where it is

An edit devhost cannot apply still never stops anything: the stack keeps running the accepted manifest and every action stays available, as today (HOLD-6). What changes is that the terminal prints the rejection as devhost's own block with the file, line, column and offending line, and every page shows it as one notice that leads to the fix. Keys: the notice stack comes before the bar in the dock's order, so after Alt+Ctrl+B focuses the bar, Shift+Tab reaches the rejection notice, the first notice in drawn order; Tab moves through Logs (on a crash's rejection), Edit (or Copy when the config editor is off), Copy Error and Dismiss in visual order; Enter or Space activates the focused one; Escape leaves the notice where it is (KEY-3, KEY-4, KEY-8).

  1. 1 One line led by the file relative to the root manifest, its line, column, key and cause, then the offending line with a caret, then where things stand; never an unmarked line among the services' output. An include reads "admin/devhost.toml:3:1", a cycle starts with its setting, a close key is offered ("did you mean "serve"?"), and the raw parser text stays behind Copy Error and in agent output's one devhost: ERR: line (FAIL-2, WORD-7, WORD-8, WORD-9, FB-10).
  2. 2 Every open page shows one condition notice, ranked with failures at the top of the notice stack, with the offending line and its number under it. Its path is shown once, shortened, and wraps inside the notice with the full path in its tooltip and accessible name, so nothing runs past the window's edge at 1600x1000, 1280x800 or 900x900 in either theme or at 1280x800 under 200% zoom, and it never sits under an open toolbar panel or docked chat (ACT-7, FB-8, WORD-1, SURF-9, SURF-1).
  3. 3 It leads with Edit while the config editor is on, then Copy Error, whose copied text starts with "devhost.toml:12:8" and holds the original parser text, then Dismiss (MENU-4, MENU-5, FAIL-2).
  4. 4 With the config editor off, Edit gives way to devhost.toml:12:8 with Copy (copying the location) alongside Copy Error and Dismiss, with no Open in Editor action anywhere (editor support withdrawn under O51; MENU-3, MENU-4, SURF-15).
  5. 5 A restart that crashed is rolled back first; then the notice names the exit and what the rollback restored, and keeps api's own last lines, frozen at its exit, for as long as it shows, whatever other services print. The notice keeps the condition style of every rejection and leads with Logs, which opens the pinned log panel filtered to api at its exit, then Edit on api's definition (or devhost.toml:14 with Copy when the editor is off), then Copy Error (FAIL-3, UNDO-1, FAIL-1, SURF-13, MENU-5, FB-8, O51).
  6. 6 Saving the same failing change again updates the one report with its count and latest time, keeping its lines and actions, never a second notice (FAIL-4).
  7. 7 The terminal reports a crash with the service's own lines and what devhost ran, then the rollback's own line, "Restored the accepted manifest: 5 of 6 running · api still fails" when not every service runs again; a repeat prints exactly one line naming what it restarted and rolled back, never nothing (FAIL-3, UNDO-1, FAIL-4, FB-10).
  8. 8 Collapsed, the badge shows a rejected configuration in ACT-7's order, below a failed, exited or blocked service, with the notice's one-line form beside it, toolbar-shell's drawing. The announcer reads the rejection once in the assertive region when it starts and once in the polite region when it ends (SURF-8, ACT-7, FB-9).
  9. 9 While the notice is visible, Config stays plain so the indicator never repeats; Escape never dismisses the notice; Dismiss does, and leaves "1 not applied" on Config while the config editor is on, else on the stack name, until a configuration is accepted; activating the marker shows the notice again (KEY-8, SURF-8, UNDO-3).
  10. 10 While the page's own modal dialog is open, the notice moves into it with the notice stack, inside its Tab cycle, and Edit (or Copy and Copy Error when the editor is off) works from there; the rest of the toolbar shows its paused state with its reason in one line (SURF-11, KEY-7, O51).

6. Fix at the file and line, or undo, and save

The person still fixes the file and saves it, and the save is step 1 again, as today. What changes is that every report leads to the file and line, and the save's outcome replaces the rejection instead of the notice vanishing without a word. There is no Undo save: the way back is to what runs (UNDO-6). Keys: Edit opens config-editor's Configuration window with focus in its text, at the line (KEY-6, SURF-4).

  1. 1 Edit opens the Configuration window on the file at the line, the failing line marked, with the rejection in its banner until a reload of that file is accepted, and after a crash, the crashed service's last lines; config-editor owns the window and its Edit target (MENU-4, SURF-4).
  2. 2 There is no Undo save: Restore Running Version writes back what runs and applies like any save, and an accepted save is undone by undoing the text and saving again, which reports its own reload (UNDO-6, REV-10).
  3. 3 With the config editor off, Copy copies devhost.toml:12:8 and confirms "Copied devhost.toml:12:8" (omitting "also in the log", O14) while the rejection notice stays until a configuration is accepted or it is dismissed, with no editor launched or opened (O51, SURF-15, MENU-4, MENU-3).
  4. 4 A fix's outcome replaces the rejection in the terminal, the log and on every page (FAIL-4, FB-3, ACT-7).

7. Read the outcome as an agent or a script

Agents and scripts still edit the same manifest files and meet the same checks, and human and agent output still differ on purpose (owner rule). What changes is that an agent that edits the manifest no longer has to read a terminal it cannot see: devhost reload applies the manifest on disk through POST /__devhost__/reload, waits for the same outcome and exits with it. stack-run-stop builds these commands; this flow specifies what they report. Keys: none; these are terminal commands.

  1. 1 devhost reload runs the same reload a save starts, waits for its outcome by the operationId it sent, prints step 4's outcome line and exits 0 when applied; with nothing changed it reads "Applied devhost.toml: nothing restarted" (FB-11, ACT-1, CC-23, CC-37).
  2. 2 A rejection prints step 5's lines and exits non-zero, and so does a restarted service that exited, named with its last output line. A lost response is read from the record by its operationId, and a request repeated with that ID runs nothing again (FB-11, REV-12, ACT-1).
  3. 3 Under AGENT=1 every rejection is one devhost: ERR: line holding every issue, with absolute paths. devhost stack info --wait (short alias devhost status --wait, O62) waits for a running reload and reports the last operation's outcome, manifest-reload rejection state and changed-file markers; every stack writes its per-manifest log, a foreground stack included, so the outcome is readable from another shell (WORD-9, FB-11, FB-7, O62, CC-21, CC-23).
