How devhost reports operations and problems

TLDR: Every operation reports the same way, from one record: its progress where it started or as one activity line, then one outcome in that place that names what changed; successes close after calibrated reading time (pausing when arriving unfocused), failures stay until handled, conditions share one ordered notice stack beside the bar (with a 320 px phone layout and app tab-title prefixes), and a lost connection or closed command-mode port says why without painting healthy services as down.

Low-fidelity wireframe. Layout, names and numbers are illustrative; the redesign ticket's acceptance criteria are authoritative.

1. Start an operation

Every control, key and command that starts work keeps its place and its key, as today: a row's Restart, Restart Changed with its badge icon and Alt+Ctrl+R, Start, Restart Stack, Switch and Restart Stack, Return to Configured Worktree, Save and Send in the Disable Reloads popover. What changes is that each write is one recorded operation from its first moment, the control that started it says what runs, and a start is heard once. Writes that ask first still ask where their own flow says (REV-1); this flow adds no question, and no question ever sits in a notice: a decision lives in its panel, popover or dialog (REV-4, SURF-2). Keys: this step adds none; each control's own key starts it (2.11 of the reference).

  1. 1 The pressed control keeps focus as the busy control, aria-busy and aria-disabled, never disabled, its label naming what runs: "Restarting api…", or "Restarting Stack · 2 of 6 started" for a confirmed Restart Stack. It is drawn with toolbar-shell's unavailable and busy state of Button, so focus never drops to the page (KEY-11, FB-9, WORD-4).
  2. 2 The page's one announcer says the start once in its polite region, "Restarting api". Its assertive region carries failures only, and step text and elapsed times never enter either region, so nothing ticks aloud (FB-9).
  3. 3 Every write carries an operationId, a lowercase UUID the page generates, and this page load's ID; the route answers 202 Accepted with the operation record before the operation runs. The page-side operation store keeps each ID this tab sent in sessionStorage, so only this tab treats the operation as its own and a reload in the middle keeps following it; a request repeated with the same ID returns the same record and runs nothing again (ACT-1, REV-12, CC-37).
  4. 4 A key whose action is unavailable says why instead of doing nothing: Alt+Ctrl+R during Restart Stack restarts nothing and shows a neutral notice naming the operation that blocks it and its progress. It closes after O14's calibrated reading time (pausing on hidden page or unfocused arrival per O53) and stays in the stack's log (MENU-3, HOLD-3, FB-6, WORD-7, O14, O53).
  5. 5 The badge's icon and the Restart Changed button are unavailable while Restart Stack runs; their reason is the activity line in the notice stack, the dock's status line, and each one's accessible description is the same sentence, "Restart Stack is running · 3 of 6 started" (HOLD-3, HOLD-1). Defaults: an operation's name is the label of the control or command that started it, on every surface; a key acts on the set its control names, here Restart Changed's set, "api, web", or its named fallback, the page's own service (MENU-6, WORD-2, SEL-1, SEL-2, O4).

2. Follow its progress in one place

Progress still shows in the surface that started the operation while it is open, as today. What changes is that it shows each target's step with its elapsed time, and that it never disappears: when that surface closes, or when the operation started somewhere else, one activity line in the notice stack carries it. Keys: Escape, a click outside the panel or Tab past its last control closes the panel and moves its operation's progress to the activity line (KEY-7, KEY-8).

  1. 1 While the surface that started it is open, each target shows its step (queued, stopping, starting, "health check 2 s of 30 s", running, failed), updated at least once a second, and the busy control shows the elapsed time; services-panel draws the rows from the published state (FB-1, ACT-3, STATE-1, ACT-2).
  2. 2 Whenever no open surface on the page shows the operation, the notice stack shows it as one activity line: the operation, its target, the targets done of the total and the elapsed time, joined by " · ". Reopening the panel moves the progress back into it and removes the line, so the page never shows both. An activity line has no Dismiss: it ends when its outcome replaces it (FB-1, FB-2, WORD-4, WORD-5).
  3. 3 The services the operation touches show restarting, starting or stopping on every surface, and every other service keeps its own state: Restart Stack never ends with the stack drawn down, and starting one service never draws the running ones as down (ACT-3, ACT-4, SEL-7).
  4. 4 An operation started in another tab, the terminal, an agent or a file saved on disk shows on every open page of the stack as an activity line ending with its origin. The step text and the elapsed time update in place, outside every live region (FB-1, ACT-1, WORD-4, FB-9).

3. Read one outcome where the progress was

Each operation still ends where it was started, as today. What changes is that every operation ends with exactly one outcome, in the words of the control that started it, which states what happened to each target and the time it took; a success says so instead of saying nothing, and it certifies the end state, never a step. Most operations start or stop processes and cannot be taken back, so there is no Undo: each outcome says what changed and stays in the log. Keys: focus stays where the person is, and nothing that arrives takes it (KEY-6).

  1. 1 With the surface that started it still open, the outcome replaces the progress there and stays until the person leaves the surface. When it replaces the busy control, as after a confirmed Restart Stack, focus moves to its sentence, a tabindex="-1" element named by it, never to an action, so a repeated Enter cannot start a second write (FB-2, FB-3, FB-6, KEY-11, FB-9, ACT-6, WORD-5).
  2. 2 With that surface closed, the outcome notice takes the activity line's place, never both. It is announced once in the polite region and closes after its calibrated reading time (1.5 s + 0.3 s/word, clamped 4–15 s, counting runs of letters and digits — 6.3 s here; Undo stays 4 s) while neither pointer nor focus is in it and the page is visible. If it arrived while the browser window was unfocused (document.hasFocus() false at arrival), its countdown waits until the window next gains focus; notices arriving while focused keep counting, and embedded frames never pause it. Logged outcomes carry "also in the log" in their accessible description; unlogged outcomes omit it. It shows only once each target passed its health check (FB-2, FB-5, FB-6, FB-7, O14, O53, ACT-11).
  3. 3 An operation this page did not start reaches it as a notice only when it failed or touched the page's own service, ending with its origin as the backend saw it: "· from the terminal", "· from another tab", "· from Claude Code, conversation Fix the nav", "· after devhost.toml changed on disk"; otherwise its rows and the log show it. Targets are named, never identified by an ID (FB-2, SEL-3, ACT-1, WORD-4, WORD-1).
  4. 4 Across the page reload an operation causes, such as a switch or Restart Stack on a recovery page, the next page in the same tab reads the outcome from the record by the ID the tab stored and shows it once, with focus on the control that started it when the new page shows it, else on the outcome's sentence. No page greets its load with an older success: a second tab shows nothing for it, and a page loaded past that success's own O14 lifetime shows no success, while a failure not yet handled shows on every page (FB-2, ACT-1, KEY-6, FB-6, O14).
  5. 5 When a chat turn that changed files ends while Hold Reloads is on (and reloads are not disabled under O56, with focus outside text entry), devhost applies the held reloads once as its own reload; the reloaded page shows "Reloaded to show Claude Code's change" once (announced politely once, closing after O14's calibrated time without "also in the log"), while chat's receipt stays the turn's one outcome (O57, FB-2, FB-12).
  6. 6 One set of outcome sentence builders, in services-panel's shared module of state words under packages/devhost-ui/src/ with its Rust counterpart in apps/devhost/src/cliout.rs, writes every outcome: the operation in the past tense, its target set, what changed, the time, then details after " · ". Restart Changed names exactly the set it restarted; a save names each restart with its reason, or that nothing restarted; a switch names both worktrees by their labels; times read "2.6 s", "14 s" and "14:02" (FB-3, WORD-4, WORD-8, WORD-11, MENU-6, SEL-1, SEL-2, SEL-4, REV-10, O9, SURF-14).
  7. 7 An outcome names the work it ended, discarded or left behind, whether or not its write asked first; a conversation a stop ended stays listed and can be resumed (FB-4, UNDO-4).
  8. 8 A chat Send reports on the sent message, naming the conversation it went to, and claims only the delivery the agent confirmed: without an acknowledgement the message keeps Delivery unconfirmed and is never resent (owner rule; SEL-8, FB-5, REV-12). A Disable Reloads request stays "Request sent to Claude Code · working" on its notice until its turn ends (O24; step 5).

4. Read a failure and recover in place

A failure is still reported where the operation started, and its original text can still be copied. What changes is that it says what failed, why and what to do in plain words, offers the action that fixes it first, and stays until the person deals with it: today's toolbar-wide error, which the status stream clears on every message, disconnect and reconnect, goes away, because each failure is the outcome of its own operation. Each retry is one write. Keys: focus stays on the control that started the operation while it exists, with the failure as its accessible description; Tab reaches the failure's actions in order (KEY-11).

  1. 1 A failure leads with the target and what happened, then the cause, the evidence (its last output lines, the probe it failed or the program holding its port) and what devhost ran, each once. It is announced once, in the assertive region, which carries failures only, and prefixes the app page's tab title until cleared (FAIL-2, FAIL-3, WORD-7, FB-9, O16).
  2. 2 It stays, in its surface and as this failure notice once that surface closes, until Dismiss (named "Dismiss api's failure") or the same operation succeeds on the same target. Status messages, reconnects, closing the surface, switching files and page reloads never remove it, because the record keeps it, and a dismissed failure does not come back on reload or in another tab (FB-6, ACT-1).
  3. 3 The action for its cause leads, with the others beside it: an exited service leads with Restart, with Logs and Edit, and after a retry fails the same way the one report counts the repeat and Edit leads; an unreachable external service leads with Check Again; a blocked worktree with Return to Configured Worktree, choosing another worktree and Check Again. No failure is drawn without a way forward (MENU-5, FAIL-4, WORD-11).
  4. 4 A manifest file not applied leads with Edit; while the config editor is off, its file and line come with Copy beside Copy Error (editor integration is removed under O51; MENU-4, WORD-2). devbox not trusting devhost's local certificate authority is a condition ranked after a rejected configuration, in the one trust sentence, with Copy for its command (ACT-7, WORD-12).
  5. 5 A response devhost cannot read never shows: no markup, raw Rust error chain or transport error. The shared request helper, used by every control request and the configuration client, turns each failed request into one sentence: the proxy's HTML means the stack is not running, a request that cannot connect means the proxy is not reachable, a 403 from an unauthenticated remote browser reads "Sign in with passkey or pair this browser to use devhost here" with Sign In with Passkey and devhost pair fallback (O36, HOLD-7), a JSON error keeps its message, and anything else names the operation and the status. The original text stays behind Copy Error, and no message contains markup; a stopped stack leads with its start command and Copy (FAIL-2, SURF-9, STATE-4, HOLD-2, WORD-7).
  6. 6 A partial result counts every target and is never a plain success or failure; it takes the failure style and the assertive region with api's lead actions. Restart Stack's rollback, devhost's own undo here, reports its own outcome naming what it put back (FAIL-1, UNDO-1).
  7. 7 A deliberate stop, cancel or replacement is never a failure: services devhost stops for an operation are its steps, a service a person stopped reads "Stopped by you", and a cancel is reported as one. Both take the neutral style, never the failure look and never the assertive region (FAIL-5, WORD-7, CC-24).
  8. 8 A write refused because the view was stale shows the refusal with the current state, and the panel redraws from it; an open question whose action becomes unavailable closes and says why, and a refused save keeps its draft (REV-13, HOLD-1).

5. See what needs you in one notice stack

Reload blocked, the hot reload notice and the configuration notice stay notices beside the bar, never dialogs, as today. What changes is that every condition that needs the person is one notice that starts and ends with the published state, clears by itself when its cause ends, never by a timer or a page reload, and shares one stack in one order with activity lines and outcomes. While a waiting agent or a failure persists, both app pages and devhost's own pages prefix their browser tab title (such as "(1) waiting · Acme Shop" or "(1) failed · Acme docs") and restore the page's own title when cleared (ACT-7, O16). Each condition notice leads with the action for its cause (a terminal-started waiting agent uses Dismiss alone); its words are its owning flow's (startup-and-recovery, manifest-hot-reload, worktree-switch, services-panel, agent-chat, running-agents, reload-control). Keys: Alt+Ctrl+B focuses the bar; Shift+Tab from the bar reaches the notices in drawn order in bottom placements (Tab in top placements); each notice's actions and 2 More are Tab stops. A focused notice action keeps Enter, Space, the arrows, Home, End and Escape, and every other key reaches the page; Escape there returns focus to the element that had it before the dock was focused and dismisses nothing. Nothing that arrives takes focus; when a focused notice closes, focus moves to Undo if shown, else the next notice's sentence, else the element focused before the notice stack, else the Services trigger, never the page body (KEY-3, KEY-4, KEY-5, KEY-6, KEY-8, O14).

  1. 1 The order: what needs the person or blocks writes first (the crash notice, failures, a configuration not applied, a blocked repository, an unreachable external service, an agent waiting, the lost connection or closed command-mode port), then activity lines, then other conditions (Reload blocked, chat off with conversations still running, the hot reload notice with a pending request), then successes and neutral notices; newest first within a group. The crash notice names api and its exit; Expand (or activating it) reopens the crash view with focus on its heading (FB-8, ACT-7, SURF-3).
  2. 2 At most three notices show; the rest fold into 2 More, which expands the stack in place with aria-expanded="true", reads Show Fewer while expanded, and keeps focus (FB-8, WORD-3).
  3. 3 The notice stack fills toolbar-shell's notice slot beside the bar, between the bar and every other devhost surface: the Services panel opens beyond it, on its trigger's side, and no panel, docked chat or the Configuration window covers a notice, so every notice button answers native hit testing at 1600×1000, 1280×800 and 900×900 in both themes and at 1280×800 under 200% zoom (SURF-1, CC-1, SURF-9).
  4. 4 Each notice kind has its own icon and its kind's word in its accessible name, distinct in forced colors: ✕ failure, ◆ condition, ? lost connection, ◐ activity, ✓ success, ⓘ neutral (WF-3). A notice carries no live role: it is a group named by its sentence, and only the announcer speaks, once when a condition starts and once when it ends; the project's Alert stops rendering role="alert" (ACT-13, FB-9, WORD-6).
  5. 5 With the dock at the top, the stack hangs below the bar and the panel opens beyond it; the DOM and Tab order follow the drawn order, so here the bar comes first. A configuration notice names the file's kind ("devhost config file not applied: config.toml line 3" for the other kind), says the stack still runs the accepted manifest, blocks nothing, and is replaced by its outcome when the stack accepts a configuration (KEY-3, WORD-1, HOLD-6, FAIL-4, MENU-4).
  6. 6 At 320 CSS pixels wide (phone layout, O8), notices span the phone width with 8 px horizontal insets, stack cleanly above or below the compact bar with wrapped text and action rows (every tap target ≥24×24 CSS px, zero horizontal overflow), and stay unobstructed alongside mobile chat and approval prompts so an authenticated phone (O36) can ask, answer and see the change (O8, SURF-9, FB-12).
  7. 7 The Disable Reloads popover anchors to the hot reload notice, which keeps its place and stays visible beside it at every acceptance viewport; the notice is never the question itself (REV-5, O2, SURF-2, WORD-11).
  8. 8 After Send, the hot reload notice stays in the third group with its pending request, naming the agent, until the request's turn ends; then it shows the result in place of Disable Reloads, which reload-control words (FB-5, O24, FB-8).
  9. 9 Collapsed, every condition notice, failure and running operation's activity line keeps a one-line form beside the badge, its first clause and its lead action (where applicable); only successes stay out of sight there and in the log, and a routine restart never changes the badge's look. toolbar-shell places the forms and draws the badge (SURF-8, FB-1, ACT-7, ACT-3).
  10. 10 The one-line forms of the other notices beside the collapsed badge: a blocked repository, an unreachable external service, a chat agent waiting, a terminal agent waiting (with Dismiss alone), an untrusted certificate authority (with Copy), chat off with a running conversation, Reload blocked (with Reload Now), the lost connection, a closed command-mode serve port (serve-command-05), and a running operation's activity line. The chat agent-waiting form names the conversation and leads with Answer (WORD-2), opening its decision card in docked chat in one activation; chat off leads with the conversation to answer or stop it (SURF-8, FB-1, HOLD-4, ACT-9, REV-9, HOLD-5, WORD-11).
  11. 11 Dismissing a condition notice whose condition persists leaves a marker on the control that owns the condition until it ends, and only then, because while the notice shows it is the one report (FAIL-4): a rejection's on Config while the config editor is on, else on the stack name, which is always on the bar, as is a dismissed untrusted authority's; activating the marker shows its notice again. The lost-connection and closed-port notices have no Dismiss, because they are the reason every write is unavailable (SURF-8, UNDO-3).

6. Lose the connection and get it back

The page still reconnects by itself, 1 s after a drop and doubling up to 10 s, and the CPU, RAM and Disk readouts still hide while it is disconnected, so a stale number never passes for a current one. What changes is that a lost connection is no longer drawn as an outage: every service keeps its last known state as unknown, every write is unavailable with one sentence that names the cause, a single closed command-mode serve port is distinguished from a stack disconnect, and the page says when it is connected again. devhost never opens a browser or starts a stack from the page: these notices offer commands to copy (owner rule). Keys: Retry Now, Copy and Open are ordinary buttons; a focused control that becomes unavailable keeps focus (KEY-11).

  1. 1 Before a stop, the stack publishes stopping before its first service stops, with the count stopped, on the trigger and as an activity line, so the toolbar never shows 6 of 6 running while the stack shuts down (ACT-3, WORD-4).
  2. 2 From the moment the status stream closes, the lost-connection notice names the cause the stack sent before it closed: here its time, how it stopped and the command that starts it again, with Copy for the command and its folder. The other reasons read "after 1 h idle", "by Ctrl-C in its terminal", "from Acme Admin's page", or "replaced by devhost stack restart" / "replaced by devhost restart" / "replaced by devhost upgrade" (O18). Stopped is read only from the stack's final message (ACT-10, HOLD-2, ACT-11).
  3. 3 The conversations the stop ended are named; each stays listed and can be resumed (FB-4, UNDO-4).
  4. 4 The Services trigger shows the connection's state instead of a count, and no row, dot or notice takes the failed look; failure looks stay for failures the server reported (ACT-5, CC-26).
  5. 5 After devhost caddy stop, the notice says the proxy is not reachable, with its start command; a reload the dev server asked for meanwhile is a detail of this notice, never a separate Reload blocked whose Reload Now would load the browser's connection error (ACT-10, HOLD-2).
  6. 6 A listener move is never a lost connection: while proxy-settings moves the HTTPS port (listeners-moving), the page keeps working on the old address and shows the move's activity line; only once every listener confirms (listeners-moved) does the outcome name the new address, and any listener that did not move, with Open, which keeps the path, query and fragment, and the page stops retrying the old address; listeners-failed keeps the old listeners and never shows the moved notice (FB-13, HOLD-2).
  7. 7 In a multi-port command-mode devhost serve -- <cmd> session, when one secondary port closes while sibling ports and the command remain healthy, the server emits a final WebSocket port-closed message with the remaining active URLs before removing that port's Caddy route. openReconnectingWebSocket.ts delivers it and stops retrying the removed hostname; the tab shows this targeted notice with Open instead of painting healthy sibling ports as a false 0/3 red outage (ACT-5, HOLD-2, CC-26).
  8. 8 A stop that left a process running past O30's allowance never reads stopped: the notice names the survivor with stack-run-stop's command that stops it (ACT-11, O30).
  9. 9 Otherwise, including a stream that closed without the stack's final message, the notice reads "Lost connection to devhost; retrying" with the next attempt's time and Retry Now, which tries at once. No delay hides a disconnect, and none is needed: the routine drop at the end of Restart Stack and at each Start is removed at its source by services-panel (HOLD-2, ACT-5, WORD-1).
  10. 10 Every service keeps its last known state, drawn as unknown with the time it was last seen, never down or failed; every write on the page (Restart, Restart Changed and its key, Start, Restart Stack, switches, Stop Stack, Save, chat Send and the Disable Reloads Send) is unavailable with the notice's one sentence, said again in each open panel's status line and given to each blocked control as its accessible description. Drafts, page context and queued operations stay (HOLD-1, HOLD-2, MENU-3, ACT-12, WORD-6, STATE-3, UNDO-2, SEL-7).
  11. 11 When the stream returns, states update in place, every write becomes available again without a page reload and nothing it blocked is replayed; the page says once, politely (without "also in the log", O14), "Connected again · 6 of 6 running", or after a replacement "Connected again · Acme Shop was replaced by PID 85102 · 6 of 6 running". The notices the outage raised clear with it: a reload held during the outage clears when the page's service still runs the process it ran when the page loaded, and otherwise stays as Reload blocked; failures the record keeps stay (ACT-5, ACT-7, ACT-10, REV-12, FB-6).

7. Read the same outcomes in the terminal and the log

The stack's terminal still logs every completed configuration change once it is complete, and human and agent output still differ by design. What changes is that every operation on a running stack, from any origin, ends with one outcome line, the same sentence the page shows, so a restart started from a page no longer leaves only "restarting service: api" behind, and every stack writes its log. Keys: in the pinned log panel, log-minimap's keys apply (KEY-12).

  1. 1 Each operation prints one outcome line in the stack's terminal and in its per-manifest log, built from the record by the Rust counterpart of the outcome sentence builders in apps/devhost/src/cliout.rs, with its origin at the end ("· from a page on <hostname>" for page-started operations; FB-10, FB-7, WORD-4, WORD-9).
  2. 2 A fix saved from the Configuration window prints the applied line, so the terminal never ends on a rejection that was already fixed; the reload's own words are manifest-hot-reload's (FB-10, FAIL-4).
  3. 3 Lines report what changed: the URL list prints at the first start and on request, with devhost stack info (short alias devhost status, O62), never again after each action (FB-10, CC-22).
  4. 4 In agent output a failure is one devhost: ERR: line holding every issue, and a failure line in the stack's log carries ERR: as a warning carries WARN:; agents and scripts read the last outcome from devhost stack info (short alias devhost status, O62) and the log, which stack-run-stop extends (FB-11, WORD-9, CC-23).
  5. 5 Every stack writes its per-manifest log, a foreground stack included, and the pinned log panel offers devhost's own lines as a source in its service filter, so an outcome that closed or was dismissed can be read again; log-minimap draws the panel, and devhost keeps no second activity list (FB-7, CC-21, SURF-13).
