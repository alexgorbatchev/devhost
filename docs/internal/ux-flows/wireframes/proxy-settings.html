Change the shared proxy settings

TLDR: The terminal says where the shared Caddy settings live and who can reach the stacks; a save states its reach before it is written, is checked and certified before it counts, and reports one outcome per stack, while open pages follow their stack to the new address with Open instead of drawing every service down, and a refused change names its line and what keeps running.

Low-fidelity wireframe. Layout, names and numbers are illustrative; the redesign ticket's acceptance criteria are authoritative.

1. Find where the shared Caddy settings live

The settings still live in the devhost config file, found as today (DEVHOST_CONFIG_DIR, else XDG_CONFIG_HOME, else ~/.config/devhost), and a missing file still leaves every setting at its default; Caddy still listens on every interface by default (owner rule). What changes is that the terminal says where the file is and who can reach the stacks, so neither is a guess. This flow words the proxy line; stack-run-stop prints it among its start and status lines, and first-run-setup in devhost caddy start's outcome. Agent output carries the same facts in its own layout, with the absolute path (WORD-9, FB-11). Keys: none; terminal output only.

  1. 1 devhost caddy --help ends with where the shared Caddy settings live: the path resolved for this environment, shortened with ~. The words are "devhost config file" and "shared Caddy settings", never "settings file", "global config" or "proxy config" (WORD-1, WORD-8, SURF-15).
  2. 2 devhost caddy start names what runs, its listener and its reach, the file and how to stop it (FB-10).
  3. 3 devhost start and devhost status print the same facts as one proxy line (FB-10, FB-11).
  4. 4 A loopback bindHost reads "this machine only" with both loopback listeners, and with http = true the line adds the HTTP port. On macOS, as on Linux, a loopback bindHost from port 1024 listens on loopback only; today macOS silently listens on every interface (REV-11).
  5. 5 privileged-ports' help line says what it does before it does it: it downloads Caddy if needed and asks for a password (WORD-9).
  6. 6 On macOS it no longer claims that no setup is needed: it says what applies, and why a loopback bindHost below port 1024 is refused (step 6).
  7. 7 On Linux it says before a download what downloads and from where, and names the size once it is known, since caddyserver.com sends no length (first-run-setup's download lines and its proposed exception to WORD-9); before sudo it says it may ask for a password (WORD-9).
  8. 8 A devhost caddy download that replaces a Caddy holding the grant says, on its own line, to run privileged-ports again (WORD-8, WORD-9).
  9. 9 Under AGENT=1, privileged-ports refuses before any sudo with one line, as the trust commands do, so a cached sudo ticket never lets an agent change Caddy's capabilities silently; the trust commands keep their rule as written (REV-8).

2. Change a setting, with its reach stated before the save

A save still applies through hot reload from any editor, with no question, and the Configuration window keeps config-editor's rules: off by default, saving only from this machine, validating before it writes and creating a missing file (owner rules, HOLD-7). What changes is that, before the save, the window says what saving the draft will do, from the backend's check of it; these are statements, never a question, and Save stays available beside them (REV-1, REV-10). The plan comes from /__devhost__/config/validate (CC-37); with the config editor off, devhost reload --dry-run prints the same plan (CC-23). This flow gives each setting its words; config-editor draws the line. Keys: Mod+S saves, as in config-editor's window (KEY-9).

  1. 1 With the devhost config file picked under "This machine", a line under the header says how far its changes reach (SEL-11, SEL-6).
  2. 2 Beside Save, one line states what saving does: the stacks whose URLs move and where, by name, with every stack also listed in the line's tooltip and accessible description when there are more than two (SEL-1, SEL-6, REV-10).
  3. 3 Making the stacks reachable from the network takes the warning style; Save stays available (REV-10).
  4. 4 Opening the stack directory to the network warns what other devices can read and that it has no sign-in; while bindHost is a loopback address, the line says the save changes nothing (REV-10).
  5. 5 A service that uses its public URL restarts with it, and the line names it with its reason, the page's own service first (REV-10, SEL-3).
  6. 6 When nothing that runs would change, the line says so. The line and the problems are checked again whenever the running shared Caddy settings change, for example after another stack's start applied the file, so the line never describes settings that no longer run (REV-13).
  7. 7 When the save moves the address of the page the window is open on, the line adds that the page moves and that its unsent chat text and page context come along, because the page hands them over before the move (step 5); nothing is discarded, so no question asks (REV-3, UNDO-2).
  8. 8 Problems the check finds show on their line before the save, in step 6's words, and a draft the check refuses is not saved, as config-editor's save does today (MENU-4, REV-11).

3. devhost checks the change, tells open pages, then moves Caddy once

As today, every running stack watches config.toml, the first to take the shared route lock applies a change once for the machine, and Caddy moves in one reload, a new adminAddress included, so devhost caddy stop and devhost caddy trust keep finding it where it runs. What changes is that devhost runs every check it can before anything moves, tells open pages before their address closes, and certifies that the new listener answers before anything reports the change applied (REV-11, FB-5). Nothing here asks: the apply is part of the save's one write (REV-10). Keys: none; this step takes no input.

  1. 1 Settings another process already applied are not applied twice (Kept).
  2. 2 Every check runs before Caddy moves, and a failed one refuses the change with nothing moved, naming the check and what holds it: the program and PID on a held port, the stack, the service and the manifest line of a claimed hostname (REV-11, MENU-4).
  3. 3 The applying process reaches every running stack through its control server on the loopback control port the state directory records; each stack sends its pages {"type": "listeners-moving", "origin", "operationId"} with that page's own scheme and hostname on the new port (HOLD-2).
  4. 4 Caddy moves in one reload under the route lock, as today. On macOS, a loopback bindHost from port 1024 now listens on loopback only, where today it silently listens on every interface (REV-11).
  5. 5 A success certifies the end state: only a handshake that reaches Caddy through both loopback addresses writes the record that every stack, link, list and the stack directory read (FB-5, ACT-1).
  6. 6 A move devhost could not certify is put back before anything reports it: Caddy returns to the running settings and the old address answers again (UNDO-1, FB-5).
  7. 7 Moving URLs never changes a service's state; the one exception is a service whose definition uses its public URL, which restarts (step 7) (ACT-2, REV-10).

4. Read the outcome in every stack's terminal and log

Every running stack still reports the change in its own terminal, and its services keep running. What changes is that each stack prints one outcome line naming what changed, with each key's old and new value, then only what moved, and writes the same line to its log; the full URL list prints at the first start and on request (devhost status), never again after each change (FB-3, FB-10, CC-22). Every running stack follows the record of what Caddy runs, whoever moved it (FB-7, ACT-1). Agent output prints the same facts on one line in its own layout, with the absolute path and every changed key's old and new value (WORD-9, FB-11). Keys: none; terminal output only.

  1. 1 One outcome line per stack: verb first in the past tense, what changed, the time it took and its origin. It replaces "Applied the shared Caddy settings from <path>." followed by every URL (FB-3, WORD-4, FB-7).
  2. 2 Only the URLs that moved, labelled by service; a URL that did not move is not printed again (FB-10).
  3. 3 stack-run-stop's directory line names the stack directory at its new address, and a change of a port or of bindHost adds step 1's proxy line (FB-10, SURF-15).
  4. 4 A change of bindHost names the key's old and new value and its reach in the person's words, then the proxy line, so the reach is never a guess (FB-3, WORD-4).
  5. 5 While http = true, each service's plain-HTTP URL prints beside its HTTPS one, because a tunnel needs that address (FB-3).
  6. 6 Turning stackDirectoryAllowRemote on adds one warning line naming what other devices can now read (WORD-7).
  7. 7 A save that changes nothing that runs says so (FB-10).
  8. 8 A change that another stack's devhost start or devhost caddy start applied is reported by every running stack with that origin, within 2 s; today only a stack's own watcher moves its URLs, so running stacks kept the old port's links (ACT-1, ACT-12, WORD-4).

5. Open pages follow the move

The app keeps running, and devhost still reloads no page by itself: Open is a navigation the person chooses, never held by Hold Reloads (UNDO-2). What changes is that a page whose address moved is told before its port closes, keeps its services' last known states instead of drawing them down, and offers the new address, while its toolbar follows its stack there. notices-and-feedback draws the notice and the lost connection; this flow supplies the move's cause and makes the new address readable. A reload the page's dev server asks for meanwhile is a detail of this notice, never a Reload blocked whose Reload loads the closed port. While the page's own modal dialog is open, the notice moves into it and Open works from there (SURF-11). Pages opened on another device lose their connection when bindHost becomes a loopback address, as the line beside Save said. Keys: Open and Dismiss are ordinary buttons in the notice's Tab order, activated by Enter or Space; the notice never takes focus, and Escape never dismisses it (KEY-4, KEY-6, KEY-8, KEY-9).

  1. 1 listeners-moving arrives before port 443 closes, and the page shows the move's progress as an activity line in the notice stack (FB-1, WORD-4).
  2. 2 When its status stream closes with the move, the trigger shows the connection's state; the page connects its status stream to the same hostname on port 4443, and stops retrying port 443 once that answers (ACT-5, HOLD-2).
  3. 3 Once port 4443 answers with the move's record, the activity line gives way to the condition notice "devhost moved to port 4443". Open opens this page at port 4443 in the same tab with its path, query and fragment kept, and its accessible name is "Open this page at port 4443". The notice ranks with the lost connection, above activity lines and successes, is read once in the polite region, and fits every acceptance viewport, a long address wrapping with the full URL in its tooltip and accessible name; it ends when the person opens the new address or the move is undone (HOLD-2, SURF-15, FB-5, FB-8, FB-9, SURF-9, WORD-8).
  4. 4 The toolbar is live again from port 4443, and its service links name port 4443 (ACT-12, ACT-2).
  5. 5 Between the close and the new address answering, every service keeps its last known state, drawn as unknown with the time it was last seen, never down or failed (ACT-5, CC-26).
  6. 6 Every write on the old page (Restart, Restart Changed and its key, Start, Restart Stack, switches, Save, Send) is unavailable with one reason, said once in the status line and given to each blocked control as its accessible description, because a write from the old address comes from another origin, which the control server refuses; reads, page context and chat drafts stay (HOLD-1, HOLD-2, MENU-3).
  7. 7 Before its stream closes, the page hands its unsent chat text, pasted images and page context to the control server's draft record under the new address, so Open brings them back; configuration drafts are kept per stack and file and are unaffected. A screenshot share ends with the page, and the outcome names it (UNDO-2, FB-4, REV-3).
  8. 8 Dismiss leaves the marker "moved" on the stack name until the page is opened at the new address or the move is undone (SURF-8, UNDO-3).
  9. 9 A move devhost could not certify is undone before the page goes anywhere: the old address answers again, the page reconnects there, and the activity line gives way to step 6's failure, never to "moved" (FB-5, REV-13).
  10. 10 The Configuration window that saved the change shows the move beside Save while it runs, then its outcome from the record with where this page continues and Open. Focus moves to the outcome's sentence, never to the page body, and Save is then unavailable with the same reason (FB-2, FB-9, KEY-11, HOLD-2).

6. A change that is not applied

As today, a change that is not applied leaves Caddy on the settings it runs, renders their files back, keeps every stack and every action running, and a repeated rejection is printed once (HOLD-6, FAIL-4). What changes is that every surface names the file, line, column and key, the cause in plain words, the fix and what keeps running, leads to the line, and clears the rejection whenever config.toml matches what Caddy runs, from any path (FAIL-2, MENU-4, ACT-7). Agent output prints one devhost: ERR: line with the location and the original text (WORD-9, FB-11). The Configuration window is config-editor's; this flow supplies the rejection and the running text. Keys: Edit, Open in Editor, Copy Error and Dismiss are ordinary buttons in the notice's Tab order; the notice never takes focus, and Escape never dismisses it (KEY-6, KEY-8).

  2. 2 On macOS, a loopback bindHost below port 1024 is refused with its fixes, where today it silently listens on every interface; the same file makes devhost caddy start exit non-zero with the same cause before Caddy starts (REV-11).

7. Give a service its public URL

Service references still fill in another service's address when the stack starts, and a reference whose value changes still restarts only the services that use it, as the environment-variables guide promises for ports. What is new is the publicUrl property: the service's first public URL as devhost prints it, so an app on any HTTPS port can build links that answer. devhost never adds it to every service's environment by itself, because a port change would then restart every routed service of every stack. A reference to a service without a hostname fails at start, as url fails for a service without a port. Keys: none; the manifest is edited in any editor or in the Configuration window.

  1. 1 A manifest uses publicUrl in env or command the way it uses url, inside a reference's double braces.
  2. 2 The value follows the running shared Caddy settings: the port only when it is not 443, and the service's path when it has one.
  3. 3 A service that uses it restarts when a change moves its public URL, showing restarting with that reason, then running; every other service keeps its state throughout (ACT-2, ACT-3, REV-10).
  4. 4 The line beside Save named the restart before the save (step 2), and the outcome names it with its reason (FB-3, SEL-11).
  5. 5 When such a restart fails, the move still stands, because Caddy already runs the new settings: the stack's outcome is a partial result with the failed service's evidence, and its row leads with Restart, then Logs and Edit (FAIL-1, FAIL-3, MENU-5).
