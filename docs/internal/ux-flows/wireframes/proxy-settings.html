Change the shared proxy settings

TLDR: The terminal says where the shared Caddy settings live and who can reach the stacks; a save states its reach before it is written, is checked and certified before it counts, and reports one outcome per stack, while open pages follow their stack to the new address with Open, relay previews keep answering on any port, and a refused change names its line and what keeps running.

1. Find where the shared Caddy settings live

The settings still live in the devhost config file, found as today (DEVHOST_CONFIG_DIR, else XDG_CONFIG_HOME, else ~/.config/devhost), and a missing file still leaves every setting at its default; Caddy still listens on every interface by default (owner rule). What changes is that the terminal says where the file is and who can reach the stacks, so neither is a guess. This flow words the proxy line; stack-run-stop prints it among its start and status lines, first-run-setup in devhost caddy start's outcome, and serve-folder in a session's header. Terminal text says "this machine" for the machine the command runs on (O61). Agent output carries the same facts in its own layout, with the absolute path (WORD-9, FB-11). Keys: none; terminal output only.

  1. 1 devhost caddy --help ends with where the shared Caddy settings live: the path resolved for this environment, shortened with ~. The words are "devhost config file" and "shared Caddy settings", never "settings file", "global config", "machine config" or "proxy config"; devhost start --help names the file the same way for domainSuffix (WORD-1, WORD-8, SURF-15).
  2. 2 devhost caddy start names what runs, its listener and its reach, the file and how to stop it; its listener part is worded as the proxy line's in every variant, the macOS warning included (FB-10).
  3. 3 devhost start and devhost status, the short form of devhost stack info, print the same facts as one proxy line (FB-10, FB-11, O62).
  4. 4 bindHost = "127.0.0.1" with every port at 1024 or above reads "direct connections from this machine only" with both loopback listeners, and says that relay previews and SSH forwards still reach the stacks. On macOS, as on Linux, it now listens on loopback only; today macOS silently listens on every interface (O39, REV-11).
  5. 5 On macOS, bindHost = "127.0.0.1" with any port below 1024 (the HTTP port too, 80 by default) keeps every interface, so existing port-443 setups keep starting, and a warning naming the fix follows the proxy line on every start, status and save; nothing is refused (O39, WORD-7).
  6. 6 privileged-ports' help line says what it does before it does it: it downloads Caddy if needed and asks for a password (WORD-9).
  7. 7 On macOS it no longer claims that no setup is needed: it says what applies, and from which port a loopback bindHost takes effect (O39).
  8. 8 On Linux it says before a download what downloads and from where, and names the size once it is known, since caddyserver.com sends no length (first-run-setup's download lines and its proposed exception to WORD-9); before sudo it says it may ask for a password (WORD-9).
  9. 9 A devhost caddy download that replaces a Caddy holding the grant says, on its own line, to run privileged-ports again (WORD-8, WORD-9).
  10. 10 Under AGENT=1, privileged-ports refuses before any sudo with one line, as the trust commands do, so a cached sudo ticket never lets an agent change Caddy's capabilities silently; this extends REV-8, which keeps the trust commands as written (REV-8).

2. Change a setting, with its reach stated before the save

A save still applies through hot reload from any editor, with no question, and the Configuration window keeps config-editor's rules: off by default, validating before it writes and creating a missing file (owner rule). With it on, it reads and saves from this machine and from a browser in another environment that signed in with the shared devhost passkey or paired (O36, O38, O54, HOLD-8). What changes is that, before the save, the window says what saving the draft will do, from the backend's check of it; these are statements, never a question, and Save stays available beside them (REV-1, REV-10). The plan comes from /__devhost__/config/validate (CC-37); with the config editor off, devhost reload --dry-run prints the same plan (CC-23). This flow gives each setting its words; config-editor draws the window. Browser lines say "devbox's network", because their reader may be elsewhere (O61). Keys: Mod+S saves, config-editor's row of the 2.11 keyboard map.

  1. 1 With the devhost config file picked under the machine's name, a line under the header says how far its changes reach (SEL-11, SEL-6, O61).
  2. 2 Beside Save, one line states what saving does: the stacks whose URLs move and where, by name, with every stack also listed in the line's tooltip and accessible description when there are more than two; a port change restarts no service (SEL-1, SEL-6, REV-10, O45).
  3. 3 The save moves the address of the page the window is open on, so the line adds that the page moves and that its unsent chat text and page context come along, because the page hands them over before the move (step 5); nothing is discarded, so no question asks (REV-3, UNDO-2).
  4. 4 bindHost = "127.0.0.1" names the machine the stacks stay reachable from, and that relay previews and SSH forwards still reach them (O39, O61).
  5. 5 Making the stacks reachable from the network takes the warning style; Save stays available (REV-10).
  6. 6 On macOS, bindHost = "127.0.0.1" with any port below 1024 changes no listener, and the warning-style line says why and what fixes it (O39).
  7. 7 Opening the stack directory to the network warns that anyone there reads it without signing in, while signed-in browsers already can; while Caddy listens on loopback only, the line says the save changes nothing, and on macOS below port 1024, where Caddy keeps every interface, the warning stands (O47, O39, REV-10).
  8. 8 A domainSuffix or [remote] change names only the stacks it changes and that they wait for their next start; the rest of the save applies at once (step 7).
  9. 9 When nothing that runs would change, the line says so. The line and the problems are checked again whenever the running shared Caddy settings change, for example after another stack's start applied the file, so the line never describes settings that no longer run (REV-13).
  10. 10 Problems the check finds show in config-editor's problem list and gutter before the save, in step 6's words, and a draft the check refuses is not saved, as config-editor's save does today (MENU-4, REV-11).
  11. 11 A browser in another environment that has not signed in sees only the unauthenticated toolbar state, with Sign In with Passkey and the way to pair; it reads and saves nothing (HOLD-7, O36).

3. devhost checks the change, tells open pages, then moves Caddy once

As today, every running stack watches config.toml, the first to take the shared route lock applies a change once for the machine, and Caddy moves in one reload, a new adminAddress included, so devhost caddy stop and devhost caddy trust keep finding it where it runs. What changes is that devhost runs every check it can before anything moves, tells open pages before their address closes, and certifies that the new listener answers before anything reports the change applied (REV-11, FB-5). The [caddy] part always applies for the whole machine; domainSuffix and [remote] are decided per stack and never hold it back (step 7). Nothing here asks: the apply is part of the save's one write (REV-10). Keys: none; this step takes no input.

  1. 1 Settings another process already applied are not applied twice (Kept).
  2. 2 Every check runs before Caddy moves, and a failed one refuses the change with nothing moved, naming the check and what holds it: the program and PID on a held port, the stack, the service and the manifest line of a claimed hostname (REV-11, MENU-4).
  3. 3 The applying process reaches every running stack through its control server on the loopback control port the state directory records; each stack sends its pages {"type": "listeners-moving", "origin", "operationId"} with that page's own scheme and hostname on the new port. A relayed page's public port stays 443, so it gets none (HOLD-2).
  4. 4 Caddy moves in one reload under the route lock, as today, and every configured route moves with it, so a stopped stack's tab still opens its stopped-stack page over HTTPS while an unconfigured hostname gets no certificate (O63, O15). On macOS, a loopback bindHost from port 1024 now listens on loopback only; below 1024 Caddy keeps every interface and step 1's warning prints (O39).
  5. 5 A success certifies the end state: only a check that reaches Caddy on every address the bind host resolves to ([::1] alone for "::1"), with a hostname its TLS serves, writes the record that every stack, link, list, the relay connector and the stack directory read (FB-5, ACT-1, O63).
  6. 6 A move devhost could not certify is put back before anything reports it: Caddy returns to the running settings and the old address answers again (UNDO-1, FB-5).
  7. 7 Moving URLs never changes a service's state and restarts no service (ACT-2, REV-10, O45).

4. Read the outcome in every stack's terminal and log

Every running stack still reports the change in its own terminal, and its services keep running. What changes is that each stack prints one outcome line naming what changed, with each key's old and new value, then only what moved, and writes the same line to its log; the full URL list prints at the first start and on request (devhost status), never again after each change (FB-3, FB-10, CC-22). Every running stack follows the record of what Caddy runs, whoever moved it: a save, another stack's devhost start, a devhost serve session or devhost caddy start (FB-7, ACT-1). Agent output prints the same facts on one line in its own layout, with the absolute path and every changed key's old and new value (WORD-9, FB-11). Keys: none; terminal output only.

  1. 1 One outcome line per stack: verb first in the past tense, what changed, the time it took and its origin. It replaces "Applied the shared Caddy settings from <path>." followed by every URL (FB-3, WORD-4, FB-7).
  2. 2 Only the URLs that moved, labelled by service; a URL that did not move is not printed again (FB-10).
  3. 3 stack-run-stop's directory line names the stack directory at its new address with the machine's name (FB-10, SURF-15, O61).
  4. 4 A change of a port or of bindHost adds step 1's proxy line, with its macOS warning when one applies (FB-10, O39).
  5. 5 A change of bindHost names the key's old and new value and its reach in the person's words, then the proxy line, so the reach is never a guess (FB-3, WORD-4).
  6. 6 On macOS, a loopback bindHost below port 1024 applies, moves nothing and says so, then the proxy line and its warning (O39).
  7. 7 While http = true, each service's plain-HTTP URL prints beside its HTTPS one, because a tunnel needs that address (FB-3).
  8. 8 Turning stackDirectoryAllowRemote on adds, after its outcome line, one warning line naming what anyone on the network can now read without signing in (WORD-7, O47).
  9. 9 A save that changes nothing that runs says so (FB-10).
  10. 10 A change that another stack's devhost start or devhost caddy start applied is reported by every running stack with that origin, within 2 s; today only a stack's own watcher moves its URLs, so running stacks kept the old port's links (ACT-1, ACT-12, WORD-4).

5. Open pages follow the move

The app keeps running, and devhost still reloads no page by itself: Open is a navigation the person chooses, never held by Hold Reloads (UNDO-2). What changes is that a page whose address moved is told before its port closes, keeps its services' last known states instead of drawing them down, and offers the new address once it answers, while its toolbar follows its stack there. notices-and-feedback draws the notice and the lost connection; this flow supplies the move's cause and makes the new address readable. A reload the page's dev server asks for meanwhile is a detail of this notice, never a Reload blocked whose Reload Now loads the closed port. While the page's own modal dialog is open, the notice moves into it and Open works from there (SURF-11). Pages opened directly from another device on the network lose their connection when bindHost becomes a loopback address, as the line beside Save said; pages opened through a relay preview keep working (O39). Keys: Open and Dismiss are ordinary buttons in the notice's Tab order, activated by Enter or Space; the notice never takes focus, and Escape never dismisses it (KEY-4, KEY-6, KEY-8, KEY-9).

  1. 1 listeners-moving arrives before port 443 closes, and the page shows the move's progress as an activity line in the notice stack (FB-1, WORD-4).
  2. 2 When its status stream closes with the move, the trigger shows the connection's state; the page connects its status stream to the same hostname on port 4443, and stops retrying port 443 once that answers (ACT-5, HOLD-2).
  3. 3 Only once every listener confirms (listeners-moved, read with the move's record from port 4443) does the activity line give way to the success notice "Moved to https://shop.acme.test:4443/", naming any listener that did not move (FB-13). Open opens this page at port 4443 in the same tab with its path, query and fragment kept, and its accessible name is "Open this page at port 4443". The notice is the move's outcome, a success that stays until Open or Dismiss because the old page can no longer make changes, ranked below conditions, is read once in the polite region, and fits every acceptance viewport and the 320 CSS pixel phone layout, a long address wrapping with the full URL in its tooltip and accessible name; it ends when the person opens the new address or the move is undone (HOLD-2, SURF-15, FB-5, FB-8, FB-9, FB-13, SURF-9, WORD-8, O8).
  4. 4 The toolbar is live again from port 4443, and its service links name port 4443 (ACT-12, ACT-2).
  5. 5 Between the close and the new address answering, every service keeps its last known state, drawn as unknown with the time it was last seen, never down or failed, and the panel's status line says why changes wait (ACT-5, CC-26, HOLD-2).

6. A change that is not applied

As today, a change that is not applied leaves Caddy on the settings it runs, renders their files back, keeps every stack and every action running, and a repeated rejection is printed once (HOLD-6, FAIL-4). What changes is that every surface names the file, line, column and key, the cause in plain words, the fix and what keeps running, leads to the line, and clears the rejection whenever config.toml matches what Caddy runs, from any path (FAIL-2, MENU-4, ACT-7). A bindHost = "127.0.0.1" below port 1024 on macOS is not a rejection: it applies with step 1's warning (O39); a domainSuffix or [remote] change is not one either (step 7). A browser in another environment that has not signed in receives no status stream, so it sees only the unauthenticated toolbar state and no line of config.toml (HOLD-7, O36, O38). 7. Hostnames, relay previews and services follow the proxy

Routing settings still apply to a running stack only at its next start, as documented, and services keep running through every change: devhost adds no public URL variable or reference, so a port change restarts no service (O45). What changes is that a domainSuffix or [remote] change waits only for the stacks it changes and never holds back the rest of the save, that relay previews keep answering whatever Caddy's port and wherever it moves, and that the docs teach services to read their public URL from the request. Keys: Copy Command and Dismiss are ordinary buttons in the notice's Tab order (KEY-4).

  1. 1 A stack whose hostnames are all full names records the new suffix for later manifest reloads and reports only what the save changed; it shows no rejection (FB-3).
  2. 2 A stack with a short host label still applies the save's [caddy] part, so Caddy never stays on the old port, and prints the hostnames that will change with the command that applies them on its own line. A later save while the suffix waits is applied and reported, never refused in silence (HOLD-6, WORD-8, FAIL-4).
  3. 3 Its pages show the wait as a condition notice with Copy Command; it blocks nothing. Restart Stack keeps the hostnames the stack started with, and devhost stack restart applies the suffix (ACT-7, HOLD-6).
  4. 4 A stack running in remote mode keeps its relay settings until its next start, while the save's [caddy] part applies for every stack; the relay connector takes Caddy's address from the record of what Caddy runs, so a move by a save, another project's start or a serve session leaves every preview answering (ACT-12).
  5. 5 When the connector cannot reach Caddy, the remote stack prints one line naming the address it tried and the fix (FAIL-2, WORD-7).
  6. 6 A relayed page's public port is 443, so the control server's origin check passes it whatever Caddy's local port, and its toolbar shows the stack's real state; a start whose own public origin is refused fails with a named cause. The connector keeps its lease table in memory and reuses connections to Caddy, so bursts of module requests no longer queue (O36, ACT-5, FB-5).
  7. 7 Caddy and the relay forward the scheme, hostname and port the browser used, and the docs, the example manifest and the skill teach building absolute URLs from them instead of https:// before a hostname, which carries no port; a value needed outside a request, such as an API origin baked into a frontend build, still names the port per machine (O45).
