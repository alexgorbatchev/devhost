Keep agent edits from reloading the page

TLDR: Disable Reloads opens a popover that shows the agent, the conversation and the exact request before anything is sent, the request's progress, question and result stay in the notice's slot with the restart the change needs, Hold Reloads counts and keeps every held reload, and once reloads are disabled later chat turns end with "Reload to see the change" and Reload Page instead of a reload devhost starts.

Low-fidelity wireframe. Layout, names and numbers are illustrative; the redesign ticket's acceptance criteria are authoritative.

1. Read the notice

The hot reload notice still shows only with chat on, on a page whose dev server's reload client loaded: Bun's development script, Next.js's portal element, a loaded /@vite/client or a webpack hot-update global, read at load and again as resources arrive, as today. Hold Reloads on the bar is still on by default. What changes is the notice's words, its place in the stack and its two buttons: Disable Reloads opens a popover instead of sending (step 2), and Dismiss can be undone. The notice shows on every load of such a page until dismissed; the dismissal and Hold Reloads are kept per stack and page origin in this browser, never per worktree, so a worktree switch keeps them, while the request and whether reloads are disabled are kept on the server (step 3) (SEL-11, CC-9). Keys: Alt+Ctrl+B moves focus to the dock, whose notices come before the bar in DOM and Tab order; Disable Reloads and Dismiss are Tab stops in the notice stack, and a focused notice action keeps only Enter, Space, the arrow keys, Home, End and Escape, so every other key reaches the page (KEY-3, KEY-4, KEY-5). This flow binds no new key; every hint comes from the one binding definition (KEY-13, BAR-4).

  1. 1 The title names the dev server and what it does, "Vite reloads this page when files change", with the body "Agent edits can reload it while you work."; for the other clients it names Bun, Next.js or webpack. Visible text says reloads, never hot reloading, which names applying a manifest. The notice means the client loaded, not that it is connected or that reloads are on, and never claims more (WORD-1, O24, CC-31).
  2. 2 Disable Reloads keeps its label (O2); its accessible description says an agent receives the request: "Opens a request for Claude Code to turn off reloads in this worktree; nothing is sent until you press Send" (REV-5).
  3. 3 Dismiss hides the notice for now, never for good: callout 7 shows its Undo, and Show Reload Notice in the Hold Reloads popover (step 6) brings it back later (UNDO-3, CC-20).
  4. 4 Hold Reloads already keeps every script reload from replacing the page, with no agent and no change to the worktree's files. Its state is drawn by shape and text, ☑ on and ☐ off, in forced colors too, and the bar item opens its popover (step 6) (ACT-13, SEL-11).
  5. 5 The notice is a card named by its sentence with no live role, so it is never announced on load: it is standing information, and the announcer reads only its request's start and result. It is one of FB-8's other conditions, so it sits in the third group with Reload blocked, below anything that needs the person, such as api's exit; a request waiting for the person's answer and a failed request rise to the first group, as an agent waiting and a failure (FB-8, FB-9).
  6. 6 Collapsed, the toolbar keeps the notice's one-line form beside the badge, "Vite reloads this page", whose Disable Reloads opens the same popover; while the page's own modal dialog is open, the notice moves into that dialog with the notice stack and stays operable.   7. 7 Dismiss replaces the notice with "Reload notice hidden" and Undo for 4 s, not counted while the pointer or focus is in it; Undo brings the notice back where it was with focus on Disable Reloads. Its accessible description says where it stays: "also in the Hold Reloads popover" (UNDO-3, FB-6, O14).
  8. 8 A browser without the Navigation API has no Hold Reloads, as today; the notice says so once in its body, "This browser cannot hold reloads", so Disable Reloads is the remaining way (MENU-3).

2. Review the request

Pressing Disable Reloads still prepares a request asking a coding agent to turn off the dev server's reloads in this worktree. What changes is that nothing is sent and nothing starts until the person presses Send: the editable request is the question, every time (REV-1, REV-5, O2). Keys and focus: focus starts in the request, which is text entry, so page-wide chords are suspended there and Enter inserts a line break; Tab leaves the text and moves through the popover's controls in visual order; Send has no key. Escape, Cancel, Tab past the last control, Shift+Tab before the first, or a click outside close the popover and send nothing, and focus returns to Disable Reloads when it was opened from the keyboard, or, when the person opened it with the pointer, to the page element that had focus before that click. The popover is non-modal (KEY-1, KEY-2, KEY-5, KEY-6, KEY-7, KEY-8, KEY-9, REV-4). An edited request is kept for the page's life, so reopening the popover shows the person's last text (UNDO-4). From another environment, a phone included, a browser signed in with the shared devhost passkey or paired with a devhost pair link sends the request as this machine does; one that has not signed in sees callout 14 (HOLD-8, O36, HOLD-7, review-16).

  1. 1 A non-modal dialog anchored to the notice and named by its title, "Ask Claude Code to turn off reloads?", which names the agent. Disable Reloads keeps its place, outlined, beside it, and no conversation, process or message exists until Send (SURF-2, REV-5, WORD-10).
  2. 2 The recipient: the agent and model as the composer's chip, which opens Chat Settings as it does there, and "starts a new conversation"; under it, each open conversation of this worktree is a radio option by its title, agent and state, a radio group the arrow keys move through. New conversation is selected by default, and the request never joins a conversation the popover does not name. Picking "Fix the nav" names its agent, which is fixed for that conversation, and the title follows: "Ask Codex to turn off reloads?". agent-chat owns the choice of conversation and the send; this popover only shows it (SEL-8, O27, KEY-10).
  3. 3 The approval line agent-chat's composer shows, how the agent's CLI is configured to ask before edits and commands, here in its warning style because this Claude Code never asks: the agent's own approvals are the only brake on a change to shared configuration (O13, REV-6).
  4. 4 The mode line is text, never a control: This worktree (live) with the worktree's label and "no new worktree, commit or merge" (REV-5, O1, SEL-4, WORD-10).
  5. 5 The request is editable and holds focus, written for the detected dev server and starting with what it asks and where; here it names Vite's server.hmr, and for Bun the switch line reads "In the Bun.serve() options of web's entry file, set development: { hmr: false }." The page's URL and its service come from the page, the worktree from the route that answered it; the manifest sentence is O26's default (WORD-10, SEL-3, O26).
  6. 6 While the hold is on, the hold line is text without a button: Hold Reloads already keeps this page without an agent (O2).
  7. 7 Cancel, then Send, which sends the text exactly as edited (step 3). Only Send sends, and it has no key (KEY-9).
  8. 8 Docked chat, compact or expanded, sits beside the notice stack as its own column and never covers the notice or the popover. At every acceptance viewport the popover opens inside the viewport, never clipped, with its title, mode line, request, Send, Cancel and the hold line in view; only the request scrolls (SURF-1, SURF-6, SURF-9).
  9. 9 For a dev server with no verified switch, Next.js and webpack until the fixtures verify one, a line above the request says so, and the request is the generic one, still editable. With the hold off, the hold line becomes Hold Reloads, which turns the hold on, sends nothing and closes the popover; for such a dev server it leads the buttons (O25, O2).
  10. 10 When chat cannot take a message, the request stays with Copy, Send is unavailable but focusable (aria-disabled) with one reason under it, which is also its accessible description, and Hold Reloads stays offered. When chat's connection is lost while the popover is open, it stays open and focus stays where it was: HOLD-5 names this popover and keeps its request with Copy, which decides over HOLD-1's general close. The other reasons read "No coding agent found: devhost looks for codex and claude on devbox's PATH. A rejected manifest blocks nothing (HOLD-5, HOLD-2, HOLD-4, HOLD-6, HOLD-1, MENU-3, MENU-5, KEY-11).
  11. 11 Collapsed, the popover anchors to the notice's one-line form beside the badge and holds the same contents (SURF-8).
  12. 12 While the page's own modal dialog is open, the notice and its popover sit inside that dialog and work, Send included, and the rest of the toolbar shows its paused state with its reason, "Paused while this page's dialog is open" (SURF-11, KEY-7).

4. Follow the request

The agent still edits through its own approvals, which only the person answers, as today. Words: the conversation's state is working or waiting for you; the agent is named by its product name and the conversation by its title; a service's state, such as web restarting, comes only from the published state, and on a page that lost its status stream web shows unknown with the time it was last seen, never down (WORD-1, WORD-4, WORD-6, ACT-2, ACT-5). 5. Read the result and apply it

devhost still restarts nothing by itself to apply the agent's change. What changes: when the request's turn ends, the notice says what the agent changed and what devhost sees, offers the restart the change needs, and keeps a correct change from meeting the same warning and a second request on every load. There is no Undo: devhost cannot take back an agent's edit, so the result names its way back instead, and the page's own state survives because every reload waits for the person (UNDO-5, UNDO-3). Durations, clock times and paths follow one format ("1 min 12 s", "14:05", "~/acme") (WORD-8). Keys: the result's actions are Tab stops in the notice stack, its lead action first (KEY-3, MENU-5).

6. Keep the page through reloads

Hold Reloads still holds every script reload of the page through the Navigation API: the dev server's, its reload after a restart, and the app's own location.reload(), a documented limitation whose explanation the popover gives. The browser's own refresh and devhost's own reloads always go through, and hot module replacement is never held, as today. What changes: held reloads are counted, explained and kept, never dropped, hidden or silently let through. The hold runs whenever the toolbar's script is injected and the person has it on, whatever other segment shows (SEL-11; toolbar-shell's). Keys: ArrowLeft and ArrowRight on the bar reach Hold Reloads; in its popover, Escape, Tab past the last control or a click outside closes it and returns focus to Hold Reloads (KEY-4, KEY-6, KEY-7, SURF-2).

  1. 1 Reload blocked counts every held reload and says what devhost knows about them: how many since when, the cause it can see, here web's restart from the operation record or the service's launch time, and the files the published changed mark names under the page's service's watch paths, or "No watched file of web changed" when none did. A reverted edit leaves the list, because the mark compares content with what the running process launched with (SEL-3, ACT-8, SEL-2).
  2. 2 When every changed file was applied in place by a hot update this page saw after the change, and web has not restarted since the page loaded, the notice reads "Already current: Vite applied src/Button.tsx in place" and the condition ends by itself, leaving its line in the stack's log; otherwise it never claims the page is current (ACT-7, ACT-8).
  3. 3 services-panel draws the same note beside web's changed mark, which stays as published (ACT-8).
  4. 4 Dismiss on Reload blocked keeps the page as it is and leaves the held marker, "2 held", on Hold Reloads until a reload clears it, drawn with a shape of its own, never by color alone, in forced colors too; the item's accessible name reads "Hold Reloads, on, 2 held". toolbar-shell carries the marker into the collapsed badge (SURF-8, UNDO-3, ACT-13).
  5. 5 Hold Reloads is an arrow stop on the bar that opens its popover with Enter, Space or the arrow toward the panel; focus moves to its switch, which shows its state word, On or Off (KEY-4, KEY-6).
  6. 6 The switch's reach names everything it holds and what it never holds, the documented limitation included (SEL-11).
  7. 7 While any reload is held, the held count with Reload Now; while the hot reload notice is dismissed, Show Reload Notice; and where the choice is kept (UNDO-3, FB-6, CC-9).
  8. 8 Turning the hold off while reloads are held never reloads the page: Reload blocked becomes "2 reloads pending" with Reload Now, and later reloads go through; turning it on again holds again, and the pending count stays until a reload (UNDO-3, CC-20).
  9. 9 Reload Now is devhost's own reload. The reloaded page says what it applied, with focus on that sentence, never at the top of the document, a success that closes after its reading time, here the 4 s minimum; chat's unsent draft and page context come back with it (FB-4, KEY-6, UNDO-2, O14).
