Startup pages, crash recovery and app error pages

TLDR: Every state of a service gets one devhost page, or the crash view over the app, led by the action that can fix its cause and showing the evidence that explains it; an app's own 404 or 5xx passes through with a devhost notice instead of being replaced; and every restart shows its progress and its outcome where it started, never closing without a word.

Low-fidelity wireframe. Layout, names and numbers are illustrative; the redesign ticket's acceptance criteria are authoritative.

1. Open a service URL

The person still opens the hostname themselves, devhost never opens a browser, and the app's own response still passes through whenever the app answers. Status pages still work without the toolbar and, for the state, the cause, the service's details and its logs, without JavaScript. What changes is that devhost answers each published state with its own page, led by the action that can fix it, and that scripts get a short status instead of an empty 502. A missing file in a served folder keeps devhost's file server's own 404 inside the file browser, which serve-folder draws (SURF-16). Keys: a status page is a full page with the document's standard keys and no shortcuts of its own; every action is a button or a link in reading order (KEY-1).

  1. 1 The heading names the service and its state, "api could not start", and comes first in reading order; the HTTP status is a secondary detail under it, never read before it. The document title starts with the heading's words, so a background tab says what failed, and carries the attention count while the failure lasts (FB-9, WORD-6, WORD-3, O16, ACT-7).
  2. 2 One line counts the whole stack, failures first, and names the worktree the service runs from with its shared label; the words are the glossary's (stack, service, worktree, status page), never "project" or "down". The page links onward in the same tab, to the stack directory as All Stacks on devbox, named by the machine (ACT-6, WORD-5, SEL-4, WORD-1, WORD-11, SURF-15, O61).
  3. 3 One page per published state, each drawn with the shared state indicator (shape and word, never color alone) and led by its cause's action: starting shows progress until ready; exited leads with Restart api (step 3); a service the run left out leads with Start admin, the Services panel's own Start, naming what else it starts (MENU-5, ACT-2, ACT-13, O10, SEL-7).
  4. 4 A fresh worktree that lacks its setup leads with the command named from the failing service's output, to run in that worktree, then Restart web; devhost runs nothing new itself. Recognising the missing setup is worktree-switch's needs-setup matcher (MENU-5, O32).
  5. 5 A service blocked by its worktree says so in one sentence, used as the status line and as the accessible description of the unavailable Restart api. Return to Configured Worktree leads and asks in place every time, with Cancel taking the pressed button's place, focused and taking Enter; Escape or a click elsewhere on the page cancels and returns focus to the button. Check Again reads the worktree list again; the page's first read stops nothing, and the repository's services that still run from the deleted folder keep running until a recovery is chosen (O43). worktree-switch owns the switch, its question and its outcome (HOLD-4, HOLD-1, MENU-3, REV-1, REV-2, REV-4, KEY-8, SEL-4).
  6. 6 An external service, or a devhost serve --port session with nothing listening, gets its own page: what devhost routes and how it checks, the last result and its time, once that devhost cannot restart it, and Check Again, which runs the check now. It has no Restart and no log, which devhost cannot have, and it never blocks its repository's worktree switch, so the worktree list shows no warning for it (ACT-9, MENU-5, MENU-3, HOLD-1, O7).
  7. 7 A daemon that stopped on its own: devhost runs its status command once when its health check starts failing, so the page says whether it still runs ("its status command reports PID 72459" when it runs but fails its check), with the check's last result, a log labelled for what it holds, and Restart mail (ACT-2, FAIL-3, SURF-13).
  8. 8 This machine and a browser signed in with the shared devhost passkey, or paired through a one-time devhost pair link, use every action here alike, the phone included. A browser that has done neither gets the heading and the cause but no log or worktree list, and every action stays in place, unavailable, with one visible reason that is also its accessible description; nothing starts (HOLD-7, HOLD-8, O36, O37).
  9. 9 A preview visitor through devhost's relay gets devhost's own pages from the connector, never a bare text line or the gateway's 502: a stopped stack names itself, the machine, when it stopped and its start command; a name no stack holds says so, listing close running previews only to a signed-in browser; a broken local hop names its cause and the next step. The connector stays registered for the stopped stack's 24 hours. On this machine, a hostname with no route keeps stack-directory's page, and an unknown HTTPS hostname gets no certificate (SURF-16, FAIL-2, O15, O46, O47, O63).
  10. 10 A request that is not a page load gets the app's own response while the app answers; while the service is not running, devhost answers 503 with Retry-After and a body under 2 KB naming the service, the stack and the phase, JSON under Accept: application/json, one text line otherwise, never Caddy's empty 502. A page load still gets the status page (SURF-16, FB-11, CC-4).

2. Wait while the service starts

The starting page still answers while the service is not ready and still reloads the tab into the app by itself once it is, at the same URL. What changes is that it says what it waits for and how long, shows only this attempt, and reads the stack's live state instead of probing the URL every second. Keys: Tab reaches the attempt line, the log, which is one focusable scrolling element, and Jump to Latest, which carries the count of new lines once the reader scrolls up (SURF-13, WORD-2).

  1. 1 The health check it waits on, with the elapsed time and its limit, updated at least once a second; or the dependency it waits for, "waiting for db to pass its health check" (ACT-4, STATE-1, WORD-6, WORD-8).
  2. 2 What started this attempt and when: "Started by devhost start at 14:02:11", "Restart from the Services panel at 14:05:10" or "after devhost.toml changed on disk at 14:06:02" (ACT-1, FAIL-3).
  3. 3 Restart api stays in its place, unavailable, with the running operation and its progress as its visible reason, which is also its accessible description; while the stack starts the reason reads "Starting Acme Shop · 2 of 6 started" (HOLD-3, HOLD-1, MENU-3).
  4. 4 The log, labelled "api output", shows only this attempt's lines, opened at the end and following new lines while the reader is at the bottom. Earlier attempts sit in a collapsed group saying how each ended, and every attempt starts with a divider naming its time and what started it, as the terminal separates them; an attempt with no output says so with its start time (ACT-4, SURF-13, STATE-2, STATE-3).
  5. 5 A restart reads restarting with its step, stopping then starting, never failed, exited or down; a first start and a restart share one look (ACT-3, WORD-6).
  6. 6 Once the service is ready, and only then, the page requests its URL once and reloads into the app; a leftover of a killed run answering on the port is never reported ready. Without the live stream the page backs off to checks at 1, 2, 5 and 10 s, then every 30 s, says when it last checked, and checks nothing while the tab is hidden (FB-5, ACT-11, ACT-12, STATE-4).
  7. 7 When the page cannot read its stack's state it keeps its last content as unknown with its age, never as down, and every action waits with one reason and Retry Now. When the stack stops, the page says so in one sentence with its time, reason and start command, with Copy, never as failed services; devhost never starts a stack from a page, and for 24 hours the stack's hostnames answer the stopped-stack page over HTTPS (HOLD-2, ACT-5, ACT-10, STATE-3, O15, O63).

3. Read the failure on the recovery page

A failed service still leaves the rest of the stack running, and its hostname, every alias and path route, still shows what went wrong with its logs and a restart, as the recovery contract says. What changes is that the status page and the toolbar's crash view are one shared recovery view, rendered in both stylesheets with the same words, actions and log, and shown once: on devhost's own page the crash view never opens over it for the same failure (SURF-14, SURF-3, CC-2). Keys: Tab order is the cause, the lead action, the other actions, the log, then the worktree list's disclosure; every action is a button (KEY-10).

  1. 1 One cause sentence in plain words follows the heading. A failed health check of a running process reads failed, an ended process exited; no page shows markup, a raw Rust error chain or the proxy client's raw error (FAIL-2, WORD-7, WORD-8, ACT-2).
  2. 2 The evidence devhost observed, each piece once: the exit code, or the signal by name with its status, time and sender ("terminated by SIGTERM (143) at 21:53:34, not sent by devhost"); the probe it failed; a fixed port another program holds, with that program; and what devhost ran, the command, its folder when it differs from the stack's, and the manifest file and line (FAIL-3, WORD-8, FAIL-5).
  3. 3 Actions in the order of the cause's fix: Restart api leads with the primary style, then Edit, then Restart Stack, secondary, on its own line with its reach. A fixed port another program holds makes Edit lead, because Restart Stack cannot free it; an automatic port another program took makes Restart Stack lead, because it assigns a new one. With worktrees on, the shared worktree list sits collapsed below, with worktree-switch's switch control, its two steps and its question; Enter in its find field never switches (MENU-5, MENU-4, SEL-4, SEL-5, REV-2, KEY-9).
  4. 4 The service's own last lines, kept per service and frozen at its exit, so another service's output never pushes them out and a burst of lines arrives complete and in order; the log opens at the end with the exit summary pinned above it. It is one focusable scrolling element named "api output", one element per line, terminal colors as styles, never a live region; a line wraps in full, and one over 2,000 characters folds to its first and last 300 characters with Show All 50,138 Characters and Copy, as every log does (SURF-14); an identical repeated block shows once with its count; when older lines are no longer kept it says so and names devhost logs api (SURF-13, FAIL-3, FAIL-4, SURF-9, STATE-4).
  5. 5 When the page's service, or a service it depends on, exits while the app is open, the same view opens over the app as the crash view, a modal dialog; any other exit stays in the Services panel, and devhost's own stops never open it. Focus goes to its heading, never a button, with the cause sentence as the dialog's description and Restart api as the next Tab stop; Tab cycles inside it, docked chat and the notice stack included and operable, while the page and the bar are inert; Alt+Ctrl+R does nothing while it is open. Two exits read "api and worker exited", more a count, each with its own cause, evidence and Restart. A Restart of the page's own service that fails in the Services panel opens the view over the panel as that restart's outcome, with no second notice (SURF-3, KEY-6, KEY-7, KEY-1, SEL-3, FAIL-5, FB-2).
  6. 6 Escape or Minimize folds the view into its crash notice; Escape never dismisses the failure. Minimize shows its key cap outside its accessible name, with aria-keyshortcuts="Escape", from the binding's one definition, in the platform's notation (KEY-8, KEY-13, BAR-4, WORD-2).
  7. 7 The crash notice names the service and the exit; Expand (named "Expand api's failure") reopens the view with focus on its heading. While it is minimized the page, Config, Services and Chat respond. While focus is in a text field, chat holds a draft or a decision card, or an agent of this worktree works or waits, the view opens minimized like this, announced once as a failure, and focus stays where it was; the next exit opens it again by the same test (SURF-3, FB-9, CC-2).

4. Restart the service in place

Restart api still restarts one service on one press, keeping its automatic port, and still succeeds only once the new process is healthy, as today. What changes is that the page shows the restart's steps and its outcome where it was pressed, keeps focus there, and never sends the same restart twice: the route answers 202 Accepted with the operation's record, the page keeps the operation's ID for this tab, a lost response is read back from the record, and a press after api already recovered is refused with "api is already running" and the page redraws (ACT-1, CC-37, REV-12, REV-13). Keys: Enter or Space on the focused button; focus never falls to the page body (KEY-11).

  1. 1 The pressed button keeps focus, busy and unavailable to a second press (aria-busy, aria-disabled, never disabled) and reads "Restarting api…". It hands off to services-panel's restart, the same operation as devhost service restart api (REV-1, KEY-11, FB-9, MENU-1, MENU-6, CC-11).
  2. 2 The restart's steps show in place, updated at least once a second: queued behind another service's restart, stopping, starting, the health check with its time; the log starts the new attempt with its divider (FB-1, ACT-3, SEL-7).
  3. 3 A retry that fails updates the one report in place with its count and time instead of adding a second report; when it failed exactly as before, one line says so and names where the command comes from (FAIL-4, MENU-4).
  4. 4 Edit then leads with the primary style, because rerunning the same command cannot help. The failure is announced once, in the assertive region; focus stays on Restart api, whose accessible description becomes the cause sentence (MENU-5, FB-9, KEY-11).
  5. 5 Success reloads the tab into the app, where the outcome shows once, read from the operation's record, with focus on its sentence, never at the top of the document; it closes by itself after O14's reading time, counted from when the browser window has focus (O53), and no page greets its load with an older success (FB-2, FB-3, FB-6, WORD-4, KEY-6).

5. Edit the service's definition

The Configuration window is still config-editor's, and a save still applies through hot reload without a question. What is new is that the recovery page and the crash view point at the definition that failed: Edit sits beside Restart on both, so a failure is no longer a dead end that only reruns the same command (MENU-4, MENU-5). Keys: Edit is a button in the recovery view's Tab order; closing the window returns focus to the crash notice's Expand, which stands in for the minimized view's Edit (SURF-4, KEY-6).

  1. 1 Edit opens the Configuration window at the service's definition, "devhost.toml line 14, services.api.command", marked, with this failure's evidence in the window's banner: the exit with its time, the cause sentence and the frozen last lines, with Show All Output. From the crash view it first minimizes the view to its crash notice (MENU-4, SURF-4, SURF-3).
  2. 2 Save's reach is stated beside Save, which stays available, never a question (REV-10).
  3. 3 With the config editor off, or on a status page without the toolbar, Edit gives way to the file and line with Copy. devhost opens no editor, so there is no Open in Editor (MENU-3, MENU-4, SURF-15, O51).
  4. 4 A save that fixes the definition applies through hot reload, which restarts api; manifest-hot-reload reports the reload. The recovery page reads restarting and, once api is ready, reloads into the app (step 2) (owner rule; ACT-3).

6. Restart the whole stack from the crash view

Restart Stack still stops every managed service and starts them again with new automatic ports, keeping fixed ports, the selected worktrees, external services, every page's status stream and chat sessions, and still uses the accepted manifest, as today; it is the same control on a recovery page. What changes is that its reach is named beside it, its progress and its outcome stay in the view, and a failure is never silent. Healthy services keep running when one fails: the error-pages-01 stopgap ships first, and the rollback builds on it (UNDO-1, REV-11). It restarts services inside the running stack, the same operation as the Services panel's, and its terminal form is devhost service restart --all (MENU-6, CC-11; applied default of owner item q86). Keys: Enter or Space presses it once; there is no question here (REV-1).

  1. 1 Where the page's service is already down and Restart Stack is the remedy on offer, it runs on one press. Its label keeps the operation's name, and the line beside it states the reach: the count, that automatic ports change, the worktree and how long it took last time; its tooltip and accessible description list the 6 services by name and its terminal form, "In a terminal: devhost service restart --all" (REV-2, BAR-2, SEL-1, MENU-6, CC-11, CC-17).
  2. 2 Pressed, it stays in place as the busy control and keeps focus, and the view lists each service with its step; the other actions wait with that operation and its progress as their reason (FB-1, REV-4, KEY-11, HOLD-3).
  3. 3 When one service cannot start, the view stays open and the outcome replaces the progress in it, counting what runs and naming the failure with its lead actions; focus moves to the outcome's sentence, never to an action (FAIL-1, FB-2, FB-9, SURF-3).
  4. 4 The rollback restores what ran before, service by service with their previous automatic ports, and says so in its own words; while it restores, the view reads "Restoring the services as they ran before Restart Stack". The Worktrees trigger reports no attention for it (UNDO-1).
  5. 5 The failure stays in the view, and in the crash notice while the view is minimized, until the person dismisses it or the same operation succeeds; a status message, a reconnect or a page reload never removes it (FB-6, ACT-1).
  6. 6 While a manifest edit is rejected, Restart Stack still runs, from the accepted manifest, and its reach line names the change it leaves out. While another operation runs it is unavailable with that operation and its progress as its reason, and the control API answers 409 naming that operation (HOLD-6, HOLD-3, CC-37).
  7. 7 On success the services run again, so the crash view closes by itself and the outcome shows as a notice in its place; from a recovery page, the page reloads into the app and the outcome shows there, read from the operation's record (FB-2, FB-3, WORD-4).
